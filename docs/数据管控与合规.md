# 数据管控与合规

本文档说明本程序对**派生数据**（从受限格式里解出来的音频）采取的管控措施，以及仍然存在的边界。

---

## 1. 什么是「派生数据」

本程序内部没有内置任何在线音源，在运行过程中也不会从网络下载任何媒体内容。程序的所有音频输入，完全依赖从本地两种带有访问限制的专用容器格式中解析并提取音频流：

| 来源 | 操作 | 派生数据 |
| --- | --- | --- |
| 网易云 `.ncm` | 解密（AES-128-ECB / ncmdump） | mp3 或 flac 字节 |
| B 站客户端缓存 `.m4s` | 剥掉私有头，得到标准 MP4 容器 | 可播放的 m4a 副本 |

通过上述转换流程生成的两类派生数据，依然受到原始发布平台版权条款以及对应用户服务协议的法律约束。如果用户将这些已经脱离原客户端加密保护的文件随手复制到外部环境，这些音频立刻就会转变为脱离监管的非法传播源。为了防范这类合规风险，程序在架构上必须提高随意导出和二次分发的门槛，增加「顺手传播」的操作难度，同时完整记录运行期间的数据处理动作，确保后续审计能够准确追溯系统内「发生过什么」。

## 2. 三层管控措施

### 2.1 第一层：最小落盘

| 措施 | 说明 |
| --- | --- |
| 解密结果只在内存中传递 | 从不写入你的音乐目录 |
| 音频只存在于会话专属临时目录 | 每次启动重新生成，退出即整体销毁（含崩溃残留，下次启动清扫） |
| 读完立刻擦除 | 解密子目录在字节读回内存后立即覆盖擦写并删除，不等垃圾回收 |
| **本地保留副本**（2.2.0 起） | 导入 B 站缓存时另存一份到曲库音频目录，跨启动长期保留：迁走或删掉缓存文件夹后仍可播放。源缓存仍在时优先用会话副本。占用在设置面板「LOCAL AUDIO COPIES」可见 |
| 临时目录带隐藏属性 | 阻止「顺手翻到并拷走」 |
| 覆盖写零后删除 | 先用 0 覆盖整个文件并落盘，再删除 |
| 硬链接保护 | 遇到被多处引用的文件只摘目录项、绝不覆写——覆写会透过硬链接把别处那份一起毁掉 |
| 派生副本必须是独立文件 | 一律复制出独立副本，不做硬链接 |
| 升级清理 | 启动时擦除旧版本遗留的长期副本，只删本程序生成的副本，不碰你的缓存原文件 |

在现代固态硬盘上，由于磨损均衡机制（Wear Leveling，主控为了延长闪存寿命会把写入动态分散到不同物理块）和 TRIM 指令的存在，应用层即使反复执行覆盖写零，物理介质层面也无法真正确保数据被彻底清除。因此，用零字节重写文件只是一道提高逆向与数据恢复门槛的防范手段，本机制真正的底层防护，依靠的是严格限制生命周期的专属会话目录，以此确保音频内容默认不会在磁盘中长期驻留。

整个运行机制中，唯一会长期留存在磁盘上的音频，只有曲库音频目录里的本地副本。这一设计的目的，是满足用户在「移走源缓存后依然可以离线播放」与「衍生副本不驻留磁盘」之间的取舍需求。该文件是剥离了所有用户标识与原始链接等元数据的标准 m4a 格式，磁盘开销仅仅等同于音频文件本身的体积。一旦用户从曲库中移除对应的曲目，该副本就不再被任何逻辑引用；若用户直接将该存储目录完全清空，软件在检测不到本地副本后，也会自动降级退回原有逻辑，即在需要播放时重新读取原始缓存来实时生成临时副本。

### 2.2 第二层：不可导出

本程序完全剥离了任何形式的「导出 / 另存为 / 分享」功能，并且在系统底层架构与接口设计上彻底阻断了向外导出的可能性：

- 查验系统内部声明的所有数据接口，没有预留任何可以传入「输出路径」的参数槽位，整体 I/O 流向只允许读取外部数据进入运行环境，不存在将解密数据定向写出到指定位置的能力；
- 前端界面层完全没有接入任何调用操作系统写文件的底层 API，也不具备获取本地任意文件系统写入权限的凭证；
- 经过解密或提取所生成的派生数据，在界面渲染层仅仅作为短周期的内存对象存在，一旦所属页面或视图被关闭，对应的内存就会随着生命周期的结束被立刻回收。

这项约束并非停留在「界面上隐藏了导出按钮」的表层逻辑，而是在内部数据通道中根本没有建立能够把内存音频字节流重新封包并写入外部磁盘的执行链路。

### 2.3 第三层：可追溯

系统每次完成音频解密或者从缓存中提取媒体流时，都会自动在本地审计日志文件中追加记录一条标准的 JSON 数据：

```json
{"t":"2026-09-22T13:41:07.812Z","v":"1.1.0","sid":"a1b2c3d4e5f6",
 "event":"ncm-decrypt","result":"ok:exe","bytes":9241837,"ext":"mp3"}
{"t":"2026-09-22T13:42:19.004Z","v":"1.1.0","sid":"a1b2c3d4e5f6",
 "event":"bili-extract","src":"D:\\...\\32707317016-1-30280.m4s","bytes":1617712,"ext":"m4a","result":"ok"}
```

| 字段 | 含义 |
| --- | --- |
| `t` | UTC 时间戳（ISO 8601） |
| `v` | 产生该记录的版本号 |
| `sid` | 会话 ID —— 同一次运行的所有记录可归组 |
| `event` | `ncm-decrypt` / `bili-extract` / `bili-scan` |
| `result` | `ok:exe` / `ok:builtin` / `failed` / `rejected:not-ncm` |
| `src` | 来源文件路径（**仅本机**，用于回答「这条数据是从哪来的」） |
| `bytes` / `ext` | 产物体积与格式 |

- 本地日志的存储容量上限严格限制为 **500 条**，在写入新记录触发阈值时，程序会自动丢弃生成时间最早的历史条目。
- 用户前往设置面板的「数据管控」配置项，即可直观查阅当前的审计日志数量，并支持通过点击「清日志」按钮立即抹除所有历史记录。
- 审计记录文件始终存放在当前操作系统的本机用户数据目录内，程序内部没有任何网络上报模块，永远不会向远程服务器外发或同步这些记录。

### 2.4 输入侧限制

- 程序在启动解密流程前，会首先读取并严格比对目标文件的容器魔数（Magic Number，即位于文件头用于标识格式的一组固定特征字节）；一旦确认不是合规的 NCM 封装格式，流程将立即阻断并拒绝执行，以此确保本工具无法被当作随意尝试破解未知二进制流的通用解密器。
- 针对 B 站媒体缓存的提取逻辑，处理范围严格局限在用户本地磁盘中业已存在的缓存分片，整个提取阶段绝不会向远程网络发出任何抓取音频流的请求；唯一的网络交互，仅限于根据缓存索引中附带的静态图片 URL 发起单次请求，把封面图下载并保存在本地。
- 在整个数据读取、解析与派生阶段，外部输入的原始缓存文件以及 `.ncm` 格式的源文件受到只读保护，程序永远不会对其执行修改、重命名或物理删除操作。

## 3. 程序内可见性

相关的管控状态与安全限制会在 ⚙ 面板中集中呈现：

- **「数据管控」行**：界面中会直接标出 `内存解密 · 会话级临时目录 · 无导出 · 审计 N 条` 这些当前生效的策略；如果将鼠标指针悬停在上方，能查看每一项机制的具体说明以及记录行为的审计文件路径；旁边还配有「清日志」按钮，点击后可以一键清空审计日志的所有内容
- **「版本」行**：展示软件当前运行的具体版本号
- **首次启动告知弹层**：弹窗会逐条列出所有生效的管控措施与明确的使用边界，用户必须主动点击「我已了解」按钮确认后弹窗才会关闭，并且该提示弹层只能在软件首次启动时触发一次

## 4. 自动化验证

前面提到的各项管控机制都配套了可反复运行的自动化回归测试，不依赖人工核对或者口头保证。在命令行中执行以下脚本即可启动整套检查：

```powershell
node scripts\数据管控验证.js app
```

这套测试一共包含 16 项具体的断言检查，用来确认系统行为与安全设计完全一致：

| 组 | 验证内容 |
| --- | --- |
| 落盘位置 | 副本确实落在会话目录、不在用户数据目录、文件真实可读 |
| 擦除逻辑 | 擦除前能读到明文标记 → 擦除后文件与目录都消失；递归擦除生效；被多处引用的文件擦除后源文件内容一字不变 |
| 陈旧清扫 | 上次残留的会话目录被清掉 |
| 静态断言 | 魔数校验存在；无 write/save/export 类接口；提取音频走会话目录；退出销毁会话目录；存在升级清理；界面层不暴露写文件方法 |

针对文件清除行为的测试，并没有为了方便验证而单独写一套专供测试用的模拟逻辑，而是把主程序实际运行所使用的擦除逻辑代码直接提取出来调用。这样能确保测试覆盖到的就是即将打包发布给用户的真实生产代码，避免出现测试通过但实际业务逻辑失效的情况。

## 5. 使用边界（用户责任）

> 请只能将本程序用于**个人本地播放**你已合法获得的内容。
> 解出的音频受原平台版权约束，**请勿传播、分发或用于任何商业用途**；
> 由此产生的法律责任由用户自行承担。

系统内置的技术管控手段固然能够减少无意间扩散数据的风险，却无法免除用户主动遵守版权规则的法律义务。从系统权限的角度来看，任何具备本地文件读取权限的软件，都无法在操作系统层面限制用户手动将解密后的文件拷贝到其他目录或外部存储设备。面对这种底层限制，本程序重点防范的是自身环节被滥用为内容外流的通道：在运行全程坚持不在硬盘中写入中间明文音频、不提供对外导出功能、不开放网络分享接口。与此同时，系统完整记录每一次解密与派生音频的具体操作过程，确保所有动作都留存可供追溯的日志记录。

## 7. 已知边界

| 边界 | 说明 |
| --- | --- |
| 覆盖擦除不保证取证级不可恢复 | 因为固态硬盘（SSD）普遍带有磨损均衡机制，并且操作系统会定期执行 TRIM 命令清理无效块，应用软件在文件系统层发出的覆写指令无法精确覆盖物理闪存上的原始数据；目前的保底手段是尽量缩短文件留存时间，做到「不长期落盘」 |
| 封面图仍缓存在用户数据目录 | 封面文件属于图片资源，与音频本体不同；保留本地缓存是为了避免播放器每次切歌都重新发起网络下载。如果用户需要清理这些图片，直接手动删除该目录即可 |
| 审计日志含本机文件路径 | 记录完整路径的目的是回答「这条数据从哪来」，方便排查来源；这部分日志只保存在本机磁盘上，不会上传，且支持一键清空 |
| 无法阻止手动复制 | 会话目录在程序运行期间必须保持存在，因为播放器解密后需要直接读取里面的内容；在软件运行期间，用户如果通过操作系统的文件管理器手动拷贝这些临时文件，程序在技术上无法阻止 |
| 内存中的字节无法控制 | 音频解码播放期间，派生数据必然会解密并驻留在进程内存中，这是任何播放器在工作原理上的固有前提，无法避免 |
| **历史版本曾损坏两个用户缓存文件** | 在 v1.1.0 到 v1.1.3 版本中，实现逻辑存在「硬链接 + 覆盖擦除」的设计缺陷，导致执行清理时会顺着硬链接就地毁掉部分源文件。该问题在 v1.1.4 中已经修复；针对**已损坏的文件无法由本程序恢复**，需要从原始备份中重新获取 |
