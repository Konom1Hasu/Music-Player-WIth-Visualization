# 数据管控与合规

本文档说明本程序对**派生数据**（从受限格式里解出来的音频）采取的管控措施、措施的技术实现，
以及仍然存在的边界。

---

## 1. 什么是"派生数据"

本程序本身**不含任何在线音源**，不会下载任何内容。它能从两种受限容器里解出音频：

| 来源 | 操作 | 派生数据 |
| --- | --- | --- |
| 网易云 `.ncm` | 解密（AES-128-ECB / ncmdump） | mp3 或 flac 字节 |
| B 站客户端缓存 `.m4s` | 剥掉私有头，得到标准 MP4 容器 | 可播放的 m4a 副本 |

这两类派生数据受原平台版权与用户协议约束。**一旦被随手复制出去，就成为非法传播源**，
因此程序必须让"顺手传播"变得困难，并且让"发生过什么"可被追溯。

---

## 2. 三层管控措施

### 2.1 第一层：最小落盘

| 措施 | 实现 |
| --- | --- |
| 解密结果只在内存中传递 | `convert-ncm` 返回的是 `Buffer`（经 IPC 结构化克隆到渲染进程），**从不写入用户音乐目录** |
| 解出的音频只存在于**会话专属**临时目录 | `%TEMP%\mp-session-<12位随机会话ID>\`，每次启动重新生成 |
| B 站可播放副本同样落在会话目录 | `ensureM4a(audioPath, SESSION_AUDIO_DIR)`，不再写进 `userData\bili_audio` |
| 临时目录带隐藏属性 | 尽力调用 `attrib +h`，阻止"顺手翻到并拷走" |
| 读完立刻擦除 | 解密子目录在 `ncmdump.exe` 退出、字节读回内存后**立即**覆盖擦写并删除，不等 GC |
| 退出即整体销毁 | `will-quit` 拦截退出 → 递归擦除会话目录 → 真正退出（4 秒兜底，不会关不掉） |
| 崩溃残留也会被清 | 每次启动执行 `sweepStaleSessions()`，清掉所有 `mp-session-*` 目录 |
| **升级清理** | 启动时 `purgeLegacyAudioCache()` 擦除 1.0.x 遗留在 `userData\bili_audio` 的长期副本（只删本程序生成的副本，不碰用户的 B 站缓存原文件） |
| 覆盖写零后删除 | `wipeFile()` 先用 0 覆盖整个文件并 `fsync`，再 `unlink`（单会话上限 256 MB，避免退出卡顿） |

> **为什么"不长期落盘"比"擦除"更重要**：SSD 的磨损均衡与 TRIM 使彻底擦除无法在软件层保证。
> 覆盖写零只是提高恢复门槛的**威慑**手段，真正的保底是**根本不长期落盘** —— 也就是会话目录这一层。

### 2.2 第二层：不可导出

程序**不提供任何"导出 / 另存为 / 分享"能力**，并且从接口层面就做不到：

- 全部 27 个 IPC 通道中，**没有任何一个接受"输出路径"参数**（`read-audio`、`convert-ncm`、
  `read-cover` 都是"读进来"，不是"写出去"）
- `preload.js` 通过 `contextBridge` 暴露 16 个方法，**没有任何写文件方法**
- 渲染进程没有 `nodeIntegration`（`contextIsolation: true`），拿不到 `fs`
- 派生数据在渲染进程里只作为 `Blob` / `objectURL` 存在，随页面生命周期结束而释放

这条保证是**结构性**的：不是"我们没做这个按钮"，而是"没有可用的路径能把字节写到磁盘"。

### 2.3 第三层：可追溯

每次解密与提取都会向本机 `userData\audit.log` 追加一条 JSON 记录：

```json
{"t":"2026-09-22T13:41:07.812Z","v":"1.1.0","sid":"a1b2c3d4e5f6",
 "event":"ncm-decrypt","result":"ok:exe","bytes":9241837,"ext":"mp3"}
{"t":"2026-09-22T13:42:19.004Z","v":"1.1.0","sid":"a1b2c3d4e5f6",
 "event":"bili-extract","src":"D:\\...\\32707317016-1-30280.m4s","bytes":1617712,"ext":"m4a","result":"ok"}
```

| 字段 | 含义 |
| --- | --- |
| `t` | UTC 时间戳（ISO 8601） |
| `v` | 产生该记录的版本号 |
| `sid` | 会话 ID —— 同一次运行的所有记录可归组 |
| `event` | `ncm-decrypt` / `bili-extract` / `bili-scan` |
| `result` | `ok:exe` / `ok:builtin` / `failed` / `rejected:not-ncm` |
| `src` | 来源文件路径（**仅本机**，用于回答"这条数据是从哪来的"） |
| `bytes` / `ext` | 产物体积与格式 |

- 上限 **500 条**，超出自动裁剪最旧的
- 设置面板 → 「数据管控」一行显示当前条数，点「清日志」一键清空
- **审计文件只在本机 `userData` 下，程序从不外发、不上传**

### 2.4 输入侧限制

- `convert-ncm` **先校验 `CTENFDAM` 容器魔数**，不是真正的 NCM 直接拒绝。
  这样它就不是一个"拿任意文件来试解的通用解密器"
- B 站缓存提取只处理**本机已存在的缓存文件**，全程不发起任何音频下载请求
  （仅封面图会按缓存里的 URL 取一次并本地缓存）
- 原始缓存文件与 `.ncm` 源文件**从不被修改或删除**

## 3. 程序内可见性

管控措施不是只写在文档里 —— 设置在 ⚙ 面板中可见：

- **「数据管控」行**：显示 `内存解密 · 会话级临时目录 · 无导出 · 审计 N 条`
  - 悬停可看到完整说明与审计文件路径
  - 旁边的「清日志」按钮一键清空审计
- **「版本」行**：显示当前程序版本号
- **首次启动告知弹层**：完整列出上面的管控措施与使用边界，需点「我已了解」才消失
  （记录在 `localStorage.mp_notice_v110`，只在首次启动出现一次）

## 4. 自动化验证

管控措施是可回归验证的，不是口头承诺：

```powershell
node scripts\数据管控验证.js app
```

覆盖 16 项断言：

| 组 | 验证内容 |
| --- | --- |
| 落盘位置 | 副本确实落在传入的会话目录、不在 `userData`、文件真实可读 |
| 擦除逻辑 | 擦除前能读到明文标记 → 擦除后文件与目录都消失；递归擦除生效 |
| 陈旧清扫 | 上次残留的 `mp-session-*` 被清掉 |
| 静态断言 | 魔数校验存在；无 write/save/export 类 IPC；`prepare-bili-audio` 用会话目录；退出销毁会话目录；存在升级清理；`preload` 不暴露写文件方法 |

> 第 2 组不是"另写一份复制品来测"，而是**从 `main.js` 源码里摘出擦除实现**再执行，
> 所以测的是即将发布的真实代码文本。

## 5. 使用边界（用户责任）

> 请仅将本程序用于**个人本地播放**你已合法获得的内容。
> 解出的音频受原平台版权约束，**请勿传播、分发或用于任何商业用途**；
> 由此产生的法律责任由使用者自行承担。

程序的管控措施降低了"误传播"的可能，但**不能替代用户自身的合法使用义务** ——
任何具备本地文件读取权限的程序都无法阻止用户手动复制文件到别处。
本程序能做的，是确保**自己不成为传播链条的一环**（不落盘、不导出、不分享），
并让每一次派生产生都可追溯。

## 7. 已知边界

| 边界 | 说明 |
| --- | --- |
| 覆盖擦除不保证取证级不可恢复 | SSD 磨损均衡 + TRIM 下无法在软件层保证；保底手段是"不长期落盘" |
| 封面图仍缓存在 `userData\bili_cover` | 封面是图片，不是音频；缓存可避免每次重新下载。如需清理可直接删除该目录 |
| 审计日志含本机文件路径 | 目的是回答"这条数据从哪来"；只在本机，且可一键清空 |
| 无法阻止用户手动复制 | 会话目录在程序运行期间必须存在（播放器要读它）；运行期手动拷贝无法阻止 |
| 内存中的字节无法控制 | 播放期间派生数据必然存在于进程内存；这是任何播放器的固有前提 |
