## [1.4.6] — 2025

**主题：** 频谱计算搬进 Web Worker（修"可视化帧率很低"）、进度只为"下次续上"而存、补回音量 / 倍速 / 拖拽导入。

### 修复

**★ 可视化帧率很低**

1.4.4 把 1.3.0 的自研频谱搬过来时，我省掉了它的 Web Worker（当时判断"120 段 × 1024 点
≈ 12 万次乘加/帧，主线程吃得下"）。实际跑起来不是这样：这段计算和三维场景抢同一个主线程，
于是频率越高、场景越忙，频谱就越卡 —— 用户反馈的"帧率很低"就是它。

现在按 1.3.0 的做法搬进 Worker（`player.ts` 的 `initSpectrumWorker`）：主线程每帧只做
`getFloatTimeDomainData` → `postMessage`（转移一个 4KB 副本）→ 拿回 121 个浮点数直接出图，
**计算量归零**。worker 起不来或 45 帧内没有回包（被策略挡住等）就 `terminate()` 并永久退回
同步计算，功能不受影响。

### 变更

**播放位置：不再写"进度记录"，只为下次续上**

原来 `timeupdate` 里每 5 秒往 IndexedDB 落一次位置（`persist`）。现在位置只留在内存，
仅在**暂停 / 切歌 / 关窗 / 切到后台**时各落一次 —— 目的只有一个：下次播放这首时从上次的位置续上。
详情面板里的 `POSITION / 上次进度` 字段也换成了 `FAVORITE / 收藏`（不再展示进度）。

### 新增（补回独立播放器上有、终端版缺的功能）

| 功能 | 位置 | 说明 |
| --- | --- | --- |
| **音量条** | 播放条右下（`VOL` ＋ 滑条） | 与设置里的背景音乐音量各自独立，选择记在本地 |
| **播放速度** | 播放条 `1×` 键 | 1× → 1.25× → 1.5× → 2× → 0.75× 循环，非 1× 时按键高亮，选择记在本地 |
| **拖拽导入** | 整个窗口 | 文件或文件夹直接拖进来即导入（与 `＋` 按钮同一条管线） |

### 验证

`tsc && vite build` 通过（62 modules）；文档一致性 13 / 数据管控 27 / 设置持久化 31 / ID3 编码 15 全过。
Worker 的失败回退路径在代码里显式判了帧数（45 帧），所以即使被策略挡住也只是回到同步计算。

### 新增：恢复旧版曲库

1.4.1 修过的那条根因在这里兑现了后果：界面从随机端口改成固定 41739，而 **IndexedDB 按"源"隔离**，
旧版导入的曲目在新版里读不到 —— 但它们的音频**都还在磁盘上**。实测：

```
当前 profile  file://（独立播放器）      359 个 ID3(mp3)  3.05 GB
当前 profile  http://127.0.0.1:60994       1 个（1.4.0 那版）
旧 profile    file://（独立播放器）      455 个 ID3(mp3)  3.73 GB
D:\CloudMusic                             380 个音频文件   3.10 GB（本来就在磁盘上）
```

实现：

- `app/recover.html`：一个页面两种模式 —— `?mode=read` 在旧源上把每条记录
  （字段 + 音频 Blob 字节 + 可选封面）交出来；`?mode=write` 在新版的源上写进 `rhine-music`
- `app/main.js` 新增两个模式：`--recover-library` 枚举 userData 下所有旧源
  （`file://` 与每个 `http_127.0.0.1_<随机端口>`，后者逐个临时起一个只读服务把页面送到那个源上）、
  `--recover-ingest` 把跨 profile 的交接区吃进当前 profile
- **不往音乐目录写文件**：项目对派生数据（ncm 解出 / B 站副本）有"不导出"的硬约束，
  所以跨 profile 的交接只走系统临时目录 `%TEMP%\rhine-recover`，吃完即删
- 合并按"标题 + 艺术家"去重，可重复运行；旧数据全程只读
- 入口：`scripts\恢复旧曲库.ps1`（第 1 步当前 profile、第 2 步旧 profile、第 3 步把交接区吃进来）

### 验证

- 两处 blob 存储按文件头点数：359 + 455 个 `ID3` 开头（真 MP3，17–29 MB 一个）✓
- `app/recover.html` 的两段脚本、`app/main.js`、`app/preload.js` 全部通过 `node --check`；
  `scripts\恢复旧曲库.ps1` 通过 PowerShell 解析校验
- **本会话跑不了 Electron**，所以恢复流程需要在本机执行一次：每一步都会弹结果框，
  报告"读到多少条 / 音频多少个 / 新增多少首 / 跳过多少首"

## [1.4.4] — 2025

**主题：** 频谱换成 1.3.0 版独立播放器那套自研分析器（原样搬过来，不是"看着像"）。

### 变更

之前终端里的频谱是"`AnalyserNode.getByteFrequencyData` → 对数分频 → 画柱"。
用户连着反馈"没实现 1.2.0 / 1.3.0 版本的效果"，于是把那版**真正**搬过来 ——
在终端详情区画布上跑 1.3.0 的同一条流水线（新增 `app-rhine/src/spectrum.ts`）：

| 环节 | 1.3.0 的做法（现已照搬） |
| --- | --- |
| 分析 | `SPECTRUM_N = 1024` 时域窗 + Hann 加窗 + **Goertzel** 逐带计算（120 个对数频段，42Hz–16kHz） |
| 归一 | 每帧按本帧峰值归一后做**对数压缩** `log10(1+100·min(1,m/mx))/log10(101)` |
| 频段增益 | 手工调的 `bandBoost` 曲线：**宽丘 + 细针**的左峰（细针对准低频峰所在柱的中心）、中高频人声尖峰、中频谷，钳在 0.58–2.9 |
| 倾斜 | `pow(5, tilt·(1−i/n))`，tilt 由"频谱平衡 55"换算 |
| 幂次 | `pow(min(1,v), 2.1)` 拉大高低差 |
| 鼓点 | 用**未归一化**的低频原始幅度做 onset（`(rise−0.08)×2.2`，参考电平 0.05 慢跟随），再以**乘法泵动**作用在低频窗上 —— 加法会把十几根一起顶过 1.0，量化后变成平直方块 |
| 抖动 | 三条量（幅度/空间频率/单边颤动）随"抖动 1.00"缩放，向上幅度按**剩余余量**缩放，避免峰心两侧被一起钳住而失去针形 |
| 量化 | **14 级**阶梯（观感里的"台阶") |
| 平滑 | 一阶跟随，上行系数 0.70→0.50、下行 0.58→0.80（随频率放缓） |
| 峰值线 | `peaks[i] = max(peaks[i]·0.97, bars[i])`，画 2px |
| 样式 | 五种：融合 / 音色 / 条形 / 圆环 / 波形（默认融合）；配色仍取终端自己的令牌 |

**有意的差异**（都记在 `spectrum.ts` 的头部注释里）：

- **不用 Web Worker**：面板是 30fps 重绘，120 段 × 1024 点 ≈ 12 万次乘加/帧（约 370 万次/秒）主线程吃得下，
  省掉 worker + 看门狗回退的复杂度
- **滑块固定成 1.3.0 的默认值**（倾斜 55、鼓点 0.40、抖动 1.00、峰宽 σ 0.048、左峰目标增益 1.05）
- 配色取终端令牌（`#c9a878 → #9b7247 → #252820`，夜态另有一套），版式与动效参数与源版本一致

### 新增

- **`?viztest=1`**：不播音乐、用合成信号（55Hz 低音 + 每 4 秒一次"鼓点" + 440Hz / 2.4kHz）跑频谱，
  并把频谱实例挂到 `window.__spectrum`，用于无音频环境下的自动化核对
- **`scripts\生成频谱探针.ps1`**：在构建产物 `index.html` 里注入"预置一首带封面的曲目 + 回传柱高"的脚本，
  生成探针页（必须在 `npm run build` 之后跑，Vite 会清空 dist）

### 验证

探针在真实应用里读回 120 根柱的实测值：

```
bars = 120
min/max/mean = 0.000 / 0.537 / 0.052
顶到 0.98 以上的柱数 = 0
前 12 根 = 0.37 0.54 0.42 0.20 0.20 0.42 0.48 0.31 0.20 0.36 0.47 0.31
```

三条结论都在这几个数里：**没有一根被钳在满格**（对照 1.4.2 之前"整排顶满"）、
左区相邻柱高低穿插（0.54 / 0.20 / 0.42 相隔出现，正是"抖动"那一层在起作用）、
满高与谷底之间有完整的动态范围。

**顺带修掉一个真 bug**：时域缓冲原先只在 `ensureAnalyser()` 里分配，于是
**没有音频上下文时整条频谱恒为 0**（探针第一次跑出来全是 `0.00`，就是这个原因）。
现在缓冲由渲染循环自己保证，与音频上下文解耦。

### 新增

**曲目封面印在文档模型正面上**

左边那块抽出/选中的档案卡片，正面本来就有一块 `Database label` 印刷标签板
（GLB 里 3.753 × 2.971、正面 z ≈ 0.246，材质 `Printed_Label`）。现在在它上面
0.252 处盖一块 3.62 × 2.87 的封面板，画布 1536×1216：

- 封面方块（690×690，按 `cover` 的宽高比居中裁切填满）
- 右侧：`TRACK` / `NO.003`（大字）/ 曲名（最多两行、超出省略）/ 艺术家 / 专辑
- 抬头 `RHINE LAB, LLC. ／ MUSIC ARCHIVE · 曲目标签`、上下细线、右下角标志

细节与既有的小标签板（`RHINE LAB, LLC. / NO.001`）完全同一套做法：

- 封面板在 `label` **之前**加入模型 —— `select()` 换选时按"最后一个子节点"复制标签，
  顺序不能变
- 换选时收回中的那张卡片会**连封面画布一起快照**成独立纹理，否则克隆体和主模型共用
  一张纹理，换曲时旧卡片上的封面会跟着变
- 封面是 `data URL`（内嵌图或程序生成的默认封面），直接当纹理用；没有封面时画 `♪` 占位
- 封面板在玻璃外壳之外（外壳正面 z ≈ 0.197），所以**解密前后都看得到**，
  且只有被抽出的那一张卡片有封面，阵列里其余卡片仍保持素面标签

渲染之外还留了一条自检：`getStats().cover` 会报告封面板是否挂在模型上、图片是否载入、
以及封面方块区域的平均色 —— 用来证明"画布上真的画上了封面"，而不只是"代码跑过了"。

### 修复

**★ 可视化一直顶满**

根因是自动增益的写法：`gain = 1 / normRef`，而 `normRef` 跟着最近峰值走 ——
等于**每帧都把最响的那根柱拉到满格**；再叠加当时 1.85 的鼓点泵浦与到 1.32 的低频倾斜，
大量柱体被 `Math.min(1, …)` 直接夹在顶端，于是整排长时间贴着上沿。

现在的取值链：

| 环节 | 之前 | 现在 |
| --- | --- | --- |
| 分析器 dB 窗口 | 默认 −100…−30dBFS（对音乐太宽） | **−85…−25dB**（60dB 窗口，安静段也铺得开） |
| 曲线 | `(peak/255)^0.8` | `(peak/255)^1.05`（更贴真实动态） |
| 自动增益 | `1/normRef`，无上限 | `min(1.5, max(1, 0.78/normRef))`：正常音量**恒为 1**，只有整体很轻才抬一点 |
| 鼓点泵浦 | 上限 1.85、命中 +0.32 | 上限 **1.32**、命中 +0.2 |
| 低频倾斜 | 0.70 → 1.32 | **0.88 → 1.18** |
| 低频尖峰 | +45% | **+20%** |
| 显示上限 | `min(1, …)` | `min(0.97, …)`（满格留一点余量） |

以"大多数频段落在 120–200、峰值 200"的常见响度算：旧写法 gain≈1.2，泵浦一响
`0.87 × 1.85 ≈ 1.6` 直接夹满；新写法 gain=1，主频段落在 0.48–0.90，
只有底鼓那一瞬的泵浦会短暂顶到 0.97。

### 验证

封面链路用了真实应用 + 软件 WebGL 无头渲染（`?scene=detail` + 预置一首带封面的曲目到
IndexedDB），由页面把 `rhine.stats()` 回传：

```
mode = detail
selected = X-001
cover = {"plate":true,"imageLoaded":true,"sample":[74,71,59],"no":"001","title":"星环坠落的夜晚"}
loaded = true
```

`sample` 是画布上封面方块区域的平均色 `[74,71,59]`（深色带暖调，正是那张测试封面的颜色）——
如果图片没画上去，这里会是纸面底色 `[230,226,217]`。位置则按 GLB 的实测包围盒推算：
标签板正面 z=0.246、外壳正面 z=0.197，封面板落在 z=0.252、尺寸比标签板小 0.07，
四周留边、不越出机身（机身 5.0 × 3.7）。

  同时收紧面板其他部分（封面 130 → 118、h2 36 → 34、各行间距），把高度让给可视化。

### 修复

**★ SAVE TRACK 压住 POWERED BY RHINE LAB**

量出来的是动作行与右下角水印的重叠：`.detail-actions` 在 y 932–978、`.powered`
在 y 948–972 且 x 1571–1846，两者在 x 1571–1688 上交错 —— 按钮右端正好压住它。

```
与 POWERED BY 重叠：SAVE TRACK 无 / 脚注 无
```

这说明"看起来挡住了"和"真的挡住了"要分开查：第一版收紧后按钮已经躲开，
但**脚注还差 6px 压在水印上**，是量测脚本把两处都算了一遍才发现的。

### 可视化（与旧版拉开差别）

之前只有"对数分频 → 平滑 → 画柱"，安静段几乎不动、也看不出鼓点。现在补上
终端版漏掉的三件事，并给大画布加上层次：

| 处理 | 作用 |
| --- | --- |
| **自动增益**（跟最近峰值，参考值按 0.994/帧衰减，下限 0.18） | 安静段落也有动态，爆音段不会一根顶天 |
| **鼓点泵浦**（低频能量 vs 慢速参考；命中 +0.32，回落 0.14） | 底鼓一踩整排抬起来，肉眼可见 |
| **低频峰形**（i≈3 处的高斯峰 +45%） | 低频尖峰立得起来，不再是一排一样高 |
| **竖向渐变**（底部灰 → 中部墨 → 顶部暖色） | 大画布上有层次，不再是单色块 |
| **峰值保持线**（3px 暖色，每帧 −0.008 缓落） | 能看到"刚才有多响" |
| **参考网格**（25% / 50% / 75% 细线） | 大画布上有刻度感，与终端的工程图风格一致 |

### 帧率优化

- **频谱循环加帧预算**：画布 30fps、播放条 52 格刻度 15fps。
  原来每帧都要重绘画布并写 52 次 DOM 样式 —— 那是每帧触发布局，是最贵的一块。
- **静态底板缓存**：网格线 / 基线画进离屏 canvas，每帧只 `drawImage` 一次，
  不再 `clearRect` 整块重描。
- **刻度只在像素高度真的变了才写 DOM**。
- **窗口隐藏 / 最小化时停掉频谱循环**（`visibilitychange`）：Electron 里关掉了
  背景节流，不主动停就等于一直在算没人看的帧。
- **去掉播放条与播放列表的 `backdrop-filter: blur(7px)`**：它背后是持续动画的
  三维场景，每帧都要重新模糊 880×134 的区域。面板本身已是 0.94 不透明度，
  去掉后观感几乎不变，合成开销明显下降。

## [1.4.1] — 2025

**主题：** 把 1.4.0 里"还留着档案味"的地方清干净：词条、播放条的拥挤、以及中文标题乱码。

**★ 歌曲标题乱码：ID3 文本解码写死了 UTF-8**

用户反馈"歌曲标题存在编码不匹配的乱码问题"。根因很具体 —— 原来的解码只做
`new TextDecoder("utf-8")`，而 ID3 文本帧的编码有四种，中文 MP3 最常见的两种全中：

```
编码字节 1（带 BOM 的 UTF-16）—— 跳过 2 字节后按 UTF-8 解
  正确值：星环坠落的夜晚
  旧结果："��\u001ff�s`W=��v\u001cYZf"      ← 用户看到的就是这个
编码字节 0（规范上是 ISO-8859-1，国内大量标签实际写 GBK/GB18030）
  正确值：歌曲经典      旧结果："¸èÇú¾­µä"
```

现在按编码字节分派：1 → 显式看 `FF FE` / `FE FF` 决定 UTF-16LE / BE（不信运行时对
`utf-16` 的默认字节序，测试里 UTF-16BE 带 BOM 那条就是这么发现的）；2 → UTF-16BE；
3 → UTF-8；0 → 先严格试 UTF-8，不成立且高位字节占比 > 50% 时按 GB18030 解，
都不是才落回 windows-1252（所以 `Café Björk` 不会被误判成中文）。

顺带修掉三处同类问题：

- ID3v2.2 的 3 字节帧头（`TT2` / `TP1` / `TAL` / `PIC`）以前读不出来
- 没有 v2 标签的文件读末尾 128 字节的 ID3v1 兜底
- 内嵌封面的描述段按实际编码跳过（UTF-16 描述以 `00 00` 结尾，逐字节找第一个 0 会截断，封面会错位）

**★ 封面 3D 的绘图缓冲被设成 1×1，导致一帧都画不出来**

用户反馈"我并没有看到 3D 效果"。这一次没有靠猜 —— 我搭了一个离线桩环境把
`app/index.html` 在无头浏览器里渲染出来，dump DOM 后读到了确凿证据：

```
<canvas id="cover3d" width="1" height="1" class="on">     ← 绘图缓冲只有 1×1 像素
<canvas id="viz"      width="600" height="312">           ← 对比：可视化画布正常
```

根因是 `c3dEnable()` 里的**调用顺序**：

```
c3dResize();                     ← 此刻 #cover3d 还是 display:none
cv.classList.add('on');          ← 之后才显示
```

`display:none` 时 `clientWidth`/`getBoundingClientRect()` 都是 **0**，
而原代码写的是 `cv.clientWidth || 1`，于是取到 1 →
`setSize(1,1)`、`camera.aspect = 0/1 = 0` → 渲染到 1×1 缓冲，屏幕上什么都不会出现。
只有手动缩放窗口（触发 resize 监听）才会突然冒出来。

修复三步：

1. **先显示、后测量** —— 把 `cv.classList.add('on')` 提到 `c3dResize()` 之前
2. `c3dResize()` 改用 `getBoundingClientRect()`，量到 0 时**用父容器兜底**
3. 仍为 0 就返回 false，调用方**下一帧重试**（最多两次）

验证（同一桩环境、同样参数，只看画布属性）：

## [1.1.4] — 2025

**主题：** 修复一个会**毁坏用户原始缓存文件**的严重缺陷（硬链接 + 覆盖擦除）。
这是本项目最严重的一次事故，原因、机制与修复完整记录在下面。

### 修复

**★ 严重：擦除派生副本时会就地毁掉用户的原始缓存文件**

事故现象：B 站缓存音频突然无法播放，报 `MediaError 4`（"格式不支持或文件头异常"）。

根因链条：

1. `bili.js` 的 `ensureM4a` 对**嗅探不到 MP4 头**的源文件（`offset === 0`）走的是
   `fs.linkSync(audioPath, dest)` —— **硬链接**，副本与源文件**共享同一个 inode**。
   （当初选硬链接是为了"同盘瞬时、不占额外空间"。）
2. v1.1.0 起副本目录改为**会话临时目录**，退出时由 `wipeDir` 擦除。
3. `wipeFile` 的擦除方式是"以 `r+` 打开、整天覆写 0、`fsync`、再 `unlink`"。
   覆写是**写 inode**，于是透过硬链接直接落到用户的原始缓存文件上；
   随后的 `unlink` 只摘掉副本那个目录项 —— **源文件还在，内容已经全是 0**。
4. 下次启动时 `ensureM4a` 从"已经是全 0"的源文件生成副本，
   Chromium 自然解不出来 → `MediaError 4`。

已实测确认：用户 `Downloads\Mobile Devices\` 下**两个音频缓存文件被原地写成全 0**
（文件大小不变、非零字节数为 0）。带 9 字节自定义头的电脑端缓存不受影响，
因为它们走的是 `copyWithoutPrefix`（真正的独立副本）。

修复（两层，缺一不可）：

- **`wipeFile` 增加硬链接保护**：`nlink > 1` 时**只摘目录项，绝不覆写**。
  这是中央防线 —— 同时保护了会话临时目录与 `purgeLegacyAudioCache()`
  要清理的 `userData\bili_audio`（v1.0.x 在里面留的也正是硬链接）。
- **`ensureM4a` 彻底不再用 `linkSync`**：一律 `copyFileSync` 出**独立副本**
  （`nlink === 1`、与源 inode 不同）。多占一份磁盘，换绝对安全。

### 新增

- `scripts\数据管控验证.js` 增加 **第 3b 组「硬链接保护」回归测试**（断言数 16 → 27）：
  - 构造硬链接副本 → 用**从 `main.js` 源码摘出的真实 `wipeFile`** 擦除 →
    断言源文件 MD5 **一字不变**、链接数回到 1
  - 反向断言 `ensureM4a` 产出的副本不再与源共享 inode、且 `nlink === 1`
  - 静态断言 `wipeFile` 含 `nlink > 1` 保护、`bili.js` 不再出现 `linkSync(` 调用
    （断言前先剥掉注释，避免"注释里提到 `linkSync`"造成误报；
    正则用 `(?<!un)linkSync\(` 以免被 `unlinkSync` 误命中）

### 变更

- `app\package.json`：版本号 `1.1.3` → **`1.1.4`**
- `docs\数据管控与合规.md`：擦除一节补上硬链接保护；「已知边界」补上本次事故的说明
- `docs\架构说明.md`：数据管控层的擦除小节同步

  **不在 B 站客户端缓存目录里**，无法通过重新缓存取回。可尝试

`app/package.json` 只跟着升了版本号。

### 变更

- `app\package.json`：版本号 `1.1.1` → **`1.1.2`**（应用代码本身无变化）
- `scripts\push-to-github.ps1` 重写：
  - **`-RepoUrl` 变为可选** —— 省略时沿用已有 `origin`，日常更新只需
    `.\scripts\push-to-github.ps1` 一条命令
  - 新增**通道探测 + 自动适配**：先跑 `git ls-remote`，失败时按错误类型分类并兜底
    | 判定 | 兜底动作 |
    | --- | --- |
    | `tls` | 改用 openssl 后端 + 合并本机自签 CA 的 bundle |
    | `credential` | 直接调用 `git-credential-manager.exe` 取缓存凭证，拼成 `Authorization` 头 |
    | `network` / `nonfastforward` | 不做兜底，给出对应提示 |
  - 新增 `-Check`（只探测通道）与 `-NoAutoFix`（关闭兜底）
  - 统一用 `Invoke-GitCapture` 调用 git：临时放宽 `$ErrorActionPreference`，
    避免 git 写在 stderr 的进度信息在 `EAP=Stop` 下被当成终止性错误而中断
- `scripts\setup-push-tls.ps1` 新增 `-SetEnv` / `-EmitPath` / `-Quiet`：
  可把配置直接注入当前进程环境、可只输出 bundle 路径供其它脚本调用
- 新增 `推送.bat`（纯 ASCII 转发），双击即可推送

### 修复

- **「凭证兜底不触发」** —— 通道探测用的是 `git ls-remote`，而**公开仓库的 ls-remote
  根本不需要凭证**，所以 TLS 修好后探测就通过了，脚本误判"通道没问题"，
  一直到真正的 `git push` 才因为认证失败而报错，兜底却已经错过。
  现已把凭证兜底挂到**真正需要认证的那一步**：`push` 失败且判定为
  `credential` / `tls` 类问题时，取缓存凭证重试一次
- 「CA 收集输出绕过 `-Quiet`」：`setup-push-tls.ps1` 里两处裸 `Write-Host`
  不受 `-Quiet` 约束，被 `push-to-github.ps1` 调用时会刷出 50 多行证书清单

### 文档

- `docs\构建与安装.md` 第 6 节重写：单一命令用法、参数表、自动适配的错误分类表、
  标签列表补上 `v1.1.1`；原「推送不通时的排查」降级为原理与手动排查参考
- `README.md` 项目结构补上 `推送.bat` 与新脚本说明

## [1.1.1] — 2025

**主题：可视化调音等偏好设置的持久化修复。**

### 修复 —— 设置"重启后不保持"

三个滑块/选项的调音数据本该**全局通用、重启后保持**，实际却会静默丢失。
两类成因都属于"不报错、不崩溃，只是设置悄悄没了"：

- **鼓点强度（写 A 读 B）** — 滑块 `setItem('mp_kick')`，恢复代码却 `getItem('mp_kick2')`，
  而 `mp_kick2` 从来没有被写入过。于是每次重启鼓点强度都退回默认 `0.40`，
  滑块位置也停在中点。已改为读写同一个键 `mp_kick`
- **排序方式（只读不写）** — 恢复代码读 `mp_sort`，但 `#sortSel` 的 `change` 处理器
  只改了变量没落盘。已补上 `setItem('mp_sort', ...)`
- **排序方式（不回填控件）** — 即使读到了值，也没有写回 `<select>`，
  界面仍显示"添加顺序"，看起来就像没保存。已补 `$('#sortSel').value = sm`

顺带加固：排序方式恢复时增加 `SORT_MODES` 白名单校验
（直接信任 localStorage 里的字符串会让下拉框落到空白项）。

### 确认 —— 调音数据本来就是全局的

排查中确认了「所有歌曲通用」这一条**本来就没有问题**，并用自动化断言固定下来：

- 5 个调音参数（`tiltStrength` / `jitterK` / `kickPump` / `bassGainTarget` / `bassSigma`）
  都是模块级全局变量，没有任何一首歌单独持有一套
- 切歌/播放流程（`selectSong` / `playAt` / `playRandom` / `nextSong` / `prevSong`）
  不触碰这些变量
- `idbPut` 写单曲记录时不包含任何调音字段
- 频谱 Worker 只算**原始频段幅度 + 鼓点触发**，不含任何调音参数，
  因此 Worker 重建也不会让调音回退

### 新增 —— 回归验证

- 新增 `scripts\设置持久化验证.js`，**31 项断言**，`node` 直接跑，不需要 Electron：
  | 组 | 验证内容 |
  | --- | --- |
  | 1 | localStorage 键名交叉校验：没有"只读不写"（永远读不到）也没有"只写不读"（写了没人用） |
  | 2 | 每个 `type="range"` 滑块都要「保存 / 恢复同一个键 / 回填控件」三件事齐全 |
  | 3 | 下拉框恢复时回填控件；枚举型设置有白名单校验 |
  | 4 | 调音参数是全局的，且不被切歌流程改动；恢复走 `apply*` 而不是只改变量 |
  | 5 | 调音数据不写进单曲记录（否则就成了"每首歌一套"） |
  | 6 | 恢复时的范围闸门要与滑块 `min`/`max` 一致（改范围忘了改闸门会静默丢弃边界值） |
- 该脚本**验证过有牙齿**：把两个 bug 还原到副本上跑，能精确报出
  「只读未写: mp_kick2 读于第 2299 行 / 只写未读: mp_kick 写于第 1171 行」并退出 1

### 修复 —— 验证脚本自身的缺陷

第 6 组最初用单行正则匹配恢复语句，而 4/5 个滑块的恢复是跨两行的
（`const` 一行、`if` 一行），导致误报"没有范围闸门"。已改为向后看 4 行。

## [1.1.0] — 2025

**主题：派生数据管控 + 历史版本回滚。**

### 新增 —— 数据管控

针对程序能解出的两类派生数据（`.ncm` 解出的音频、B 站缓存剥离头后的副本），
加入「不落盘 / 不可导出 / 可追溯」三层管控。

**最小落盘**
- 解密结果只在内存中经 IPC 传递给渲染进程，**从不写入用户音乐目录**
- 新增**会话专属临时目录** `%TEMP%\mp-session-<12位随机ID>\`，每次启动重新生成
- B 站可播放副本改写到会话目录（原来长期驻留在 `userData\bili_audio`）
- 解密子目录在字节读回内存后**立即覆盖擦写并删除**，不等 GC
- `will-quit` 拦截退出 → 递归擦除会话目录 → 真正退出（4 秒兜底，不会关不掉）
- 启动时 `sweepStaleSessions()` 清掉崩溃/强杀残留的会话目录
- 启动时 `purgeLegacyAudioCache()` 擦除 1.0.x 遗留在 `userData\bili_audio` 的长期副本（升级清理）
- 临时目录尽力打上隐藏属性（`attrib +h`）
- `wipeFile()` 覆盖写零 + `fsync` 后再 `unlink`，单会话上限 256 MB 避免退出卡顿

**不可导出**
- 确认全部 27 个 IPC 通道**没有任何一个接受"输出路径"参数**
- `preload.js` 暴露的 16 个方法中**没有任何写文件方法**
- 这条保证是结构性的：不是"没做导出按钮"，而是"没有可用路径把字节写到磁盘"

**可追溯**
- 新增本地审计日志 `userData\audit.log`：时间 / 版本 / 会话 ID / 事件 / 来源文件 / 产物体积 / 结果
- 记录 `ncm-decrypt`、`bili-extract`、`bili-scan` 三类事件，上限 500 条自动裁剪
- 只在本机，程序从不外发

**输入侧限制**
- `convert-ncm` 先校验 `CTENFDAM` 容器魔数，非 NCM 直接拒绝（不再是一个通用解密器）
- B 站提取只处理本机已有缓存，不发起任何音频下载请求
- 原始 `.ncm` 与缓存文件从不被修改或删除

**程序内可见性**
- ⚙ 面板新增「数据管控」行：`内存解密 · 会话级临时目录 · 无导出 · 审计 N 条`（悬停看完整说明与审计路径）
- 同排「清日志」按钮一键清空审计
- ⚙ 面板新增「版本」行，显示当前版本号
- 首次启动弹出一次**使用边界与数据管控告知**弹层（记录在 `localStorage.mp_notice_v110`）

**新增 IPC / API**
- `get-data-policy` → `{ version, sessionId, auditCount, policy }`
- `clear-audit-log`
- `preload` 对应暴露 `getDataPolicy()` / `clearAuditLog()`

**回归验证**
- 新增 `scripts\数据管控验证.js`，16 项断言：
  副本落盘位置（3 项）、擦除逻辑（3 项）、陈旧清扫（1 项）、静态断言（8 项）、
  preload 暴露面（1 项）。`node scripts\数据管控验证.js app` 即可跑
- 擦除逻辑的测试**从 `main.js` 源码里摘出实现**再执行，测的是真实代码文本而非复制品

**文档**
- 新增 `docs\数据管控与合规.md`：技术实现、验证明细、使用边界、已知边界（含"覆盖擦除不保证
  取证级不可恢复"的诚实说明）
- README 新增「数据管控」一节；`docs\功能说明.md` 的 NCM / B 站章节同步更新

### 修复

开发过程中定位并修复的问题，一并记录以便追溯：

- **鼓点响应失效** — 低频参考值 `kickRef` 只在首次赋值（`if (kickRef <= 0)`）之后不再更新，
  导致 `kick` 迅速饱和到 1.0，乘性泵浦完全失效。改为持续跟踪 `kickRef += (lowMag - kickRef) * 0.05`，
  Worker 与同步回退两条路径都修复
- **滑动感做不出来** — 值位移混合在平滑频谱上不可见；随机抖动波方向随机、平均位移为零。
  改为每 6 条柱体一个周期的相干行波，相位每帧推进 0.26
- **打开小窗后主窗帧率减半** — `resources\app\main.js` 曾设置
  `webContents.setFrameRate(60)` 且小窗持续渲染；移除 `setFrameRate`，
  小窗改为按需渲染，并关闭 `disable-direct-composition`（保留 flip-model）
- **媒体键状态误报「被占用」** — 6 s 重试逻辑把已被本程序注册的键重新注册，
  Electron 返回 `false`（`IsRegistered` 检查），把健康状态改写成失败。改为幂等注册
- **进度条圆形滑块不跟随** — 代码只设置了 `#barFill` 的宽度，`#barThumb` 从未被定位。
  新增 `setBarUI(pct)` 同时设置填充宽度与滑块位置，接入 `timeupdate`、重置与两条拖动路径
- **暂停按钮看起来是方的** — 两个独立原因：图标原来是两个尖角矩形
  （`M6 5h4v14H6zM14 5h4v14h-4z`），改为圆角 `<rect rx="1.8">`；
  且 `#playBtn` 缺少 `icon-btn` class，因而没有 `border-radius: 50%`
- **迷你窗图标未同步改版** — 主界面换新图标集后小窗仍用旧图标，新增独立 `MIC` 图标库
- **迷你窗缩放异常** — 渲染层 `e.screenX` 已是 DIP，又除了一次 `scaleFactor`，
  125% 缩放下窗口增长慢 20%。改用主进程 `screen.getCursorScreenPoint()`
- **迷你窗拖不动** — 点击穿透靠页面 mousemove 事件驱动，快速移动后立刻按下时状态未切换。
  改为主进程 50 ms 光标轮询，即使丢事件也会自愈
- **迷你窗被游戏遮挡** — 无边框全屏游戏会重新抢 Z 序，增加 800 ms 周期重申置顶

### 已知限制

- Windows 独占全屏（Exclusive Fullscreen）下，任何普通窗口都无法覆盖，迷你窗不会显示；
  请将游戏改为「无边框窗口」或「窗口化全屏」
- Windows 媒体键是独占资源，被其它程序注册时本程序无法接管，设置面板会显示占用状态
- 60 Hz 显示器下可见帧率上限为 60，渲染路径的目标是「稳定无卡顿」而非追求更高数字
