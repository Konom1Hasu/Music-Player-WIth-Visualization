# 发布与推送

> 只回答一件事：**把当前仓库推上去，让 GitHub Actions 自动出 Setup.exe 并挂到 Release。**
> 构建与安装的细节见 [构建与安装](构建与安装.md)，版本改动见 [更新日志](更新日志.md)。

## 0. 一页速览

挪标签（`git tag -f v2.2.0 -m "2.2.0"`）→ 本机检查（`node scripts\文档一致性验证.js`）→ 双击 `.\推送.bat` → 等 CI 出包（Actions → Release，约 3–8 分钟）→ 从 Releases 下载 Setup.exe 双击装，按 §6 的清单走一遍。

## 1. 当前状态快照

所有会随着每次提交发生变动的字段，这里都统一记录**读数方式**，而不填写固定的数值。如果直接写死具体数字，文档很快就会过时失效；用户在执行推送操作之前，只需依次运行表格中列出的对应命令，就能立即获取到环境的最新读数。

| 项 | 值 / 读数方式 |
| --- | --- |
| 版本（`app\package.json`） | `2.2.0`（CI 会校验 `标签 == v{version}`，不一致直接失败） |
| 分支 | `main` |
| 本地领先远端 | `git status -sb` 首行：`main...origin/main [ahead N]`；**推送成功后应变成 `[up to date]`** |
| 版本标签 | `v2.2.0`；`git rev-list --count 'v2.2.0^{commit}..HEAD'` 必须是 **0**（改完代码要 `git tag -f` 再推） |
| HEAD | `git log --oneline -1` 的第一行 |
| 本地安装包 | ⚠ **本轮（v2.7.8）之后的 Setup.exe 还没重打**：源码、`app-rhine\dist`、`app\ui` 已是最新，但 `dist\安装包\` 里那个是旧产物。在普通终端跑 `.\打包安装包.bat`（或 `powershell -ExecutionPolicy Bypass -File scripts\build-portable.ps1` 后 `scripts\build-installer.ps1 -NoBuild`）重打一次即可 |
| 触发方式 | 推 `v*` 标签 → `.github\workflows\release.yml` 构建并上传 Release |
| 远端 | `https://github.com/Konom1Hasu/Music-Player-WIth-Visualization.git` |

**版本标签同步机制**

`v2.2.0` 属于本地标签，由于本轮经历了多次修改与重复提交，该标签仍停留在较早的历史提交上，不会自动跟随分支移动。CI 完全依据标签拉取代码并打包，**标签指向哪一个提交，导出的 Release 产物中包含的就是哪一个版本的内容**。因此，推送代码前必须确保标签与当前 HEAD 完全同步（即距离为 0），必要时执行 `git tag -f` 覆盖旧标签。

**标签对象校验注意事项**

> ⚠ 本项目使用的是**带注释的标签**（附注标签对象，`git cat-file -t v2.2.0` 输出为 `tag`）。运行 `git for-each-ref --format='%(objectname)'` 时输出的是标签对象本身的 SHA 哈希值，并非目标提交编号；若要查看标签实际绑定的提交，须执行 `git rev-parse --short 'v2.2.0^{commit}'` 解析提交 SHA。

```powershell
cd "D:\harness work\音乐播放器"

# ① 工作区干净、版本号三处一致（package.json / README / 更新日志的 2.2.0 小节）

# ② 文档与代码同步（15 项：版本↔更新日志、README 结构图、相对链接、.ps1 的 BOM、.bat 纯 ASCII…）

node scripts\数据管控验证.js
node scripts\设置持久化验证.js

# ④ 安装包是本轮代码打的（不是旧的）

```

**执行要求**
  - 只要有任意一条检查未通过，必须立即停下排查修复，严禁强行推送。
  - 持续集成流水线配置了相同的校验逻辑；若强行推送，流水线在执行相同检查时同样会失败并直接驳回当前的 Release。
## 3. 推送

### 3.1 先把标签挪到当前提交（推荐每次都做）

```powershell
git tag -f v2.2.0 -m "2.2.0"
git rev-parse --short 'v2.2.0^{commit}'                       # 期望：与下面的一致
git rev-parse --short HEAD
git rev-list --count 'v2.2.0^{commit}..HEAD'                  # 期望：0
```

### 3.2 推送（二选一）

```powershell
.\推送.bat                                  # 双击也行；内部就是下面那条
.\scripts\push-to-github.ps1                # 自动适配 TLS / 凭证受限的网络环境
```

脚本做四件事：探测通道（必要时启用 openssl + 本机 CA、或从凭据管理器取缓存凭证）→ `git push -u origin main` → `git push origin --tags` → 打印仓库地址与推了哪些标签。它**不会**打印 token；所有 git 配置都用环境变量临时传入，不写进 `.git/config`。

> - 首次推送会弹 GitHub 登录窗口（Git Credential Manager）。GitHub 已取消密码认证，若要手填凭证请用 Personal Access Token（勾 `repo`）或改用 SSH。
> - 直连失败多半是加速器：装了 Steam++ / Watt Toolkit 就让它开着（它接管 github.com 的解析），或反过来关掉它对 GitHub 的加速。先单独探一次通道：`.\scripts\push-to-github.ps1 -Check`。
> - 远端有本地没有的提交 → 加 `-Pull`：`.\scripts\push-to-github.ps1 -Pull`。

### 3.3 通道坏了：中间人证书不被信任

`git push` 报 `schannel: ... revocation` 或 `SSL certificate problem: unable to get local issuer certificate`，就是本机有加速器（Steam++ / Watt Toolkit）对 github.com 做了中间人：它注入的根证书 Windows 认，Git 自带的 CA bundle 不认。

一次性修好，之后 `git push` 直接可用：

```powershell
# 1. 找出那张根证书的指纹（看 Subject / NotAfter，挑还在有效期内的）
certutil -store Root | Select-String -Context 12,4 'SteamTools|BeyondDimension'

# 2. 导出并转成 PEM
certutil -store Root <指纹> steamtools.cer
openssl x509 -inform DER -in steamtools.cer -out steamtools.pem

# 3. 追加到一份 CA bundle，并让 git 全局使用它（用 openssl 后端，别用 schannel）
cat "<Git安装目录>\mingw64\etc\ssl\certs\ca-bundle.crt" steamtools.pem > "$env:USERPROFILE\.workbuddy\certs\git-ca-bundle.pem"
git config --global http.sslBackend openssl
git config --global http.sslCAInfo "$env:USERPROFILE\.workbuddy\certs\git-ca-bundle.pem"

# 4. 只读探一次，通了再推
git ls-remote origin
```

不想动全局配置，就临时带参数推：

```powershell
git -c http.sslBackend=openssl -c http.sslCAInfo="<bundle 路径>" push origin main
```

### 3.4 标签被拒时（只有这一种情况需要强推）

如果早先推过一次版，远端已经存在一个**指向别处**的 `v2.2.0`，`--tags` 就会对这一个标签报 `rejected (already exists)`。这时候代码其实已经推成功了，只需补一刀：

```powershell
git push origin --force v2.2.0     # 只强制这一个标签
```

## 4. 推上去之后 CI 会做什么

持续集成脚本定义在 `.github\workflows\release.yml`，执行环境为 `windows-latest`。作业最长超时时间设为 60 分钟，实际通常运行 3–8 分钟就能走完全程：

```
取源码 → 装 Node 20（缓存 app-rhine/package-lock.json）→ npm ci
      → 校验 标签 == v{package.json.version}（不一致直接失败）
      → node scripts\文档一致性验证.js
      → 数据管控验证 / 设置持久化验证 / ID3编码验证
      → choco install innosetup
      → .\scripts\build-installer.ps1          （便携版 + Setup.exe，与本地同一条路）
      → 上报产物名与 SHA256
      → upload-artifact：音乐播放器-Setup-2.2.0
      → gh release create/upload：挂到 v2.2.0 Release
```

**执行监控与调试**
  - 进入 GitHub 仓库顶部的 Actions 标签页，点击左侧列表的 `Release` 即可查看执行记录；若流程中断，可点进出错步骤查看版本号不一致、自动化测试未通过或打包编译失败等具体日志。
  - 若不想发版只想测试构建，可在 Actions 页面的 Release 工作流中点击 `Run workflow` 手动触发（底层对应 `workflow_dispatch` 事件）；该方式生成的安装包仅保留在 Actions artifact 供排查下载，不会发布到 GitHub Release。

**版本发布与说明管理**
  - Release 说明由脚本按固定模板自动生成，内容涵盖“下载双击安装 + 按用户安装 + 卸载不删曲库 + 便携版替代 + 版本与 SHA256”，不会自动抓取提交记录生成更新日志。
  - 如需补充具体功能改动，可在 Release 页面生成后手动编辑正文，直接套用 §7 准备好的草稿。
## 5. 推送后核对（5 分钟）

1. 进入 GitHub Actions 页面查看执行结果，确认 `Release` 工作流已经顺利跑通并显示为绿色的成功图标，同时重点排查名为 `gh release upload` 的步骤，确保该任务顺利执行完毕而没有报错中断；
2. 打开仓库的 Releases 发布页面，检查新生成的 `v2.2.0` 版本下方是否已经挂载了安装包附件 `音乐播放器-Setup-2.2.0.exe`。接着比对页面上标注的 SHA256 校验码与 §1 表格中的数值。因为 CI 构建服务器和本地电脑各自独立打包了一次，两次生成的安装包二进制内容存在差异，所以**哈希不会相同**——这里核验的目的是确认页面上展示的那行校验码，与从对应发布位置下载到本地的文件哈希完全一致；
3. 将安装包下载到本地磁盘并双击运行，完整操作一遍图形安装向导流程。期间需要测试两种情况：勾选与不勾选创建桌面快捷方式各执行一次，随后验证从 Windows 开始菜单中能否正常启动播放器；
4. 运行系统自带的卸载程序，检查安装目录、开始菜单项以及桌面快捷方式是否都已经彻底清理干净；同时需要注意**曲库与设置保留**，相关数据文件不应被误删，重新安装之后之前的播放列表和个人配置仍然能够直接读取出来。

## 7. 出问题怎么办

| 情况 | 处理 |
| --- | --- |
| 标签被远端拒（`already exists`） | 远端仓库已经存在同名 Tag，推送因此会被拒绝，请执行 `git push origin --force v2.2.0` 强制覆盖远端标签（详细背景与操作见 §3.3） |
| CI 在"标签与版本一致"那步失败 | Git 标签名称与 `app\package.json` 中的 version 字段不匹配：用户要么使用 `git tag -f` 把标签重新指向正确的提交，要么按照 [维护指南](维护指南.md) 的步骤去同步更新项目版本号 |
| CI 在文档检查那步失败 | 可以在本地工作区运行 `node scripts\文档一致性验证.js` 命令来复现错误，接着按照控制台给出的提示去修改（这种情况大多数是因为 README 里的目录结构图漏掉了新增的文件） |
| CI 构建失败但本地能打 | 先去对应的工作流界面查看具体是在哪一步报了错并排查日志；如果线上持续无法构建，可以用本地方案做兜底：运行 `.\打包安装包.bat` 生成 Setup.exe 文件，然后直接通过浏览器手动拖拽上传到 GitHub Release 页面 |
| 发完发现要改 | 修复代码后在本地执行 `git tag -f v2.2.0` 将标签强行移到最新提交，再推送到远端仓库，CI 检测到新触发后会自动带上 `--clobber` 参数，直接覆盖 Release 资产列表中已经存在的同名附件 |
| 想整版撤回 | 直接在 GitHub 的 Releases 页面找到对应的发布记录并删除该 Release（关联的 Git 标签可以保留也可以删除，如果决定彻底清理远端标签，请运行命令 `git push origin :refs/tags/v2.2.0`） |
## 8. 本次（2.2.0）改动摘要 —— 可直接粘到 Release 说明

#### 安装与交付

下载安装文件 `音乐播放器-Setup-2.2.0.exe` 后直接双击运行，连续点击“下一步”，根据需要勾选或取消勾选“创建桌面快捷方式”，最后点击“完成”即可结束流程。

  - 程序采用当前用户维度的安装模式，运行全程不会弹出 UAC（用户账户控制）权限提权提示。
  - 后续如果需要在系统的“应用和功能”中卸载，用户的曲库数据和个人配置文件都会保留在本地，不会被自动删除。
  - 所有发布版本的一键安装包均已接入 CI（持续集成）流水线，由系统自动完成编译打包并挂载到 Release 页面供用户下载。更多技术实现细节可以参考 [更新日志 §2.2.0](更新日志.md)。

#### 播放与曲库控制

针对音频导入、播放触发逻辑及列表管理进行了多项优化与修复：

  - 修复了解析逻辑，导入的 B 站缓存音频已可正常解码播放，并增加了重复导入校验，同一音频文件或缓存文件夹不会被多次添加进曲库。
  - 用户通过回车、点击 `PLAY TRACK`、点击歌曲标题或双击歌曲卡片打开音频档案时，程序均会在载入内容的同时直接开始播放。
  - 进度记忆策略调整为单条记录，系统仅保留用户“最后一次在听的那首 + 位置”这一处断点。
  - 播放列表页面补充了切换排列顺序与列表内搜索功能；系统设置页面新增了一键重读全部封面选项，方便本地图片更新后重新抓取。
  - 重新接入了键盘与外设上的硬件媒体键，并修复了界面中回车键偶尔失灵无法响应的问题。

#### 界面交互与视觉表现

重点优化了高频操作区域的视觉样式与异常渲染问题：

  - 底部播放条图标统一更换为细描边风格，且底部的版权标语 `POWERED BY RHINE LAB` 不再会被其他悬浮元素遮挡。
  - 修复切歌时的图层渲染异常，曲目信息文本不再出现大块异常黑色背景。
  - 优化深色主题启动时的占位布局，开屏加载阶段消除无内容的纯黑色块，页面主体版面也会跟随当前窗口高度自适应撑满，避免出现异常空白。
## 9. 相关文件

- `.github\workflows\release.yml` —— 当推送以 `v*` 格式命名的版本标签时，该工作流会自动触发编译、打包并发布对应的 GitHub Release 资产。
- `scripts\build-installer.ps1` —— 用于在本地环境编译生成最终的 Setup.exe 安装程序，持续集成流程（CI）也是基于这个脚本运行相同的构建逻辑。
- `installer\music-player.iss` —— Inno Setup 安装包制作脚本，配置为按当前用户权限进行安装，并允许用户在安装界面中自主勾选是否创建桌面快捷方式。
- `scripts\push-to-github.ps1` / `推送.bat` —— 代码推送脚本，内置了 TLS 传输协议检查以及凭证缺失时的备用处理逻辑，用来降低网络连接失败的概率。
- `scripts\release.ps1` —— 发版流程辅助脚本，依次执行修改版本号、同步更新日志、提交变更并打上 Git 标签；如果检测到系统安装了 Inno Setup 编译器（ISCC），还会顺带在本地预先打包一次以验证流程。
- `scripts\文档一致性验证.js` —— 提交与推送前必须通过的校验脚本，专门用来检查说明文档与实际代码中的配置及实现是否保持一致。
- `docs\构建与安装.md` —— 包含完整构建步骤、软件安装方法以及脱机状态下离线演练方案的详细指南。
