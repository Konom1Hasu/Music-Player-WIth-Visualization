# 快捷键

软件内部的快捷键体系一共划分为三个层级。处于最顶层的是系统级的标准媒体键，也就是键盘上自带的播放、暂停和音量调节这类专用硬件按键；中间一层是系统级的全局备用组合键，即使把当前窗口最小化或者切换到其他程序，按下这些按键也同样能在后台触发对应的控制动作；最底层则是应用内快捷键，这类操作生效的前提，是必须保证软件窗口处于前台并且处于输入焦点的激活状态，一旦焦点切走就会失效。

---
## 1. 媒体键（系统级）

操作系统为这一层级的按键提供了全局监听机制，也就是让程序无需处于前台焦点也能感知输入事件。无论播放器主窗口此时正退到后台运行、已经最小化缩入系统任务栏，还是屏幕前台正全屏运行着无边框窗口模式的 3D 游戏，这些按键都可以正常捕获用户的敲击动作，并直接控制后台正在进行的音频播放。

| 键名 | 典型触发方式 | 功能 |
| --- | --- | --- |
| `MediaPlayPause` | 键盘播放键、多数耳机单击 / 双击 | 播放 / 暂停 |
| `MediaNextTrack` | 耳机双击 / 三击、键盘下一曲 | 下一首 |
| `MediaPreviousTrack` | 耳机长按 / 三击 | 上一首 |
| `MediaStop` | 键盘停止键 | 暂停 |
| `MediaPlay` | 部分耳机 / 声卡驱动的独立播放键 | 播放 |
| `MediaPause` | 部分耳机 / 声卡驱动的独立暂停键 | 暂停 |

程序完成启动初始化时，会尝试将上述六个媒体键全部向 Windows 系统申请注册。之所以采取全部注册的策略，是因为市面上存在一部分耳机设备，硬件厂商在设计固件时将「播放 / 暂停」拆分成了两个互不相干的操作，分别向操作系统投递独立的 `MediaPlay` 与 `MediaPause` 键值信号，并不会直接发送通用的 `MediaPlayPause` 指令。为了确保这部分特殊设备在触发时不会漏掉操作，程序必须把这两组键值全部纳入监听范围。

### 媒体键是独占资源

在 Windows 操作系统的底层输入架构中，媒体键属于独占型的系统硬件资源。这意味着在同一时刻下，某一个特定的媒体键只能允许单一程序成功注册并保持持有状态，其他软件无法共享该事件。一旦某些游戏、聊天通讯工具或者其他音乐播放软件在启动时提前抢占注册了这些键位，本程序在调用系统接口申请持有权时就会遭到操作系统拒绝，导致后续无法直接捕获到对应的按键触发事件。用户可以在设置面板中找到「`HEADPHONE / MEDIA KEYS`」这一行状态检测项，直接查看本程序当前的按键接管情况：

| 显示 | 含义 |
| --- | --- |
| `媒体键 ✓ 已接管` | 六个键全部注册成功 |
| `✕ 被占用` + `未拿到：…` | 有一部分被抢走，后面列出**具体键名** |
| `✓ 备用组合键可用` | §2 那套组合键可用 |
| `最近一次：播放 / 暂停 · 来源 MediaPlayPause · 12:52:04` | 刚按下的键被系统认成了哪一个 |

面对注册失败的按键，程序会在后台启动一个定时器，每隔 **6 秒**就自动发起一轮重新注册请求，至于前面已经成功持有的键位则会跳过，不会产生多余的重复操作。只要用户彻底退出了产生抢占冲突的外部软件，原本被占用的键位资源就会被系统释放，本程序便会在下一个 6 秒检测周期到达时自动完成接管，恢复完整的按键控制。

## 1.5 有线耳机按键

有线耳机的线控按键不同于常规的电脑键盘按键。这类硬件在按下时产生的电平变化，是通过操作系统遵循的 HID（人机接口设备，也就是接入电脑并由人直接操作的输入输出外设）规范中专门定义的「消费者控制」（HID Consumer Control）通道向上传递的。Windows 系统收到这层底层硬件信号以后，会在操作系统内核层把这些原始输入统一转换成对应的系统级标准多媒体按键事件，然后再把转换后的消息依次派发给当前系统中已经注册监听了该按键事件的各个应用程序进程。

| 耳机上的操作 | 系统发出 | 本程序的动作 |
| --- | --- | --- |
| 单击（中键） | `MediaPlayPause` | 播放 / 暂停 |
| 双击 | `MediaNextTrack` | 下一首 |
| 三击 | `MediaPreviousTrack` | 上一首 |
| 长按 | 多数固件直接走系统语音助手 | 拿不到 |
| 音量键 | `VolumeUp` / `VolumeDown`（系统接管，本程序不抢） | 系统音量 |
| 接听键 单击 | `MediaPlayPause`（多数固件） | 播放 / 暂停（= 接听 / 挂断） |
| 接听键 长按 | `MediaStop`（部分固件） | 暂停 |
| 结束通话键 | `MediaStop` | 暂停 |

### 怎么确认「我的耳机键被认成了什么」

1. 首先打开设置面板，找到标有 `HEADPHONE / MEDIA KEYS` 的状态显示行。
2. 在耳机上按下一颗物理按键，该行右侧区域会立即刷新出具体的识别日志，实时展示出**动作 · 来源键名 · 时间**这三项关键数据，例如展示为 `下一首 · 来源 MediaNextTrack · 12:52:05`。
3. 如果用力按下了耳机按键但操作界面完全没有反应，面板里的那一行日志文字也没有发生更新，通常意味着遇到了以下两种硬件或软件层面的问题：
   - 当前按键已经被操作系统中正在运行的其他应用程序提前注册占用了（这类情况常见于前台正在运行的游戏或其他后台音乐播放器）。用户可以先查看面板自检信息中明确标注为「未拿到」的具体键名，彻底退出产生冲突的第三方程序，随后静待 6 秒，本程序就会通过后台重试机制自动找回控制权；
   - 耳机硬件本身发出的信号没有走操作系统的标准媒体键通道，少数硬件厂商的线控固件会把上面的多功能按键转换成私有协议指令直接发送给专属驱动。面对这类非标硬件信号，用户只能改用第 2 节中整理出来的备用组合键方案进行控制。

### 接听 / 挂断那颗键

市面上很多手机配属的线控耳机往往只配备单单一颗实体功能键。当用户把这种耳机插入 Windows 电脑使用时，操作系统底层的协议转换模块通常都会把这颗多功能按键映射成标准媒体键。正如上文表格所整理的那样，在绝大多数系统环境下，它原本就可以直接生效并控制媒体播放。如果按下这颗按键却没有得到任何响应，根本原因通常不是本程序缺少对应的按键解析逻辑，而是因为在操作系统派发按键消息的调用链路上，事件被其他更高优先级的软件中途劫持了。常见的劫持方包括 Windows 系统内置的「手机连接 / Phone Link」、微信客户端、QQ、Discord 等即时通信工具，或者是耳机品牌方强制随硬件安装的驱动控制软件。这些软件在启动后会直接调用系统接口，强行将接听按键的操作抢先标记为语音通话中的「接听电话」事件。如果在按下耳机按键之后，电脑屏幕上突然弹出了前述通信软件的来电或通话界面，而本程序设置面板里 `HEADPHONE / MEDIA KEYS` 显示行的状态完全没有发生改变，用户就可以明确判定按键事件已经被这些外部通信软件截断拦截了。

解决这类按键拦截问题可以通过以下两种途径进行处理：

1. 直接关闭或者从系统托盘彻底退出那些强行抢占按键的软件（其中以 Windows 系统的手机连接组件引发的抢占最为常见），退出完成后等待 6 秒，本程序内置的后台轮询机制就会自动把该键重新注册回来；
2. 或者是打开耳机专用的驱动配置软件，把线控上的物理接听与挂断动作重新绑定为常规的键盘快捷组合键。为了方便用户建立起清晰直观的按键映射关系，本程序在底层专门提供了两个含义对应的快捷组合键：

| 耳机按键想做的事 | 建议绑成 |
| --- | --- |
| 接听（播放 / 继续） | `Ctrl` + `Alt` + `A` |
| 挂断（暂停） | `Ctrl` + `Alt` + `H` |

重新绑定完成之后，只要在耳机上按下该物理按键，设置面板的状态行就会明确打印出 `播放 / 暂停 · 来源 Ctrl+Alt+A（接听）` 这一行文本，用户借此就能直观确认键盘按键映射已经成功打通。这两个专用组合键与第 2 节介绍的其他全局快捷键完全一致，全部属于系统底层注册的全局快捷键。这意味着即便播放器窗口正处于后台失焦状态，或者前台正有大型 3D 游戏处于全屏独占运行模式，按键信号依然可以准确送达并被程序正常处理。另外需要说明的是，本程序从架构设计上就主动摒弃了全局底层键盘钩子（Keyboard Hook，一种在操作系统事件分发给应用前强行监听并修改所有按键消息的系统机制）这种暴力抢占按键的技术方案。之所以不采用钩子，是为了防止搭载反作弊系统（Anti-Cheat）的游戏进程把播放器的钩子模块误判为注入式作弊外挂；但也正因为程序没有使用这种强行拦截并篡改输入的底层钩子，面对那些依赖厂商私有硬件指令与协议通信的特殊按键，程序完全无法截获到任何硬件信号，更无法实现强制接管。遇到这种情况，用户只能依赖耳机外部驱动面板进行改绑。

### 耳机带「USB 声卡 / 配套软件」的情况

对于这一类自带独立 USB 外置声卡或拥有专属桌面端管理软件的耳机硬件，它们的控制中心软件通常都内置了允许用户自由映射物理按键的自定义宏功能。面对这种设备，建议用户直接在耳机的驱动软件中把各个线控物理按键分别映射为第 2 节列出的全局备用组合键，这样在功能定义上刚好可以与耳机线控上的三颗物理实体键建立起严丝合缝的一对一绑定。

| 快捷键 | 功能 |
| --- | --- |

### 迷你悬浮窗控制

某些前台游戏在以独占全屏模式运行时，或者启用了绕过系统事件队列直接读取硬件数据的原始输入（Raw Input）机制，操作系统会限制指针消息的分发，不再向处于非激活状态的后台窗口传递光标点击、悬浮或拖拽事件。这样一来，即使迷你悬浮窗始终置顶显示在屏幕最上层，也会因为收不到鼠标事件而彻底失去响应。

遇到这种鼠标输入被前台独占游戏完全拦截的情况，用户可以使用系统全局快捷键直接控制悬浮窗，完成位置平移与尺寸缩放。为了防止这些操作与上一节中用来切歌的 `Ctrl+Alt+←/→` 发生冲突，设计时在方向键前方特别加入了 `Shift` 修饰键，从而将常规的切歌控制通道完整留给耳机按键映射继续使用。

| 快捷键 | 功能 |
| --- | --- |
| `Ctrl` + `Alt` + `Shift` + `←` | 迷你窗左移 14 px |
| `Ctrl` + `Alt` + `Shift` + `→` | 迷你窗右移 14 px |
| `Ctrl` + `Alt` + `Shift` + `↑` | 迷你窗上移 14 px |
| `Ctrl` + `Alt` + `Shift` + `↓` | 迷你窗下移 14 px |
| `Ctrl` + `Alt` + `0` | 迷你窗放大（宽高各 +20 px） |
| `Ctrl` + `Alt` + `9` | 迷你窗缩小（宽高各 -20 px） |
| `Ctrl` + `Alt` + `L` | 锁定 / 解锁迷你窗（锁定后忽略指针事件，防误触） |

## 3. 应用内快捷键（窗口聚焦时）

这一部分的快捷键在设计上被划分成了两套彼此独立的交互逻辑。在日常状态下，系统默认处于运行状态的是以音乐档案终端形式呈现的主操作界面。至于较早版本的独立播放器界面，它作为底层保留的兜底容灾方案，只会在极端异常的情况下启用：也就是主程序启动并检测到 `app/ui` 目录下的前端构建静态资源损坏或者文件丢失时，系统才会把它动态加载出来供用户应急操作。

### 3.1 主界面：音乐档案终端

| 快捷键 | 功能 |
| --- | --- |
| `←` `→` | 切换档案分组（列） |
| `↑` `↓` | 前后翻档案（同一列内，可循环） |
| `Enter` | 档案阵列里：**打开档案并播放**（进详情 + 起播当前这一首）；已在详情里：**播放 / 暂停这一首**。开屏阶段按 `Enter` 直接进系统 |
| `/` | 打开曲目检索（`TRACK INDEX`） |
| `Esc` | 按优先级：关弹窗 → 收起歌曲编辑面板 → 从详情回到档案阵列 |

在用户界面的设置面板底部，界面中显示的交互指南完整对应了这一排日常操作提示：`←` `→` 切列　`↑` `↓` 选档　`ENTER` 读取　`/` 检索　`ESC` 返回。

**什么算「正在打字」**：为了防止全局单键快捷键与用户正常的键盘打字操作发生指令冲突，程序对系统当前的聚焦元素制定了明确的判断规则。只有当输入光标确实落在了单行输入框、多行文本区域、下拉选择框，或者设置了可编辑属性的页面容器内部时，系统才会将当前状态识别为正在打字，进而主动拦截并挂起所有单键快捷键的触发动作。相对地，播放进度条与音量调节滑块这类纯视觉控制器并不属于文本录入组件。即便用户刚刚用鼠标拖拽调节过它们、组件外框依然保留着聚焦样式，只要直接按下回车键、方向键或是 `/` 键，系统仍旧会照常响应这些快捷键对应的控制行为。

### 3.1.1 鼠标：播放条与播放列表上的点击

| 点哪里 | 结果 |
| --- | --- |
| 播放条的**曲名 / 艺术家**那一块 | **打开这一首的档案**（只切画面与选中态，不改变播放状态） |
| 播放条的**其它位置**（频谱那一块等） | 回到档案阵列 |
| 播放条上的按钮（播放暂停 / 上一首 / 下一首 / 收藏 / 导入 / 列表…） | 各按钮自己的功能，**不会**被当成「打开档案」或「返回」 |
| 进度条、音量条 | 拖拽调整 |
| 弹窗开着时点播放条 | 先收掉弹窗 |
| 播放列表里**点曲名那一行文字** | 播放这首**并打开它的档案**（无视 `OPEN ARCHIVE ON PLAY` 偏好） |
| 播放列表里点行内其它空白处 | 只播放（是否打开档案看 `OPEN ARCHIVE ON PLAY`） |
| 播放列表行的 `↳` / `♡` / `✕` | 下一首播放 / 收藏 / 移除 |

## 4. 快捷键失效排查

1. **设置面板 →「媒体键」自检行**：只要界面中的状态标记为 `✓ 已注册`，就证明程序已经成功调用系统的全局热键接口，与 Windows 操作系统的全局按键注册管道处于正常联通状态。在这一前提下按下快捷键依然没有反应，原因通常出在硬件层面，应当优先排查耳机物理接线是否松动、键盘内置固件宏定义是否覆盖了默认键位，或者无线蓝牙外设的剩余电量是否过低；若是状态栏显示了 `⚠` 或 `✕`，表明系统级按键监听权限已经被操作系统中其他的后台程序强行霸占了。处理这类冲突时，需要把存在冲突的游戏或竞品音频播放器完全退出，等待 6 秒后本程序就会在下一个扫描周期自动发起重试并恢复注册状态。
2. **游戏是否为独占全屏**：当游戏运行在传统的独占全屏（Exclusive Fullscreen，也就是由单一应用程序直接接管显卡输出与显示屏的运行机制）模式时，Windows 系统会将全部图形交换链和底层输入硬件通道直接交由游戏进程托管。这种独占机制会导致外部播放器的浮动窗口无法继续悬浮在屏幕最顶层，也无法捕获到任何鼠标指针输入信号。遇到这种情况时，用户只需要在游戏的图形画面设置里把显示模式切换为「无边框窗口」即可恢复正常交互。
3. **是否被安全软件拦截**：部分安全防护工具或杀毒软件在执行主动防御机制时，容易把应用程序对底层接口的监听判定为潜在风险，进而主动拦截未签名的第三方应用程序调用 Windows 底层 API 注册全局快捷键的操作。如果快捷键始终无法注册成功，用户可以打开安全防护软件的历史拦截日志进行核查，并将本程序的主执行文件直接添加至信任白名单中，以此解除系统接口的调用限制。
4. **NCM 解密组件是否被杀软隔离**：如果负责解码的 NCM 加密格式转换组件被杀毒软件误伤并移入了隔离区，该故障只会单纯导致 NCM 格式的加密音频源文件无法正常解码播放，因为音频解码与输入事件属于两条完全独立的运行流水线，这个故障与系统全局快捷键的监听循环以及按键响应链路没有任何逻辑上的关联。
