# 快捷键

软件内部的快捷键体系一共划分为三个层级。处于最顶层的是系统级的标准媒体键，也就是键盘上自带的播放、暂停和音量调节这类专用硬件按键；中间一层是系统级的全局备用组合键，即使把当前窗口最小化或者切换到其他程序，按下这些按键也同样能在后台触发对应的控制动作；最底层则是应用内快捷键，这类操作生效的前提，是必须保证软件窗口处于前台并且处于输入焦点的激活状态，一旦焦点切走就会失效。

---
## 1. 媒体键（系统级）

操作系统为该层级按键提供了全局监听机制。无论播放器处于后台、最小化到任务栏，还是屏幕前台正全屏运行无边框窗口模式的 3D 游戏，程序无需处于前台焦点即可捕获敲击动作，直接控制后台音频播放。

| 键名 | 典型触发方式 | 功能 |
| --- | --- | --- |
| `MediaPlayPause` | 键盘播放键、多数耳机单击 / 双击 | 播放 / 暂停 |
| `MediaNextTrack` | 耳机双击 / 三击、键盘下一曲 | 下一首 |
| `MediaPreviousTrack` | 耳机长按 / 三击 | 上一首 |
| `MediaStop` | 键盘停止键 | 暂停 |
| `MediaPlay` | 部分耳机 / 声卡驱动的独立播放键 | 播放 |
| `MediaPause` | 部分耳机 / 声卡驱动的独立暂停键 | 暂停 |

程序启动初始化时会向 Windows 申请注册全部六个媒体键。这是由于部分耳机固件将「播放 / 暂停」拆分为独立的 `MediaPlay` 与 `MediaPause` 键值信号投递，并不发送通用的 `MediaPlayPause` 指令；全部注册可确保覆盖这类特殊硬件，避免漏判操作。

### 媒体键是独占资源

在 Windows 底层输入架构中，媒体键属于独占型系统硬件资源，同一时刻同一键位仅允许单一程序注册持有，无法跨软件共享。若游戏、通讯工具或其他播放软件提前抢占注册，本程序申请持有权时将被系统拒绝，导致无法捕获对应事件。

用户可在设置面板的「`HEADPHONE / MEDIA KEYS`」项查看当前的接管状态：

| 显示 | 含义 |
| --- | --- |
| `媒体键 ✓ 已接管` | 六个键全部注册成功 |
| `✕ 被占用` + `未拿到：…` | 有一部分被抢走，后面列出**具体键名** |
| `✓ 备用组合键可用` | §2 那套组合键可用 |
| `最近一次：播放 / 暂停 · 来源 MediaPlayPause · 12:52:04` | 刚按下的键被系统认成了哪一个 |

**冲突恢复机制**
  - 后台定时器每隔 **6 秒**自动尝试重选注册未成功的按键，已持有的键位会自动跳过。
  - 一旦外部冲突软件退出并释放键位，程序将在下一个 6 秒周期自动接管并恢复控制。

## 1.5 有线耳机按键

有线耳机的线控按键不同于常规的电脑键盘按键。这类硬件在按下时产生的电平变化，是通过操作系统遵循的 HID（人机接口设备，也就是接入电脑并由人直接操作的输入输出外设）规范中专门定义的「消费者控制」（HID Consumer Control）通道向上传递的。Windows 系统收到这层底层硬件信号以后，会在操作系统内核层把这些原始输入统一转换成对应的系统级标准多媒体按键事件，然后再把转换后的消息依次派发给当前系统中已经注册监听了该按键事件的各个应用程序进程。

| 耳机上的操作 | 系统发出 | 本程序的动作 |
| --- | --- | --- |
| 单击（中键） | `MediaPlayPause` | 播放 / 暂停 |
| 双击 | `MediaNextTrack` | 下一首 |
| 三击 | `MediaPreviousTrack` | 上一首 |
| 长按 | 多数固件直接走系统语音助手 | 拿不到 |
| 音量键 | `VolumeUp` / `VolumeDown`（系统接管，本程序不抢） | 系统音量 |
| 接听键 单击 | `MediaPlayPause`（多数固件） | 播放 / 暂停（= 接听 / 挂断） |
| 接听键 长按 | `MediaStop`（部分固件） | 暂停 |
| 结束通话键 | `MediaStop` | 暂停 |

### 怎么确认「我的耳机键被认成了什么」

用户可以通过设置面板实时排查按键映射与冲突状态：

**状态查看**
  - 打开设置面板并定位至 `HEADPHONE / MEDIA KEYS` 状态显示行。
  - 按下耳机物理按键，该行右侧会实时刷新出包含**动作 · 来源键名 · 时间**的日志，例如 `下一首 · 来源 MediaNextTrack · 12:52:05`。

**无响应排查**
  - 若按键后界面与日志均无反应，多因按键被游戏或后台播放器等程序提前占用；可查看面板自检信息中标记为「未拿到」的键名，彻底退出冲突程序并静待 6 秒，程序会自动通过后台重试机制找回控制权。
  - 少数耳机的线控固件采用私有协议向专属驱动发送指令，未走系统标准媒体键通道；此类非标硬件信号需改用第 2 节整理的备用组合键方案控制。

### 接听 / 挂断那颗键

市面上多数单键手机线控耳机在 Windows 下会被协议转换模块映射为标准媒体键，正常情况下可直接控制播放。若按下后无响应，通常是事件在系统派发链路上被更高优先级的软件截断。常见劫持方包括 Windows 内置的「手机连接 / Phone Link」、微信、QQ、Discord 等通信工具，或是耳机专属驱动控制软件。若按下按键后弹出通信软件的来电或通话界面，而面板中 `HEADPHONE / MEDIA KEYS` 状态未更新，即可判定按键已被外部通信软件拦截。

可通过以下两种途径解决按键拦截问题：

**排查与改绑方案**
  - 直接关闭或从系统托盘彻底退出强行抢占按键的软件（多见于 Windows 手机连接组件），等待 6 秒后，程序内置的后台轮询机制会自动重新注册该键。
  - 打开耳机专用驱动配置软件，把线控上的物理接听与挂断动作重新绑定为本程序提供的两个专用全局快捷键：

| 耳机按键想做的事 | 建议绑成 |
| --- | --- |
| 接听（播放 / 继续） | `Ctrl` + `Alt` + `A` |
| 挂断（暂停） | `Ctrl` + `Alt` + `H` |

**机制说明**
  - 绑定完成后按下物理键，设置面板状态行会打印 `播放 / 暂停 · 来源 Ctrl+Alt+A（接听）` 以确认成功打通。这两个按键属于系统底层注册的全局快捷键，与第 2 节介绍的其他全局快捷键一致，在窗口失焦或前台运行独占全屏 3D 游戏时仍可准确送达。
  - 为避免被搭载反作弊系统（Anti-Cheat）的游戏误判为作弊外挂，本程序未采用全局底层键盘钩子（Keyboard Hook）；因此程序无法截获厂商私有协议指令，遇到此类特殊硬件信号时只能通过耳机驱动面板改绑。

### 耳机带「USB 声卡 / 配套软件」的情况

对于自带独立 USB 外置声卡或拥有专属桌面端管理软件的耳机，其控制中心通常内置了自定义宏功能。建议直接在驱动软件中将各线控物理按键分别映射为第 2 节列出的全局备用组合键，与线控上的三颗实体键建立一对一绑定。

## 2. 全局备用组合键（系统级）

| 快捷键 | 功能 |
| --- | --- |
| `Ctrl` + `Alt` + `Space` | 播放 / 暂停 |
| `Ctrl` + `Alt` + `→` | 下一首 |
| `Ctrl` + `Alt` + `←` | 上一首 |
| `Ctrl` + `Alt` + `↑` | 音量 +5% |
| `Ctrl` + `Alt` + `↓` | 音量 −5% |
| `Ctrl` + `Alt` + `A` | **接听**（播放 / 继续）—— 给耳机接听键改绑用 |
| `Ctrl` + `Alt` + `H` | **挂断**（暂停）—— 给耳机挂断键改绑用 |
| `Ctrl` + `Alt` + `P` | 播放 / 暂停（别名） |
| `Ctrl` + `Alt` + `N` | 下一首（别名） |
| `Ctrl` + `Alt` + `B` | 上一首（别名） |

### 迷你悬浮窗控制

某些前台游戏在以独占全屏模式运行时，或者启用了绕过系统事件队列直接读取硬件数据的原始输入（Raw Input）机制，操作系统会限制指针消息的分发，不再向处于非激活状态的后台窗口传递光标点击、悬浮或拖拽事件。这样一来，即使迷你悬浮窗始终置顶显示在屏幕最上层，也会因为收不到鼠标事件而彻底失去响应。

遇到这种鼠标输入被前台独占游戏完全拦截的情况，用户可以使用系统全局快捷键直接控制悬浮窗，完成位置平移与尺寸缩放。为了防止这些操作与上一节中用来切歌的 `Ctrl+Alt+←/→` 发生冲突，设计时在方向键前方特别加入了 `Shift` 修饰键，从而将常规的切歌控制通道完整留给耳机按键映射继续使用。

| 快捷键 | 功能 |
| --- | --- |
| `Ctrl` + `Alt` + `Shift` + `←` | 迷你窗左移 14 px |
| `Ctrl` + `Alt` + `Shift` + `→` | 迷你窗右移 14 px |
| `Ctrl` + `Alt` + `Shift` + `↑` | 迷你窗上移 14 px |
| `Ctrl` + `Alt` + `Shift` + `↓` | 迷你窗下移 14 px |
| `Ctrl` + `Alt` + `0` | 迷你窗放大（宽高各 +20 px） |
| `Ctrl` + `Alt` + `9` | 迷你窗缩小（宽高各 -20 px） |
| `Ctrl` + `Alt` + `L` | 锁定 / 解锁迷你窗（锁定后忽略指针事件，防误触） |

## 3. 应用内快捷键（窗口聚焦时）

这一部分的快捷键在设计上被划分成了两套彼此独立的交互逻辑。在日常状态下，系统默认处于运行状态的是以音乐档案终端形式呈现的主操作界面。至于较早版本的独立播放器界面，它作为底层保留的兜底容灾方案，只会在极端异常的情况下启用：也就是主程序启动并检测到 `app/ui` 目录下的前端构建静态资源损坏或者文件丢失时，系统才会把它动态加载出来供用户应急操作。

### 3.1 主界面：音乐档案终端

| 快捷键 | 功能 |
| --- | --- |
| `←` `→` | 切换档案分组（列） |
| `↑` `↓` | 前后翻档案（同一列内，可循环） |
| `Enter` | 档案阵列里：**打开档案并播放**（进详情 + 起播当前这一首）；已在详情里：**播放 / 暂停这一首**。开屏阶段按 `Enter` 直接进系统 |
| `/` | 打开曲目检索（`TRACK INDEX`） |
| `Esc` | 按优先级：关弹窗 → 收起歌曲编辑面板 → 从详情回到档案阵列 |

在用户界面的设置面板底部，界面中显示的交互指南完整对应了这一排日常操作提示：`←` `→` 切列　`↑` `↓` 选档　`ENTER` 读取　`/` 检索　`ESC` 返回。

**输入状态判定规则**

为了防止全局单键快捷键与用户正常的键盘打字操作发生冲突，系统依据当前聚焦元素判定是否处于「正在打字」状态：

  - 仅当输入光标停留在单行输入框、多行文本区域、下拉选择框或设置了可编辑属性的容器内时，系统判定为正在打字，并主动拦截所有单键快捷键。
  - 播放进度条与音量调节滑块属于纯视觉控制器而非文本录入组件，即便刚通过鼠标拖拽且保留聚焦样式，按下回车键、方向键或 `/` 键仍会照常响应快捷操作。

### 3.1.1 鼠标：播放条与播放列表上的点击

| 点哪里 | 结果 |
| --- | --- |
| 播放条的**曲名 / 艺术家**那一块 | **打开这一首的档案**（只切画面与选中态，不改变播放状态） |
| 播放条的**其它位置**（频谱那一块等） | 回到档案阵列 |
| 播放条上的按钮（播放暂停 / 上一首 / 下一首 / 收藏 / 导入 / 列表…） | 各按钮自己的功能，**不会**被当成「打开档案」或「返回」 |
| 进度条、音量条 | 拖拽调整 |
| 弹窗开着时点播放条 | 先收掉弹窗 |
| 播放列表里**点曲名那一行文字** | 播放这首**并打开它的档案**（无视 `OPEN ARCHIVE ON PLAY` 偏好） |
| 播放列表里点行内其它空白处 | 只播放（是否打开档案看 `OPEN ARCHIVE ON PLAY`） |
| 播放列表行的 `↳` / `♡` / `✕` | 下一首播放 / 收藏 / 移除 |

### 3.2 旧版独立播放器界面（兜底）

| 快捷键 | 功能 |
| --- | --- |
| `空格` | 播放 / 暂停 |
| `→` | 快进 5 秒 |
| `←` | 后退 5 秒 |
| `↑` | 音量 +5% |
| `↓` | 音量 -5% |
| `M` | 打开 / 关闭迷你悬浮窗 |
| `L` | 展开 / 收起播放列表面板 |
| `F` | 收藏 / 取消收藏当前歌曲 |

| `Enter` | 在歌曲编辑弹层中保存（光标在文本输入框时） |

## 4. 快捷键失效排查

排查快捷键失效问题时，请先通过界面状态定位原因，再针对不同场景进行处理。注意，负责解码的 NCM 加密格式转换组件若被杀毒软件误伤并移入隔离区，只会单纯导致 NCM 格式的加密音频源文件无法正常解码播放，音频解码与输入事件属于完全独立的运行流水线，与系统全局快捷键的监听循环及响应链路无关。

**系统接口与硬件状态排查**
前往**设置面板 →「媒体键」自检行**查看状态标记：
  - 若显示为 `✓ 已注册`，证明程序已成功调用系统全局热键接口，与 Windows 操作系统的全局按键注册管道联通正常。此时按键无反应通常属于硬件层面故障，请优先排查耳机物理接线是否松动、无线蓝牙外设电量是否过低，或键盘内置固件宏定义是否覆盖了默认键位。
  - 若状态栏显示为 `⚠` 或 `✕`，表明系统级按键监听权限被其他后台程序占用。请完全退出存在冲突的游戏或竞品音频播放器，等待 6 秒后，程序会在下一个扫描周期自动发起重试并恢复注册状态。

**系统环境与冲突拦截排查**
若接口注册受阻或无法接收输入信号，可排查外部运行环境的拦截与独占机制：
  - **安全软件拦截**：部分安全防护工具或杀毒软件的主动防御机制可能误判底层接口监听，主动拦截未签名的第三方应用程序调用 Windows 底层 API 注册全局快捷键。若快捷键始终无法注册成功，可检查安全软件的历史拦截日志，并将本程序的主执行文件添加至信任白名单以解除限制。
  - **游戏独占全屏**：当游戏运行在传统的独占全屏（Exclusive Fullscreen，即由单一应用程序直接接管显卡输出与显示屏）模式时，Windows 会将全部图形交换链和底层输入硬件通道交由游戏进程托管，导致外部播放器的浮动窗口无法悬浮在屏幕最顶层且无法捕获鼠标指针信号。可在游戏的图形画面设置中将显示模式切换为「无边框窗口」以恢复正常交互。
