## 一、总体判断

项目的核心实现分布在 `app/main.js`(1472 行)、`app/index.html`(2943 行)、`app-rhine/src/player.ts`(3049 行) 以及 `spectrum.ts`(527 行) 当中，累计包含约 8000 行有效代码。开发团队在绝大部分非常规实现旁边，都用注释清晰交代了背后的技术考量。这些记录里沉淀了大量**真实踩坑与实测数据**，例如 `wipeFile` 针对 nlink>1 场景专门补充的防御逻辑、`ensureM4a` 从最初的硬链接方案改回物理复制的完整事故复盘，以及后台计算线程 worker 遗漏 `kickRef` 变量导致“泵动恒为 1”的排查记录。这种在代码旁直接记录故障现场与归因的工程习惯，所承载的技术价值甚至超过了代码本身。不过，在审阅这套实现的过程中，也发现了一处技术文档说明与实际代码行为脱节的重要偏差（具体细节见 §5.1），建议开发团队排期优先处理。

**值得肯定的设计（建议保持，不要"重构掉"）**：

| 设计 | 为什么好 |

| 派生数据三层管控（内存解密 / 会话临时目录 / 无任何可写盘 IPC）+ 审计 + 16 项离线断言 | 把合规从口头声明变成可执行验证，28 个 IPC 通道无一接受输出路径 |

## 二、性能优化点（按性价比排序）

### 2.1 ★★★ 音频输出的采样率必须对齐，否则会多一级重采样

**位置**：`app-rhine/src/player.ts:1814`、`app/index.html:1145`

在底层音频管线中，`createMediaElementSource()` 一旦调用就**无法撤销**，此后 `<audio>` 标签的所有声音输出都会被重定向，必须经由 `AudioContext` 节点流出。如果初始化时指定的采样率与实际音源不一致（例如 44100 Hz 的标准 CD 音轨、无损 FLAC，或是 48000 Hz 的 m4a 格式），Chromium 的混音引擎就会在内部强制插入一个**重采样器**进行插值运算。对于主打“本地无损播放器”定位的软件来说，这种转换会引入高频相位失真与量化噪声，造成听觉上可以感知的隐性音质损失。

正确写法只有这一套，没有旁路：

```js
const ctx = new AudioContext();            // 无参 —— 跟随输出设备速率
const source = ctx.createMediaElementSource(audio);
source.connect(analyser);
analyser.connect(ctx.destination);          // 必须接回
```

此处的实现必须严格遵守两条工程约束：

**初始化与路由约束**
  - **必须无参构造**：实例初始化时不传 `sampleRate` 参数，Web Audio 引擎才会自动选用当前物理输出设备的首选采样率。根据标准，`sampleRate` 的有效区间严格限制在 `[3000, 768000]`，传入区间外的值（包含 0）均会直接抛出 `NotSupportedError` 异常中断执行。
  - **不能省略 `analyser.connect(ctx.destination)`**：`createMediaElementSource()` 会掐断媒体元素到扬声器的默认直通路由并劫持到图谱网络中，若未显式连接到 `destination` 终点节点，将造成软件无声且频谱无反应，且该状态在页面生命周期内完全不可撤销。

详见 [架构说明 §4.0](架构说明.md)。

> 附带一处隐患（已一并修掉）：旧逻辑在 `ensureAnalyser()` 执行失败时会将内部标记直接设为 `vizDenied = true`，此后应用生命周期内永久不再尝试重连，界面也不会向用户提供任何反馈。现已将其重构为**有限重试**机制（配置常量 `VIZ_MAX_ATTEMPTS = 3`），并在失败后弹出 toast 提示，同时在设置面板中明确显示具体的报错原因。

### 2.2 ★★★ B 站音源每次都整份读进内存

**位置**：`app-rhine/src/player.ts:746` `loadBiliAudio()`

```js
const blob = await blobUrlOf(s);       // ← 总是走 blob，从没试过 file://
```

现在的 `blobUrlOf` 内部会调用 `desktop.readAudio(p)` 获取音频数据。在这个调用链路下，主进程首先调用 Node.js 的 `fs.readFileSync` 将磁盘文件整份同步读取为内存块，紧接着经由 IPC 进程间通信通道执行结构化克隆并序列化发往渲染进程，最后在渲染层重组成一个内存 `Blob` 对象。如果要播放一首体积为 10 MB 的普通 m4a 音频，整个数据流必须完整经历“磁盘读入 → 主进程 Buffer → IPC 跨进程复制 → 渲染层拼合 Blob”这套繁重流程。与旧界面直接走 `file://` 协议相比，这种做法白白制造了多次跨进程与跨上下文的整块内存拷贝。尽管源代码中的注释强调“必须绕开 file:// 限制”，但旧界面早期早已通过“先试 file://、失败再 blob”的容错机制解决了权限与加载问题（也就是依赖监听 `audio.addEventListener('error')` 事件实现自动降级的那段逻辑）。

针对内存拷贝与流式解码问题，建议采用以下优化方案：

**改造建议**
  - **`file://` 优先降级策略**：调整加载策略为 **`file://` 优先 + 失败才 blob** 的双层结构，直接接入 Chromium 原生媒体播放管线以支持分片流式解码，将运行时的内存峰值开销从 O(文件大小) 压缩至 O(缓冲区) 级别。
  - **自定义协议流式映射**：由主进程调用 Electron 的 `protocol.handle()` 统一注册自定义 `mp-audio://` scheme 协议并虚拟映射到临时会话目录，渲染层直接通过该协议 URL 进行流式读取，彻底消除多余内存拷贝，并解决缓存会话副本路径在每次冷启动后变动的历史包袱。

### 2.3 ★★ 歌词命中查找是每帧线性扫描

**位置**：`app-rhine/src/player.ts:1966`

```js
let idx = 0;
for (let i = 0; i < lines.length; i++) if (lines[i].t <= cur) idx = i;
```

当前这套歌词行高亮逻辑完全由播放器的 `timeupdate` 定时事件驱动（定义在 `player.ts:2713`）。浏览器底层派发该事件的频率大约为 4~66 Hz（在 Chromium 环境下通常维持在每 250ms 触发一次，并且项目业务代码里还叠加了 `requestAnimationFrame` 的高频帧渲染通道）。一首时长 5 分钟的标准歌曲其歌词数组通常包含 100~150 行数据，尽管单次执行的绝对运算耗时不长，但在高刷帧率下反复从头到尾进行全量遍历**是纯粹的浪费**，更何况解析后的 `lines` 数组本身已经严格按时间戳递增排好序。**建议**将算法替换为对半折半的二分查找，或是利用播放时间连续性特征引入单调递增游标（`app/index.html` 内的 `updateLyricsHighlight` 方法同理）：

```js
while (cursor + 1 < lines.length && lines[cursor + 1].t <= cur) cursor++;
while (cursor > 0 && lines[cursor].t > cur) cursor--;   // 支持 seek 回退
```

### 2.4 ★★ `player.ts` 单文件 3049 行，职责混杂

当前单个脚本文件就堆积了 3049 行代码，内部承载了 ID3 音频元数据解析、IndexedDB 底层存储封装、曲目列表排序、核心播放生命周期控制、失效音源自愈机制、歌词同步滚动、UI 模板字符串组装（例如在 `bar.innerHTML = ...` 中直接内嵌数十行 HTML）、DOM 事件监听绑定、系统运行时诊断探针以及设置面板 markup 生成等过多关注点。

这种组织方式带来的具体隐患与重构路径如下：

**架构现状与隐患**
  - **排查成本高与单测缺失**：微小的交互改动迫使开发者在 3000 行的庞大上下文中排查；且厚重的上下文耦合导致完全无法对“歌词解析器”或“音源仲裁自愈”等纯计算逻辑编写自动化单元测试（导致现有的 4 套离线验证脚本无法实施覆盖）。
  - **跨模块逻辑漂移**：该模块与 `app/index.html` 遗留页面在 ID3 解析算法、默认封面回退路径、多规则排序、曲目去重键构建以及音源自愈流程上存在明确的重复逻辑，两套独立维护的实现在业务迭代中已经出现逻辑分歧。

**解耦拆分建议**
  - **按职责边界细化拆分**：将大文件拆分为 `library.ts`（曲库模型、IDB 读写与去重机制）、`source.ts`（音源裁决与网络自愈算法，作为纯函数实现）、`lyrics.ts`、`bar.ts`（底部播放控制条 UI 渲染与动效）以及 `diagnostics.ts`。
  - **优先抽离纯逻辑模块**：优先拆解逻辑最独立且具备纯函数属性的 `source.ts` 与 `lyrics.ts`，以便最先被测试套件完整覆盖，沉淀为防止音频回退的长期回归断言。

### 2.5 ★ 音频无预加载，切歌首帧有等待

当前的切歌控制链路呈现为典型的线性调用：`playNextSong()` → `loadBiliAudio()` → `await prepareBiliAudio` → `await readAudio` → `play()`，整条调用链是**串行阻塞**执行的。用户从在界面上按下“下一首”按钮到扬声器真正发出声音，中间必须完整等待一次 IPC 跨进程调度循环加上一次磁盘全量 I/O 读取；而当前在 DOM 上配置的 `audio.preload = "metadata"` 选项仅仅只会命令浏览器预先抓取媒体头部的元数据字段，并不能提前加载后续音频帧。

为消除切歌等待，可从预加载触发时机与缓存策略两方面进行优化：

**预加载与调度方案**
  - **基于播放进度的前瞻预加载**：在 `timeupdate` 回调中增加前瞻判断，当播放进度“距离音轨结尾 < 15 秒且后续播放队列非空”时，提前在后台触发针对下一首曲目的 `prepare` 任务，将跨进程通信与解析耗时前置。
  - **就绪缓存池与随机模式选曲提前**：在内存中维护容量为 1~2 项的“已就绪音源”LRU 双向链表缓存池以提前持有解码上下文；同时将随机播放模式下的候选歌曲决策时机提前，改变目前在 `playRandom()` 触发当下才临时摇号计算导致无法预加载的问题。

### 2.6 ★ `app/index.html` 中的三处小瑕疵（旧界面，兜底路径）

针对旧界面兜底链路中存在的性能与准确性缺陷，集中归纳为以下三项问题及调整建议：

**计算复杂度与 DOM 渲染**
  - **列表渲染高阶复杂度消除**：界面渲染函数 `renderList()` 在外层 `for` 循环体内对每个音频实体重复调用 `view.indexOf(s)` 计算序号，导致算法复杂度恶化为 **O(n²)**，在 1000 首曲目重绘时触发百万次线性扫描；此处直接改用外部循环自带的索引 `i` 即可完全消除开销。
  - **进度条拖拽防抖与强制重排抑制**：顶部常驻进度条 `bar` 绑定的 `pointermove` 交互事件缺乏防抖或节流保护，且每次派发为了读取 `e.clientX` 都直接调用 `getBoundingClientRect()` 重新测量控件盒模型，导致拖拽时每秒触发数十次昂贵的同步强制重排与重绘（定位在 `app/index.html:2090`）。

**数据去重准确性**
  - **抗碰撞去重键重构**：`songKeys()` 引入 `file.size` 拼接去重键，会导致内容相同但因重命名或转码体积微变的文件被漏判为不重复，或使名称与字节大小偶发一致的无关文件被误判为重复；建议重构为「文件绝对路径（存在时优先）+ 文件内容首尾特定若干 KB 数据段提取的内容哈希前缀」的组合方案。
## 三、架构与工程建议

### 3.1 两份实现的漂移风险（最重要）

| | `app/index.html` | `app-rhine/src/player.ts` |
|---|---|---|
| B 站音源 | `file://` 优先，失败降级 blob | **一律 blob** |
| 进度记忆 | 全局一条 `mp_state` | 全局播放头 + `pendingSeek` 双保护 |
| 频谱柱数 | 120 | 150 |
| 列表重建 | 每次全量 `innerHTML` | `listSig` 签名 + 搜索过滤 |

从功能完整度与鲁棒性来看，app-rhine 明显比旧版更成熟。然而查看 `main.js:384-388` 的加载逻辑可以发现，`app/index.html` 依然保留在容灾兜底链路中。维护两套相互独立的实现意味着**每个 bug 理论上都要修两遍，现实中极容易出现只修了一条链路的疏漏**。此前排查出的 `mp_kick2` 写 A 读 B 故障，以及源码注释里提到的“重写时一并丢了自愈”，本质上都是双轨并行开发所直接踩出来的坑。

**建议措施**
  - 在工程定位上明确将 `app/index.html` 降级为「UI 服务起不来时的降级只读界面」，彻底冻结该侧新功能开发并在 README 与维护指南中明确载明，或进一步大幅裁剪至仅保留“当前曲目 + 播放/暂停”的最小能力。

### 3.2 用主进程 `protocol.handle()` 替代内嵌 HTTP 服务

当前工程为了在本地同时满足 ES module 模块加载与绝对路径引用，在主进程内部启动了一个监听 `127.0.0.1:41739` 的静态 HTTP 服务。团队甚至在 `main.js:332-335` 的注释中，直接把**固定端口**当成了 IndexedDB 存储源（Origin）保持稳定的核心依赖。这种设计虽然能跑通，但结构非常脆弱：一旦固定端口遭遇外部占用，程序就不得不回退到随机端口，进而导致浏览器存储源发生改变，造成**静默丢失整个曲库**的严重后果（此时系统通常只能留下一行不起眼的 `main-error.log`）。归根结底，这是在用复杂的网络传输层手段来绕弯解决本地协议层的问题。

**建议措施**
  - 改用 Electron 主进程的 `protocol.handle('app', ...)` API 注册自定义 scheme（例如 `app://ui/index.html`）。
  - 通过自定义协议提供天然稳定的存储源，彻底摆脱对 Node 内置 `http` 模块与本地端口占用的依赖，规避防火墙误拦截并从底层根治 IndexedDB 域变动隐患。

### 3.3 `app/main.js` 的 IPC 通道命名与校验

在现有的全部 28 个 IPC 通道里，像 `read-audio`、`read-cover` 与 `read-asset` 这类负责文件读取的通道，目前仅仅依赖**白名单文件名**（`read-asset`）或者**完全相信调用方传来的绝对路径**（`read-audio`、`read-cover`）来进行安全约束。其中 `read-audio(p)` 的实现能够直接吃下外部传入的**任意路径**，并将目标文件的完整二进制字节读出返回。即使渲染层没有开启 `nodeIntegration`，一旦渲染歌名或歌词富文本的逻辑里漏出了 XSS 跨站脚本攻击漏洞或文本注入点，攻击者就能立刻利用这条通道，把它当成现成的“任意文件读取”原语来窃取本地数据。

**通道安全加固**
  - 对 `read-audio` 实施准入校验，在主进程维护已导入音频路径集合，严格限制其仅能读取曲库登记过的路径。
  - 将 `read-asset` 现存的文件名白名单过滤机制扩展至封面读取等同类通道。

**架构抽象统一**
  - 在主进程统一封装 `safeHandle(channel, fn)` 包装函数，集中处理入参合法性校验与底层错误归类，消除各 handler 内部重复的 `try/catch` 与 `{ error: String(...) }` 结构。

### 3.4 验证脚本可以更"自动"

项目目前已经积累了 4 套脱机运行的离线断言脚本（覆盖了数据管控 16 项、设置持久化 31 项、ID3 15 项以及文档一致性 16 项），同时还配套了一系列用于分析运行状态的观测探针（包括渲染快照、版面探针和频谱离线观测）。这种“在无图形界面环境下也能验证用户界面正确性”的测试思路，非常适合推广到 CI 持续集成流程中。

**建议措施**
  - 使用自动化流程串联 `渲染快照.ps1`、`截图转文本.js` 和 `版面探针.mjs`，在 CI 流水线中针对关键界面状态（空库、单曲载入、播放中、迷你窗、编辑弹层）自动抓取渲染快照并比对预设基线图。
  - 建立闭环的视觉回归测试机制，替代人工肉眼抽查，精准捕捉样式修改引发的跨模块隐蔽排版问题。
## 四、创新机会（有依据、可落地）

### 4.1 ★★★ 变速播放的"不变调"（Time-Stretch）

系统当前直接通过 `audio.playbackRate = speed`（`app/index.html:2128`）调用浏览器的原生变速逻辑，导致音调随播放速度线性偏移，**0.75× 明显变闷、1.5× 明显变尖（花栗鼠）**，严重影响课程与有声书等依赖人声清晰度场景的体验。

**现状分析与落地路径**
  - Chromium 底层的 `<audio>` 标签已将 `preservesPitch` 默认置为 `true`，但该特性在 Electron 运行时往往未显式激活，需在代码层面确认；若需深度处理，也可在现有的 `AudioContext` 链路中接入 WSOLA 或 Phase-Vocoder 节点维持基频。
  - 先在控制台或启动逻辑中读取 `audio.preservesPitch` 与兼容别名 `audio.mozPreservesPitch` 的布尔值：若为 `false`，显式赋值为 `true` 即可消除失真；若已为 `true`，则应将其封装为**设置里的可见开关**，避免底层控制对用户完全隐藏。这是目前项目中**投入产出比最高的一条**改进项。

### 4.2 ★★★ 响度归一化（ReplayGain / EBU R128）

本地曲库来源混杂（B 站缓存、NCM、CD 抓轨），各文件录音电平与母带标准参差不齐，造成歌曲间的**响度差异巨大**，连续播放切歌时极易出现“突然炸耳”或“突然听不见”的极端情况。

**分析与补偿机制**
  - 在文件导入与元数据解析阶段，后台调用 `OfflineAudioContext`，按 EBU R128 标准计算全曲短时响度，或采用开销更小的 RMS 算法测算整体电平，将增益补偿数值写入曲目数据库。
  - 进入播放流程后，直接通过管线中的 `GainNode`（在 §2.1 音频图中有对应位置）动态补偿音量；单次导入分析即可根治跳变落差，计算出的电平值亦可直接用于构建**响度视图**。

### 4.3 ★★★ 音源版本化 + 无缝交叉淡入（Gapless）

当前播放器切歌采用“停止当前音频 → IPC 读取磁盘 → 重新解码播放”的串行阻塞时序，**必然存在播放间隙**，打破了音频流的连续感，削弱了概念专辑的连贯体验。

**实现步骤**
  - 播放器为入库曲目计算内容哈希并维护统一 `sourceId`，以哈希字符串命名转储音频副本，保证重启后引用稳定并支持缓存校验，顺带化解 §2.2 提到的“路径每次变”导致数据失效的问题。
  - 前端维护双 `<audio>` 播放实例，在曲目尾部执行 200~400ms 的交叉淡入淡出（Crossfade），结合 §2.5 的下首预加载机制消除底层缓冲停顿，实现真正的 gapless 无缝切换。

### 4.4 ★★ 封面主色驱动的动态主题

播放器目前仅内置 4 套预设主题（深色/浅色/网易云红/莱茵生命），视觉风格较为固定。系统此前已将样式抽离为 CSS 自定义属性并由 `applyTheme` 统筹，弹层界面也支持变量继承，**基础设施已就绪，只差颜色来源**接入。

**提取与渲染流程**
  - 现有的 `coverToDataUrl` 逻辑已使用 canvas 元素进行降采样与缩放，直接顺手调用上下文对象的 `getImageData` 方法读取像素点数据提取主副色，运行时性能损耗极低。
  - 程序将解析出的色值通过 CSS 变量动态写入 `--accent-light` 和 `--accent-strong`，即可增加第 5 种“跟随封面”的自适应显示模式。

### 4.5 ★★ 队列级频谱预分析 → 更"准"的鼓点与可视化

目前应用中的鼓点检测属于实时因果系统，运行在播放主线程上，依靠慢速跟随的动态阈值 `kickRef` 判断突发能量。这种在线计算**无法预知，只能反应**，视觉呈现永远滞后于物理声波。

**离线解算与前馈应用**
  - 音频载入或入队时，后台利用离线 Goertzel 算法或推送至 Web Worker 以 10× 倍速提前解算频域数据，预先提取整首歌的低频能量包络线与精准节拍时间网格，大幅提高节拍识别命中率。
  - 驱动动效的信号**可提前 20~30ms 点亮**，完全抵消音频输出缓冲与屏幕渲染的物理延迟，消除延迟感；可视化引擎还可依据后续能量走势提前准备节拍编排与高潮预热转场，实现由“反应式”向“编排式”可视化的跨越。

### 4.6 ★ 其它小创新

| 想法 | 说明 |
|---|---|
| **频谱指纹去重** | 现有的查重逻辑完全依赖文件元数据中的标题、歌手与物理文件大小，遇到标签不全或重命名文件时极易发生漏判误判。通过对音频前段提取出一段几十字节的低频频谱指纹，系统就可以根据声学特征精准识别出"同一首歌不同码率/不同来源"的重复项目，并顺便在界面中为用户提示"库里这首有更高音质的版本"以便整理。 |
| **播放统计可视化** | 底层曲目结构中已经持久化记录了 `plays`（播放次数）和 `lastPlayed`（最后播放时间）字段，但目前前端缺少数据呈现载体。可以增设一页"收听画像"面板，展示用户的常听时段分布、歌手偏好比重以及曲目收藏/跳过率等统计图表，设计语言也能紧密契合莱茵生命"数据分析终端"设定。 |
| **迷你窗的"歌词优先"模式** | 迷你播放视窗目前的 UI 属于固定卡片布局，占用屏幕空间较多。可以将其改造成仅保留单行文本高度的"纯歌词条"，在桌面端呈现出类似游戏内 HUD 悬浮插件的效果。 |
| **导入时后台渐进处理** | 现在的 `addFiles` 函数对选中的文件采用串行机制逐首执行 `await` 解析，导致用户在单次导入 500 首这类大批量操作时，通知组件 toast 会长时间卡在固定进度不再刷新。应当将其重构为基于 Web Worker 的并发执行池，并向界面分发平滑更新的百分比进度条。 |
| **`ncmdump.exe` 的替代** | 核心进程内用纯 JavaScript 编写的解密函数 `decryptNcmBuffer` 已经具备独立解析能力，打包附带的 Windows 可执行文件 exe 只是作为处理异常格式时的兼容性兜底方案。播放器可以在首次利用 JS 解密验证成功后，在本地持久化标记"此设备不需要 exe"，后续不再加载外部程序。移除打包体积中占用的 850 KB 不是重点，关键在于**外部可执行文件**在安全软件眼里始终是风险点，去掉外部进程调用有助于避免安全拦截与权限告警。 |
## 五、优先级路线图

各项任务按先后顺序推进，括号内标注了预估耗费的时间：

#### 快速见效与低风险修复

这一阶段集中处理改动极小、收益明确的播放缺陷与性能热点：

  - 确认并在代码中显式配置 `preservesPitch` 属性（§4.1，1~2 小时），解决倍速播放时的音调偏移问题。
  - 优化纯算法性能：将歌词检索重构成二分查找或游标移动机制（§2.3，纯性能零风险），并优化 `renderList` 内时间复杂度为 O(n²) 的序列号计算逻辑（§2.6，两行改动）。

#### 音频链路与协议底层整改

修复既有管路逻辑缺陷，消除内存与端口冲突隐患：

  - 修复 Web Audio 音频图连接（§2.1，1~2 天）：维持无参调用 `new AudioContext()` 并将 `analyser.connect(destination)` 接回主输出管路，不再尝试已被证伪的“旁路”与 `sampleRate: 0` 方案。
  - 读取 B 站本地缓存音源优先使用 `file://` 协议（§2.2，1~2 天），以流式读取将内存占用降至 O(缓冲) 级别。
  - 改用 Electron 的 `protocol.handle('app', ...)` 彻底替换内嵌本地 HTTP 服务（§3.2，1~2 天），根除端口占用导致的音乐库数据丢失问题。

#### 核心播放体验与架构重构

投入周期较长的进阶功能开发与代码治理：

  - 引入下一首预加载与双音源 Crossfade 机制（§2.5 + §4.3，1 周），消除切歌缝隙以达成无缝播放（gapless）。
  - 接入全局响度归一化算法（§4.2，1 周），平衡不同音轨响度，解决切歌时音量忽大忽小的问题。
  - 拆分单体文件 `player.ts`（§2.4，1 周）：抽离出 `source.ts` 与 `lyrics.ts` 两个子模块，并补全单元测试与断言校验。

#### 交互创新与工程基建

完善产品特色表现力并加固工程底座：

  - 实现面向播放队列的离线频谱预先分析（§4.5，有辨识度的创新），将可视化升级为可提前计算调度的“编排”效果。
  - 提取当前播放专辑封面主色，实时生成动态高亮主题（§4.4，基础设施已就绪，性价比极高）。
  - 推进基础工程建设：补充端到端界面的视觉回归对比测试（§3.4），并正式明确 `app/index.html` 仅作为主界面加载失败时的降级容灾方案（§3.1）。
## 六、一句话总结

项目的**下限已经很高**，合规管控、崩溃兜底、降级路径以及实测注释全都是专业水准，**上限的瓶颈也不在功能多少，而在两件事**：

**架构与工程瓶颈**
  - 把频谱和可视化对音频主链路的侵入性代价（像重采样、blob 拷贝）还给用户，彻底消除额外计算带来的性能负担。
  - 把攒下的观测探针体系从人工核对升级为自动回归，让监测数据可以通过自动化流程持续验证。

创新上最有价值的不是到处加新功能，而是**用已有的 AudioContext（浏览器原生负责处理和合成音频的上下文环境）和已有曲库数据把"能播"变成"好听、连贯、有个性"**：

**核心体验升级**
  - 像变速不变调、响度归一、无缝衔接、可视化编排这四件事都建立在现有架构上，开发时直接复用本地能力即可，完全不需要依赖任何在线服务。
