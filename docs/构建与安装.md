# 构建与安装

涵盖从源码构建便携版、安装到本机、自行打包分发，以及推送到远端时的网络排查流程。

## 1. 环境要求

| 项目 | 要求 |
| --- | --- |
| 操作系统 | Windows 10 / 11 x64 |
| PowerShell | 5.1 或更高（Windows 自带） |
| 磁盘空间 | 约 300 MB（Electron 运行时约 222 MB + 应用源码约 5 MB + 解压临时空间） |
| 网络 | 仅首次构建需要（下载 Electron 运行时）；已有本地运行时则完全离线 |
| 管理员权限 | **不需要**（安装到用户目录） |

**运行与使用**
  - 如果仅需安装并运行本程序，本地无需配置 Node.js。
  - 用户可前往 Releases 页面下载打包好的 Setup.exe 运行安装（详见 §5.1），或直接双击根目录下的 `安装.bat` 脚本完成部署（详见 §5.2）。

**二次开发与构建依赖**
  - 只有在修改前端源码需重新生成产物，或在本地重新打包安装程序时才需要 Node.js：其中前端依赖 Vite 工具链构建，安装包通过 Inno Setup 编译器生成（详见 §3.6）。
  - 若环境中未安装 Node 相关依赖，构建脚本会自动跳过前端重新生成步骤，直接复用 `app\ui` 目录现有的打包产物，流程可正常完成且不会报错中断。
## 2. 目录约定

```
音乐播放器/
├── app/          ← 应用源码，唯一需要修改的地方
├── scripts/      ← 构建与安装脚本
├── dist/         ← 构建输出（已被 .gitignore 排除，不入库）
└── docs/         ← 文档
```

日常开发时，请不要直接编辑 `dist/` 目录下的任何文件。具体到 `dist/音乐播放器-win32-x64/resources/app/` 这一路径，它属于打包流程自动生成的构建产物，也就是最终运行程序所解压提取的资源。只要用户执行打包构建操作，系统就会把 `app/` 目录里的最新源码完整复制过去，原有文件会被直接覆盖，因此手动写入该目录的修改都会丢失。
## 3. 构建便携版

### 3.1 一键构建

用户可以直接双击仓库根目录下的 **`构建.bat`** 启动构建，也可以在 PowerShell 终端中执行下列命令完成调用：

```powershell
cd '路径\音乐播放器'
.\scripts\build-portable.ps1
```

### 3.2 构建流程

```
1. 校验 app/ 必需文件（index.html / main.js / preload.js / mini.html / package.json）
2. 检查可选模块（bili.js / cover.js / ncmdump.exe），缺失只警告不报错
3. 准备 Electron 运行时：
     ① -RuntimeDir 指定的目录
     ② 已有的 dist\音乐播放器-win32-x64\
     ③ 从镜像下载 Electron 31.7.7 win32-x64 并解压
4. electron.exe 重命名为 音乐播放器.exe，删除 default_app.asar
5. 准备界面产物：app-rhine 能构建就 `npm run build` 并同步到 app\ui；
   没有 node_modules 时跳过重建、沿用 app\ui 里已有的产物并提示一行
6. 清空并重建 resources\app，把 app\ 完整复制进去
7. 对必需文件做 MD5 校验，确认同步无误
8. 打印产物路径与体积
```

第 5 步的处理方式吸收了 2.0.1 版本留下的经验教训。在早期的自动化脚本中，流程既不会主动重新编译前端工程 `app-rhine/dist`，也不会把前端改动同步到 `app/ui/` 目录下，导致便携版最终打包的仍然是上一版本遗留的陈旧 JS 代码。因此在正式**发布**软件时，必须执行一次完整的前端构建，而后续的 `release.ps1` 流程会自动确保前置的 `node_modules` 依赖环境准备就绪。
### 3.3 参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `-ElectronVersion` | `31.7.7` | Electron 版本号 |
| `-RuntimeDir` | 空 | 已有运行时目录（含 `electron.exe` 或 `音乐播放器.exe`） |
| `-OutDir` | `dist\音乐播放器-win32-x64` | 输出目录 |
| `-Mirror` | `https://npmmirror.com/mirrors/electron` | 下载镜像前缀 |
| `-Force` | 关 | 强制重新下载运行时 |

### 3.4 示例

```powershell
.\scripts\build-portable.ps1                                                 # 只同步源码到已有运行时（最快，日常改代码用这个）
.\scripts\build-portable.ps1 -RuntimeDir 'D:\downloads\electron-v31.7.7-win32-x64'  # 本地运行时，完全离线
.\scripts\build-portable.ps1 -ElectronVersion 33.0.0                         # 换 Electron 版本
.\scripts\build-portable.ps1 -Force                                          # 强制重建（重新下载运行时）
```

### 3.5 手动构建

```powershell
# 1. 下载 Electron 31.7.7 win32-x64 并解压到 dist\音乐播放器-win32-x64
#    https://npmmirror.com/mirrors/electron/31.7.7/electron-v31.7.7-win32-x64.zip
# 2. 重命名 exe
Rename-Item 'dist\音乐播放器-win32-x64\electron.exe' '音乐播放器.exe'
# 3. 把 app\ 复制成 resources\app
Remove-Item 'dist\音乐播放器-win32-x64\resources\app' -Recurse -Force -ErrorAction SilentlyContinue
Copy-Item 'app' 'dist\音乐播放器-win32-x64\resources\app' -Recurse
```

### 3.6 打一键安装包（Inno Setup）

用户可以将生成的便携运行目录进一步压缩封装，打包生成为**单文件 Setup.exe** 安装程序：

```powershell
# 需要 Inno Setup 6（命令行编译器 ISCC.exe）
winget install -e --id JRSoftware.InnoSetup

.\scripts\build-installer.ps1      # 也可以双击 打包安装包.bat
# 产物：dist\安装包\音乐播放器-Setup-<版本>.exe
```

打包脚本执行的具体逻辑如下：首先脚本会调用一次 `build-portable.ps1` 组装便携环境（如果传入了 `-NoBuild` 参数则直接跳过该步骤）；接着校验 `resources\app\ui\index.html` 的资源引用状态，确保它确实引用了最新生成的前端界面产物，避免历史旧界面被错误打包进安装程序；随后调用 `installer\music-player.iss` 启动编译流程；最终输出目标产物的文件实际体积以及对应的 SHA256 校验哈希值。

| 参数 | 说明 |
| --- | --- |
| `-Version` | 覆盖版本号（默认读 `app\package.json` 的 `version`） |
| `-OutDir` | 输出目录，默认 `dist\安装包` |
| `-NoBuild` | 跳过便携版构建，直接用已有的 `dist\音乐播放器-win32-x64` |
| `-Quiet` | 编译时不输出进度 |

安装向导的设计刻意压缩了交互路径，减少用户安装过程中点击鼠标的次数。向导仅保留必要节点：展示欢迎信息 → 选择安装目录（系统默认路径为 `%LOCALAPPDATA%\Programs\音乐播放器`）→ 勾选附加任务（面板中包含 ☑ 创建桌面快捷方式，系统默认保持勾选状态，用户可按需取消）→ 执行文件写入安装 → 显示完成面板（支持勾选"立即运行"选项启动软件）。安装流程没有插入多余的许可协议阅读页（MIT 协议文本会直接跟随核心文件释出到 `resources\app\LICENSE.txt` 中）、没有独立的开始菜单文件夹分组配置页，也去除了最后的"准备安装"确认等待页。

#### 安装脚本核心策略

安装包的具体运行逻辑由 `installer\music-player.iss` 文件统一控制，涵盖以下核心决策：

**权限与版本管理**
  - 按用户安装（采用 `PrivilegesRequired=lowest` 配合 `{localappdata}\Programs` 路径），双击即可直接拉起运行且无需弹出系统 UAC 提权确认窗口；通过固定 AppId 自动识别并覆盖旧版本，避免系统中并存多份副本。
  - 不写 `ArchitecturesAllowed`：由于该指令参数规则在 Inno 6.3 前后变更过，写死会导致其他版本的 ISCC 报错中断；加之软件属于纯文件树结构且部署在 `{localappdata}` 作用域内，并不依赖 64 位特殊系统级安装逻辑。

**用户数据与快捷方式**
  - 卸载不删用户数据：卸载时存放在 `%APPDATA%\music-player` 目录下的用户核心数据（包括曲库缓存、收藏夹记录及个性化设置）均完整原样保留。
  - 桌面快捷方式是可选任务：向导通过 `[Tasks] desktopicon` 定义（Inno 中默认勾选），并在 `[Icons]` 配置行绑定 `Tasks: desktopicon` 条件属性，用户取消勾选即不向桌面写入图标。

**资源汉化与定制**
  - 汉化文本采用「英文基础语言包 `Default.isl` 叠加自定义覆盖消息」实现，以解决 Inno Setup 官方未内置简体中文资源包且社区规则分散的问题，直接覆写界面展示文本。
  - 支持自定义安装图标：将准备好的 `app.ico` 放入 `installer\` 目录后，自动化构建脚本即会在打包时一并载入应用。

> ⚠ 在文本编码规范方面，`installer\music-player.iss` **必须存成 UTF-8 带 BOM** 的格式，否则 Inno Setup 会退回并按照当前系统的本地 ANSI 代码页解析，导致中文字符全部变成乱码；同理，位于 `scripts\*.ps1` 的 PowerShell 脚本在 PowerShell 5.1 环境下如果没有检测到 BOM，同样会强制退回本地代码页读取。与之相反，位于根目录与 `scripts\` 下的 **`.bat` 批处理文件必须完全不包含非 ASCII 字节**：这是因为 cmd.exe 解释器是按照原始字节偏移量重新定位并读取批处理指令的，一旦在注释内容中混入了双字节中文路径，就会使偏移量计算错位，导致后续的代码文本被当成系统命令执行（此前在实际排查中，终端就曾因此错误输出 `'Needs' 不是内部或外部命令` 这类碎片报错）。针对这两项编码要求，项目目前已交由 `scripts\文档一致性验证.js` 脚本实施常态化校验（对应检查清单中的第 [9] 与第 [10] 项）。

**已在本机验证过**：开发者已使用 Inno Setup 6.7.3 环境成功编译出大小为 94.4 MB 的目标安装文件 `音乐播放器-Setup-2.1.1.exe`，并对打包结果连续实施了两轮静默安装与卸载测试（其中一轮指定携带 `desktopicon` 任务参数，另一轮则不携带）。实际测试结果表明，桌面快捷方式的生成控制符合预期，执行卸载后应用安装目录与桌面快捷方式均被彻底清理，相关的详细测试记录可参见 `docs\更新日志.md` 文件中的「未发版」小节。
### 3.7 自动构建与发布（GitHub Actions）

当开发者在云端配置好 `.github\workflows\release.yml` 自动化工作流之后，**只要向远端推送一个 `v*` 格式的版本标签，系统就会自动执行编译打包并将安装包挂载到 Release 页面中**，用户后续只需直接下载生成的 Setup.exe 执行双击安装即可。

```
打标签（v2.1.2）  →  Actions 跑起来
                      ├─ 校验标签与 app\package.json 的版本号一致
                      ├─ 文档一致性 + 三套离线回归验证（数据管控 / 设置持久化 / ID3）
                      ├─ choco install innosetup
                      ├─ build-installer.ps1 → 便携版 + Setup.exe
                      ├─ 上传 Actions 产物（artifact）
                      └─ gh release create / upload → Release 里挂上 Setup.exe
                  →  用户下载 音乐播放器-Setup-2.1.2.exe，双击安装
```

- **触发**：通过推送以 `v*` 开头的版本标签触发流水线（日常可由 `scripts\release.ps1` 辅助完成打标）；开发者也可以在 GitHub 的 Actions 控制台中手动发起 `workflow_dispatch` 运行，但手动触发只会产出临时的 artifact 构建产物，不会改动发布状态或触碰 Release
- **标签必须等于 `v` + `app\package.json` 的版本号**：如果推入的 Git 标签与代码配置中的版本字段不相符，流水线会直接判定失败并阻断运行，避免出现"发布标签标识为 2.1.2、安装包实际为 2.1.1"的混乱版本
- 生成的**发布说明**中会同步列出最终编译产物的完整文件名以及经过计算的 SHA256 校验和
- 持续集成环境与本地运行环境**共用同一套打包逻辑**（均通过串联调度 `build-portable.ps1` 与 `build-installer.ps1` 执行），CI 管道不会维护任何另一套独立的打包规则
## 4. 每日开发流程

日常开发时的操作顺序固定为：修改代码，将改动同步到运行时环境，最后启动程序进行测试：

```powershell
.\scripts\build-portable.ps1                      # 同步（运行时已存在，秒级完成）
.\dist\音乐播放器-win32-x64\音乐播放器.exe          # 运行
```

**文件同步机制**

源码目录 `app/` 中的各个文件与最终运行环境里的路径保持着一一映射的关系（从 `app/<文件名>` 对应到 `resources/app/<同名文件>`）。涉及同步的文件包括：
  - 核心逻辑与配置：`main.js`、`preload.js`、`package.json`
  - 界面结构：`index.html`、`mini.html`
  - 功能模块与依赖：`bili.js`、`cover.js`、`ncmdump.exe`

> 客户端处于启动状态时，Windows 系统会占用并锁定 `resources/app` 路径下的文件。构建脚本在执行时会优先尝试直接覆盖写入；如果覆盖失败导致报错，用户需要先退出正在运行的播放器程序，然后再重新执行构建命令。
## 5. 安装到本机

### 5.1 普通用户：下载 Setup.exe 双击安装（推荐）

访问 **[Releases](https://github.com/Konom1Hasu/Music-Player-WIth-Visualization/releases)** 页面下载预编译好的 `音乐播放器-Setup-x.y.z.exe`。下载完成后双击运行安装包，按照向导提示点击下一步直至完成即可。安装过程写入的是当前用户的本地目录，**不需要管理员权限**，也不会触发系统的用户账户控制（UAC）弹窗。

| 项 | 说明 |
| --- | --- |
| 安装形态 | 单文件安装程序（Inno Setup 打包，见 §3.6） |
| 安装位置 | `%LOCALAPPDATA%\Programs\音乐播放器`（按用户；不弹 UAC） |
| 快捷方式 | 桌面（可取消勾选）＋ 开始菜单「音乐播放器」 |
| 卸载 | 「应用和功能」里的「音乐播放器」，或开始菜单里的「卸载 音乐播放器」 |
| 用户数据 | 曲库 / 收藏 / 设置都在 `%APPDATA%\music-player`，**卸载不会删除** |
| 升级 | 装新版本会覆盖到同一目录（AppId 固定），不会并存两份 |

安装包与免安装便携版的核心功能完全一致，区别只在于安装包会自动处理系统层面的集成工作。它会为用户生成桌面与开始菜单快捷方式，并在当前用户的注册表项 `HKCU` 中写入卸载信息，让系统的「应用和功能」列表能够读取并展示入口。播放器本体在日常运行中依然不会读写注册表。如果用户希望文件结构保持干净独立、无需系统集成，可以直接使用便携版（见 §7.2）。

### 5.2 从源码一键安装（`安装.bat`）

在项目根目录中**双击运行 `安装.bat`** 即可完成全部部署流程。脚本会依次自动处理各个阶段：检测并在需要时触发项目构建、将必要文件释放到安装路径、生成桌面和开始菜单快捷方式，并在最后**直接打开播放器**供用户使用。全部步骤执行成功后，批处理终端窗口会自动退出。

上述双击操作在底层完全等价于通过命令行执行：

```powershell
.\scripts\install.ps1 -Launch
```

如果用户希望在部署结束后暂不运行播放器，可以使用以下命令：

```powershell
.\scripts\install.ps1              # 直接跑脚本
.\安装.bat -NoLaunch               # 或者双击时想装完不启动
```

执行时无需手动区分“先编译再安装”的前后顺序，`安装.bat` 内部集成了构建调用逻辑。脚本还对环境缺失做了容错处理：当检测到前端开发依赖目录 `app-rhine\node_modules` 不存在时，它不会中断报错，而是输出一行警告信息并跳过前端界面的重新打包，转为直接沿用 `app\ui` 中已经存在的界面产物。这种方式本质上是通过 PowerShell 实施的绿色解压安装，过程中不会生成 Setup.exe 安装包，也不会向注册表添加卸载菜单。若需要生成与 Releases 页面一致的标准安装程序，请参考 §3.6 执行安装包打包流程。

### 5.3 安装流程

```
1. 调用 build-portable.ps1 准备产物（含界面产物：能构建就重建，不能就沿用 app\ui）
2. 若程序正在运行则先结束进程
3. 清空并重建安装目录
4. 复制 dist\音乐播放器-win32-x64\* 到安装目录
5. 在安装目录写入 卸载.bat
6. 创建桌面快捷方式
7. 创建开始菜单快捷方式
8. 启动程序（安装.bat 默认带上；install.ps1 要 -Launch）
```

### 5.4 安装位置

程序默认部署在 `%LOCALAPPDATA%\Programs\音乐播放器`。环境变量展开后，在多数标准 Windows 系统中对应的物理路径为 `C:\Users\<用户名>\AppData\Local\Programs\音乐播放器`。

### 5.5 参数

| 参数 | 说明 |
| --- | --- |
| `-InstallDir` | 自定义安装目录 |
| `-Launch` | 安装完成后立即启动（`安装.bat` 默认带） |
| `-NoLaunch` | 装完不启动（仅当同时给了 `-Launch` 时才有意义） |
| `-NoBuild` | 跳过构建，直接复制已有 `dist` 产物 |
| `-NoShortcuts` | 不创建快捷方式 |

```powershell
.\scripts\install.ps1 -Launch                                # 安装并启动（= 双击 安装.bat）
.\scripts\install.ps1 -Launch -InstallDir 'D:\Apps\音乐播放器'  # 安装到 D 盘
.\scripts\install.ps1 -NoShortcuts                           # 只复制文件，不创建快捷方式
.\scripts\install.ps1 -NoBuild -Launch                       # 已构建过，跳过构建步骤
```

### 5.6 卸载

**对于通过 Setup.exe 安装的情况（§5.1）**：用户可以进入 Windows「设置 → 应用 → 已安装的应用」，找到「音乐播放器」条目点击卸载；也可以直接打开系统开始菜单，在「音乐播放器」程序组中点击「卸载 音乐播放器」快捷方式。安装程序写入的卸载键值完全位于当前用户的 `HKCU` 注册表树中，目的只是向 Windows 注册管理入口，运行中的播放器自身从不会在注册表内残留业务数据。

**对于通过 `安装.bat` 或 `install.ps1` 部署的情况（§5.2）**：提供三种等效的处理方式供用户选择。第一种是直接执行安装目录中的 **`卸载.bat`**，脚本会自动终止残留进程、移除安装文件夹并清理桌面及开始菜单图标；第二种是手动删除安装目录 `%LOCALAPPDATA%\Programs\音乐播放器`；第三种则是手动清理桌面和开始菜单的快捷方式。脚本部署全程没有向注册表写入任何键值，因此直接抹掉对应的文件目录即可算作彻底卸载。

无论采用上述哪一种方式进行卸载，系统都**不会删除用户数据**。曲库元数据存储所使用的浏览器本地存储（IndexedDB）、播放列表收藏夹以及全局配置文件，都被隔离保存在 Electron 专门分配的用户数据（`userData`）目录中：

```
%APPDATA%\music-player
```

用户如果确定需要彻底清理所有使用痕迹，必须手动删除该数据文件夹。这一分离机制带来的好处是：后续执行版本覆盖、重新安装或在脚本部署与安装包形态之间切换时，原有的曲库记录与使用偏好都不会意外丢失。
## 6. 推送到 GitHub

日常更新只需要一条命令（**沿用已有的 `origin`，不需要再写仓库地址**），也可以双击根目录的 **`推送.bat`**：

```powershell
.\scripts\push-to-github.ps1
.\scripts\push-to-github.ps1 -RepoUrl 'https://github.com/你的用户名/music-player.git'   # 首次推送时指定仓库地址
```

### 6.1 参数

脚本支持通过以下参数控制推送行为与网络策略：

| 参数 | 说明 |
| --- | --- |
| `-RepoUrl` | 仓库地址。**可省略** —— 省略时沿用已有 `origin` |
| `-Branch` | 分支名，默认 `main` |
| `-Pull` | 推送前先 `fetch` 并合并（远端有本仓库没有的提交时用） |
| `-Check` | 只探测推送通道，不做任何推送 |
| `-NoAutoFix` | 关闭自动适配，只用最朴素的 `git push` |

**目标仓库与分支配置**
用于指定代码同步的目标地址与分支：
  - `-RepoUrl`：省略时脚本会自动读取本地仓库已配置的 `origin` 远程地址；仅在需要推送到新远程仓库或临时调试镜像地址时显式传入。
  - `-Branch`：指定目标分支，未传入时直接以 `main` 分支为准。

**推送行为与执行控制**
用于调整推送前的数据同步逻辑及脚本的执行策略：
  - `-Pull`：当远端仓库存在本地未同步的提交记录导致推送被拒时，添加此参数可在推送前先执行 `fetch` 并将远端更新合并到本地。
  - `-Check`：用于排查网络故障，仅验证当前网络与远端推送通道的连通性，全程不向远程仓库写入任何数据。
  - `-NoAutoFix`：完全停用脚本内置的环境检测和配置自动调整功能，使执行流程回退到原生最基础的 `git push` 命令。
### 6.2 脚本会做什么

执行该脚本时，程序会按阶段依次处理环境校验、目标配置与远端推送：

**环境与工作区检查**
  - 确认系统环境中已安装并能运行 git，且终端当前路径属于有效的 Git 仓库。
  - 读取提交身份（`user.name` / `user.email`），若有缺失则通过终端交互式询问用户，并将输入写入当前仓库的本地配置。
  - 检查工作区是否存在未提交的代码修改，若有改动会主动询问用户是否在继续前先完成提交。

**仓库配置与通道探测**
  - 明确远程仓库 `origin` 的目标地址（直接沿用现有配置或根据传入的 `-RepoUrl` 参数进行更新），并将当前本地默认分支统一重命名为 `main`。
  - **探测推送通道**并尝试连接远端，连接失败时会根据具体的错误类型自动切换适配方案（具体规则见下文）。

**远端推送与状态处理**
  - 运行 `git push -u origin main` 推送分支并建立追踪关系；脚本会显式检查退出码，推送失败时依据截获的错误类型输出对应的排查提示。
  - 运行 `git push origin --tags` 推送本地所有版本标签；由于分支代码已推送成功，该步骤即使失败也不会中断流程。
### 6.3 自动适配的两类障碍

脚本执行时会预先运行一次 `git ls-remote` 命令来探测网络通道是否通畅。如果这次探测调用失败，脚本会**根据具体的错误类型**来选择对应的兜底处理逻辑：

| 判定 | 触发特征 | 兜底动作 |
| --- | --- | --- |
| `tls` | `unable to get local issuer certificate`、`schannel`、`SEC_E_NO_CREDENTIALS` | 改用 **openssl 后端** + 合并本机自签 CA 的 bundle |
| `credential` | `could not read Username`、`couldn't create signal pipe` | 直接调用 `git-credential-manager.exe` 取缓存凭证，拼成 `Authorization` 头 |
| `network` | `Could not resolve host`、`Failed to connect` | 不做兜底，直接报错 |
| `nonfastforward` | `rejected`、`fetch first` | 提示加 `-Pull` |

只要运行环境配置正常，上述两项兜底策略都不会被触发，此时脚本的执行过程与普通的 `git push` 完全一致。

**兜底策略的安全与隔离设计**

  - 配置隔离：所有兜底配置仅借助 **`GIT_CONFIG_*` 环境变量**动态生效，**不会被写入本地的 `.git/config` 文件**，仅对当前执行的命令有效，不影响后续终端中的 git 操作。
  - 凭据脱敏：读取已缓存的凭据信息时，日志中**只会提示已成功获取凭据，绝对不会打印 token 的具体内容**，以防敏感信息泄露。

### 6.6 推送不通时的排查：schannel 与加速器

> 本节说明底层机制与手动排查步骤。在日常开发中，用户不需要查阅这里的内容，因为 `push-to-github.ps1` 脚本内部已经集成了自动适配逻辑（见 §6.3）。

**症状 A：`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e)`** —— 这里的 schannel 是 Windows 操作系统自带的安全通道组件，也是 Windows 版 git 默认使用的 TLS 网络安全层后端。此时该组件完全处于瘫痪状态，并且这种异常会对**所有** HTTPS 站点生效，哪怕尝试访问 `https://www.baidu.com` 也会直接报错。用户可以运行 Node.js 脚本来进行对比测试，因为 Node.js 内置了独立的 OpenSSL 库，发送网络请求时不依赖系统的 schannel，这样就能准确区分究竟是实际网络中断还是安全协议后端故障：

```powershell
node -e "require('https').get('https://www.baidu.com',r=>{console.log('HTTP',r.statusCode);process.exit(0)}).on('error',e=>{console.log('ERR',e.code);process.exit(1)})"
```

如果上述 Node 脚本可以顺利返回 HTTP 状态码，就说明底层网络连接正常，纯粹是系统的 schannel 后端出现了故障，用户可以参考后文的解决办法进行修复。

**症状 B：`SSL certificate problem: unable to get local issuer certificate`** —— 这代表底层的 TCP 网络握手已经成功，但是在验证服务器下发的安全证书时，客户端找不到对应的上级受信任签发机构。如果用户电脑上安装并启用了 **Steam++ / Watt Toolkit** 这类网络加速工具，通常就会出现这个报错。加速器会在后台把 `github.com` 的域名解析劫持指向本地的 `127.0.0.1` 环回地址，同时借助**它自身生成的根证书**充当 TLS 中间人代理。用户可以执行下方这条命令，检查当前连接实际接收到的证书是由谁签发的：

```powershell
node -e "const h=require('https');h.get({host:'github.com',rejectUnauthorized:false},r=>{const c=r.socket.getPeerCertificate();console.log('issuer:',c.issuer.CN,'|',c.issuer.O)}).on('error',e=>console.log(e.code))"
# 输出示例：issuer: SteamTools Certificate | BeyondDimension
```

加速工具在安装时会把该根证书写入 **Windows 证书库**，由于 schannel 会直接读取系统证书库，配置为 schannel 的 git 天然会信任这个证书；相反，git 的 **openssl** 后端只能识别自身安装目录下自带的静态 CA bundle 证书清单文件，找不到加速器的自签根证书，于是抛出症状 B 中的错误。

**解决办法：改用 openssl 后端 + 把本机自签 CA 合并进 bundle**

```powershell
.\scripts\setup-push-tls.ps1 -Test      # 生成 bundle 并立刻验证通道
.\scripts\setup-push-tls.ps1 -PrintEnv  # 只打印要设置的环境变量
```

该自动化脚本的完整处理流程如下：先读取并提取 git 自带的 `ca-bundle.crt` 公共受信任根证书清单作为基础模板；接着遍历读取 Windows 系统路径 `Cert:\LocalMachine\Root` 中所有**自签且未过期**的根证书并追加到末尾，加速工具注入的中间人 CA 证书就会被同步收录进去；然后将合并后的完整内容输出保存到 `dist\git-ca\ca-bundle.pem` 文件中；最后在进程级别注入特定环境变量（即 `GIT_CONFIG_COUNT`、`GIT_CONFIG_KEY_n` 和 `GIT_CONFIG_VALUE_n`），在运行时动态将 `http.sslBackend=openssl` 以及 `http.sslCAInfo` 配置项传递给 git 执行程序。之所以采用环境变量注入而不直接修改写入 `.git/config` 文件，是为了确保本地工作区的持久配置不受污染。

> 动态合并出的 bundle 文件由于包含了本机私有的 CA 证书数据，在工程中已被 `.gitignore` 规则屏蔽，因此 `dist/` 目录下的内容不会被意外提交到远程仓库。另外一种处理方式是，用户也可以直接在 Steam++ 软件面板中关闭针对 GitHub 的网络加速选项，让系统的 schannel 直接连接公网中真正的 GitHub 服务器。
### 6.7 推送不通时的排查：凭证助手起不来

```
sh.exe: *** fatal error - couldn't create signal pipe, Win32 error 5
fatal: could not read Username for 'https://github.com': terminal prompts disabled
```

如果出现上述报错，说明底层网络与 TLS 握手已经走通，否则系统会抛出 §6.6 中描述的症状 A 或症状 B；当前是卡在**获取凭证**这一步。Git for Windows 在解析配置项 `credential.helper = manager` 时，会把 `manager` 指向 `mingw64/bin/git-credential-manager`。这是一个 shell 包装脚本，git 执行它之前必须先启动 MSYS 环境下的 `sh.exe` 进程。然而在某些权限受限的系统环境中，安全策略会直接禁止进程创建用于进程间通信的命名管道，导致 `sh.exe` 启动失败并抛出 Win32 错误代码 5（访问被拒绝）。由于凭证助手根本没有机会运行，git 只能回落到让用户在终端手动输入账号密码的逻辑，又因为非交互环境下终端提示已经被禁用，推送操作便直接中止。

排查时，用户首先要确认凭证管理器中是否确实已经保存了对应的凭证：

```powershell
cmdkey /list | Select-String 'git:https://github.com'
# 期望：Target: LegacyGeneric:target=git:https://github.com  User: <你的用户名>
```

只要凭证已经存在，就可以采用绕开的办法：完全不依赖 git 自带的凭证调用链路，而是直接从底层读取已缓存的凭证，手动拼接为 HTTP 认证头后传给 git 使用：

```powershell
# 直接调用 exe（用 PowerShell 的管道，不涉及 MSYS）；输出含 username= 与 password=（token）
$c = "protocol=https`nhost=github.com`n`n" |
     & 'C:\Program Files\Git\mingw64\bin\git-credential-manager.exe' get
```

取得凭证之后，用户需要提取出其中的 `$user` 与 `$token`，将拼接好的 `username:password` 字符串转换成 Base64 编码，以 `Authorization: Basic ...` 的形式提供给 git。为了防止敏感凭据在进程列表或系统日志的命令调用记录中泄露，**走 `GIT_CONFIG_*` 环境变量而不是命令行参数**，这样可以有效减少凭证信息的暴露面：

```powershell
$b64 = [Convert]::ToBase64String(
         [Text.Encoding]::UTF8.GetBytes("$user`:$token"))
$env:GIT_CONFIG_COUNT   = '3'
$env:GIT_CONFIG_KEY_0   = 'http.sslBackend';  $env:GIT_CONFIG_VALUE_0 = 'openssl'
$env:GIT_CONFIG_KEY_1   = 'http.sslCAInfo';   $env:GIT_CONFIG_VALUE_1 = '<bundle 路径>'
$env:GIT_CONFIG_KEY_2   = 'http.extraheader'; $env:GIT_CONFIG_VALUE_2 = "Authorization: Basic $b64"
git push -u origin main
```

沿用这套自动化脚本时，还有两个容易踩到的问题需要注意：git 默认会把所有推送进度信息直接写入标准错误流 stderr，如果当前环境开启了 `$ErrorActionPreference = 'Stop'`，PowerShell 会把这些常规进度输出误判为严重的终止性错误，进而强行中断执行；另外，脚本内容如果包含中文字符，对应的 `.ps1` 文件必须严格保存为带签名的 UTF-8 with BOM 编码格式，否则 PowerShell 可能会出现乱码或解析失败。具体处理细节可以参考 [维护指南 §6.4、§6.1](维护指南.md)。
### 6.8 为什么不把运行时提交上去

| 限制 | 数值 |
| --- | --- |
| GitHub 单文件硬上限 | 100 MB |
| 本项目 `音乐播放器.exe` | **约 172 MB**（超限，无法推送） |
| 完整运行时 | 约 222 MB |
| 仓库推荐体积 | 1 GB 以内 |

**不采用 Git LFS 的考量**
  - 完整运行时占用约 222 MB 空间，会直接消耗 GitHub 免费账户 1 GB LFS 总配额的五分之一以上。
  - 后续拉取仓库的用户在克隆时都必须完整下载这部分体积，会产生不必要的带宽开销。

**仓库当前的维护策略**
  - 项目在 `.gitignore` 规则中明确排除了 `dist/` 输出目录，保持代码仓库纯粹，只存放纯文本源码、构建脚本和相关文档。
  - 用户在完成代码克隆之后，在本地执行一次 `scripts\build-portable.ps1` 脚本，即可自行构建出所需的运行时环境。

目录 `versions/archive/` 完整保存了 `musicplayer.html` 历史上 12 个关键节点的逐字节快照文件。当用户在调试音频可视化效果时改乱了代码，可以借助这些快照迅速退回到已知可用的历史状态。管理脚本在执行时会自动进行递归查找，用户日常不需要特意记忆快照存放的具体子路径。

### 8.1 快照来源与可靠性

这些快照是通过分析 DSH 会话日志提取出来的。脚本提取出针对 `musicplayer.html` 的**全部 write 与 edit 操作，并严格按照时间倒序重放**，最终还原出当时的代码文件。因为会话日志里的 `edit` 记录采用的是精确字符串匹配替换机制，所以只要反向重放过程没有报错，就能实现逐字节完全一致的历史状态还原。在处理 P 系列版本时，整个流程累计完成了 204 处替换，全部成功且没有发生过一次失败。

### 8.2 使用脚本

```powershell
.\scripts\use-version.ps1 -List                   # 列出全部版本（并指出当前 app\index.html 对应哪一个）
.\scripts\use-version.ps1 -Version Q1             # 回滚到 Q1
.\scripts\use-version.ps1 -Version R1 -NoBuild    # 只换源码，不重新构建
```

参数 `-Version` 检索历史快照时遵循严格的查找顺序：首先尝试匹配完整的文件名，匹配不上再匹配版本前缀，最后才检索关键词。只要能唯一确定一个快照目标，脚本就会执行切换。如果输入的参数同时命中了多个候选文件，脚本会中断报错并打印出所有候选结果，绝对不会随意猜测用户的意图。

### 8.3 脚本做了什么

脚本执行时依次处理文件备份、快照替换与生效构建，且因 `dist/` 已被 `.gitignore` 忽略，生成的备份不会污染 Git 仓库状态：

**备份当前环境**
  - 计算当前 `app/index.html` 的 MD5 校验和，并将其复制备份到 `dist\版本备份\index-<时间戳>-<版本名>.html`。
  - 将当前切换生效的版本名称记录写入到 `dist\版本备份\当前版本.txt` 之中。

**覆盖与构建生效**
  - 将选中的目标历史快照文件复制覆盖为 `app/index.html`，随后校验写入文件的 MD5 值确保复制无误。
  - 在默认运行模式下，自动调用执行 `build-portable.ps1` 进行编译，让回滚后的代码改动立即在播放器中生效。

### 8.4 切回最新版

```powershell
git checkout -- app/index.html                                   # 方式一：git
.\scripts\use-version.ps1 -Version index-20260922-214648-当前开发版  # 方式二：用备份
```

运行命令携带 `-List` 参数时，终端输出的「本机备份」区域会显示出当前机器上存在的所有备份文件名。用户只需要直接选中并复制目标文件名，传给命令即可完成还原。

### 8.5 兼容性

**底层接口支持**
  - 归档的 12 个历史快照均为自包含单文件 HTML（内嵌全部脚本与样式）。
  - 快照运行时调用的 IPC 接口（包含 `findLyrics`、`convertNcm`、`setRenderMode`、`getGpuStatus` 以及 `getDisplayInfo`）在当前 `app/preload.js` 中均已保留，直接替换为 `app/index.html` 即可运行，**不需要一并回滚 `main.js` 或 `preload.js` 这些底层支撑文件**。

**功能缺失说明**
  - 由于快照诞生于早期的「单文件播放器」开发阶段，代码中**完全不认识**后续接入的新特性，包括：B 站本地缓存提取（`bili.js`）、新版封面解析（`cover.js`）与 NCM 官方格式解密工具（`ncmdump.exe`）。
  - 同时不支持悬浮独立小窗口 `mini.html`、多位歌手自动识别、键盘多媒体按键自检以及播放器主题切换系统。

## 9. 故障排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `找不到 app 目录` | 当前终端所处的工作目录不正确，导致脚本无法在相对路径下定位到该文件夹 | 可以使用 `cd` 命令切换到项目的仓库根目录，或者直接在文件管理器中双击运行 `构建.bat` |
| `app 目录缺少必需文件` | 项目源码下载不完整，缺失了核心的前端界面或主进程脚本 | 检查 `app/` 目录下是否包含 `index.html`、`main.js`、`preload.js`、`mini.html` 以及 `package.json` 这些文件 |
| 下载 Electron 失败 | 当前网络连接不稳定，或者官方下载镜像源无法正常访问 | 可以在执行脚本时加上 `-RuntimeDir` 参数来指定本地已经下载好的运行时目录，也可以配置系统网络代理之后再次重试 |
| `无法清理旧安装目录` | 之前运行的应用进程仍在后台驻留，导致旧版本的文件被锁定而无法删除 | 请手动退出正在运行的程序；虽然安装脚本内部已经尝试自动结束相关进程，但偶尔仍需要用户手动确认关闭 |
| `同步校验失败` | 脚本向目标目录复制文件的过程中，某些目标文件正被其他程序打开占用 | 请彻底退出当前运行的程序，然后重新执行一次构建命令 |
| 启动后白屏 | 目标安装路径下的 `resources/app` 资源目录写入不完整，导致主窗口无法正常加载前端页面 | 重新完整运行一次构建脚本，让脚本重新复制打包前端资源 |
| NCM 无法解密 | 解密所依赖的可执行文件 `ncmdump.exe` 不存在，或者该文件被系统杀毒软件当作风险程序拦截隔离 | 请确认 `app/ncmdump.exe` 文件确实留在对应目录下，并将其手动添加到安全软件的信任白名单中 |
| 提示脚本被禁止运行 | 当前系统的 PowerShell 执行策略处于受限状态，阻止了未签名的脚本执行 | 可以直接运行 `安装.bat` 或 `构建.bat`（这两个批处理文件在调用时已经内置了 `-ExecutionPolicy Bypass` 参数绕过限制），或者以管理员身份打开 PowerShell 窗口并执行 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 命令来放行本地脚本 |
