# 维护指南

这里重点回答一个具体的工程维护问题：**当开发人员修改了代码之后，要通过什么机制保证配套文档和更新日志也能同步补齐，不会被遗漏？** 具体的解决办法分为三个层面：首先需要整理出一张明确的映射对照表，说明改动哪一部分代码时必须同步修改哪些文档；其次要配置一套自动化检查工具，只要提交代码时漏改了文档，检查任务就会直接报错失败；最后还要借助自动化发布脚本，把这项检查强制绑定为版本发布流程的前置条件，检查没通过就无法继续发版。
## 1. 一条命令走完发布

```powershell
.\scripts\release.ps1 -Bump patch      # 修 bug
.\scripts\release.ps1 -Bump minor      # 加功能
.\scripts\release.ps1 -Bump major      # 破坏性变更
```

脚本在执行过程中会严格按照以下顺序处理各项任务：

```
1. 检查工作区是否干净（有改动会问你是否先提交）
2. 计算新版本号，并校验它确实比当前版本大、标签没被占用
3. ★ 检查 docs\更新日志.md 里有没有新版本的段落
     —— 没有就生成骨架并**停下**，等你写完再跑一次
4. 写入 app\package.json 的版本号 + README 顶部的「当前版本」
5. 跑三套验证：文档一致性 / 数据管控 / 设置持久化（任一失败就中止）
6. 构建便携版
7. git commit + 打附注标签 vX.Y.Z
8. 推送分支与标签（走 push-to-github.ps1，自带受限网络适配）
```

**关键在第 3 步和第 5 步**：流程对文档完整性有硬性要求，只要更新日志尚未补充完整，或者相关文档与代码实际状态不一致，发布流程就会立刻中断。通过这种前置卡口机制，用户哪怕不小心漏写了文档改动，相关疏漏也不会直接被推送到远端仓库，脚本会在本地执行阶段当场抛出错误并中止操作。

当用户首次执行 `-Bump patch` 命令时，脚本由于无法预知本次发布具体的业务改动细节，不能凭空补充说明文字，因此只会自动填入对应的基础模板骨架，随后主动退出运行状态：

```
    docs\更新日志.md 里没有 [1.1.3] 段落
已经生成骨架，请把内容写实。写完更新日志再跑同样的命令就会继续往下走：
    .\scripts\release.ps1 -Version 1.1.3
```

在补充完说明之后重新执行，只要通过 `-Version` 显式传入同一个目标版本号，脚本便会识别到该版本已经完成递增计算，直接跳过生成步骤并继续向下执行。

### 参数

| 参数 | 说明 |
| --- | --- |
| `-Bump` | `patch` / `minor` / `major` |
| `-Version` | 显式指定版本号，例如 `1.2.0` |
| `-Message` | 提交信息；不指定时从更新日志的「主题」那行自动生成 |
| `-NoPush` | 只到打标签为止 |
| `-NoBuild` | 跳过构建（只改文档时用） |
| `-Yes` | 不再交互确认 |
## 2. 只跑检查（不发布）

```powershell
node scripts\文档一致性验证.js
```

用户在任何开发阶段都可以运行这条命令，脚本在几毫秒内就能输出检测结果。它集中校验了 16 项指标：

| 组 | 检查内容 |
| --- | --- |
| 1 | `app/package.json` 的版本号在更新日志里有 `## [x.y.z]` 段落，且段落有实质内容（不是占位） |
| 2 | README 顶部「当前版本 vX.Y.Z」与 `package.json` 一致 |
| 3 | 更新日志的版本号严格从新到旧排列、没有重复 |
| 4 | README「项目结构」提到了**每一个受版本管理的顶层条目** |
| 5 | README「项目结构」提到了 `scripts\` 与 `docs\` 下的**每一个文件**（反向也查：结构图里不许有仓库里不存在的文件） |
| 6 | README「文档」小节的链接都有效 |
| 7 | README 与 `docs\*.md` 里所有相对 Markdown 链接都能解析到真实文件 |
| 8 | 当前版本已有 git 标签、每个标签都有对应的更新日志段落（WARN 级） |

在日常提交中，第 5 组规则最容易被遗漏：用户经常在新建脚本或补充文档后，忘记同步更新 README 中的目录结构图。

> 该检查器**故意不调用 git 子进程**。这是因为在部分受到安全策略限制的运行环境里，系统会直接拦截 Node.js 通过管道创建子进程的调用，导致报出 `spawnSync git EPERM` 错误，进而造成校验逻辑静默失效。为了杜绝这种情况，脚本改用 Node.js 的原生 API 直接遍历本地文件系统，直接解析 `.git\refs\tags` 目录以及 `.git\packed-refs` 打包引用文件，确保在任何受限环境下都能跑出完全一致的判定结果。

### 2.1 版面遮挡怎么查（改过任何绝对定位的尺寸 / 位置之后）

界面里的各个面板全都固定放置在 **1920×1080 舞台**（即根节点 `#stage`，页面缩放时再依靠全局的 `transform: scale()` 进行等比缩放）之中。正因为坐标系完全确定，界面组件之间是否存在异常遮挡是**可以通过几何坐标精确计算出来**的，不需要人工肉眼比对截图：

```powershell
# 版面核查脚本已在 2.7.8 的清理中移除；改版面请按 docs\功能说明.md §11.1 的定位数值逐块核对
# 另开终端用无头浏览器打开下面任一个地址（--virtual-time-budget 给 20000）：
#   http://127.0.0.1:41888/_layout.html?scene=detail                        详情模式
#   http://127.0.0.1:41888/_layout.html?scene=archive&modal=settings        档案模式 + 设置弹窗
```

排查遮挡时，程序会先将每个面板的绝对矩形坐标换算回原始的 1920×1080 像素基准，随后计算出**当前所有可见方块在两两组合下的重叠像素面积**。分析报告的具体标准如下：

- 整套界面中，除了“浮层弹窗盖在底层背景元素上方”属于符合设计预期的正常遮挡以外，其余任何可见组件之间的像素重合都应判定为版面缺陷。
- 标记为 `[不可见，不参与重叠统计]` 的节点必须调用 `checkVisibility` 接口统一判断，因为该接口会顺着 DOM 树向上递归排查整条祖先链的 opacity 透明度。档案陈列区域与详情展示面板在隐藏时，依靠的是外层父级容器的 `opacity: 0` 样式来收起，如果只检测组件本身的 computed opacity 属性，就会误判成可见并引发假报警。
- 输出面板指标时，弹窗所在行会同时打印出 `可用高 / 内容高` 的具体像素数值。一旦内部内容的高度超出了外框的可用高度，对应容器**必须**声明 `overflow-y: auto` 滚动属性；如果缺少该样式，超出的内容就会直接溢出到边框外侧，甚至向下盖住底部的音频播放控制条。

启动无头浏览器时推荐选用 Edge（执行 `msedge.exe --headless=new`），对于带有 3D 渲染的页面，必须额外附带启动参数 `--use-angle=swiftshader --enable-unsafe-swiftshader`；缺少这一步会导致软件模拟光栅化失效，页面初始化直接崩溃，测量工具采集到的也就全是一片空白的初始状态。实际操作时还要避开三个常见问题：绝对不要把控制台的 stderr 标准错误重定向到本地文件，某些受限环境会拦截 stdio 管道句柄，导致无头浏览器进程根本拉不起且不输出任何错误信息；绝对不要携带 `--dump-dom` 参数，页面的 requestAnimationFrame 帧循环与 WebGL 渲染循环会一直处于活跃状态，无头环境判定不到空闲期，实测会导致进程直接挂死两分多钟；每次执行都要指定一个全新的 `--user-data-dir` 临时目录，否则前一次测试残留的后台无头守护进程会直接拦截并接管新实例，随后立刻退出，导致测试流程意外中断。

## 4. 写更新日志的约定

每个版本一个 `## [x.y.z] — 年份` 段落，含「主题 / 新增 / 变更 / 修复」四段：

```markdown
## [1.2.0] — 2025
**主题：** 一句话说清这个版本干了什么。
### 新增
- 面向用户的新能力
### 变更
- 行为/接口/默认值的变化（**破坏性变更要标注**）
### 修复
- 修了什么、**根因是什么**
```

撰写更新日志时，有两条实践经验需要遵循：**记录修复条目必须写明根本原因，不能只罗列故障表面现象。** 举例来说，记录时不应该只写简单的“修复鼓点不响应”，而要详细记录为“低频参考值 `kickRef` 只在首次赋值后不再更新，导致 kick 饱和到 1.0，乘性泵浦失效”。这种具体的机理描述，才能让团队在半年后回溯代码时获取真正有价值的技术信息。此外，**文档中的各个小节段落不能只有标题而缺失正文**，自动化检查器只要检测到标题下方的文字内容过短，就会将其判定为未完成的占位内容并直接抛出错误。
## 5. 代码注释与提交信息的约定

代码注释的核心原则是说明写这段逻辑的**原因**，不用复述代码本身已经表现出来的**执行动作**。在开发过程中排查修复过的缺陷与隐蔽问题，必须在对应位置保留清晰的说明文字，防止后续维护人员因为不了解前因后果，误把必要的特殊处理重新改回有缺陷的写法：

```js
/* 键名必须是 mp_kick：滑块写入的就是 mp_kick。这里曾写成 mp_kick2，而 mp_kick2 从来没被写入过
   → 每次重启都读不到，鼓点强度静默回到默认 0.40。 */
```

这类注释目前分布在几个典型文件中，例如 `app\main.js` 里记录了 Chromium 启动参数的配置原因，`app\index.html` 里说明了音频可视化参数的具体来源与推导过程，`scripts\*.ps1` 各种脚本中则专门标注了处理 cmd/chcp 编码切换、文件 UTF-8 BOM 标记以及重定向 stderr 报错输出时遇到的实际问题。

Git 的提交信息统一采用带有类型前缀的中文简短描述，帮助团队快速识别修改性质：`feat(vX.Y.Z):` 用于新增功能或发布新版本，`fix(vX.Y.Z):` 用于修复缺陷，`chore(vX.Y.Z):` 用于调整构建流程与工程脚本等工具链内容，`docs:` 专门用于只修改文档的情况。运行自动化发布脚本 `release.ps1` 时，如果用户没有显式传入 `-Message` 参数，脚本会自动提取更新日志第一行的主题内容，拼接生成格式为 `release(vX.Y.Z): <更新日志里的主题>` 的提交信息。
## 6. 写 PowerShell 脚本的五个坑（都是真踩过的）

### 6.1 含中文的 `.ps1` 必须存成 UTF-8 **with BOM**

Windows PowerShell 5.1 在读取没有 BOM（字节顺序标记，即用来标识文件编码的特定开头字节）的 UTF-8 脚本文件时，默认会直接按照当前系统的 ANSI/GBK 编码去解码。如果中文字符转换后的字节序列中，恰好包含会被语法解析器误认成引号或反引号的数值，执行时就会抛出「字符串缺少终止符」这类语法解析错误。排查时直接查看文件内容，排版和文字却完全显示正常。处理这种问题的有效办法就是为文件补上 BOM：

```powershell
$p = 'scripts\xxx.ps1'
$t = [System.IO.File]::ReadAllText($p, (New-Object System.Text.UTF8Encoding($false)))
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))
```

不过其他文件不能套用这个操作，像是 `.md` 和 `.json` 文件**不要**加 BOM，因为 GitHub 的渲染引擎以及 git 本身对带 BOM 的文本支持都不够好。

### 6.2 `Get-Content -Raw` 读不了无 BOM 的 UTF-8 文本

这是由同一个编码机制引发的问题，但产生的影响更加隐蔽：**运行过程完全不报任何编码错误，只是读取出来的文本内容悄悄变成了乱码**。一旦乱码混入流程，`package.json` 里面的中文描述被破坏就会导致随后的 `ConvertFrom-Json` 转换操作直接失败；README 文本里的 `**当前版本 vX.Y.Z**` 也会因为字符失真而无法被正则表达式匹配到，最终外部现象就表现为「版本号没被写进去」。为了彻底避开这一缺陷，脚本内读取文件时建议统一调用自定义的 `Read-Utf8()`：

```powershell
function Read-Utf8([string]$p) { [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8) }
```

### 6.3 变量名不区分大小写 —— `$A` 和 `$a` 是同一个变量

PowerShell 的语法规定了变量名不区分大小写。在错误的写法中，局部变量 `$A` 实际上和传入的形参 `$a` 指向了同一个变量。由于参数 `$a` 预先声明了类型为 `[string]`，后续把切分出来的数组重新赋值给 `$A` 时，系统会静默把它转成由空格拼接的普通字符串 `"1 1 3"`。随后通过 `$A[2]` 索引去取值，拿到的仅仅是字符串下标为 2 的字符 `'1'`，并不是预期中的第三个数字 3。结果就是版本号比较逻辑永远返回 0，从表面看完全猜不到错误根源在变量命名上。因此，参数名称与局部变量名称必须取得完全不一样：

```powershell
# 错
function Compare-Ver([string]$a, [string]$b) { $A = $a.Split('.') | ForEach-Object { [int]$_ } ... }
# 对
function Compare-Ver([string]$Left, [string]$Right) { $verL = @($Left.Split('.') | ForEach-Object { [int]$_ }) ... }
```

### 6.4 原生命令写到 stderr 会被 `EAP=Stop` 当成致命错误

许多外部命令行工具习惯将普通的提示信息和处理进度写进 stderr（标准错误输出流）。例如 `git` 在遇到 `.gitattributes` 引发的换行符提示 `LF will be replaced by CRLF`，或者执行远程推送输出 `To https://...` 时都会写入 stderr；`node` 在执行失败时也同样写入 stderr。如果脚本开头设置了 `$ErrorActionPreference = 'Stop'`（即报错行为首选项设为终止执行），这些本来正常的控制台输出就会被 PowerShell 当作致命异常捕获并直接中断程序，从表面看起来就像是 "`git add` 把发布流程搞崩了"。建议对所有原生命令都进行统一封装，在执行前临时把 EAP 限制放宽，命令执行完后再自行读取退出码做判断：

```powershell
function Invoke-Git {
    param([Parameter(ValueFromRemainingArguments = $true)][string[]]$GitArgs)
    $old = $ErrorActionPreference
    $ErrorActionPreference = 'Continue'
    try { $out = @(& git @GitArgs 2>&1); $code = $LASTEXITCODE }
    finally { $ErrorActionPreference = $old }
    return [pscustomobject]@{ Code = $code; Text = ($out -join "`n") }
}
```

这里需要注意，Windows PowerShell 5.1 中的 `$ErrorActionPreference` **不覆盖原生命令的退出码**，只要命令自身没向 stderr 写内容，即使进程执行失败返回了非零状态，PowerShell 也不会自动报错。用户必须在代码里显式检查 `$LASTEXITCODE` 的数值，不然即使推送动作失败了，脚本后续照样会继续打印出"推送成功"。

### 6.5 `.bat` 里不要出现中文，也不要在 `chcp` 附近放多字节字符

批处理解释器 `cmd.exe` 在执行 `chcp` 切换活动代码页之后，内部会按照**切换前所记录的文件字节偏移位置**重新定位并读取接下来的批处理内容。如果这部分位置正好碰上了占用多个字节的中文字符，读取指针就会直接切到某个汉字的半截字节上，把损坏的数据当成指令，甚至直接把原本写在行内的 `rem` 注释行错误解析成可执行命令并抛出报错。基于这个底层机制，编写 `.bat` 入口脚本时一律只存成**纯 ASCII**编码，所有需要呈现给用户的中文提示信息，全部留给它后续拉起来的 PowerShell 脚本去负责输出。
