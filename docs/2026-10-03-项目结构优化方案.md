# 项目结构优化方案（2026-10-03）

> 本文是**方案**，不是已执行的变更，请审阅后确认要执行哪几项。所有数据都是实测值（命令见各节），不是估计。

## 0. 先纠正一个前提：源码树并不"深"

| 指标 | 实测值 | 结论 |
|---|---|---|
| 源码树最大路径深度 | **4 层**（`app/ui/fonts/NOTICE.txt`） | 不深 |
| git 跟踪文件总数 | **157** | 不大 |
| `.gitignore` 是否已排除构建产物 | **是**（`dist/`、`app/ui/`、`node_modules/` 全在里面） | 已干净 |
| 每轮构建重复落盘的静态资源 | **48 个文件**，单个字体最多 **6 份** | ★ 真正的问题 |

平常大家觉得目录层数很多，其实是因为**构建产物在磁盘上被重复复制了四次**，并不是源代码本身的目录嵌套过深。下文的第 1 项专门处理这个核心痛点，第 2 到第 4 项则是在调整过程中顺便能够一起清理的内容。
## 1. 消除构建产物重复（推荐，收益最大）

在当前项目的构建流程里，同一份静态资源会被写入硬盘 4 次：

```
app-rhine/public/MiSans-Regular.woff2      ← 源码（18 个文件，入库）
        │  vite build 自动拷贝 public/
        ▼
app-rhine/dist/MiSans-Regular.woff2        ← 产物 A
        │  build-portable.ps1 第 200 行 Copy-Item 全量拷贝
        ▼
app/ui/MiSans-Regular.woff2                ← 产物 B
        │  build-portable.ps1 第 225 行把 app/ 整个同步过去
        ▼
dist/音乐播放器-win32-x64/resources/app/ui/MiSans-Regular.woff2   ← 产物 C
```

#### 现状分析与改造约束

运行统计命令（`find . -name <文件名> | wc -l`）后可以看到：`MiSans-Regular.woff2` 存在 4 份，`archive-cassette.glb` 达到 **6** 份，`atmosphere.ogg`、`score.json`、`favicon.svg`、`rolling-number.txt` 则是各有 4 份，涉及的静态资源总计多达 48 个文件。经过校验，`app-rhine/dist` 与 `app/ui` 的内容**逐字节相同**，不仅 `index.html` 和 `favicon.svg` 的 md5 校验值完全一致，各个子目录下的文件数量也能一一对应。

**★ 但不能直接删 `app-rhine/dist`**，因为有 4 个脚本仍然把这个路径作为默认输入：

| 脚本 | 行 | 用途 |
|---|---|---|
| `scripts/渲染快照.ps1` | 74 | 默认渲染目录 |
| `scripts/版面探针.mjs` | 12 | 默认注入目录 |
| `scripts/生成观测探针.mjs` | 8 | 默认 dist |
| `scripts/文档一致性验证.js` | 200 | 结构图里过滤 `dist` |

### 方案 A（推荐）：把 `app/ui` 做成指向 `dist` 的目录联接

Windows 的目录联接也就是 directory junction（可以通过命令 `mklink /J` 创建），它在创建和使用时都不需要管理员权限，而且对 Node.js 的 `fs.readFile` 以及本地 `http` 静态服务都是透明的。

```
app-rhine/dist/…           ← 唯一的真实产物（vite 直接写这里，工具链照旧）
app/ui → [junction] → …    ← 变成联接，不再占空间
```

**实施细节与验证**
  - 代码调整集中在 `build-portable.ps1` 的第 197–202 行：将原本的 `Remove-Item + Copy-Item` 全量拷贝逻辑，替换为“检查目标路径，若已存在且非联接先删除，再执行 `New-Item -ItemType Junction` 建立联接”；其他脚本因读取 `app-rhine/dist` 的能力不变而维持**零改动**。
  - 潜在风险在于打包或压缩工具可能对 junction 有特殊处理，但 `build-portable.ps1` 第 225 行调用的 `Copy-Item app\* -Recurse` 遇到 junction 会**跟随并拷成真目录**，直接将其展开为真实文件，因此最终发布包 `resources/app/ui` 仍是完整内容，不影响便携版独立运行（**这一条必须先实测验证**）。
  - 硬盘上可省下一整份包含字体、背景配乐和 GLB 模型在内的完整产物，释放约 **30 MB** 空间，同时每轮构建省去一次全量拷贝文件的开销。

### 方案 B（备选，更保守）：保留两份，但让构建脚本先删净

**实现方式与权衡**
  - 若担心引入 junction 带来跨磁盘分区报错、权限差异或部分压缩归档工具无法识别的不确定性，可保留两份实体文件。
  - 改造时保留 `Remove-Item $UiDir -Recurse -Force`（当前构建已有），并在拷贝完成后增加比对 `dist` 与 `ui` 目录下 `index-*.js` 哈希值的检查步骤，两边不一致即刻报错中断。
  - 此方案**不省空间，只防“产物不一致”**。

> **建议：先做方案 A 并实测 `Copy-Item` 对 junction 的行为；不行再退回方案 B。**
## 2. 拆分 `player.ts`（3451 行 / 516 分支）

在当前整个工程里面，`player.ts` 是体积最大、复杂度最高的核心文件：

| 文件 | 行数 | 分支数（if/else/switch/三元） |
|---|---|---|
| **`player.ts`** | **3451** | **516** |
| `scene.ts` | 1484 | 111 |
| `main.ts` | 1329 | 199 |
| `spectrum.ts` | 654 | 32 |

把多达 516 个条件分支集中塞进同一个文件，会导致排查与维护变得异常繁琐，每次修改业务逻辑都必须在这 3451 行代码之间来回翻找跳转。这次重构的核心原则是依据各个函数的具体**职责**进行模块切分，而不是机械地按照代码行数随意截断：

| 新模块 | 从 player.ts 搬出的内容 | 大约行数 | 对外导出 |
|---|---|---|---|
| `library.ts` | `Song` 类型、曲库持久化（IndexedDB）、`addFiles`/`importFolder`/`importFiles`/`readTags`/`parseID3`/`repairTags`/`probeDuration` | ~700 | `getSongs` `addFiles` `removeSong` `onLibraryChange` |
| `bili-source.ts` | B 站缓存相关：`fileUrlToPath`/`playablePathOf`/`blobUrlOf`/`ensurePlayableSource`/`loadBiliAudio`/`importBili`/`armPendingSeek` | ~450 | `importBili` `loadBiliAudio` |
| `playback.ts` | 播放控制、媒体键、音量、预取：`togglePlay`/`playNext`/`playPrev`/`playAt`/`cycleMode`/`peekNext`/`prefetchSong`/`handleMediaKey` | ~500 | 播放类全部导出 |
| `viz.ts` | 频谱接线：`initSpectrumWorker`/`ensureAnalyser`/`vizFrame`/`vizTestTimeData`/`armSpectrumWatchdog`（**算法留在 `spectrum.ts`，这里只搬接线**） | ~400 | `startViz` `vizStop` |
| `lyrics.ts` | `lrcLines`/`stepLyrics` | ~70 | `stepLyrics` |
| `song-edit.ts` | 歌曲信息编辑 / 封面：`songEditMarkup`/`mountSongEdit`/`applySongEdit`/`useCoverImage`/`reloadEmbeddedCover`/`rereadMetadata` | ~380 | 编辑类导出 |
| `player.ts`（保留） | 只留：播放条 UI、列表渲染、`buildUI`、事件绑定、深色主题、启动恢复 | ~900 | — |

推进拆分工作时，有两条底线必须严格遵守：

**认知预期**
  - 分支总数并不会单纯因为文件切开就直接缩减，原先的 516 个分支依旧完整存在，只是被分摊到了各个独立的领域模块中。
  - 拆分的目的是改善代码的可维护性，而不是立刻压缩分支规模；后续要想真正削减分支数量，必须依赖第 3 项和第 4 项中对重复代码的清理。

**兼容性与类型保障**
  - 既有的 `main.ts` 以及作为旧回退页的 `app/index.html` 目前都通过 `import { … } from "./player"` 大量依赖该模块对外暴露的符号，因此逻辑迁出后，必须在重构后的 `player.ts` 内部统一配置 re-export（通过 `export * from ...` 等方式将子模块的导出重新抛出），否则 `main.ts` 的所有引入路径都会直接报错中断。
  - 改造实施过程中，必须执行 `tsc --noEmit` 命令进行全量静态类型检查来严格把关。
## 3. 合并 `versions/` 归档（12 个 HTML 散在顶层）

```
versions/A_pre0912.html  B_preVizTune.html  C_preSlideWave.html  P0_current.html
         P1..P4_*.html   Q1..Q3_*.html      R1_installed_final.html   README.md
```

目录中现存的 12 个历史快照用于记录项目不同阶段状态的静态备份，完全不参与项目的构建流程，仅作为排查问题时的回溯参考：其中 A/B/C 代表早期的三代设计，P0–P4 代表正式发布前设立的测试锚点，Q 代表排查问题时的调试中间态，R1 代表最终交付的安装版定版。

为了让根目录保持清爽，建议按以下两种方案归整（均可将顶层可见文件从 13 个缩减到 2 个）：

**归档整理方案**
  - **移动到子目录**：将这些文件移动并规整到 `versions/archive/` 子目录中，同时在 README.md 内补充索引表，列出文件名、对应版本及一句话说明“这一版做了什么”。
  - **整包压缩归档**：若平时无需逐个打开核对细节，可直接打包压缩为 `versions/历史快照.zip`，同样在 README 中保留对应的文档索引。

## 5. 执行顺序建议与风险

| 序 | 项 | 风险 | 回退成本 |
|---|---|---|---|
| 1 | 消除产物重复（A/B） | **中**（junction 行为需实测） | 改回一行 `Copy-Item` |
| 2 | 合并 versions/ | 低（纯移动 + 改 README） | `git mv` 反向 |
| 3 | 整理 docs/ | 低 | 同上 |
| 4 | 拆分 player.ts | **中高**（跨文件依赖、re-export） | 直接按原文件还原 |

建议按照 **2 → 3 → 1 → 4** 的次序分步落地。

**分步落地路径**
  - 低风险前置：先处理几乎没有破坏性风险的文档与目录整理（2、3），让改动节奏稳定下来。
  - 构建调整：接着调整构建逻辑，消除产物重复（1）。
  - 核心重构：最后着手改动范围最大、也最需要完整测试覆盖的业务源码重构（4）。

**单步验证闭环**
每完成上述任一步骤，都需要严格执行闭环流水线：
  - 静态检查：运行 `tsc --noEmit` 检查全量类型。
  - 功能验证：跑完四个验证套件确保功能未受破坏。
  - 交付与对比：重新执行完整构建，并对比、汇报改动前后的实测行为差异。
## 附：本次已完成的频谱抖动强化（与本方案无关，先汇报）

用于制造动态细节的顶端补抖逻辑，被安排在“量化计算以及一阶平滑跟随”完成之后才叠加到数值上。计算时采用独立的快速相位步进参数 `TOP_TENSION_RATE = 0.85`（单位为弧度/tick）进行驱动，同时配合 `CEIL_TOP = 0.97` 与 `CEIL_DIP = 0.12` 进行上下双向限幅截断，既能保证较高柱体在接近上沿时依然具有明显的抖动跳变，又不会让数值“一直顶满”显示上限。

通过命令 `node scripts/频谱离线观测.mjs 12 --bpm=160` 进行离线实测，采集到的对比数据如下：

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| **顶端帧间抖动** | 0.0652 | **0.0957** | **+47%** |
| **顶端锯齿度** | 0.072 | **0.098** | **+36%**（超过量化步长 0.077） |
| 最高柱贴顶帧占比 | 93% | 81.3% | 不再"一直顶满" |
| 左峰顶满帧占比 | 10.3% | 3.3% | 左峰不再死顶 |
| 密集鼓点命中率（160 BPM） | — | 96.9% | 不漏拍 |

**算法跨速率表现**
  - 在 100、128 以及 175 BPM 的测试条件下表现稳定，顶端抖动数值均保持在 0.0953~0.0958 之间，鼓点命中率维持在 95%~97%。

**配套离线观测脚本变更**
  - 新增 `顶端帧间抖动（高柱 >0.5 的相邻两帧变化）` 统计项，专门用来量化高位振幅的真实“抖动大小”。
  - 修复此前直接引用 `prev` 对象导致“帧间变化”差值计算结果恒为 0 的逻辑错误。
