# 项目结构优化方案（2026-10-03）

> 本文是**方案**，不是已执行的变更，请审阅后确认要执行哪几项。所有数据都是实测值（命令见各节），不是估计。

## 0. 先纠正一个前提：源码树并不"深"

| 指标 | 实测值 | 结论 |
|---|---|---|
| 源码树最大路径深度 | **4 层**（`app/ui/fonts/NOTICE.txt`） | 不深 |
| git 跟踪文件总数 | **157** | 不大 |
| `.gitignore` 是否已排除构建产物 | **是**（`dist/`、`app/ui/`、`node_modules/` 全在里面） | 已干净 |
| 每轮构建重复落盘的静态资源 | **48 个文件**，单个字体最多 **6 份** | ★ 真正的问题 |

"层数多"的体感来自**磁盘上的产物四重复制**，不是源码目录嵌套。下面第 1 项针对这个真问题，2–4 项是顺带能一起收的。

## 1. 消除构建产物重复（推荐，收益最大）

同一个文件落盘 4 次：

```
app-rhine/public/MiSans-Regular.woff2      ← 源码（18 个文件，入库）
        │  vite build 自动拷贝 public/
        ▼
app-rhine/dist/MiSans-Regular.woff2        ← 产物 A
        │  build-portable.ps1 第 200 行 Copy-Item 全量拷贝
        ▼
app/ui/MiSans-Regular.woff2                ← 产物 B
        │  build-portable.ps1 第 225 行把 app/ 整个同步过去
        ▼
dist/音乐播放器-win32-x64/resources/app/ui/MiSans-Regular.woff2   ← 产物 C
```

实测（`find . -name <文件名> | wc -l`）：`MiSans-Regular.woff2` 4 份、`archive-cassette.glb` **6** 份、`atmosphere.ogg` / `score.json` / `favicon.svg` / `rolling-number.txt` 各 4 份，静态资源总计 48 个文件。`app-rhine/dist` 与 `app/ui` 内容**逐字节相同**（已验证 `index.html`、`favicon.svg` 的 md5 一致，各子目录文件数一一对应）。

**★ 但不能直接删 `app-rhine/dist`**，有 4 个脚本以它为默认输入：

| 脚本 | 行 | 用途 |
|---|---|---|
| `scripts/渲染快照.ps1` | 74 | 默认渲染目录 |
| `scripts/版面探针.mjs` | 12 | 默认注入目录 |
| `scripts/生成观测探针.mjs` | 8 | 默认 dist |
| `scripts/文档一致性验证.js` | 200 | 结构图里过滤 `dist` |

### 方案 A（推荐）：把 `app/ui` 做成指向 `dist` 的目录联接

Windows 的 directory junction（`mklink /J`）不需要管理员权限，对 `fs.readFile` / `http` 静态服务透明。

```
app-rhine/dist/…           ← 唯一的真实产物（vite 直接写这里，工具链照旧）
app/ui → [junction] → …    ← 变成联接，不再占空间
```

改动量：`build-portable.ps1` 第 197–202 行把 `Remove-Item + Copy-Item`（全量拷贝）换成「已存在且不是联接就先删，然后 `New-Item -ItemType Junction`」；其余脚本**零改动**（读 `app-rhine/dist` 的能力不变）。

风险点是打包/压缩工具对 junction 的处理 —— 但 `build-portable.ps1` 第 225 行是 `Copy-Item app\* -Recurse`，遇到 junction 会**跟随并拷成真目录**，所以最终发布包 `resources/app/ui` 仍是真文件，不影响便携版完整性。**这一条必须先实测验证。**

预计收益：磁盘上少一份完整产物拷贝（含字体/配乐/GLB），约 **30 MB**；每轮构建少一次全量拷贝。

### 方案 B（备选，更保守）：保留两份，但让构建脚本先删净

不想引入 junction（跨盘/权限/压缩工具的不确定性）就接受两份，把 `Remove-Item $UiDir -Recurse -Force` 写死（现在已是这么做），并加一条校验「`dist` 与 `ui` 的 `index-*.js` 哈希必须相同，否则报错」。**不省空间，只防"产物不一致"。**

> **建议：先做方案 A 并实测 `Copy-Item` 对 junction 的行为；不行再退回方案 B。**

## 2. 拆分 `player.ts`（3451 行 / 516 分支）

`player.ts` 是全项目最重的一支：

| 文件 | 行数 | 分支数（if/else/switch/三元） |
|---|---|---|
| **`player.ts`** | **3451** | **516** |
| `scene.ts` | 1484 | 111 |
| `main.ts` | 1329 | 199 |
| `spectrum.ts` | 654 | 32 |

516 个分支挤在一个文件里，任何改动都要在 3451 行里定位。按**职责**切（不是按行数切）：

| 新模块 | 从 player.ts 搬出的内容 | 大约行数 | 对外导出 |
|---|---|---|---|
| `library.ts` | `Song` 类型、曲库持久化（IndexedDB）、`addFiles`/`importFolder`/`importFiles`/`readTags`/`parseID3`/`repairTags`/`probeDuration` | ~700 | `getSongs` `addFiles` `removeSong` `onLibraryChange` |
| `bili-source.ts` | B 站缓存相关：`fileUrlToPath`/`playablePathOf`/`blobUrlOf`/`ensurePlayableSource`/`loadBiliAudio`/`importBili`/`armPendingSeek` | ~450 | `importBili` `loadBiliAudio` |
| `playback.ts` | 播放控制、媒体键、音量、预取：`togglePlay`/`playNext`/`playPrev`/`playAt`/`cycleMode`/`peekNext`/`prefetchSong`/`handleMediaKey` | ~500 | 播放类全部导出 |
| `viz.ts` | 频谱接线：`initSpectrumWorker`/`ensureAnalyser`/`vizFrame`/`vizTestTimeData`/`armSpectrumWatchdog`（**算法留在 `spectrum.ts`，这里只搬接线**） | ~400 | `startViz` `vizStop` |
| `lyrics.ts` | `lrcLines`/`stepLyrics` | ~70 | `stepLyrics` |
| `song-edit.ts` | 歌曲信息编辑 / 封面：`songEditMarkup`/`mountSongEdit`/`applySongEdit`/`useCoverImage`/`reloadEmbeddedCover`/`rereadMetadata` | ~380 | 编辑类导出 |
| `player.ts`（保留） | 只留：播放条 UI、列表渲染、`buildUI`、事件绑定、深色主题、启动恢复 | ~900 | — |

**必须守住的两条**：① 分支总数不会因此减少（516 还是 516，只是分散）—— 这是可维护性改善，不是分支减少，真正能减分支的是 3、4 项里的重复代码；② `main.ts` / `app/index.html`（旧回退页）通过 `import { … } from "./player"` 引用了一大票符号，拆分后**必须在 player.ts 保留 re-export**，否则 `main.ts` 的 import 全断，这一步要用 `tsc --noEmit` 兜底。

## 5. 执行顺序建议与风险

| 序 | 项 | 风险 | 回退成本 |
|---|---|---|---|
| 1 | 消除产物重复（A/B） | **中**（junction 行为需实测） | 改回一行 `Copy-Item` |
| 2 | 合并 versions/ | 低（纯移动 + 改 README） | `git mv` 反向 |
| 3 | 整理 docs/ | 低 | 同上 |
| 4 | 拆分 player.ts | **中高**（跨文件依赖、re-export） | 直接按原文件还原 |

建议按 **2 → 3 → 1 → 4** 执行：先做零风险的整理建立信心，再碰构建，最后做最大的源码重构（它需要最多验证）。每一项做完都会：`tsc --noEmit` → 四个验证套件 → 重建 → 汇报实测差异。

## 附：本次已完成的频谱抖动强化（与本方案无关，先汇报）

顶端补抖在"量化 + 一阶跟随之后"叠加，相位用独立快相位 `TOP_TENSION_RATE = 0.85`（弧度/tick）驱动，并用 `CEIL_TOP = 0.97` / `CEIL_DIP = 0.12` 双向限幅 —— 高柱在上沿抖动，同时不"一直顶满"。实测（`node scripts/频谱离线观测.mjs 12 --bpm=160`）：

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| **顶端帧间抖动** | 0.0652 | **0.0957** | **+47%** |
| **顶端锯齿度** | 0.072 | **0.098** | **+36%**（超过量化步长 0.077） |
| 最高柱贴顶帧占比 | 93% | 81.3% | 不再"一直顶满" |
| 左峰顶满帧占比 | 10.3% | 3.3% | 左峰不再死顶 |
| 密集鼓点命中率（160 BPM） | — | 96.9% | 不漏拍 |

跨 BPM 稳健（100/128/175 BPM）：抖动 0.0953~0.0958，鼓点命中率 95%~97%。离线观测脚本同步增强：新增 `顶端帧间抖动（高柱 >0.5 的相邻两帧变化）` 指标（这才是对应"抖动大小"的量），并修正 `prev` 引用导致"帧间变化"恒为 0 的问题。
