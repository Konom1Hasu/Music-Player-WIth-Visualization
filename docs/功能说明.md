# 功能说明

本文档详细说明音乐播放器的全部功能与使用方式。

> **来源署名：第 11 章那套「音乐档案终端」的界面源码与 Blender 工程文件来自
> B 站 UP 主 [@路北路陈](https://space.bilibili.com/3546646728820438)**
> （仓库 [LBEILC/RhineLabUI](https://github.com/LBEILC/RhineLabUI)，MIT）。
> 本仓库做的是**反向整合**：把这套界面接上真实的播放内核，并按播放器信息改写界面词条；
> 界面与美术资产的著作权归原作者。详见 [README 的「致谢」](../README.md#致谢)。

> **仓库里有两套可播放的界面。** ① 以莱茵生命终端为底座的**音乐档案终端**
> （`app-rhine/`，当前主界面，见第 11 章）；② 早期的**独立播放器界面**
> （`app/index.html`，作为兜底保留）。第 1–10 章描述的是通用能力
> （导入、元数据、NCM、歌词、媒体键、主题等），两套界面共用同一套播放内核。

## 1. 曲库导入

### 1.1 导入文件

点击左栏「+ 添加」→ 选择文件，支持多选。

支持的音频格式：

| 格式 | 说明 |
| --- | --- |
| `.mp3` | 最常见，ID3v1 / ID3v2 标签与内嵌封面均支持 |
| `.flac` | 无损，支持 Vorbis Comment 与内嵌封面 |
| `.m4a` / `.aac` | AAC 系，支持 MP4 元数据 |
| `.wav` | 支持 LIST/INFO 标签 |
| `.ogg` | Vorbis |
| `.wma` | Windows Media Audio |
| `.ape` | Monkey's Audio |
| `.ncm` | 网易云加密格式，**导入时自动解密**（见 1.4） |

### 1.2 导入文件夹

点击「添加文件夹」→ 选择目录。程序会**递归**扫描该目录下所有支持的音频文件。

### 1.3 拖拽导入

直接把文件或文件夹拖到窗口任意位置即可，无需点击按钮。

### 1.4 NCM 自动解密

网易云音乐的 `.ncm` 是加密容器。本项目内置了两条解密路径：

1. **首选：随包的 `ncmdump.exe`**（官方实现，兼容全部 NCM 变体）
   - 把解密后的 mp3 / flac **连同完整 ID3 标签（标题 / 歌手 / 专辑 / 封面）** 一起写出
   - 程序在系统临时目录中解密，完成后读回内存，再清理临时文件
2. **回退：内置 AES-ECB 解密**
   - 当 `ncmdump.exe` 不可用或被安全软件拦截时启用
   - 直接解析 NCM 头部密钥块、RC4 密钥、元数据 JSON，再 AES-128-ECB 解密音频体
   - 通过文件头魔数嗅探真实格式（`ID3` / `fLaC` / `OggS` 等）

解密结果**只在内存中传递**，不会在你的音乐目录里产生任何新文件。
`ncmdump.exe` 写出的中间文件位于本次会话专属临时目录，字节读回内存后**立即覆盖擦写并删除**。

另外，`convert-ncm` 会先校验 `CTENFDAM` 容器魔数 —— 不是真正的 NCM 文件直接拒绝，
因此它不是一个"拿任意文件来试解"的通用解密器。

> 管控细节见 [数据管控与合规](数据管控与合规.md)。

## 2. 元数据识别

### 2.1 识别优先级

```
内嵌标签（ID3v2 / Vorbis / MP4）
      ↓ 缺失时
同目录 cover.jpg / cover.png / folder.jpg / 与音频同名的图片
      ↓ 缺失时
文件名解析（"歌手 - 歌名" 等常见格式）
```

### 2.2 多歌手识别

以下写法都会被拆分成**多个独立歌手**，并对每位歌手分别建立索引：

| 写法 | 拆分结果 |
| --- | --- |
| `周杰伦/费玉清` | 周杰伦、费玉清 |
| `周杰伦、费玉清` | 周杰伦、费玉清 |
| `周杰伦 & 费玉清` | 周杰伦、费玉清 |
| `周杰伦 feat. 费玉清` | 周杰伦、费玉清 |
| `周杰伦 ft. 费玉清` | 周杰伦、费玉清 |
| `周杰伦; 费玉清` | 周杰伦、费玉清 |

分隔符识别包含 `/`、`、`、`,`、`&`、`;`、`feat.`、`ft.`、`with`、`×` 等，
并带有「不误伤」保护：`AC/DC`、`/` 出现在 URL 中、`R&B` 等已知组合不会被拆开。

### 2.3 重新识别

对**已导入**的歌曲可以一键重跑识别流程（设置面板 → 重新识别）。
用于以下场景：

- 之前导入时文件名不规范，后来补了 ID3 标签
- 歌手拆分规则更新后需要重新索引
- 封面当时读取失败

重新识别只更新元数据，**不会**丢失收藏、播放次数与播放进度。

## 3. 播放

### 3.1 播放模式

| 模式 | 行为 |
| --- | --- |
| 列表循环 | 播完最后一首回到第一首 |
| 顺序播放 | 播完最后一首停止 |
| 单曲循环 | 当前曲目结束后重头再播 |
| 随机播放 | 随机选曲，尽量避免连续重复 |

点击播放控制区的模式按钮循环切换。

### 3.2 下一首播放

在任意曲目上右键 / 悬停菜单选择「下一首播放」，该曲目会被**插入**到当前播放位置之后，
而不是替换整个播放列表。

### 3.3 倍速播放

0.5× ~ 2.0×，调节后立即生效并随歌曲切换保持。

### 3.4 进度记忆

> **★ 位置只保留一条**：`localStorage` 的播放头 `rhine-playhead` =「最后一次在听的那首 + 位置」。
> **任何一首曲目都不再各自记住自己的上次位置** —— 切走再切回来一律从头播。
> 曲目记录里的 `pos` 恒为 0（落库时由 `persist()` 抹平），旧版本写进库里的值读了就清零。

由**系统设置 → 播放行为**里的三个开关控制（默认都开，存 `localStorage` 的 `rhine-play-prefs`）：

| 开关 | 默认 | 打开时 | 关掉时 |
| --- | --- | --- | --- |
| REMEMBER LAST POSITION | 开 | 只记「最后一次在听的那首 + 位置」这一条，下次启动接着听 | **完全不写**：播放头与曲目 `pos` 都不落，启动也从零开始 |
| RESUME LAST TRACK | 开 | 启动时把播放条恢复到上次在听的那一首与位置 | 启动不恢复，播放条留空 |
| OPEN ARCHIVE ON PLAY | 开 | 起播时自动打开这首歌的档案详情 | 只播不跳转，停在档案阵列里 |

「关掉记住上次位置」不是只写一个偏好就完事：它会顺手把已经存下来的东西清一遍
（每首曲目的 `pos`、`rhine-playhead`），并作废正在等待的续播点（`pendingSeek`）。

保存的其它状态：当前曲目、收藏状态、播放次数、音量、播放模式、主题、可视化参数 —— 下次启动自动恢复。
若上次退出时正在播放，会恢复到暂停状态（不会突然出声）。

**★ 为什么"每首歌都记录进度"会反复出现**：早先的实现把 `audio.currentTime` 写进**每一首**曲目
（`selectSong` 离开时、`timeupdate` 每 4 秒、`pause`、`savePosition` 四条路径各自落库），
于是每首歌都攒下自己的续播点。现在这四条路径**全部**只更新那一条全局播放头
（`savePlayhead()` 直接取 `audio.currentTime`，不再读 `s.pos`），曲目记录彻底不带位置。
无头核对（`_probe_pos`）：甲曲拖到 3.86 秒 → 切乙曲 → 切回甲曲 = 从 0 起播，
IndexedDB 三条记录 `pos` 全 0，播放头只有一条且指向最后在听的那首。

## 4. 歌词

### 4.1 来源优先级

1. 与音频文件**同名**的 `.lrc`
2. 音频文件**内嵌**歌词（ID3 USLT / SYLT 帧）
3. 同目录下文件名相似度最高的 `.lrc`
4. 上级目录中的 `.lrc`

### 4.2 编码

自动尝试 UTF-8 → UTF-8 BOM → GBK，避免中文歌词乱码。

### 4.3 显示

- 逐行滚动，当前行高亮放大
- 支持翻译行（同时间戳的第二行会作为译文并列显示）
- 无歌词时显示占位提示，不影响播放

## 5. 频谱可视化

### 5.1 为什么不用 `AnalyserNode`

`AnalyserNode.getByteFrequencyData()` 输出的是**等宽线性**频段。
音乐的绝大部分能量集中在低频，结果是左侧几条柱体剧烈跳动、右侧一片死寂，观感很差。

本项目自己实现了完整的频谱管线。

### 5.2 处理链路

```
AudioBuffer / MediaStream
   ↓ 取 1024 点时域样本
   ↓ Hann 窗（减少频谱泄漏）
   ↓ Goertzel 逐 bin 精确计算指定频点能量
   ↓ 对数频率分带 → 120 条柱体（每条约 1/12 倍频程）
   ↓ 峰值归一化（自适应 gain，随信号强度跟随）
   ↓ 对数压缩（dB 域取包络）
   ↓ 时间平滑（快攻慢放：上升快、回落慢）
   ↓ 鼓点泵浦（低频能量乘性调制）
   ↓ 相干行波叠加（滑动感）
   ↓ 逐柱峰值保持 + 衰减
输出到 canvas
```

### 5.3 关键参数

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `SPECTRUM_N` | 1024 | 时域采样点数 |
| `SPECTRUM_BANDS` / `BAR_N` | 120 | 柱体数量 |
| `VIZ_LEVELS` | 14 | 柱体灰度层级 |
| `kickPump` | 0.40 | 鼓点泵浦强度 |
| `bassSigma` | 0.048 | 低频高斯权重宽度 |
| `bassGainTarget` | 1.05 | 低频增益目标 |
| `BASS_WIDE_CENTER` | 0.12 | 低频能量中心位置 |
| 行波频率 | `i / 6` | 每 6 条柱体一个完整周期 |
| 行波速度 | `0.26` / 帧 | 约 12 条/秒，方向右 → 左 |

### 5.4 高耸条

低频峰值的位置由 `bassPeakBar()` 实时计算，`NEEDLE_CENTER` 随之自动左移到柱体序列的
最左边缘，配合倾斜因子 `Tp = pow(5, tilt * (1 - BASS_PEAK_BAR / BAR_N))`
让高峰呈现**窄而尖**的形态，而不是胖墩墩的一坨。

### 5.5 鼓点响应

历史上这里有一个真实 bug：低频参考值 `kickRef` 只在第一次被赋值
（`if (kickRef <= 0) kickRef = lowMag;`）之后再也不更新，导致 `kick` 迅速饱和到 1.0，
乘性泵浦彻底失效。

修复方式是让参考值持续跟踪：

```js
kickRef += (lowMag - kickRef) * 0.05;
```

并用上升沿检测触发泵浦：

```js
const kRise = lowMag / (kickRef + 1e-6);
const kick  = Math.max(0, (kRise - 0.08) * 2.2);
```

Worker 路径与同步回退路径**两处都**做了同样的修复。

### 5.6 滑动感

早期的「值位移混合」在平滑频谱上完全不可见，随机抖动波的方向也是随机的
（平均位移为零，看起来只是抖，不像滑动）。现在改为**相干行波**：

```js
const wave = Math.sin((i / 6 + wavePhase) * Math.PI * 2) * 0.18;
// ...
wavePhase += 0.26;   // 每帧推进，波峰从右向左移动
```

每 6 条柱体一个完整正弦周期，相位每帧推进 0.26 → 约 12 条柱体/秒的**定向滑动**。

### 5.7 性能

- 频谱分析跑在 **Web Worker** 里，主线程零阻塞
- Worker 创建失败时自动降级为同步计算（功能不变，帧率略降）
- 可视化渲染由**定时器**驱动，而不是 `requestAnimationFrame`，
  避免窗口被遮挡 / 后台时被 Chromium 节流到 1 fps
- 迷你窗复用主窗已经算好的柱体数据，不重复计算

## 6. 迷你悬浮窗

- 主界面右上角按钮
- 快捷键 `Ctrl+Alt+M`
- 托盘 / 菜单

### 6.2 特性

| 特性 | 实现 |
| --- | --- |
| 置顶 | `setAlwaysOnTop(true, 'screen-saver')` + 周期性 `moveTop()` 保活 |
| 不抢焦点 | `setFocusable(false)`，点击不会让游戏失焦 |

| 透明度 | 滑块调节，`setOpacity` |
| 锁定 | `Ctrl+Alt+L`，锁定后忽略指针事件，防误触 |

### 6.3 与独占全屏游戏

Windows 的**独占全屏**（Exclusive Fullscreen）会让 DWM 完全交出显示输出，
此时任何普通窗口都无法覆盖，这是操作系统层面的限制。

解决方案：把游戏改为「**无边框窗口**」或「窗口化全屏」。这样迷你窗可以正常置顶显示，
且点击迷你窗不会切出游戏。

## 7. 媒体键与耳机线控

### 7.1 双通道

Windows 上媒体键有两条独立路径：

1. **Chromium Media Session（SMTC）** — 系统媒体控制面板 / 部分蓝牙耳机走这条
2. **Electron `globalShortcut`（Win32 RegisterHotKey）** — 键盘与多数有线耳机线控走这条

两条都注册，命中任意一条都能工作。

### 7.2 幂等注册

`globalShortcut.register()` 对一个**已经被本进程注册**的键会返回 `false`。
历史上定时重试逻辑因此在重试时把健康状态误判成「被占用」，并把快捷键显示成不可用。

现在注册是**幂等**的：先查 `getHotkeyStatus()`，`detail[key] === true` 的键直接跳过重注册。

### 7.3 自检

设置面板中的「媒体键」一行显示：

| 显示 | 含义 | 处理 |
| --- | --- | --- |
| `✓ 已注册` | 全部成功 | 无需处理 |
| `⚠ 被占用` | 部分成功 | 关闭冲突程序，或用应用内快捷键 |
| `✕ 全部被占用` | 全部失败 | 同上 |

媒体键在 Windows 上是**独占**资源，同一时刻只能被一个程序注册。

### 7.4 防抖

按键事件做了 300 ms 防抖，避免部分耳机在单击时连发多次事件导致「播放→暂停」互相抵消
（表现为按了没反应）。

## 8. 主题与个性化

### 8.1 主题

| 主题 | 主色 | 说明 |
| --- | --- | --- |
| 深色 | 蓝紫 `hsl(250 85% 60%)` | 默认，暗环境护眼 |
| 浅色 | 蓝紫（浅底） | 亮环境使用 |
| 网易云红 | `#EC4141` | 参考网易云桌面端配色 |
| 莱茵生命 | 琥珀 `#c5a16b` | Rhine Lab 风格「仪器面板」变体，见下 |

所有弹层、滑槽、进度条把手、卡片边框都会跟随主题切换。

> **例外：开屏流程不跟随深色主题。** 开屏复刻的是参考片里的固定帧（浅底 + 深色字/线，
> 墨色全部写死），深色主题从档案界面开始生效。曾经深色主题只改了开屏底、没改墨色，
> 于是深色主题下开屏变成"深色字画在深色底上"的一整块黑，要等 26.92 秒才被扫掉，
> 连那个 `ENTER SYSTEM ↗`（跳过开屏）按钮也因为颜色继承 body 而在浅底上看不见。
> 现在开屏底固定为原片浅色、`.skip` 颜色写死为 `#080a08`。
> 开屏期间按 `ENTER` / `ESC` 或点右上角的 `ENTER SYSTEM ↗` 可随时进系统，不必等满时间轴。

#### 莱茵生命（仪器面板变体）

配色取自 [RhineLabUI](https://github.com/LBEILC/RhineLabUI)（明日方舟 · 莱茵生命，MIT，
界面源码与 Blender 工程作者：B 站 UP 主 **@路北路陈**）的
暗色面规范 —— 它自己的 `DESIGN.md`「明暗配色」一节写得很明确：

```
背景 #11181b   正文 #e0e3dc   辅助文字 #a6b0b1   分隔线 #536166   琥珀强调 #c5a16b
（另用 panel #202a2f / field #2a363b / 暖棕悬停 #9b7247）
```

与另外三套主题的区别**不只在换色，还在材质** —— 下面三条都是照搬原规范的做法：

| 做法 | 说明 |
| --- | --- |
| **1px 实心细线** | `--card-border` 直接用分隔线色 `#536166`，不再是半透明描边 |
| **构件直角** | 按钮、pill、列表项、封面、可视化区一律 `border-radius: 0`（原规范的按钮就是 1px 描边 + 无圆角）；只有大面板留 2px 免得割裂 |
| **选择用「竖线刻度」而非色块** | 原规范用长短竖线表达选中。所以列表选中项在这里是**左侧黄铜竖条 + 极淡底**，不是整块高亮 |

另外两处细节：数字用等宽字形（`tabular-nums`，时间读数不随数字宽度左右抖）；
封面四角加黄铜直角标记（取景框 / 刻度的意象）。

> **刻意保留圆形的**：播放键、收藏键、圆形滑钮。圆形是"可点"的强提示，
> 而且早先明确要求过暂停键不要方 —— 这里是有意混搭，不是漏改。

实现上换色走 `applyTheme()` 的 `rhine` 分支（改 CSS 变量），
材质差异走 `:root[data-theme="rhine"]` 限域规则 —— 主题名由
`document.documentElement.dataset.theme` 写入，否则只能"干换颜色"。

## 9. B 站缓存提取

用于播放**你本机已缓存**的 B 站音频。入口是**播放条上的电视图标**（`＋` 右边那个）。

### 9.1 流程

1. 点播放条上的电视图标 → 弹出系统的文件夹选择框，**选中 B 站缓存文件夹**
   ```
   手机端：<内部存储>\Android\data\tv.danmaku.bili\download\<av 或 ep 号>\<cid>\
   电脑端：<你设置的下载目录>\<标题>\…        （默认常在 Videos\bilibili\）
   ```
   选中后主进程从该目录往下遍历（最多 7 层）并识别缓存条目
2. 识别缓存条目的元数据（标题 / UP 主 / 封面）：认 `entry.json`、`videoInfo.json`、`.videoInfo`
3. **按内容而不是文件名判断哪个是音频**：读 mp4 盒子的 `stsd`，是音频轨才收；
   名字看不出内容时才退回扩展名兜底。同一集里多个清晰度取最高的一档
4. 把缓存的 `.m4s` 转成可播放副本（去掉自定义头 / 建硬链接，不重复占用磁盘）
5. 补齐标题、歌手（UP 主）、封面后加入曲库

> 关于提示语：从前这一步提示写的是"正在扫描 B 站缓存…"，但它其实**不会自己去找**
> 缓存目录，而是紧接着弹一个选文件夹的框 —— 用户会以为程序已经找到了。
> 现在提示改成"请选择 B 站缓存文件夹（含 entry.json 或 audio.m4s）"，
> 选择框标题也写了同样的要求；选不出来时提示"这个文件夹里没有识别到 B 站缓存"。

### 9.2 说明

- 只处理**本机已有**的缓存文件，不发起任何网络请求下载音频
  （只有封面图会按缓存里记录的 URL 取一次并缓存在 `userData\bili_cover`，那只是图片）
- 原始缓存文件不被修改或删除
- 列表里存的是**原始 `.m4s` 路径**（`Song.path`）。播放前先由主进程生成
  "剥掉私有头的可播放副本"，再用「读入内存 + blob URL」喂给 `<audio>`
  —— 界面挂在本机静态服务上，`file://` 音源会被 Chromium 直接拦掉，blob 是必需的一条路，不是兜底
- 播放失败时会自愈一次：强制重建副本 → 再试 blob，并提示"正在重建可播放副本…"
- 这一版把入口加回来之前，`importBili()` 其实一直没人调用：后端（`app\bili.js`）完好，
  但旧界面的 `#biliBtn` 没跟着搬进莱茵终端，功能在界面上等于不存在；
  补按钮时发现**音源通路也丢了**（详见下方数据管控），所以入口与音源一起修

### 9.3 数据管控

剥掉私有头得到的可播放 `.m4a` 属于**派生数据**，因此：

- 副本只写在 `%TEMP%\mp-session-<会话ID>\audio\`，**不再长期驻留在 `userData`**
- 程序退出时整个会话目录被覆盖擦写并删除
- 会话目录被清掉之后不影响使用：**点开哪首就按需重新生成哪首**的副本
  （`ensurePlayableSource()` 幂等，副本已正确时几乎零开销），不做启动时全库重建
- 每次提取都记一条本机审计记录（来源文件 + 产物体积）

> 管控细节见 [数据管控与合规](数据管控与合规.md)。

## 10. 封面 3D 档案

在封面区叠一层可旋转的 3D「档案」，并把**拆解 / 重组**做成可玩交互。

### 10.0 先说清楚：`.blend` 不能直接用，用的是它的导出件

压缩包里有两个 Blender 工程（`art/rhine-archive.blend`、`art/archive-assembly.blend`），
但 **`.blend` 是 Blender 的工程文件，运行中的程序读不了它** —— 没有运行时会去解析
`.blend`。正确通路是：Blender 里导出成 `glTF 二进制`（`.glb`），程序加载 `.glb`。

压缩包里已经带了导出好的两个 `.glb`，它们与那两个 `.blend` 场景一一对应
（原项目自己的 `AGENTS.md` 写明：*"通过 Blender MCP 重新生成单体与拆解资产，
保留 `art/internal_architecture.py` 和两个 `.blend` 源场景"*）：

| `.blend` 源 | 导出件 | 用途 |
| --- | --- | --- |
| `rhine-archive.blend` | `archive-cassette.glb` | **单体**：装好的档案（默认视图） |
| `archive-assembly.blend` | `archive-assembly.glb` | **拆解件**：内部结构，22 个节点带部件标签 |

本机没装 Blender，所以无法从 `.blend` 重新导出或做减面 —— 直接用现成的 `.glb` 是
唯一可行的做法（也是原项目的做法）。

### 10.1 拆解 / 重组

点击封面左下角的「**拆解**」，档案会沿 Z 轴分层散开，露出内部六个部件；
再点「**重组**」装回去。「复位」按钮同时把旋转角归零。

拆解动画**完全照抄原实现的规范**，不是自己发明的：

```
原实现（RhineLabUI model-viewer.ts）：
  PARTS = [ {id,depth} … ]                  六个部件，各带一个 depth
  按 userData.assemblyPart 把网格分组         ← 22 个节点每个都带这个 extras
  每帧：group[part].position.z = depth * spread
  spread 用阻尼跟随目标值，速率 5.5

本播放器：同上。spread 0=装好、1=拆开，阻尼速率同样 5.5。
```

| 部件 | 英文 | depth |
| --- | --- | --- |
| 紧固件 | FASTENERS | 2.75 |
| 透明盖板 | OPTICAL COVER | 1.85 |
| 折射环组 | REFRACTIVE RINGS | 0.75 |
| 光学核心 | OPTICAL CORE | −0.15 |
| 信息基板 | SUBSTRATE | −1.10 |
| 背板与框架 | CARRIER | −2.05 |

两个模型**共用同一个中心偏移**（都按单体的包围盒居中）。各自按自己的包围盒居中会让
拆解时零件整体错位 —— 它们出自同一套 Blender 坐标，必须一起平移。

装好时显示单体、`spread > 0.02` 时换成拆解件。两者在 `spread = 0` 时外形一致，
所以这个硬切换看不出来。

### 10.2 与播放状态联动

转速跟着播放状态走：**播放时正常转（0.30 rad/s），暂停时几乎停住（0.05）**，
用阻尼过渡避免一按暂停就跳。这样 3D 和"正在放歌"这件事产生联系，
而不是自顾自地转。

### 10.3 默认开启策略

**莱茵生命主题下默认开启**（这套主题的封面本来就该是那卷档案）；
其它主题默认关闭。只要用户手动关过一次，就**永远尊重用户的选择**、不再自动打开
（`localStorage.mp_cover3d` 为 `'0'`）。

### 10.4 为什么必须考虑性能

它要在封面区再开一个 WebGL 上下文，而频谱可视化已经占着 GPU。本机是 Intel UHD，
这个项目之前为了帧率折腾过很久（见 [架构说明](架构说明.md)），所以：

| 措施 | 说明 |
| --- | --- |
| 按需加载 | three.js + GLTFLoader + 两个模型共约 7.4 MB，**只有开启时才注入**，不开启一行都不加载 |
| 启动延迟 | 若上次是开启状态，等首屏渲染完 1.5 秒再加载，避免抢启动带宽 |
| 限帧 30fps | 内部按 `1/30` 秒累积后才渲染；转得慢，看不出差别 |
| 窗口隐藏即停 | 接住主进程的 `win-state`，最小化/隐藏时直接跳过绘制 |
| 像素比封顶 1.5 | 与可视化那边一致，不在核显上按 2x 渲染 |
| 取景只做一次 | 按**单体**包围盒定相机（1.72 倍留白吃掉拆解的增量），拆解途中不重新取景 —— 否则镜头自己缩放会晕 |
| 失败自关 | WebGL 不可用 / 模型读不到 / 脚本加载失败 → 提示一次并自动关闭，封面回 2D |

### 10.5 渲染与素材要点

- **透明底叠加**：`alpha: true` + `setClearAlpha(0)`，画布不遮住底下的专辑封面，
  档案像浮在封面之上
- **材质配色照抄原项目**：两个模型都没有贴图（合计 39 个材质、约 16.9 万三角形），
  材质名与 RhineLabUI `theme-material.ts` 里的 `surfaces` 表一一对应
  （`Frosted_Polymer` `#626b70`、`Optical_Diffuser` `#192226`、
  `Amber_Optical_Inlay` `#c6a36b` …），所以直接沿用那套配色，
  未知材质再按名字兜底，保证不会渲染成纯白
- **为什么锁 three r147**：页面跑在 `file://` 下，**ES module 会被 CORS 拦**，
  所以不能用现代 three.js（ESM-only），必须用 classic script（UMD）。
  r147 是最后一个同时提供 `build/three.min.js` 与 `examples/js/loaders/GLTFLoader.js` 的版本
- **为什么必须走 IPC 读模型**：同样是 `file://` 限制 —— Chromium 禁止
  `file://` 页面对本地文件发 XHR/fetch，`GLTFLoader.load()` 会直接撞 CORS。
  所以由主进程读字节、渲染进程 `loader.parse()`。该通道**只读且只放行白名单文件名**
  （不接受任意路径），遵守[数据管控](数据管控与合规.md)里那条结构性保证

### 10.6 与主题的关系

3D 档案在**四套主题下都可用**，但模型的材质配色固定用 RhineLabUI 那套
（因为材质名就是它的材质体系），不跟随主题换色。

## 11. 音乐档案终端（莱茵生命终端底座）

主界面是一套 1920×1080 的档案终端界面：整套 UI 挂在 `#stage` 里，
按 `scale(min(窗口宽/1920, 窗口高/1080))` 整体缩放。音乐库被映射成"档案"，
界面上的每一块都改造成了播放器的一部分。

### 11.1 三块界面各自负责什么

| 界面 | 位置 | 对应的播放器功能 |
| --- | --- | --- |
| 档案阵列（五列、每列八份、可循环） | 画面中部三维阵列 | 播放列表：曲目按顺序轮转进五列 |
| 抽出的档案卡片 | 画面左侧三维模型 | **当前曲目的封面印在正面标签板上**（含 `NO.` / 曲名 / 艺术家 / 专辑） |
| 详情区 | 右侧 `.detail-content`（1154 / 289 / 宽 636） | 曲目面板：封面、曲目信息、实时频谱、当前歌词 |
| 播放条 | 左下（left 59 / bottom 40 / 880×134） | 传输控制、进度、播放模式、收藏、导入、B 站缓存导入、播放列表入口 |
| 播放列表（抽屉） | 左下（left 59 / bottom 198 / 880×560，`☰` 开合） | 顶部**搜索框**（曲名 / 艺术家 / 专辑，回车播第一条命中、ESC 清词再按收抽屉、`✕` 清除）＋ 曲目列表：点行播放、`✕` 移除、`↳` 下一首播放、`♡` 收藏、`◐` 昼夜 |

> 播放条底边距 2.2.0 从 80 改到 40（抽屉同步 238 → 198，保持两者 24px 的间距），
> 配合 `fit()` 的"允许横向过扫描"把窗口上下那两条空带收窄 —— 用户反馈"顶部和底端太空"。

**封面是怎么印上去的**：GLB 正面本来就有一块 `Database label` 印刷标签板
（3.753 × 2.971、正面 z ≈ 0.246）。场景在它上面 z 0.252 处盖一块 3.62 × 2.87 的封面板，
画布 1536×1216 上画：封面方块（按宽高比居中裁切填满）＋ `TRACK` / `NO.003` / 曲名 /
艺术家 / 专辑 ＋ 抬头与细线。封面板在外壳（正面 z ≈ 0.197）之外，所以解密前后都可见；
只有被抽出的那一张卡片带封面，阵列里其余卡片保持素面。换选时收回中的卡片会把封面画布
**快照成独立纹理**，避免共用一张纹理导致旧卡片的封面跟着变。

### 11.2 操作

- **选档**：左右方向键切列、上下方向键翻档案、回车读取档案（**只进详情，不自动播放** ——
  起播请按播放键、点播放列表里的一行，或按空格）。
  已经在详情里时，回车是**播放 / 暂停这一首**（详情区主按钮就是 `PLAY`）；
  档案栏底下那行提示写的是「`ENTER` 读取」，与之一致。`ESC` 或详情层左上角的返回键回到阵列。
- **起播即打开档案**（默认开，设置里可关）：在播放列表里点一行、或按播放键起播之后，
  终端会自动切到这首歌的详情，并收起播放列表抽屉 —— 列表与档案两个入口的结果保持一致
- **播放列表（`☰`）**：点一行＝播放并打开它的档案；`✕` 移除这首歌
  （**当场从列表与曲库里一起消失**，剩下的行号立刻重排）；`↳` 下一首播放；`♡` 收藏。
  抽屉点外面会自动收起 —— 它是压在左侧三维阵列上的浮层，不收起来就会吃掉点阵列的那一下
- **播放条**：`⏮ ▶ ⏭`、播放模式 `↻`（列表循环 / 顺序播放 / 单曲循环 / 随机播放）、
  **播放速度 `1×`**（1× → 1.25× → 1.5× → 2× → 0.75× 循环）、
  `♡` 收藏当前曲目、`＋` 导入文件（右键 ＝ 导入整个文件夹）、
  **电视图标 ＝ 导入 B 站缓存**（见 §9）、`☰` 播放列表；
  底部一行是 当前时间 / 进度条 / 总时长 / **音量条**（与背景音乐音量各自独立）
- **拖拽导入**：把文件或文件夹直接拖进窗口即可（与 `＋` 同一条管线）
- **播放位置**：只为"下次接着放"而存，不显示、不当作播放记录。
  内存里跟着 `timeupdate` 走，落库有两条保护：**每 4 秒一次的兜底落库**
  （防止崩溃 / 强杀把位置丢掉）＋ 暂停 / 切歌 / 关窗 / 切到后台时各落一次；
  下次播放这首时从上次的位置续上（离曲尾不足 5 秒或不足 4% 则从头开始，
  避免一进来就结束）。落库时机见 `posSavedAt`，续播见 `pendingSeek` 与 `playing` 兜底。
- **曲库加载**：读 IndexedDB **不挡启动** —— 界面先按空库立起来（占位档案），
  读回来之后再刷一次档案阵列、刻度、播放列表与详情面板。
  读库兜底是 8 秒，且只在"真的一条都没回来"时生效；只要数据回来了就用真实结果。
  （旧写法是固定 1.5 秒的 `Promise.race` 超时，读得慢就整轮当空库 ——
  曲目全部进不来、位置记忆也无从谈起，这是 1.4.8 修掉的真实故障。）
- **详情区**：曲目面板（**没有页签**）—— 封面、曲名与艺术家、元数据四格、
  **大尺寸实时频谱**，频谱下方一行"当前歌词"字幕；底部 `＋ SAVE TRACK` 收藏、`PLAY ▶` 播放或暂停

### 11.3 实时频谱

右侧栏的竖向空间整块留给可视化（`01 曲目 / 02 歌词 / 03 播放记录` 三个页签已按要求删除；
歌词改为频谱下方的一行字幕，跟着进度整行替换）。

频谱用的是**1.3.0 版独立播放器那套自研分析器**（`app-rhine/src/spectrum.ts`，原样搬过来的），
且**观感参数一律照 1.3.0 的原值**（用户 2026-09-25 明确要求"参数设置请完全参照 1.3.0 版本的播放器"；
2.0.0 那轮"去毛刺"已整轮撤回，改回原值的逐项对照见 [更新日志 2.1.0](更新日志.md)）：

- **分析**：`AnalyserNode.getFloatTimeDomainData` 取出时域缓冲 → 取最新 **1024 点** → Hann 加窗 →
  **Goertzel** 逐带计算 120 个对数频段（42Hz–16kHz）→ 每个分析节拍按本帧峰值归一 →
  对数压缩 `log10(1+100·min(1,m/mx))/log10(101)`
- **柱高**：频段增益曲线（宽丘 + 细针的左峰、中高频人声尖峰、中频谷）→ 倾斜补偿
  `pow(5, tilt·(1−i/n))` → `pow(min(1,v), 2.1)` → **乘法鼓点泵动** → **正弦行波抖动**
  （幅度 0.45×K，空间频率 0.1+0.2·(K−0.4)，相位每拍 +0.03×K，向上幅度按余量缩放）→
  **14 级量化** → 单边颤动（0.055×K）→ 一阶跟随平滑（上行 0.70→0.50、下行 0.58→0.80）→ 峰值指示线。
  **量化前没有横向平滑、`render()` 里也没有二次插值** —— 屏幕上的就是这一份柱高
- **鼓点**用未归一化的低频原始幅度做 onset（`(rise−0.08)×2.2`，参考电平 0.05 慢跟随）；
  用乘法而不是加法，避免十几根一起顶过 1.0 被钳成平直方块
- **五种样式**：融合 / 音色 / 条形 / 圆环 / 波形（默认融合），配色取终端令牌
- **播放条**：52 格 2px 电平刻度，直接取频谱柱的采样值
- **取不到运行中的 `AudioContext` 就不接管音频元素** —— 宁可没有频谱，也不能没有声音

参数固定成 1.3.0 的默认值（倾斜 55、鼓点 0.40、抖动 1.00、分析窗 1024、14 级量化、
峰宽 σ 0.048、左峰目标增益 1.05）。

**帧率**：频谱的计算放在 **Web Worker** 里 —— 主线程只取时域数据、转移一个 2KB 副本、
拿回 121 个浮点数出图。**分析节拍 30Hz（每 33ms 一帧，与 1.3.0 的分析节拍一致），渲染节拍 60Hz**：
worker 只负责算，主线程按 60fps 把**同一份柱高**重画（不做二次插值，所以阶梯与抖动与 1.3.0 一致），
滚动、缩放一类的合成因此更顺。worker 起不来或 120 帧内没有回包就 `terminate()` 并永久退回同步计算；
时域缓冲在两侧轮流用、靠 transfer 归还，每帧不产生垃圾。
播放条刻度跟着渲染节拍走，只在像素高度真的变化时才写 DOM；暂停后整机降到 15fps
（只画收起动画）；窗口隐藏 / 最小化时停掉整个循环
（Electron 关闭了背景节流，不主动停就会一直算没人看的帧）。
播放条与播放列表不使用 `backdrop-filter` —— 它背后是持续动画的三维场景，
每帧重新模糊一块 880×134 的区域并不便宜。

**无音频时的自检**：加 `?viztest=1` 会用合成信号（粉噪打底 + 55/110/220Hz 基音与谐波 +
700±400Hz 扫频 + 每 4 秒一次鼓点包络）驱动频谱，并把实例挂到 `window.__spectrum`；
`scripts\生成观测探针.mjs` + `scripts\观测服务.js` 可以起一个本地服务把探针页跑起来，
让它把实测值（播放列表行数、续播落点、worker 耗时）POST 回来核对 —— 无图形环境也能拿到数字证据。
`?diag=1`（或 `localStorage.rhine-diag=1`）把播放内核挂到 `window.__audioEl` / `window.__lastLoad` /
`window.__lastSeek` / `window.__rhineViz`，用来核对"点这首有没有接上上次的位置"与渲染帧数。

**柱高本身怎么量**：无头浏览器里 `requestAnimationFrame` 在虚拟时间下会停摆、媒体也解不出码，
页内探针**测不到柱高**。这时用离线工具直接跑流水线：

```
node scripts\频谱离线观测.mjs 12
```

它直接 import `src/spectrum.ts`，用同一套合成信号跑 12 秒，打印最高/最低/平均柱高、
低频与高频的落差、相邻柱高差与逐帧抖动；开头还会自检源码里的关键常量，
参数被改过就报错退出（避免量的是旧参数）。

### 11.7 恢复旧版曲库

新版把界面从"随机端口"改成固定端口 41739，而 **IndexedDB 是按"源"隔离的**
（scheme + host + port）—— 随机端口等于每次启动都换存储域，于是旧版导入过的曲目在新版里读不到。
它们并没有丢，只是分散在几个旧源里（音频以 Blob 形式存在 IndexedDB 中）：

| 旧源 | 位置 |
| --- | --- |
| 早期独立播放器 | 当前 profile 的 `file://` 源 |
| 1.4.0 之前的终端界面 | 当前 profile 的 `http://127.0.0.1:<随机端口>` 源 |
| 更早的一份独立安装 | 另一个 profile（`%APPDATA%\music-player-desktop`）的 `file://` 源 |

恢复入口是一条命令：

```
scripts\恢复旧曲库.ps1
```

它分三步：① 恢复当前 profile 里的旧源；② 用 `--user-data-dir` 指向旧 profile 再恢复一次；
③ 回到当前 profile 把交接区吃进来。每一步都会弹框报告读了多少条、音频多少个、新增/跳过多少首。

实现要点：

- `app/recover.html` 一个页面两种模式：`?mode=read` 在旧源上把记录（字段 + 音频 Blob 字节 + 封面）交出来，
  `?mode=write` 在新版的源上写进 `rhine-music`
- `--recover-library` 会枚举 userData 下所有旧源；对每个 `http://127.0.0.1:<端口>` 源，
  临时起一个只读静态服务把页面送到那个源上（**数据只有在该源里才读得到**）
- **不往音乐目录写任何文件**：本项目对派生数据（ncm 解出 / B 站副本）有"不导出"的硬约束
  （见 [数据管控与合规](数据管控与合规.md)），跨 profile 的交接只走系统临时目录
  `%TEMP%\rhine-recover`，吃进曲库后立即删除
- 合并按"标题 + 艺术家"去重，可重复运行；**旧数据全程只读**，不改不删

### 11.4 与终端的一致性

- 所有播放器元素都在 `#stage` 内，跟随 1920×1080 基准一起缩放，
  不会出现"界面缩了、播放条没缩"
- 配色、字号、字距全部取自终端自身的令牌：纸面 `#e8e5e1`、细线 `#c1b8a7`、
  实心 `#252820 / #f0eee5`、暖色强调 `#9b7247`、橄榄 `#565c46`
- 昼 / 夜切换（播放列表右上角 `◐`）的夜态同样用终端的深色家族
- 提示条复用终端自己的 `#toast`

### 11.5 曲目信息与标签编码

界面上**不再出现档案术语**：详情区、检索弹窗、选中提示里的字段一律按播放器语义显示 ——
科室→艺术家、编目范围→时长、相关人物→专辑、权限→来源格式（对应实现见 `player.ts` 的 `toRecord()`）。
音乐库为空时也用同一套版式的占位态，不会退回旧的"档案内容"排版。

标题 / 歌手 / 专辑来自音频标签。ID3 文本帧的编码有四种（UTF-16 带 BOM、UTF-16BE、
UTF-8、以及规范上是 ISO-8859-1 但国内大量写成 GBK 的），解码按编码字节分派：

| 编码字节 | 处理 |
| --- | --- |
| 1 | 显式看 `FF FE` / `FE FF` 决定 UTF-16LE / BE（不信运行时对 `utf-16` 的默认字节序） |
| 2 | UTF-16BE |
| 3 | UTF-8 |
| 0 | 先严格试 UTF-8；不成立且高位字节占比 > 50% 时按 GB18030 解；都不是才落回 windows-1252 |

另外：

- ID3v2.2 的 3 字节帧头（`TT2` / `TP1` / `TAL` / `PIC`）也能读
- 没有 v2 标签时读文件末尾 128 字节的 ID3v1 兜底
- 内嵌封面按图片描述的实际编码跳过描述段（UTF-16 描述以 `00 00` 结尾，逐字节找会截断）
- **旧版本的乱码会被自动修回来**：早先的版本写死 UTF-8，中文标签已按乱码存进曲库；
  启动时只对"看起来就是乱码"的条目重跑一次识别（判据见 `looksBroken()`），
  修好后写回并从终端提示条告知修了几首
- 退化验证：`node scripts\ID3编码验证.js`（15 项，直接取 `player.ts` 里的函数执行）

### 11.6 已知边界

- 档案阵列一屏只有五列 × 八份 ＝ 40 个位置；曲目超过 40 首时，多出来的部分只在播放列表里可见
- 播放列表是覆盖式浮层，在详情视图里会盖住左下的 `.object-caption`
  （点面板外面、或在列表里点歌之后会自动收起，见 §11.2）
- 详情展开时，在三维阵列上点**别的**档案会切过去并退回阵列；点正在特写的那一张不算"切换"
  （那多半是想拖拽看它，保持原样）。⚠ 这一条在无头环境里判不了：无头下三维动画时间轴是停住的
  （`cameraDetail` 恒为 0、动画停在 `running@0`），详情取景根本没跑起来
- 终端的界面由主进程的本地静态服务提供，**端口固定为 41739**：界面源（`http://127.0.0.1:41739`）
  必须跨启动稳定，否则 IndexedDB 里按源隔离的曲库、收藏、播放进度会读不回来。
  端口被占用时退回随机端口，此时会写一条日志说明本次的存储域与上次不同
