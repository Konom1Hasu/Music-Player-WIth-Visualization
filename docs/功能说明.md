## 1. 曲库导入

### 1.1 导入文件

用户可以在界面左侧栏找到并点击「+ 添加」，随后在弹出的系统对话框中选择文件。这里支持一次选中多个音频文件批量加入。

支持的音频格式：

| 格式 | 说明 |
| --- | --- |
| `.mp3` | 最常见，ID3v1 / ID3v2 标签与内嵌封面均支持 |
| `.flac` | 无损，支持 Vorbis Comment 与内嵌封面 |
| `.m4a` / `.aac` | AAC 系，支持 MP4 元数据 |
| `.wav` | 支持 LIST/INFO 标签 |
| `.ogg` | Vorbis |
| `.wma` | Windows Media Audio |
| `.ape` | Monkey's Audio |
| `.ncm` | 网易云加密格式，**导入时自动解密**（见 1.4） |

### 1.2 导入文件夹

点击界面上的「添加文件夹」并选定目标目录后，程序会自动开启**递归**扫描，层层遍历该目录下包含的全部子文件夹，把所有符合格式要求的音频文件都整理出来。

### 1.3 拖拽导入

除了点击按钮，用户也可以直接从文件管理器中把音频文件或整个文件夹拖放进窗口的任意区域，程序识别后就会立即开始解析，不需要专门寻找操作入口。

### 1.35 重复曲目不再导入

为了防止曲库膨胀混乱，同一个音频文件或者同一个 B 站缓存文件夹**不会被导入两次**：

- 程序默认采用文件的完整绝对路径作为判重依据；由于浏览器的安全沙箱机制有时无法获取系统真实路径，遇到这种情况就会自动退回到以“文件名 + 体积”结合的复合规则来识别。
- 只要检查到待添加的曲目已经存在，程序在向本地数据库写入记录前就会主动忽略该条目，哪怕用户单次同时拖入两份一模一样的文件，曲库最终也只会保留一份；待全部文件扫描完毕后，界面会弹出状态反馈 `导入完成：新增 N 首，跳过重复 M 首`，如果选中的文件全部早已收录，则会显示 `这些曲目已经在曲库里了（跳过重复 M 首）`。
- 每次启动应用并读取曲库时，系统还会自动执行一次针对历史残留重复项的清理。这里的审查策略更为严格，只认“同一路径”这一项确定的物理条件，执行完成后界面会提示“已清理 N 首重复曲目”。至于多条重复记录保留哪一个，程序会按照 收藏状态 → 播放次数从高到低 → 最早导入时间 的优先级顺序进行挑选，而被合并清除的条目，它们的收藏标记与累计播放次数也会直接累加合并到保留下来的记录中。
- 由于仅依靠“文件名 + 体积”匹配可能存在同名巧合的误伤风险，这类条目不会参与启动时的自动清理逻辑，如果用户确认不需要，可以在歌曲列表里通过点击 `✕` 图标手动将其移除。

### 1.4 NCM 自动解密

网易云音乐导出的 `.ncm` 文件属于专属加密容器，本程序在导入过程中会自动完成解密还原，内部准备了两套处理路径：

1. **首选：随包的官方解密工具**（兼容全部 NCM 变体），解出来能把音频**连同完整标签（标题 / 歌手 / 专辑 / 封面）** 一块读出来。
2. **回退：内置 AES-ECB 解密**，工具不可用或被安全软件拦截时启用，按文件头魔数判断真实格式（`ID3` / `fLaC` / `OggS` 等）

整个解密还原出的原始音频流**只在内存里传递**。这一机制确保了处理全程既不会在用户的原始音乐目录下生成任何解密副本，在系统临时目录中转产生的临时数据块也会在读回内存的第一时间被数据覆盖擦写，随后彻底从磁盘中删除。程序在启动解密前会严格校验文件头部的固定容器魔数，如果检测出目标并不是真正的 NCM 格式就会直接终止解析，它不是一个拿任意文件来试解的通用解密器。

> 管控细节见 [数据管控与合规](数据管控与合规.md)。

## 2. 元数据识别

### 2.1 识别优先级

系统读取音频信息时，按照内嵌标签、同目录图片、文件名解析这三个层级依次兜底匹配。程序会优先读取音频文件内部封装的 ID3 等内嵌标签信息；如果音频文件内没有内嵌封面，系统会转去扫描音频所在的文件夹，查找 `cover.jpg`、`cover.png`、`folder.jpg` 或者与音频文件同名的外部图片文件作为歌曲封面；假如同目录中依然找不到可用图像，且歌曲标题或艺术家标签存在缺失，系统最后会尝试解析文件本身的命名格式，提取 `"歌手 - 歌名"` 等常见命名规范里的字段来补齐信息。

### 2.2 多歌手识别

遇到合唱或协作曲目时，系统会自动把以下几种常见的连接写法拆分成**多个独立歌手**，并对每位歌手分别建立索引：

| 写法 | 拆分结果 |
| --- | --- |
| `周杰伦/费玉清` | 周杰伦、费玉清 |
| `周杰伦、费玉清` | 周杰伦、费玉清 |
| `周杰伦 & 费玉清` | 周杰伦、费玉清 |
| `周杰伦 feat. 费玉清` | 周杰伦、费玉清 |
| `周杰伦 ft. 费玉清` | 周杰伦、费玉清 |
| `周杰伦; 费玉清` | 周杰伦、费玉清 |

拆分逻辑支持的常见分隔符包含 `/`、`、`、`,`、`&`、`;`、`feat.`、`ft.`、`with`、`×` 等字符。为了防止误切专有名词，解析模块内置了词组保护机制：类似 `AC/DC` 这种乐队专名、网址 URL 路径中包含的斜杠 `/`，以及像 `R&B` 这类音乐流派名称，都会被系统完整保留，不会被当作多歌手标记强行拆开。

### 2.3 重新识别

针对库内**已导入**的歌曲，用户可以在软件中一键重新执行完整的识别流程（进入设置面板 → 点击重新识别选项即可触发）。这项功能主要用于处理以下几种常见场景：

- 音频最初导入时文件名格式不够规范，用户后续在本地重新写入了完整的内嵌标签
- 系统的歌手拆分规则在版本迭代中更新，曲库需要按新规则重新拆分并建立索引
- 文件首次入库扫描时网络不稳定或文件被占用，导致封面当时读取失败

执行重新识别操作只会刷新歌曲的标签、封面等元数据文本与图像，**不会**丢失用户已标记的收藏状态、累计播放次数以及当前的音频播放进度。

## 3. 播放

### 3.1 播放模式

| 模式 | 行为 |
| --- | --- |
| 列表循环 | 播完最后一首回到第一首 |
| 顺序播放 | 播完最后一首停止 |
| 单曲循环 | 当前曲目结束后重头再播 |
| 随机播放 | 随机选曲，尽量避免连续重复 |

用户点击播放控制区域内的模式切换按钮，即可在上述四种播放模式之间按顺序循环切换。

### 3.2 下一首播放

用户在任意曲目条目上点击鼠标右键，或者在悬停弹出的操作菜单中选择「下一首播放」，系统便会将选中的歌曲直接**插入**到当前正在播放的曲目紧随其后的位置。这项操作只会调整队列顺序，完全不会覆盖或替换掉播放列表中已有的其它曲目。

### 3.3 倍速播放

系统支持在 0.5× 到 2.0× 的范围内调整播放速率。数值更改后会立即对正在播放的音频生效，并且在切换到下一首歌曲后依然持续保持这一速率设置。点击位于底部播放条上的 `1×` 按钮，倍速会在 1× → 1.25× → 1.5× → 2× → 0.75× 这一预设档位序列中循环轮替。

**变速保音调（time-stretch，指时间伸缩处理，并非简单的变采样率播放）**：这种处理方式能确保音频在 0.75× 慢速下人声不会沉闷发浑，在 1.5× 快速下语调也不会变得尖锐怪异。这两档通常是用户收听播客或有声书时使用频率最高的倍速，实际听感上的差异极为明显。系统设置面板中的 **PITCH ／ TIME-STRETCH** 一栏会明确显示底层音频引擎是否真正启用了该特性；如果系统检测到当前运行环境缺乏必要的接口支持，界面便会直接显示警告提示 `⚠ 此环境不支持`。

### 3.3.1 切歌预取（消除"按了没反应"）

当前曲目播放至接近末尾时（剩余时间约为 12 秒；如果遇到短曲目，则按照总时长的 15% 自动换算，但判断阈值下限不低于 6 秒），后台程序会**提前把下一首的音源备好**。这一机制省去了切歌瞬间读取磁盘文件并建立缓冲的时间开销，有效避免了用户手动切歌后界面出现短暂卡顿或"按了没反应"的迟滞感。

- 一旦用户手动更改播放队列（例如执行了"下一首播放"操作）或者直接切歌，先前得出的预取结果便会立即作废，系统随之重新计算下一首候选目标。
- **随机播放不预取** —— 随机算法必须在上一首播完的瞬间根据权重随机抽取下一首，提前无法预知具体曲目，因此不执行预先载入。
- 后台音频预取若发生异常或失败，并不会中断正在进行的播放，后续切歌依然会退回到正常的实时读取流程。

### 3.3.2 B 站音源走内存读取

播放器前端界面部署在本机搭建的静态 Web 服务环境中。出于跨域与安全策略限制，浏览器会主动拦截指向 `file://` 协议的本地绝对路径请求；如果直接尝试读取 B 站缓存文件，底层播放组件会抛出 MediaError 4 错误，提示「格式不支持或文件头异常」。针对这个问题，程序统一采用"将音频数据整份读入内存，再转为临时 Blob 地址"的处理路径。
这样做需要在载入每首歌曲时将数据全量读入内存，无法享受流式分段解码带来的内存开销优势；不过它能确保任意受管文件无需依赖降级重试即可一次性顺利出声。

### 3.4 进度记忆

> **★ 位置只保留一条**：系统记录的播放进度仅限定为「最后一次在听的那首 + 位置」这个单一状态元组。
> **任何一首曲目都不再各自记住自己的上次位置** —— 用户从当前歌曲切换离开后再重新切回，该曲目一律从零秒起点开始播。

这三个控制项位于系统设置 → 播放行为面板中，在初始状态下默认均处于开启状态：

| 开关 | 默认 | 打开时 | 关掉时 |
| --- | --- | --- | --- |
| REMEMBER LAST POSITION | 开 | 只记「最后一次在听的那首 + 位置」这一条，下次启动接着听 | **完全不写**，播放头与曲目位置都不落，启动也从零开始 |
| RESUME LAST TRACK | 开 | 启动时把播放条恢复到上次在听的那一首与位置 | 启动不恢复，播放条留空 |
| OPEN ARCHIVE ON PLAY | 开 | 起播时自动打开这首歌的档案详情 | 只播不跳转，停在档案阵列里 |

当用户选择「关掉记住上次位置」这一项时，系统在停用记忆特性的同时，会连带清空数据库中此前已经写入的全部历史进度，并将当前处于挂起状态的所有续播断点统一标记为失效。

除播放进度之外，系统还会自动保存一系列界面与运行状态，包括当前选中曲目、用户收藏标记、单曲累计播放次数、音量大小、播放模式、界面主题以及各项可视化渲染参数。这些数据会在下一次软件启动时自动加载并恢复。为了避免在未预期的场景下打扰用户，若软件上次退出时音频正处于播放中，重新启动后系统只会将状态恢复至暂停，绝不会自动发出声音。

### 3.5 系统设置里的其它几行

| 行 | 作用 |
| --- | --- |
| `HEADPHONE / MEDIA KEYS` | **耳机 / 媒体键自检**：左边显示注册状态，右边实时显示"最近一次按下的键被认成了什么"。有线耳机的三键线控与**接听键**走的都是媒体键通道，这一行就是用来确认"我的耳机键到底有没有被认出来" —— 详见 [快捷键 §1.5](快捷键.md)；耳机软件能改键时，接听 / 挂断可绑 `Ctrl+Alt+A` / `Ctrl+Alt+H` |
| `PITCH ／ TIME-STRETCH` | 变速是否保音调，如实显示当前取值（`✓ 已启用（保音调）` / `⚠ 此环境不支持`）—— 见 [§3.3](#33-倍速播放) |
| `ANALYSER ROUTING` | 频谱分析链路的去向。正常显示 `已接入 · 44kHz`；频谱起不来时显示 `频谱未启动` 并把**原因**写进悬浮提示 |
| `COVER ACCENT` | 强调色是否跟随封面（默认开）—— 见 [§8.1](#跟随封面强调色动态取自封面) |
| `BEAT PRE-ANALYSIS` | 是否在播放前离线分析整首（**默认关**，v2.7.7 起：新版频谱不消费节拍先验）。显示当前这首测出的 BPM 与拍点数、后台还剩几首待分析 —— 见 [§5.7](#57-节拍预分析beat-pre-analysis默认关闭) |
| `RE-READ ALL COVERS` | 一键把所有曲目的封面从本地文件重读一遍 |
| `LOCAL AUDIO COPIES` | 显示导入 B 站缓存时固化到曲库目录的音频副本占了多少盘（源缓存删掉也能播的那一份） |

**★ 旧版调音参数不再继承（v2.7.7）。** 早期版本中提供的五个调音参数（平衡、峰宽、抖动、鼓点以及峰高）
是专门服务于 1.3.0 版本自研可视化算法的遗留配置。当系统将频谱渲染架构整体迁移至 SelfMusic 引擎之后，这几个维度在新引擎的数据结构中已经没有可对应的物理意义。
因此，负责传输这套旧参数的数据通道，以及本地存储中对应的特定键名（`rhine-viz-params`、`rhine-viz-imported` 和 `mp_*`），均已伴随旧版算法代码一并彻底移除。
用户当前在界面中可以调节的，是收拢在「SELF-MUSIC VISUALIZER」配置组下面的十六枚调节滑块（具体细节请查阅 [§5.4](#54-十六枚可视化滑块设置--self-music-visualizer)）。
系统内置的默认配置方案，即完全等同于在本机上独立运行 SelfMusic 时的标准官方参数集。

## 4. 歌词

### 4.1 来源优先级

1. 与音频文件**同名**的 `.lrc`
2. 音频文件**内嵌**歌词（ID3 USLT / SYLT 帧）
3. 同目录下文件名相似度最高的 `.lrc`
4. 上级目录中的 `.lrc`

### 4.2 编码

解析歌词文本时，程序会按照 UTF-8 → UTF-8 BOM → GBK 的顺序依次尝试解码，以此避免包含中文的歌词文件出现乱码问题。

### 4.3 显示

- 歌词内容会跟随播放进度逐行向上滚动，当前正在播放的行会被高亮并放大显示
- 支持解析并展示翻译行，文本中如果包含两个时间戳完全相同的行，第二行就会被当作译文，与原文并列排版展示
- 没有匹配到可用歌词时，界面会展示占位提示文本，音频仍然会正常播放，不受任何影响

### 4.4 右侧「可视化 ⟷ 歌词」切换（2.3.0 新增）

详情区右侧的展示区域提供了两种显示形态：用于展示声音频率变化的**实时频谱**，以及按时间同步推进的**歌词滚动列表**。用户可以通过详情区顶部工具栏（位于 `TRACK` 行正下方的那一条）右侧的**分段开关**执行切换。控件把两个可选项目都绘制在了界面上（`可视化` / `歌词`），当前选中的项目会使用反白效果突出，不需要去猜测单个按钮当前的文本状态代表哪一边。执行切换动作时，系统只会替换内部视图并补发一次歌词对齐同步，**不重绘详情区**；因为全量重绘会导致解密动画重新播放一遍，底层的频谱处理实例也会被销毁并重建。分段开关的选择状态会在软件重启后保留，如果本地存储中读出了无法识别的脏值，系统会自动回落到"可视化"状态。

歌词列表会依照音频的时间长度逐行展开排版：

- 滚动容器的顶部与底部两端都叠加了渐隐遮罩层，利用边缘淡出的视觉效果营造出内容从深处升起的层次感
- 针对当前唱到的行，界面应用了**三重高光**样式进行强调：文字字号从普通行的 16px 加粗放大至高亮行的 **22px**，文字颜色替换为前景深色，并且在左侧边缘绘制一道 **3px** 宽的竖线；如果单纯依靠改变颜色，在投影仪或低对比度屏幕上往往难以分辨，只有配合足够明显的字号放大，用户扫视一眼才能立刻确认播放位置
- 视图滚动采用基于位移合成的处理方式，配合 0.42 秒的过渡动效平滑位移，其定位目标是**让当前行精准停留在可视区域的垂直中线上**
- **点某一行 = 跳到那一句**，但在点击跳转后**刻意不自动起播**。这是因为用户可能只是在翻阅浏览歌词内容，突然自动发声可能会打扰到用户；如果确认需要收听，用户可以再去点击播放控制条，刚才的点击跳转已经把音频播放进度精准重置到了对应那句的开头位置
- 针对行点击跳转行为增加了一道**闸门**校验逻辑：系统只有在确认"详情区当前展示的曲目确实是正在播放的这一首"时，才会真正去修改播放进度；如果不加这道限制，点击操作就会直接把**正在播的那首**的进度强行拖拽改道

> **★ 详情区展示的曲目 ≠ 正在播的曲目。** 详情区展示的内容代表"当前被用户点击打开查看的那一首"，它与当前后台正在发声播放的曲目可以互不相同。
> 歌词界面的滚动同步以及点击行跳转的判定，全部都必须以"展示的那首"作为准则，否则就会出现"界面打开了曲目 A 却错误看到曲目 B 歌词"的混乱情况。
> 见 [维护指南](维护指南.md)。

## 5. 频谱可视化

位于详情区右侧的频谱模块，目前**完整迁移了 SelfMusic（桌面端）的技术实现**。从最底层的核心算法、运行时的实时取数路径，直到最终的画面绘制外观，这三层架构均严格对齐了桌面端的逻辑，并且在逐位数值与逐条渲染指令上完成了比对验证（详见 [§5.8](#58-性能与时延) 罗列的校验清单）。下文将循序渐进，按照“数据如何获取与准备 → 画面如何渲染 → 提供了哪些可调参数 → 结果如何验证”的逻辑依次展开。

### 5.1 为什么不用 `AnalyserNode` 的标准频段

Web Audio API 原生提供的 `getByteFrequencyData` 接口输出的是**等宽线性**频段。然而在绝大多数音乐中，声音能量几乎都集中在中低音频区间，高频能量相对较弱。如果直接使用线性频段绘制，画面往往呈现为左侧少数几根柱体剧烈跳动，而右侧大半区域处于无波动的静止状态。为了解决分布失衡的问题，整个管线改为自行提取原始的时域样本进行运算：
核心分析引擎每次截取 **4096 点**的音频窗，按照人耳听觉特性的对数刻度划分为 **96 段**频带。此时 `AnalyserNode` 仅仅作为“获取离散时域采样点”的数据入口
（配置 `fftSize = 4096`，通过 `getFloatTimeDomainData` 读出数据），后续所有频段划分与视觉呈现逻辑全部由本系统独立处理。

### 5.2 处理链路

在切歌操作触发后，系统首先**将整首音频解码为保持其原生采样率的单声道 PCM 样本**。播放期间，主循环以 16ms 为固定步长执行分析：
平滑位置时钟实时推算播放头当前行进的准确位置 → 从该位置向后截取 4096 点的**前视窗**音频切片（超出音频末尾的数据通过补零填充）→
分析引擎依据 96 段对数频带算出实时柱高、峰值顶盖位置以及四路音色活跃度数值 → 结果直接传递给绘制层完成上屏。

| 环节 | 关键点 |
| --- | --- |
| 整曲解码 | 维持源音频的原生采样率（先解析 mp3 / flac / wav / mp4 / ogg 的文件头元数据），使用 `OfflineAudioContext(1,1,原生率)` 进行恒等解码；如果源文件是单声道则直接读取，如果是双声道立体声则在 int16 数值域内计算左右通道的均值 |
| 平滑时钟 | 底层播放器回报的时间位置大约每隔 52ms 才会更新跳变一次，若直接基于该时间取窗，会导致连续数帧取到相同音频片段后又突然跳步；因此改为结合每帧的真实物理流逝时间自行累加递增（单帧最大推移限制为 +0.10s），当平滑时间与播放器时间偏差在 60ms 内时按照 5% 的速率缓慢拉回，遇到起播、拖动进度条或切歌等跳变超过 250ms 的场景时则直接硬对齐 |
| 折算了真实帧间隔 | 每次刷新都将两帧之间的实际时间差折算并传递给引擎（数值强行限制在 8~60ms 之间）—— 因为引擎内部诸如“每帧柱体衰减量”这一类系数都是按照 20ms 的基准间隔标定的，实际渲染步长一旦发生浮动，就必须换算为等速衰减 |
| 取窗 | 每次截取的采样区间为 `[当前位置, 当前位置+4096)`，超出音频总长度的部分补零（这属于**前视窗**机制，读取的是当前播放点之后的声音，而不是“最近已经播放的 4096 个样本”） |
| 回退 | 遇到音频时长超过 15 分钟、文件体积大于 120MB 或解码环节抛出异常等情况时 → 系统自动降级切换至分析“最近一窗”的实时流式路径，渲染视觉效果略有差异，但能确保画面不会呈现空白状态 |

### 5.3 关键参数

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 分析窗长 | 4096 点 | 与 SelfMusic 桌面端中的 `SpectrumAnalyzer(fft_size=4096)` 设定完全一致 |
| 频段数 | 96 | 采用对数分带算法，屏幕上最终对应渲染为 96 根独立的柱体（**不再经过额外的二次重采样**） |
| 分析节拍 | 16ms | 步长对齐 SelfMusic 内部采用的 `QTimer` 定时周期；浏览器底层的 rAF 循环只单独承担重绘职责 |
| 柱几何 | 贴底、宽 = 槽位 × 0.70、左右留白 6px | 布局规则严格还原 `visualizer.py` 中 `paintEvent` 的排布逻辑 |
| 柱不透明度 | `α = 0.45 + 0.55 × 柱高` | 透明度按照柱身高度**逐柱动态映射**，不采用固定的台阶式分级 |
| 渐变 | 0 / 45% / 100% 三处停点 | 从亮色过渡到主色，再延伸至底色（色彩数值由当前设备加载的界面主题决定） |
| 峰值顶盖 | 峰值 > 0.004 才画 | 单条顶盖厚度为 2px，悬浮于峰值点上方 3px 处，不透明度固定为 α 0.85 |
| 音色指示条 | 左上角四条（鼓 / 低音 / 人声 / 镲） | 几何结构定义为 `label_w / 条长 / 条厚 / 间距 = 30 / 38 / 5 / 10`，整体渲染起点坐标定在 (8, 6) |

桌面端最初给出的绝对像素尺寸均基于标准 CSS px 计算。在本工程绘制时，为了适配多端缩放，所有坐标与长宽都会先乘以**画布比例系数**（即 `canvas.width / clientWidth`）。
正因为进行了比例转换，柱体与间距无论是在详情页的窄面板中，还是在全屏展现的宽面板中，其几何比例都能保持一致。

### 5.4 十六枚可视化滑块（设置 → SELF-MUSIC VISUALIZER）

为了便于精细控制画面表现，频谱引擎层的 16 个核心配置项全部封装为了可视化滑块。用户拖动任一滑块都会立即刷新当前画面，并同步持久化到 `localStorage['rhine-sm-display']`（以版本标识为 2 的格式 `{ v: 2, values: {…} }` 写入缓存）；如果想要重置，点击 RESET 按钮即可恢复初始状态。需要说明的是，**系统默认提供的这一套数值完全还原自当前机器上运行的 SelfMusic 实际效果**，并非组件库出厂时的原始模板参数：具体配置包括顺滑 0、软膝 95、细纹 0、左塔泵动 60、弹性 300、右细节 80、右丰 100、陡峭 114、倾斜 39、音色 93、毛刺 16、尖塔 100、低频高耸 110、回落 95、谷深 100 以及开启静音呼吸。

> 从 v2.7.8 版本开始，本地存储数据全面升级为 v2 格式，并附带**一次性自动迁移**机制：系统在启动时若检测到 v2.7.5 时期写入的旧版纯对象存档，会自动完成版本替换 ——
> 程序不会沿用过去的旧版键值，而是直接覆盖为当前这套实测配置并重新落盘；如果该设备之前从未产生过存档，则仅加载内置默认参数，不向本地写入冗余字段。

**调参过程保证实时反馈**：当设置面板的滚动位置进入该参数组所在的显示区域时，系统会自动执行避让动画 —— 弹窗的背景模糊滤镜与半透明底色均被移除，
面板整体向左侧平移紧贴屏幕边缘，使得处于详情页右侧的频谱**毫无遮挡、完整呈现**在视野中；一旦用户将面板滚离当前参数区或者直接将其关闭，界面就会重新复原。
该交互具有 0.3s 的平滑补间过渡，而且全部属于自动化行为，用户在拖动滑块调节数值的过程中，滑块控件自身不会发生任何位移跳动。

以下两项参数的调节逻辑容易被误解（面板说明文字中也对此作了特别注解）：

- **回落**参数代表“当前数值向目标高度逼近的更新比例”——**参数设定得越大，柱体追随音频变化的速度越快、整体视觉表现越富有弹性**，而不是数值越大下落越缓慢
- **尖塔**数值大于 1 时表示执行**平台削离逻辑**（算法负责将相邻粘连成一片的平顶高台拆散为多根相互独立的突起尖峰），而不是把频谱能量在垂直方向上整体向上抬升

### 5.5 峰值顶盖与四路音色指示条

- **峰值顶盖**：算法会为每根柱体计算其触及的历史最高位置，并在该点上方独立绘制一条厚度为 2px 的短横线（固定透明度 α 0.85）。这个标记承载的是**峰值保持**逻辑 ——
当瞬态音频过后柱体迅速下落时，横线仍然会悬停在半空并以相对缓慢的步长逐步向下跌落。因此在画面高频波动时，顶部会出现多条脱离柱身悬空漂浮的细线，这种表现完全符合桌面端原版的预期设计。
- **四路音色指示条**（位于画面左上角）：实时呈现 `鼓 / 低音 / 人声 / 镲` 这四组频段的活跃程度，取值范围规范在 0~1 之间，数据直接读取自引擎暴露的
  `last_timbre` 变量（即内部 `_timbre_activity` 函数的输出值）。哪一类乐器在当前节拍中占主导地位，指示条的涨落能够直观反映；
  当检测到某一路频段的活跃度降为 0 时，界面上只保留底层的灰色背景槽，不再绘制彩色填充段。

### 5.6 回落与静音

- 当外部输入信号中断停止后，所有的柱身高度与顶部峰值横线会按照每帧乘算 0.9 的递减系数逐步收缩归零。直到所有柱体高度完全归为零值之后，渲染驱动循环就会主动将帧率下调至大约 15fps，仅仅维持必要的基础状态维护与淡出动画刷新。
- **静音呼吸**（由控制面板中的「静音呼吸」滑块管理）：在无声音输入的空白静音段内，使各根柱体产生幅度极微弱的波浪式起伏起落。该功能默认处于启用状态（数值对齐 SelfMusic 实测参数）。
- 在触发切歌的瞬间，系统会立即强行重置清空当前渲染画布，以防上一首曲目尚未衰减完毕的残留频谱平滑过渡蔓延到新音频上。

### 5.7 节拍预分析（BEAT PRE-ANALYSIS，默认关闭）

该机制的作用是在音频正式播放之前，预先在后台将整首曲目以离线方式完整解析一遍（流程为转码为 8kHz 单声道，随后送入 16 段 Goertzel 算法进行特征提取），计算出整曲的时间节拍网格与响度包络数据并保存在缓存中。
该模块最早建立的目的是配合**上一代旧算法**工作（用于支撑踩点预判逻辑，例如在鼓点抵达前提前 28ms 触发高亮渲染、每隔 4 个节拍切换一次柱体形态、以及在副歌爆发前提前预热动画）——
但是本版本引入的 SelfMusic 属于波形逐位还原算法，坚决不依赖任何主观预设的前置修饰机制，上述三套基于预判的联动特性在当前架构下均已失去应用场景，
因此这一分析流程**在默认状态下被置为关闭**（若手动开启，其唯一的行为仅是在后台静默执行离线特征提取并将结果填入缓存）。

> 这一项的开关与监控信息仍然完整保留在系统设置界面中：能够直接看到系统当前解析出的 BPM 估算值、检测出的节拍点总量、后台队列中尚待扫描的曲目数量，
> 以及用来启闭该机制的控制开关。后台分析算法及其对应的测试套件（`scripts\节拍预分析验证.mjs`）代码均予以保留，用户如果有二次开发或验证需求可自行启用。

### 5.8 性能与时延

- 频谱引擎单次执行完整的数学运算（即从 4096 点时域信号解算为 96 段对数柱高）是在主线程进行的，完成一帧的消耗大约仅有几毫秒；数据分析以恒定的 16ms 为节拍循环调度，依赖独立构建的
  高精度定时器保持节拍（如果直接挂载到浏览器的 rAF 上，原本 16ms 的期望周期就会被屏幕 16.7ms 的原生步长强制离散拉长至 33ms，导致分析速率降低）。
- **界面实际绘制工作完全绑定 rAF 保持全帧率输出**，画布上呈现的柱高精确映射引擎每一帧的瞬时计算值（绘制管线在前后两帧之间**不进行任何线性插值** —— 这一设计与原版逐帧硬刷新的实现方式完全一致）。
- 底部主播放进度条包含的 52 格电平刻度指示，其刷新节拍与主渲染管线保持同步；音频一旦进入暂停状态，全系统绘制帧率即刻收拢降低到 15fps。
- 当系统检测到主窗口处于隐藏、最小化或被其他应用完全遮蔽时，将彻底中断并挂起渲染驱动循环；在弹出轻量级迷你播放窗口时，迷你窗会直接订阅并复用主窗口算好的柱体数组，不会开启二次运算。
- **构建的三层一致性校验**（每当对相关模块做出改动时，测试必须全部通过方可合并）：
  1. 核心引擎对拍测试：建立 Node 运行环境下的 `selfmusic-spectrum.ts` 与 Python 权威参考基准 `musicapp/selfmusic.py` 之间的自动化对比，
     在中性档、实测档以及全范围参数扫描三种典型场景下，分别对连续 1000 帧 × 96 根柱体的 heights 与 peaks 两项数据集进行逐位数值比对，确保完全一致。
  2. 运行时数据路径对拍：向两个环境输入相同的单声道 PCM 序列与完全同构的 (位置, 帧间隔) 模拟调用序列，连续比对 400 帧数据，heights 与 peaks 两个通道的最大绝对差值满足 max|Δ| = 1.8e-07。
  3. **视图渲染层对拍**：执行自动化检查脚本 `node scripts\频谱离线观测.mjs` —— 脚本直接分析 `visualizer.py` 的**源代码文本**提取出全部几何常数与变换方程，
首先将绘制层实际派发出的各类底层 Canvas 指令与原生实现进行一一对照，随后逐一校准 96 根柱体的顶部位置、底部基线、悬空顶盖坐标以及左上角的四路指示条渲染参数。

### 5.9 帧率：频谱的帧率 = 三维场景的帧率

频谱的可视化画布与背景中的三维唱片档案网格注册在**同一条底层的渲染调度队列**中。这种架构决定了“一旦三维场景由于负载过重跌落到 30fps，频谱模块的重绘上限同样只能被锁在 30fps”。如果用户在交互中观察到频谱有明显的顿挫感或视觉延迟，应当优先排查三维渲染模块是否存在性能瓶颈，而不应盲目去改动音频引擎的分析采样参数。

为此系统内置了两项应对策略：

1. **设置面板中实时显示检测帧率**：打开系统设置并定位到 `RENDER QUALITY` 参数区，其摘要信息行会明确打印出应用当前运行的实际画布分辨率、抗锯齿方案类型、纹理采样乘数以及当前测得的实时物理帧率；当帧率偏低时，界面会动态弹出提示建议“把上面的预设调到「性能」能明显改善”。
2. **帧率偏低触发自动降级兜底**（该机制仅执行一次，且前提是用户从未在该设备上手动调整过画质档位）：若监控到场景运行的中位数帧率 `< 50`，且配置项仍处于标准预设分类下 → 系统将遵循 `极高 → 高 → 原始 → 性能` 的顺序自动向下跌落一级，调整完成后自动保存配置到本地磁盘，并弹出 Toast 提示告知用户降级缘由以及手动恢复的路径；若当前系统已经处于最低档位，则仅发送一次告警提示，不再进行档位变动。
3. **播放状态下移除手动节流门控**（更新于 2026-10-08）：播放过程中的渲染调度直接接入 rAF，跑满当前显示器支持的物理刷新率。旧版本曾在播放主循环内人为限制了一道 15ms 的防抖门槛，该策略在 60Hz 屏幕上运行时由于步长重叠恰好能够正常放行，但在电竞高刷新率显示屏上（例如 165Hz 面板，rAF 循环间隔大约仅有 6ms），该逻辑会导致“每三帧动画只能放行绘制一帧”，实测造成有效刷新率被腰斩。现在仅在音频暂停后才主动降速到大约 15fps（由于柱体与顶盖的回落淡出动画需要保持完整更新，因此不能直接终止循环）。

此外，管线顺带精简掉了高频的样式属性重算开销。详情展示页面涉及的图层不透明度以及平移变换位移等字段，重构为了**仅当数值发生实际改变时才执行写入**的机制，不再在每一帧强制将整片 DOM 树标记为需要重排重绘的脏节点。

### 5.10 GPU 选型与低画质档的精度修正（2026-10-04）

**★ 经排查确认，本程序在此前的版本中始终被系统调度在集成显卡上运行。** 原有工程逻辑曾试图通过启动参数强制指定“调用直连主屏幕的集成 GPU 以节省功耗”，然而该命令行参数在 Windows 平台对应的 Chromium 内核构建中实际并未被实现。这段参数注入没有产生预期效果，导致应用在双显卡设备上被操作系统自动回退并全部分配到了核显环境。目前的架构调整为默认主动向系统申请高性能独立 GPU。对于希望降低整机功耗、切回集成显卡的用户，系统提供了两种配置途径：一是在启动命令行中追加 `--low-power-gpu` 启动标志，二是在配置文件 `settings.json` 中直接把 `preferDiscreteGpu` 属性的值设定为 `false`。

该调度问题直接影响了此前用户反馈的“档案唱片纹理模糊”故障。在常见的“Intel 核显 + 独立显卡”的高清高刷笔记本配置中（例如典型的 2560×1600@165Hz 屏幕），集成显卡在主线程高频刷新下很难独立稳定支撑三维档案的着色开销，进而极易命中 §5.9 阐述的性能保护策略，导致画质被自动级联调低至「性能」预设档；雪上加霜的是，旧版「性能」档在开启 150% 缩放比例的屏幕上，最终生成的渲染缓冲区有效像素仅仅相当于全屏目标分辨率的一半稍多，致使那些低对比度的细节线条在降采样后变得模糊难辨。针对这一痛点，本版特别针对「性能」预设档补充了三项对渲染帧率几乎无额外开销的精度修正配置，其余较高画质档位则继续保持其原有的基准参数不变。

| 参数 | 原值 | 新值 | 理由 |
| --- | --- | --- | --- |
| 抗锯齿 | 关 | SMAA | 由于三维唱片档案采用离屏缓冲机制完成合成渲染，旧版本在该管线内完全关闭了抗锯齿算法，导致纹理刻线和卡片边缘在缩放旋转时产生的走样边缘表现为肉眼可见的“模糊” |
| 磨砂盖板透光 | 0.5 | 0.75 | 盖板材质的核心视觉是采样当前屏幕帧缓冲来计算光线折射的，当底层帧缓冲降级到半分辨率之后，由于采样基数不足，被盖板遮挡的图章图案自然会变得松散偏软 |
| 各向异性过滤 | 4 | 16 | 三维场景中的卡片大多以倾斜视角呈现在视口中，各向异性过滤算法能够显著提升斜视方向上高频贴图的采样锐度，且现代图形芯片在处理该功能时的性能开销极低 |

用户本地已经保存的画质设置项会自动平滑迁移至全新的参数规范体系下：只要本地存储的数据与过去的某套旧预设完全一致，系统就会自动将该记录按照**预设档位名称**映射转换为对应的新版结构，这样既维持了用户当初设定画质档位的真实初衷，又能让界面享受到上述精细度修正带来的画面改善；而对于用户曾经深度调整过的自定义参数组合，系统则予以原样继承保留，杜绝强制重置或误改用户偏好。

## 7. 媒体键与耳机线控

### 7.1 双通道

Windows 系统处理媒体键信号时，底层提供了两条相互独立的接收路径：

1. **系统媒体会话（SMTC）** — 即 Windows 系统媒体传输控制，系统媒体控制面板以及部分蓝牙耳机的播放控制指令主要走这条通道。
2. **全局热键（Win32 RegisterHotKey）** — 传统的系统全局热键接口，键盘上自带的多媒体按键与多数有线耳机的线控信号走这条通道。

程序在启动时会同时向这两条通道注册监听。只要用户触发的操作命中了其中任意一条路径，控制指令就能正常生效。

### 7.2 幂等注册

系统底层的热键注册接口存在一个特性：如果传入的按键已经被当前进程**已经注册过**，接口并不会忽略，而是会直接返回失败错误。早先版本设计了定时重试机制，这种失败返回会导致程序把原本正常的健康状态误判成「被占用」，进而向界面错误展示快捷键不可用。现在的逻辑调整为了**幂等**操作，也就是多次执行也能保持结果一致：程序在调用注册接口前，会先查询目标按键的注册状态；确认已经在当前进程名下的按键，就会直接跳过重复注册流程。

### 7.3 自检

用户可以在设置面板中的「媒体键」一行查看当前的按键注册状态：

| 显示 | 含义 | 处理 |
| --- | --- | --- |
| `✓ 已注册` | 全部成功 | 无需处理 |
| `⚠ 被占用` | 部分成功 | 关闭冲突程序，或用应用内快捷键 |
| `✕ 全部被占用` | 全部失败 | 同上 |

媒体键在 Windows 系统中属于**独占**资源，同一时刻只能被系统里的一个程序成功注册，无法由多个软件共享。

### 7.4 防抖

程序为所有接收到的按键事件专门加入了 300 毫秒的时间防抖限制。这样处理是为了防止某些耳机硬件在用户单击按键时连续发送多次硬件事件，导致「播放→暂停」状态在瞬间连续切换并相互抵消，最终在用户看来表现成按了按键却没有产生任何反应。

> 在整个开屏动画播放期间，用户只要按下键盘上的 `ENTER` 或 `ESC` 键，或者直接用鼠标点击右上角的 `ENTER SYSTEM ↗` 按钮，就可以直接绕过剩余画面进入系统，完全不必等待时间轴播放完毕。
>
> **时长**：为了保证视觉体验，系统在开机阶段**不压倍速**播放动画，策略改为**从片子的后半段进**。采用该方案后，遮盖底层界面的遮罩层会在系统启动后约 6.7 秒完全淡出并清零；
> 原片前半段的内容会被直接跳过，画面直接从鉴权打字效果切入，依次展示扫描环旋转、黑色底板掠过、全屏白场，最后停留在档案阵列上。
> 整个开场动画到用户能够自由操作界面的总时长大约为 19.8 秒。由于后半程只是镜头在档案阵列上持续推进，这段时间里已经没有任何遮挡层覆盖界面，不会影响界面的渲染展示。

#### 莱茵生命（仪器面板变体）

配色方案直接提取自开源项目 [RhineLabUI](https://github.com/LBEILC/RhineLabUI)（基于明日方舟 · 莱茵生命设计风格，采用 MIT 协议开源，界面前端源码与 Blender 资产工程作者为 B 站 UP 主 **@路北路陈**）所定义的暗色面板设计规范：

（另用 panel #202a2f / field #2a363b / 暖棕悬停 #9b7247）
```

这套主题与系统内另外三套默认主题的差异**不只在换色，还在材质**与排版质感的全方位重构：

| 做法 | 说明 |
| --- | --- |
| **1px 实心细线** | 卡片描边直接用分隔线色，不再是半透明描边 |
| **构件直角** | 按钮、pill、列表项、封面、可视化区一律直角无圆角；只有大面板留 2px 免得割裂 |

> **刻意保留圆形的**：播放键、收藏键、圆形滑钮。圆形控件在人机交互中具有强烈的“可点击”视觉心理暗示，
> 加上此前在产品定义时明确要求过暂停键不能设计成锋利的方形 —— 此处的几何形态差异属于有意为之的混搭设计，并不是遗漏了样式修改。

#### 跟随封面（强调色动态取自封面）

当用户处于主界面（即挂载 `app-rhine` 样式类的那套终端视图）时，系统的强调色**默认从当前封面里取**。此时诸如歌曲列表中选中项的左侧指示竖条、各种滑槽填充区、进度条把手以及外层卡片描边等原本呈现琥珀色的组件，颜色都会随着当前播放的专辑封面实时变动。

色彩提取的底层逻辑是先将大尺寸的封面图片压缩到极小的分辨率后再开始像素采样，算法会结合饱和度与明度双重指标进行加权计算，筛选出既明亮又稳重的基准色。为了防止封面相邻区域的像素跳变造成每一帧的颜色剧烈闪烁，系统会对**色相相近**的候选像素执行一轮聚类平均算法，最后还会根据当前处于深色还是浅色主题来动态纠正色彩明度，确保前景部件与底板之间始终保留充足的对比度。

边界处理：

| 情况 | 行为 |
| --- | --- |
| 没有封面 | 去掉内联变量，**回落主题默认色** |
| 封面是灰度图 / 采不出合格颜色 | 同上，回落默认（不会变成脏色） |
| 封面没变 | 指纹判重，不重复采样 |
| 深浅主题切换 | 按新底色**重算**明度修正 |
| 不想要 | 设置面板 → **COVER ACCENT** 关掉（默认开，关一次就记住） |

### 8.2 图标

## 9. B 站缓存提取

这项功能用来解析并播放**用户本机已经下载完成**的 B 站音频文件。功能入口设在**播放条上的电视图标**，位置就在 `＋` 图标的右侧。

### 9.1 流程

1. 点击播放条上的电视图标后，程序会唤起操作系统的原生文件夹选择窗口，由用户手动**选中 B 站缓存文件夹**。
   ```
   手机端：<内部存储>\Android\data\tv.danmaku.bili\download\<av 或 ep 号>\<cid>\
   电脑端：<你设置的下载目录>\<标题>\…        （默认常在 Videos\bilibili\）
   ```选定目标目录后，程序会以此为根节点向下递归遍历（遍历深度最多限制为 7 层），并在扫描过程中自动匹配和识别符合格式的缓存条目。
2. 解析并读取缓存目录中记录的元数据，提取出视频标题、UP 主昵称以及封面图片地址。
3. **程序完全依赖文件内部的容器与媒体数据判断音频轨，不根据文件名推测**：只要能解析出内部封装的轨道格式，就直接按音频轨提取；只有在封装格式无法确认内容类型时，才会回退到以文件扩展名作为保底判定依据。当同一集视频中存在多个不同清晰度的音频流时，提取逻辑会自动选取规格最高的一档。
4. 程序会把提取出的 `.m4s` 缓存流转换成标准音频文件（剥离 B 站写入的自定义文件头与偏移量），接着**完整拷贝并固化一份到专用的曲库目录**（`userData\library\audio\`）。这样可以彻底切断播放逻辑对客户端源缓存路径的依赖，实现两者完全解耦。
5. 填充并关联对应的标题、歌手（即 UP 主）与封面图等信息，最后将生成的标准曲目写入曲库数据库。

> 界面提示语已经过修正：执行到这一步时，程序**不会在后台自动盲测搜索**缓存路径，而是直接弹出文件选择窗口等待用户选取。
> 当前明确的引导提示为"请选择 B 站缓存文件夹（含 entry.json 或 audio.m4s）"；
> 如果所选路径下没有合规内容，系统则会提示"这个文件夹里没有识别到 B 站缓存"。

### 9.2 说明

- 本功能只读写并处理**用户本机已经存在**的本地缓存，执行过程中绝不修改、覆盖或删除 B 站原本的缓存结构，也不会向远端服务器发起任何音频下载请求。唯一的网络访问仅仅是按照缓存元数据中记录的 URL 将封面图片拉取到本地缓存，且该动作仅针对静态图片。
- **音频流与源缓存目录完全解耦**：导入扫描阶段就会将转换好的音频副本直接落盘到曲库目录。系统检索可用音源时执行严格的降级顺序：
  **固化副本 → 会话副本（从源缓存实时转换生成的临时流）→ 原始缓存文件本身**。正是因为这套分级回退机制，即使用户后续在客户端中清理了下载内容或移动了源文件夹，曲库里的歌曲**依然能够正常发声播放**。当这三层音源全都不复存在时，界面的错误提示会直接明确指出故障根因（例如输出"原始文件不存在（可能已在 B 站缓存里被删除）：C:\\...\\audio.m4s"），彻底避免了界面没有任何反馈的静默失败。
- 曲库数据库中现在记录的是指向固化副本的**长效持久化路径**，而原始缓存路径仅作为溯源线索保留，用于"源文件仍健在时按需重新生成副本"。过去的设计错误地将扫描期间生成的会话临时路径写入了持久层，导致应用进程一旦重启该临时路径就会失效，进而引发了"报错后播放进度和错误提示一个字节都不变"的问题。
- 播放列表中对音频来源进行了真实、明确的状态标注：包含 `B 站缓存 · 已存本地`（表示已生成固化副本）、`B 站缓存`（表示固化未完成，仍依赖原始缓存）；
如果标记为 `音源缺失`，则代表源文件已被移除且曲库内无可用副本，该音频已经无法发声，系统不会再将其伪装成可用歌曲展示给用户。
- 针对早期旧版本导入的历史数据，部分曲目数据库中可能仅记录了源文件路径而缺失本地副本。系统在初次点播该曲目时会自动补充固化；用户也可以打开设置面板，找到 `LOCAL AUDIO COPIES` 配置项并点击「补齐未固化的」按钮，执行批量扫描与一键修复。
- 如果在播放阶段遇到了损坏或丢失错误，播放内核会尝试自愈流程：依次触发强制重新生成固化副本、重新分配会话临时流、回退使用本地保留副本，并在处理期间向界面输出"正在重建可播放副本…"的提示状态。

### 9.3 数据管控

从 B 站客户端缓存转换生成的音频文件在架构上被定义为**派生数据**，因此必须遵循以下治理规则：

- **供即时播放使用的会话级临时副本**只允许写入操作系统的全局临时目录，当应用退出或进程注销时立即全量抹除。这部分临时文件的丢失对日常使用没有任何负面影响：
对于**已固化**的曲目，程序直接读取曲库目录下的长效副本；对于**没固化**的历史条目，用户点击哪一首，系统就按需单曲转换哪一首（满足幂等性约束），避免在每次应用冷启动时对全曲库执行繁重无意义的重新生成。
- **作为特例设计，导入的 B 站缓存**强制在专有曲库目录中沉淀一份固化数据。由于 B 站客户端默认将内容存放在用户目录下的 `Videos\bilibili`，极其容易被外部软件清理策略或用户的手动维护动作删改；如果不执行内部固化，播放器的可用性就会严重受制于一个外部不可控的目录权限。
这部分固化音频与临时缓存相同，仅存放于当前设备存储中，不提供外部导出选项，严禁上传至云端网络，同时**播放器内部的所有自动清理逻辑都不会将其删除**。
- 固化文件写入磁盘后，必须立即执行**文件内容头校验**。一旦检测到底层写入被意外截断（文件残缺）或磁盘空间预分配导致的纯 0 字节损坏文件，读取接口会无条件拒绝交付。系统会直接报错并打印原因，绝不允许向曲库索引注入不可播放的无效引用。
- 提取任务每执行一次，安全审计模块都会在本地记录对应的审计事件日志，包含解析的来源绝对路径以及转换后的产物体积。

> 完整的管控策略与合规实现方式，请参考 [数据管控与合规](数据管控与合规.md)。

## 10. 封面 3D 档案

界面在封面区域上方叠加了一个支持鼠标拖拽旋转的 3D「档案」展示层，同时将**拆解 / 重组**开发成可以实时操作的交互动作。

### 10.0 先说清楚：`.blend` 不能直接用，用的是它的导出件

代码仓库中虽然同时保留了 Blender 源工程以及两个导出好的模型文件，但前端运行环境没有直接解析 `.blend` 文件的能力。程序在实际执行时加载的全是导出件，也就是呈现完整闭合状态的单体档案（作为默认展示视角），以及带有 22 个部件标签节点的拆解件。运行程序的机器如果没有预先安装 Blender 软件，就无法执行重新导出或者精简模型面数的操作，直接读取现成的导出文件是当前环境下唯一能够跑通的做法。

### 10.1 拆解 / 重组

当用户点击封面左下角的「**拆解**」按钮后，档案模型会沿着 Z 轴方向分层拉开距离，逐步呈现出原本包裹在内部的六个部件；再次点击「**重组**」按钮，所有分散的部件会重新拼合收拢。「复位」按钮则负责在模型复原的同时，把当前的旋转角度彻底重置归零。

| 部件 | 英文 | 分层位置 |
| --- | --- | --- |
| 紧固件 | FASTENERS | 2.75 |
| 透明盖板 | OPTICAL COVER | 1.85 |
| 折射环组 | REFRACTIVE RINGS | 0.75 |
| 光学核心 | OPTICAL CORE | −0.15 |
| 信息基板 | SUBSTRATE | −1.10 |
| 背板与框架 | CARRIER | −2.05 |

整个拆解动画利用**阻尼跟随**算法计算每一帧的位移，平滑地滑动到预设的目标层距，而不是突兀地瞬间切换位置。在这个过程中，两个模型在场景里必须**共用同一个中心偏移**参数，统一根据单体模型的轴对齐包围盒来进行居中定位。如果放任两个模型各自计算几何中心，部件在发生拆解替换的瞬间就会产生整体性的视觉错位。界面在装配完成状态下渲染单体模型，需要拆散时则无缝替换为拆解件，因为两者在完全闭合的零点状态下外形严丝合缝，切换模型资源的过程在视觉上察觉不到破绽。

### 10.2 与播放状态联动

模型的自转角速度会实时跟随播放器的播放状态改变：**处于播放状态时维持正常转速（0.30 rad/s），进入暂停状态时转速大幅降到接近停滞（0.05）**。数值变化全程采用阻尼平滑过渡，防止用户按下暂停键时画面出现生硬的顿挫与跳帧。这种联动机制让 3D 动画与音乐播放流程建立起直观的上下文关联，不再只是脱离状态自顾自地旋转。

### 10.3 默认开启策略

该功能在**莱茵生命主题下默认开启**，因为这套主题的设计初衷就是把封面呈现为那卷特定的档案；在其它主题环境下则保持默认关闭状态。一旦用户在界面上手动关闭过一次该组件，程序就会**永远尊重用户的选择**并记住该状态，后续绝对不再擅自自动打开。

### 10.4 为什么必须考虑性能

引入该模块意味着要在封面容器中额外建立一个独立的 WebGL 上下文，而底层的音频频谱可视化模块已经占据了一部分 GPU 资源。在集成显卡等性能受限的硬件上，团队曾花费大量精力平衡绘制负载（详见 [架构说明](架构说明.md)），因此实现中采取了以下针对性的限制措施：

| 措施 | 说明 |
| --- | --- |
| 按需加载 | 三维库 + 加载器 + 两个模型共约 7.4 MB，**只有开启时才注入**，不开启一行都不加载 |
| 启动延迟 | 若上次是开启状态，等首屏渲染完 1.5 秒再加载，避免抢启动带宽 |
| 限帧 30fps | 内部按 1/30 秒累积后才渲染；转得慢，看不出差别 |
| 窗口隐藏即停 | 最小化 / 隐藏时直接跳过绘制 |
| 像素比封顶 1.5 | 与可视化那边一致，不在核显上按 2 倍渲染 |
| 取景只做一次 | 按**单体**包围盒定相机（1.72 倍留白吃掉拆解的增量），拆解途中不重新取景，否则镜头自己缩放会晕 |
| 失败自关 | WebGL 不可用 / 模型读不到 / 脚本加载失败 → 提示一次并自动关闭，封面回 2D |

### 10.5 渲染与素材要点

- **透明底叠加**：渲染画布的背景清除色设为完全透明，不会遮挡位于下层的专辑原图，让 3D 档案呈现出自然悬浮在封面之上的层次感。
- **材质配色沿用原 Theme**：两个模型文件均未附带外部贴图纹理，整组资源合计包含 39 个材质球与大约 16.9 万个三角面。模型内部的材质名称与原项目定义的材质列表严格对应，当程序解析到未知材质名时，会按照名称规则执行兜底填色，保证不会直接渲染成刺眼的纯白色。
- **锁定的三维库版本较老**：由于受限的宿主页面环境不支持解析标准的 ES module 模块语法，项目只能引入传统 script 标签方式构建的库文件。
- **模型走本机 IPC 读取**：受限于运行时的沙盒安全机制，渲染页面无法直接访问操作系统的本地文件系统，必须发起进程间通信通知主进程读取模型文件的原始二进制字节流，再传回前端页面进行反序列化解析。这条数据传输通道**只读且只放行白名单文件名**，坚决屏蔽外部传入的任意绝对路径，从底层严格遵守[数据管控](数据管控与合规.md)所约定的结构性安全规范。

### 10.6 与主题的关系

虽然 3D 档案功能在**四套主题下都可用**，但模型资源内部的材质命名自成一套独立的色彩规范，因此材质配色会始终固定沿用原有的 UI 配色方案，不会随着宿主界面的主题切换而动态改变表面颜色。

## 11. 音乐档案终端（莱茵生命终端底座）

系统的主界面设计为一套基准分辨率为 1920×1080 的档案终端界面。整套 UI 挂载在舞台容器内部，页面会读取当前的视口尺寸，按照公式 `min(窗口高/1080, 窗口宽/1840, contain × 1.2)` 进行整体缩放。在具体的适配策略上，画面会在纵向上按高度完整铺满视口；横向为了避免出现黑边，允许两侧各自最多裁剪掉 40 个基准像素，运行时计算得出的实际裁剪像素值会实时写入界面的缩放变量供样式调用。
这套界面把底层的音乐库完整映射为具体的“档案”，原本属于终端面板的每一个独立显示区域，都被改造并绑定成了播放器的各个功能组件。
### 11.1 三块界面各自负责什么

| 界面 | 位置 | 对应的播放器功能 |
| --- | --- | --- |
| 档案阵列（五列、每列八份、可循环） | 画面中部三维阵列 | 播放列表：曲目按顺序轮转进五列 |
| 抽出的档案卡片 | 画面左侧三维模型 | **当前曲目的封面印在正面标签板上**（含 `NO.` / 曲名 / 艺术家 / 专辑） |
| 详情区 | 右侧（宽 636 / **底边锚定 112**） | 曲目面板：封面、曲目信息、**实时频谱 ⟷ 歌词列表**（顶部工具栏分段开关切换，见 §4.4） |
| 播放条 | 左下（left 59 / bottom 80 / **900×148**） | 传输控制、进度、播放模式、收藏、导入、B 站缓存导入、播放列表入口；**点曲名区 = 打开当前这首的档案**，**点其它位置 = 回到档案阵列**（控件区不触发，弹窗开着时先收弹窗） |
| 播放列表（抽屉） | 左下（left 59 / bottom **238** / **900×560**，`☰` 开合） | 顶部**排列顺序下拉框**与**搜索框**（曲名 / 艺术家 / 专辑，回车播第一条命中、ESC 清词再按收抽屉、`✕` 清除）＋ 曲目列表：点行播放、**点曲名打开这一首的档案**、`✕` 移除、`↳` 下一首播放、`♡` 收藏、`◐` 昼夜 |

**排列顺序**：系统支持多种排序规则，包括导入顺序（默认）、曲名、艺术家、专辑、时长（短→长）、播放次数（多→少）以及最近添加。因为曲目在列表里的次序直接映射到了三维档案阵列中，所以调整排序时会由程序驱动**列表与阵列一起变**。在处理中文字符时，排序逻辑按照拼音字母进行比较；如果两条记录的排序键完全一致，系统会读取导入次序作为兜底依据。

**打开与双击**：按下回车键、点击 `PLAY TRACK` 按钮或者直接点击曲目标题，触发的行为统一为**打开档案并播放**。这个动作会展开右侧详情区并立即起播当前选中的曲目，早期版本中“只查看档案不播放音频”的交互定义已经被彻底废除；**双击档案卡片**同样映射到这一套逻辑，而单击卡片依然只改变当前的选中状态。
由于档案展开与音频起播共用了同一条执行逻辑，右侧详情面板、底部播放条、频谱分析模块以及三维档案阵列展示的数据始终保持精准同步。曲目起播时是否同步呼出档案，由系统设置项 `OPEN ARCHIVE ON PLAY` 的布尔值决定。开屏引导流程结束后，程序是由终端层直接执行场景切换，不会调用起播通道，用户启动软件时自然不会发出任何声音。

> **★ 版面遮挡的几条硬约束。** 所有面板都在 1920×1080 分辨率的标准舞台里采用绝对定位布局，各个元素之间是否存在重叠必须通过矩形坐标计算来判定：
>
> 1. **播放条底边距只能是 80，不能再往下压**：界面最下方还固定排列着页脚（`bottom: 35`）以及 `.powered` 标识行（`bottom: 62`）两个组件。之前参数曾被下调至 40，导致播放条直接遮挡了整行页脚，引发了用户反馈中的“全屏后下方存在遮挡”问题。
>    当底边距设为 80 时，播放条底部坐标到达 1000，与页脚顶部的 1032 像素坐标之间正好留出 32px 的安全间距；上方的抽屉列表则跟随播放条维持 10px 的相对间隔。
>    界面在大分辨率屏幕上“上下显得空旷”的视觉现象应当通过视口缩放策略来适配，不能靠压缩底部边距去填补。
> 2. **右下角那一列 `x 1586–1861` 只归 `.powered`**：详情面板的右侧边缘已经延伸到了横坐标 1790 的位置，横向维度上它必定会与该区域产生交集，要避免遮挡就只能依赖纵向维度的错位排布。因此开发时将详情区改为了**底边锚定**的设计方案，把底边像素坐标死死锁定在 y 968，无论容器内部渲染的内容有多长，它都只能向上方单向拉伸。
>    在做出这项修改之前，两个区域在界面上实测重叠了 204×24 像素的显示面积。
> 3. **播放条与抽屉的宽度上限是 910**：右侧面板的起始横坐标固定为 x 970，当播放条宽度取 900 时，其右边界刚好停在 959 的位置，为中间留出了 11px 的视觉缝隙。
> 4. **设置弹窗按内容自适应 + 内部滚动**（`max-height: 940px`）：该弹窗在早先的代码里被写死了 786px 的固定高度，但所有配置表项累加后的渲染高度达到了 1656px，超出边界的表单项就会直接冲破弹窗外框，向下盖住底部的播放条以及抽屉列表。
>
> 上述几项数值都是通过代码联调逐块测试出来的精确边界，以后每次修改界面布局结构，都必须对照坐标重新核验一次。
> 采用绝对定位构建的视图，光靠肉眼查看截图很难察觉到几十像素范围内的边界压迫（见 [维护指南](维护指南.md)）。

**封面是怎么印上去的**：卡片三维模型的正面原始结构中包含一块印刷标签板，渲染场景在这块结构之上贴合放置了一片封面板；Canvas 画布负责绘制封面图像，图像导入后会按照自身的宽高比例居中裁切并填满画框，同时叠加 `NO.` 编号、曲名、艺术家、专辑名称以及顶部抬头和装饰细线。封面板的层级位于卡片物理外壳的外侧，因此不管卡片是否经历了解密展开动画，用户都能直接看到它。整套渲染机制限制了只有处于抽出状态的那一张卡片才会贴合封面，阵列里的其余卡片则全部维持素面状态。当用户切换选中的曲目时，正在退回阵列的旧卡片会把当前封面**快照成独立纹理**并持久化保存，避免因为多个模型实例共用同一份纹理材质，导致旧卡片在收回过程中封面图像跟着新卡片一起变化。
### 11.2 操作

- **选档**：用户可以使用键盘左右方向键切换不同的列，使用上下方向键在当前列的档案列表中翻动。按下回车键会**打开档案并播放**，此时界面会切入详情层，并且立即起播选中的这首歌曲。如果当前界面已经在详情层里，回车键的功能会转变为**播放 / 暂停这一首**；档案栏底部展示的操作提示文本写的是「`ENTER` 读取」。
  按下 `ESC` 键，或者直接点击详情层左上角的返回按钮，就可以退出详情并回到外层的三维阵列。
- **起播即打开档案**（默认处于开启状态，用户可在设置面板中手动关闭）：只要点击列表中的某一行开始播放，或是直接按下播放按钮，系统就会自动切入该歌曲的详情界面，同时把右侧展开的播放列表抽屉收合起来，保证用户从播放列表或者直接从档案卡片进入时，所面对的视图结构和交互结果始终保持一致。
- **播放列表（`☰`）**：在列表里点击某一行，作用等同于直接播放该歌曲并展开对应的档案；点击 `✕` 按钮会移除这首歌，需要注意的是，该操作执行后音频会**当场从列表与曲库里一起消失**，下方剩余的所有行号也会立刻重新排列；点击 `↳` 按钮可将其设为下一首播放；点击 `♡` 则切换收藏状态。点击播放列表抽屉外部的空白区域即可让它自动收起。因为该抽屉是一个悬浮在左侧三维阵列上方的浮层，如果不及时收回，用户点击三维阵列的事件就会被抽屉层拦截，导致底层的交互无法生效。
- **播放条**：控件区域依次排列着 `⏮ ▶ ⏭` 切换与控制键、播放模式切换键 `↻`（支持 列表循环 / 顺序播放 / 单曲循环 / 随机播放）、**播放速度 `1×`** 调节项、收藏按钮、用于添加音频的导入按钮（在其上方点击鼠标右键等于导入整个文件夹）、**电视图标 ＝ 导入 B 站缓存**（具体处理规则见 §9）以及用于展开侧边的 `☰` 播放列表。
  播放条的最底部一行承载着播放状态指标，分别展示当前时间、进度条、总时长以及独立的**音量条**（该数值与系统的背景音乐音量各自独立，互不干扰）。
- **拖拽导入**：用户直接把单个音频文件或者整个文件夹拖拽进应用窗口即可完成导入，底层处理流程与点击界面中的 `＋` 按钮走的是同一条管线，两者的解析逻辑完全相同。
- **播放位置**：系统记录当前进度只是为了让用户"下次接着放"，该数据不会在界面上当作专门的播放历史记录展示。写入数据库时设计了两条保护机制：
  一是设置了**每 4 秒一次的兜底**定时写入（专门防止应用异常崩溃或被系统强制杀进程时丢失进度），二是在用户触发暂停、切歌、关闭窗口或者将应用切到后台这几种状态变化时，各自向底层写入一次。下次打开该曲目时会从上次中断的位置继续播放，但如果剩余进度离曲尾不足 5 秒或者比例不足 4%，播放器就会自动重置并从头开始，避免用户一进来就直接播完跳曲。
- **曲库加载**：读取本地数据库的操作**不挡启动**，即采用非阻塞方式运行。界面在初始阶段先按照空库状态构建骨架，展示占位档案；后台将真正的歌曲数据全部读取完毕后，再整体刷新一遍各处视图。
  > ★ **超时不等于空库**：如果在第一轮规定时间内没有读取完成，界面会先向用户显示"正在读取曲库…"的提示，接着自动采用更长的超时时间发起第二次重读并把数据补齐，
  > 只有两次读取都拿不到数据时，系统才会最终判定为空库。在包含 397 首歌曲、体积达 3.5 GB 的曲库中实测，仅将数据读取出来就需要 2.9 秒，在机械硬盘等冷盘环境下很容易超过常规耗时。
  > 早先版本因为采用了固定的短超时时间，超时后直接把整轮结果当作空库处理，在界面上就会表现为"一打开之前导入的歌曲全不见了"，而实际上底层存储里的数据一条都没有丢失。
- **详情区**：右侧的曲目面板**没有页签**这种切换结构，直接集中展示封面图片、曲名与艺术家信息，以及包含音轨属性的元数据四格。顶部工具栏提供了一个「可视化 ⟷ 歌词」分段开关，开关正下方的主体区域则会根据选择，切换呈现出**大尺寸实时频谱**（即随音频动态跳动的频率响应柱状图）或者**歌词滚动列表**。
  处于可视化频谱模式时，频谱画面正下方还会单独显示一行"当前歌词"字幕；底部操作区常驻有用于添加喜欢的 `＋ SAVE TRACK` 收藏按钮，以及控制播放和暂停的 `PLAY ▶` 按钮。
### 11.3 实时频谱

详情区右侧的完整纵向空间专门分配给音频可视化和歌词展示。自 2.3.0 版本开始，这片区域支持**两种形态**，用户可以通过顶部工具栏里的分段开关随时在二者之间来回切换（见 [§4.4](#44-右侧可视化--歌词切换230-新增)）。

- **可视化模式**（默认）：以大尺寸实时频谱为主体，并在频谱正下方显示一行单句形式的"当前歌词"字幕。
- **歌词模式**：原本的频谱区域完全替换为**歌词滚动列表**，正在播放的当前行歌词会以高亮状态保持在视口居中位置。

底层的音频分析逻辑继续复用第 5 章介绍的 SelfMusic 处理管线（具体的节点连接链路与数据取值规则见 §5.2–§5.8）：

- **96 段柱状频谱**（频谱柱底部对齐基线、每根柱子单独计算透明度、顶部带有下落式峰值顶盖、左上角配有四路音色指示条），整体视觉配色直接从终端令牌中提取。
- **播放条**：提供 52 格电平刻度，数值直接从频谱柱的采样数据中读取，并跟随渲染节拍同步刷新；为了避免无谓的重绘，程序只在计算出的像素高度确实发生改变时，才会执行实际的 DOM 写入操作。
- **播放条与播放列表不使用背景模糊**，因为界面底层始终在持续渲染三维动画场景，如果每一帧都要对大面积的图层重复执行高斯模糊运算，显卡和处理器的性能开销会变得过大。
- **取不到运行中的音频上下文就不接管音频元素**，避免因 Web Audio API 初始化失败而阻塞原本的常规播放流程；哪怕最终无法渲染出频谱画面，也必须优先保证底层音频能够正常发声。

相关实例与状态数据会直接挂载到全局对象上，主要用来在排查问题时核对"点这首有没有接上上次的位置"，同时监控实时的画面渲染帧数。
### 11.7 恢复旧版曲库

新版程序将界面服务端口从以往的随机分配改成了固定的 `41739`。浏览器内核中的 **IndexedDB 严格按照“源”（Origin，由协议 scheme、主机 host 与端口号 port 共同决定）进行存储隔离**。过去每次启动只要端口发生变化，浏览器就会切换到全新的独立存储域，这就造成旧版本里导入的曲目在新版界面中完全无法显示。实际上底层数据并没有丢失，原本保存的音频文件依然以二进制大对象（Blob）的形式，分散残留在各个旧源所属的数据库内：

| 旧源 | 位置 |
| --- | --- |
| 早期独立播放器 | 当前 profile 的 `file://` 源 |
| 1.4.0 之前的终端界面 | 当前 profile 的 `http://127.0.0.1:<随机端口>` 源 |
| 更早的一份独立安装 | 另一个 profile（`%APPDATA%\music-player-desktop`）的 `file://` 源 |

用户可以通过执行下方这行命令启动恢复流程：

```
scripts\恢复旧曲库.ps1
```

脚本内部会依次执行三个步骤：第一步，扫描并导出当前用户配置目录（profile）中所有历史源的数据；第二步，通过启动参数 `--user-data-dir` 强行指定旧版配置目录 `%APPDATA%\music-player-desktop`，再次运行扫描并提取出残留数据；第三步，重新切回当前生效的配置目录，把前面导出的中转数据统一写入当前库中。每跑完一步，界面都会弹出提示框，向用户明确汇报本阶段读取了多少条元数据、提取出多少个音频文件，以及最终新增或跳过了多少首曲目。

恢复过程的核心设计如下：

- 恢复脚本共用同一个网页，但内部划分两种工作模式：运行在旧源环境时负责读出全部记录（包含字段信息、原始音频字节与封面图片），运行在新版本端口源时则负责把这些提取到的内容写回当前曲库。
- 脚本在检测到历史随机端口对应的源之后，会针对每一个端口就地拉起一个只读的本地静态服务器来承载页面，因为**浏览器安全策略规定数据只能在完全匹配的源之下才能被读取**。
- **全过程严禁向用户的音乐目录写入任何文件**。这一规则遵循 [数据管控与合规](数据管控与合规.md) 中关于派生数据“不导出”的规定。不同 profile 之间的交接环节统一经由系统临时目录缓冲，数据一旦成功导入到新版曲库中，所占用的临时文件就会被立即清理干净。
- 曲目合并阶段默认依据“标题 + 艺术家”这两项组合判定重复，脚本因此支持反复执行；**对旧存储域中的数据全程只读**，既不会执行修改操作，也不会删除原有数据。
### 11.4 与终端的一致性

- 所有的播放器元素都挂载在舞台容器内部，统一按照 1920×1080 的标准基准尺寸等比例缩放，避免出现窗口尺寸变小时主界面缩放、但底部播放条依然保持原尺寸的脱节问题。
- 界面的颜色方案、字体大小以及字距参数，完全继承自终端系统预设的设计令牌，具体涵盖浅色纸面底色 `#e8e5e1`、边框与分割细线 `#c1b8a7`、深浅实心前景 `#252820 / #f0eee5`、暖色强调高亮 `#9b7247`，以及橄榄绿装饰色 `#565c46`。
- 用户通过点击播放列表右上角的 `◐` 按钮来执行昼 / 夜切换，切入夜间模式后，播放器会自动应用终端内置的深色家族主题。
- 界面上的各类提示条没有单独实现，而是直接调用终端原生提供的消息与提示组件，确保弹窗和通知的交互风格前后一致。
### 11.4.1 玻璃质感（2026-10-04）

效果应用的范围和浓淡经过了严格控制：开发团队**只对详情区与弹层**应用这种样式，播放条和播放列表则不包含在内。因为这些组件底层衬着持续运行动画的三维场景，GPU 如果在每一帧都要对大面积像素执行实时重采样和高斯模糊计算，性能开销会非常高，容易造成掉帧：

| 项 | 详情区 | 弹层（设置 / 检索 / 收藏） |
| --- | --- | --- |
| 底色 | `rgba(243,241,235,0.7)` | `rgba(240,238,231,0.74)` |
| 毛玻璃 | `blur(12px) saturate(1.12)` | `blur(16px) saturate(1.14)` |
| 描边 | `1px rgba(255,255,255,0.55)` | `1px rgba(255,255,255,0.6)` |
| 圆角 | `14px` | `14px` |
| 高光 | `inset 0 1px 0 rgba(255,255,255,0.72)` + 底部深内阴影（厚度感） | 同（更亮一档） |
| 投影 | `0 18px 48px rgba(90,78,58,0.14)` | `0 26px 95px rgba(99,81,58,0.22)` |

界面切换到深色主题时，系统会匹配为对应的“深玻璃”风格：底色分别调整为 `rgba(30,34,28,0.62)` 与 `rgba(26,30,24,0.7)`，边缘的高光强度和投射的阴影参数也同步调暗，确保暗色背景下的明暗关系协调。

实现过程中有两个必须遵循的关键机制：

- **毛玻璃效果来自对背景像素的取样与混合计算** —— 覆盖在表面的元素底色必须包含**半透明**通道（即 alpha 通道小于 1），下层的模糊细节才能透过来显示；一旦把底色设置成完全不透明，背后的取样计算就会彻底被遮挡，滤镜也就失去作用。
- **无障碍辅助功能的适配机制**：系统检测到用户开启了“减少透明度”这类系统级辅助选项之后，样式表会把毛玻璃滤镜和半透明底色全部撤下，替换成实心的纯色不透明纸面底色。界面不能为了追求玻璃通透的视觉质感，去牺牲文字内容本身的可读性与对比度。
### 11.5 曲目信息与标签编码

系统在界面展示上**不再出现档案术语**。详情区、检索弹窗以及选中提示里的各项字段，一律调整为播放器语义来显示，对应关系具体为：科室改为艺术家、编目范围改为时长、相关人物改为专辑、权限改为来源格式。就算当前音乐库为空，界面也会保持这一套语义版式的占位状态，不会退回到旧有的“档案内容”排版模式。

曲目展示所需的标题 / 歌手 / 专辑等元数据，均直接读取自音频标签。由于 ID3 规范中的文本帧支持四种编码标记，解码时程序会读取帧内容首部的编码字节并进行对应分派：

| 编码字节 | 处理 |
| --- | --- |
| 1 | 按 BOM 决定 UTF-16LE / BE（不信任运行时对 UTF-16 的默认字节序） |
| 2 | UTF-16BE |
| 3 | UTF-8 |
| 0 | 先严格试 UTF-8；不成立且高位字节占比 > 50% 时按 GB18030 解；都不是才落回 windows-1252 |

此外，解析模块还补充了以下处理逻辑：

- 针对早期规范，支持读取 ID3v2.2 格式的三字节帧头（包含 `TT2`、`TP1`、`TAL`、`PIC`）
- 当音频中不存在 v2 版本的标签时，解析逻辑会读取文件末尾 128 字节的 ID3v1 数据作为兜底来源
- 提取内嵌封面时，程序会依据图片描述文字的实际编码格式来计算并跳过描述段；因为 UTF-16 编码的描述文本是以双字节空字符 `00 00` 作为结束标志，若是直接逐单个字节查找 `00`，就会把描述内容提前截断而导致封面数据损坏
- **旧版本产生的乱码会被自动修回来**：早先的程序版本强制写死了 UTF-8 方式解码，导致部分中文标签此前已经作为乱码写入了本地曲库；现在软件启动时，仅会挑出“特征上判定为乱码”的条目重新执行一次编码识别流程，修复成功后把正确文本写回数据库，并通过界面提示条明确告知用户本次修复了多少首曲目
### 11.6 已知边界

- 档案阵列单屏所能展示的容量存在物理上限，网格仅划分为五列 × 八份 ＝ 40 个位置。如果曲目总数超过 40 首，超出数量上限的曲目就无法在主阵列内排布，用户只能在播放列表里浏览并点播这些多出来的部分。
- 播放列表采用了覆盖式浮层的呈现形式。处于详情视图时，展开的列表层会遮挡住界面左下角原有的说明行。用户点击播放列表面板以外的空白区域，或者直接在列表里选定曲目开始播放，面板便会自动收起并露出底下的文字，具体交互流程见 §11.2。
- 详情处于展开状态时，用户在三维阵列上点击**别的**档案，系统会切到该目标档案并同步退回到阵列总览视角；如果点击的正是当前正在特写展示的那一张，系统不会判定为“切换”动作，因为此时用户的操作意图大多是拖拽检视模型，因此视图会保持原样。⚠ 该行为在无头环境里无法进行测试验证：因为无头模式下三维动画时间轴处于完全静止状态，详情取景相关的镜头调度代码根本没有实际运行。
- 终端界面依托本机静态服务对外提供，**端口固定为 41739**。由于浏览器基于源来划分数据存储，界面源在每次应用启动之间必须保持完全一致，否则按照源彼此隔离的曲库数据、收藏内容以及播放进度就会因为换了源而读不回来。遇到端口被占用的情况，系统会退回使用随机端口，同时控制台会输出一条日志，明确提示本次运行的存储域与上次不同。
