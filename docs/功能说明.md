# 功能说明

本文档详细说明音乐播放器的全部功能与使用方式。

> **来源署名：第 11 章那套「音乐档案终端」的界面源码与 Blender 工程文件来自
> B 站 UP 主 [@路北路陈](https://space.bilibili.com/3546646728820438)**
> （仓库 [LBEILC/RhineLabUI](https://github.com/LBEILC/RhineLabUI)，MIT）。
> 本仓库做的是**反向整合**：把这套界面接上真实的播放内核，并按播放器信息改写界面词条；
> 界面与美术资产的著作权归原作者。详见 [README 的「致谢」](../README.md#致谢)。

> **仓库里有两套可播放的界面。** ① 以莱茵生命终端为底座的**音乐档案终端**
> （`app-rhine/`，当前主界面，见第 11 章）；② 早期的**独立播放器界面**
> （`app/index.html`，作为兜底保留）。第 1–10 章描述的是通用能力
> （导入、元数据、NCM、歌词、媒体键、主题等），两套界面共用同一套播放内核。

## 1. 曲库导入

### 1.1 导入文件

点击左栏「+ 添加」→ 选择文件，支持多选。

支持的音频格式：

| 格式 | 说明 |
| --- | --- |
| `.mp3` | 最常见，ID3v1 / ID3v2 标签与内嵌封面均支持 |
| `.flac` | 无损，支持 Vorbis Comment 与内嵌封面 |
| `.m4a` / `.aac` | AAC 系，支持 MP4 元数据 |
| `.wav` | 支持 LIST/INFO 标签 |
| `.ogg` | Vorbis |
| `.wma` | Windows Media Audio |
| `.ape` | Monkey's Audio |
| `.ncm` | 网易云加密格式，**导入时自动解密**（见 1.4） |

### 1.2 导入文件夹

点击「添加文件夹」→ 选择目录。程序会**递归**扫描该目录下所有支持的音频文件。

### 1.3 拖拽导入

直接把文件或文件夹拖到窗口任意位置即可，无需点击按钮。

### 1.35 重复曲目不再导入

同一个文件、同一个 B 站缓存文件夹**不会被导入两次**：

- 判重依据是文件的完整路径（浏览器环境里拿不到路径时，退回"文件名 + 体积"）
- 命中的条目在写进曲库之前就被跳过，完成后提示 `导入完成：新增 N 首，跳过重复 M 首`；全都是重复时提示 `这些曲目已经在曲库里了（跳过重复 M 首）`；一次拖进两个相同文件也只进一条
- 启动读库后还会顺手清理一次历史遗留的重复，只认"同一路径"这一条硬判据，清完提示"已清理 N 首重复曲目"。保留哪一条按 收藏 → 播放次数 → 最早导入 的顺序挑，被合并掉的收藏与播放次数会累加过去
- 按"文件名 + 体积"判断的条目不参与自动清理，需要时在列表里用 `✕` 手动移除

### 1.4 NCM 自动解密

网易云的 `.ncm` 是加密容器，导入时自动解密，内置两条路径：

1. **首选：随包的官方解密工具**（兼容全部 NCM 变体），解密后的音频**连同完整标签（标题 / 歌手 / 专辑 / 封面）** 一起读出
2. **回退：内置 AES-ECB 解密**，工具不可用或被安全软件拦截时启用，按文件头魔数判断真实格式（`ID3` / `fLaC` / `OggS` 等）

解密结果**只在内存里传递**，不会在你的音乐目录里产生任何新文件；临时目录中转的字节读回来后立即覆盖擦写并删除。会先校验容器魔数，不是真正的 NCM 文件直接拒绝 —— 它不是一个拿任意文件来试解的通用解密器。

> 管控细节见 [数据管控与合规](数据管控与合规.md)。

## 2. 元数据识别

### 2.1 识别优先级

内嵌标签 → 同目录图片（`cover.jpg` / `cover.png` / `folder.jpg` / 与音频同名的图片）→ 文件名解析（`"歌手 - 歌名"` 等常见格式）。三级依次兜底。

### 2.2 多歌手识别

以下写法都会被拆分成**多个独立歌手**，并对每位歌手分别建立索引：

| 写法 | 拆分结果 |
| --- | --- |
| `周杰伦/费玉清` | 周杰伦、费玉清 |
| `周杰伦、费玉清` | 周杰伦、费玉清 |
| `周杰伦 & 费玉清` | 周杰伦、费玉清 |
| `周杰伦 feat. 费玉清` | 周杰伦、费玉清 |
| `周杰伦 ft. 费玉清` | 周杰伦、费玉清 |
| `周杰伦; 费玉清` | 周杰伦、费玉清 |

分隔符识别包含 `/`、`、`、`,`、`&`、`;`、`feat.`、`ft.`、`with`、`×` 等，并带保护：`AC/DC`、出现在 URL 里的 `/`、`R&B` 等已知组合不会被拆开。

### 2.3 重新识别

对**已导入**的歌曲可以一键重跑识别流程（设置面板 → 重新识别），用于这几种情况：

- 之前导入时文件名不规范，后来补了标签
- 歌手拆分规则更新后需要重新索引
- 封面当时读取失败

重新识别只更新元数据，**不会**丢失收藏、播放次数与播放进度。

## 3. 播放

### 3.1 播放模式

| 模式 | 行为 |
| --- | --- |
| 列表循环 | 播完最后一首回到第一首 |
| 顺序播放 | 播完最后一首停止 |
| 单曲循环 | 当前曲目结束后重头再播 |
| 随机播放 | 随机选曲，尽量避免连续重复 |

点击播放控制区的模式按钮循环切换。

### 3.2 下一首播放

在任意曲目上右键 / 悬停菜单选择「下一首播放」，该曲目会被**插入**到当前播放位置之后，而不是替换整个播放列表。

### 3.3 倍速播放

0.5× ~ 2.0×，调节后立即生效并随歌曲切换保持。播放条上的 `1×` 按钮按 1× → 1.25× → 1.5× → 2× → 0.75× 循环。

**变速保音调（time-stretch，不是简单的变采样）**：0.75× 不会发闷、1.5× 不会变尖，这两档恰好是听播客 / 有声书最常用的档位，差别在耳朵上非常明显。
设置面板的 **PITCH ／ TIME-STRETCH** 一行如实显示当前有没有真的生效；个别运行环境不支持时显示 `⚠ 此环境不支持`。

### 3.3.1 切歌预取（消除"按了没反应"）

播放到接近曲尾时（约 12 秒；短曲目按时长的 15%、下限 6 秒），后台**提前把下一首的音源备好**，真正切歌时省掉读盘这一步，避免"按了没反应"。

- 队列变化（设为"下一首播放"）或换歌时，预取结论立刻作废重算
- **随机播放不预取** —— "下一首是谁"在那之前不可知
- 预取失败不影响正常播放

### 3.3.2 B 站音源走内存读取

界面跑在本机静态服务上，浏览器会拦掉来自 `file://` 的音源（B 站缓存直读会报 MediaError 4「格式不支持或文件头异常」），所以音源都走"读入内存 → 临时地址"这一条路。
代价是每首要整份读进内存、不能流式解码；换来的是每一首都能直接播，不会先失败一次再降级。

### 3.4 进度记忆

> **★ 位置只保留一条**：播放进度 =「最后一次在听的那首 + 位置」。
> **任何一首曲目都不再各自记住自己的上次位置** —— 切走再切回来一律从头播。

三个开关在系统设置 → 播放行为里（默认都开）：

| 开关 | 默认 | 打开时 | 关掉时 |
| --- | --- | --- | --- |
| REMEMBER LAST POSITION | 开 | 只记「最后一次在听的那首 + 位置」这一条，下次启动接着听 | **完全不写**，播放头与曲目位置都不落，启动也从零开始 |
| RESUME LAST TRACK | 开 | 启动时把播放条恢复到上次在听的那一首与位置 | 启动不恢复，播放条留空 |
| OPEN ARCHIVE ON PLAY | 开 | 起播时自动打开这首歌的档案详情 | 只播不跳转，停在档案阵列里 |

「关掉记住上次位置」会顺手把已经存下来的进度清一遍，并作废正在等待的续播点。

保存的其它状态：当前曲目、收藏状态、播放次数、音量、播放模式、主题、可视化参数 —— 下次启动自动恢复。若上次退出时正在播放，会恢复到暂停状态（不会突然出声）。

### 3.5 系统设置里的其它几行

| 行 | 作用 |
| --- | --- |
| `HEADPHONE / MEDIA KEYS` | **耳机 / 媒体键自检**：左边显示注册状态，右边实时显示"最近一次按下的键被认成了什么"。有线耳机的三键线控与**接听键**走的都是媒体键通道，这一行就是用来确认"我的耳机键到底有没有被认出来" —— 详见 [快捷键 §1.5](快捷键.md)；耳机软件能改键时，接听 / 挂断可绑 `Ctrl+Alt+A` / `Ctrl+Alt+H` |
| `PITCH ／ TIME-STRETCH` | 变速是否保音调，如实显示当前取值（`✓ 已启用（保音调）` / `⚠ 此环境不支持`）—— 见 [§3.3](#33-倍速播放) |
| `ANALYSER ROUTING` | 频谱分析链路的去向。正常显示 `已接入 · 44kHz`；频谱起不来时显示 `频谱未启动` 并把**原因**写进悬浮提示 |
| `COVER ACCENT` | 强调色是否跟随封面（默认开）—— 见 [§8.1](#跟随封面强调色动态取自封面) |
| `BEAT PRE-ANALYSIS` | 是否在播放前离线分析整首（默认开）。显示当前这首测出的 BPM 与拍点数、后台还剩几首待分析 —— 见 [§5.5.4](#554-节拍预分析提前点亮--2026-10-04) |
| `RE-READ ALL COVERS` | 一键把所有曲目的封面从本地文件重读一遍 |
| `LOCAL AUDIO COPIES` | 显示导入 B 站缓存时固化到曲库目录的音频副本占了多少盘（源缓存删掉也能播的那一份） |

**旧版调音参数会自动继承。** 频谱那五个量（平衡 / 峰宽 / 抖动 / 鼓点 / 峰高）存在旧版的浏览器存储里，新旧两套界面不同源，所以启动时会自动导入一次并弹提示（"已导入旧版调音设置：平衡 63 / …"），
之后以新版里的改动为准；没有旧版数据就用默认值。详见 [更新日志](更新日志.md) 的 2.2.0。

> **★ 例外：鼓点不照搬旧值，它有 0.40 的硬下限。** 它的定义是"鼓点之间把左峰压多低"，
> 取 0 等于关掉泵动，左峰顶到天花板后再也不下来（旧版面板自己写着"0 = 左峰一直顶满"）。
> 导入后会被夹回默认的 0.40：左峰照样能顶到最高，只是拍与拍之间会掉下来。
> 已经导入过的机器不用重导。详见 [§5.5](#55-鼓点响应)。

## 4. 歌词

### 4.1 来源优先级

1. 与音频文件**同名**的 `.lrc`
2. 音频文件**内嵌**歌词（ID3 USLT / SYLT 帧）
3. 同目录下文件名相似度最高的 `.lrc`
4. 上级目录中的 `.lrc`

### 4.2 编码

自动尝试 UTF-8 → UTF-8 BOM → GBK，避免中文歌词乱码。

### 4.3 显示

- 逐行滚动，当前行高亮放大
- 支持翻译行（同时间戳的第二行会作为译文并列显示）
- 无歌词时显示占位提示，不影响播放

### 4.4 右侧「可视化 ⟷ 歌词」切换（2.3.0 新增）

详情区右侧那块内容有两种形态：**实时频谱**与**歌词滚动列表**。用详情区顶部工具栏（`TRACK` 行下面那条）右侧的**分段开关**切换，两个选项都画出来（`可视化` / `歌词`），
当前项反白 —— 不必靠猜按钮文字才知道现在在哪一边。切换只换内容并补一次歌词同步，
**不重绘详情区**（重绘会重放解密动画、重建频谱实例）；状态重启后保持，脏值回落到"可视化"。

歌词列表按音频时长逐行铺开：

- 滚动容器上下两端有渐隐遮罩，做出"从深处升起"的层次
- 当前行**三重高光**：加粗放大（普通行 16px → 高亮行 **22px**）、换成前景深色、左缘一道 **3px** 竖线。只靠颜色的话，投影仪或低对比屏上看不出来；放大够狠才扫一眼就知道唱到哪
- 滚动用位移合成 + 0.42 秒过渡，目标是**当前行落在可视区的垂直中线上**
- **点某一行 = 跳到那一句**，但**刻意不自动起播** —— 你可能只是在浏览歌词，突然放声会吓一跳；要听就点播放条，跳转已经把进度放到了那句开头
- 跳转有个**闸门**：只有"详情区展示的这首就是正在播的这首"时才会去动进度，否则会把**正在播的那首**拖走

> **★ 详情区展示的曲目 ≠ 正在播的曲目。** 详情区展示的是"被打开的那首"，两者可以不同。
> 歌词同步与点击跳转都以"展示的那首"为准，否则会出现"打开 A 却看到 B 的歌词"。
> 见 [维护指南](维护指南.md)。

## 5. 频谱可视化

### 5.1 为什么不用 `AnalyserNode`

浏览器自带的分析节点输出**等宽线性**频段，音乐的能量绝大部分集中在低频，画出来是左边几条柱剧烈跳动、右侧一片死寂。这里的频谱是自研管线，按键位自己的需求设计。

### 5.2 处理链路

取 512 点时域样本 → 加窗减少频谱泄漏 → 逐 bin 计算指定频点能量 → 合并成 120 个对数频段（每条约 1/12 倍频程）→ 重采样到 150 根柱 → 自适应增益归一化 → 对数压缩 →
快攻慢放的时间平滑 → 鼓点泵浦 → 相干行波 → 逐柱峰值保持与衰减 → 画到画布。

### 5.3 关键参数

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 分析窗长 | 512 点 | 约 10.7 毫秒的群延迟。**2026-10-08 由 1024 点降到 512**（用户要求"延迟要低"）：窗短了延迟就短，代价是等效噪声带宽翻倍（约 70Hz → 141Hz），低频那根"细针"对邻频带更敏感。这是目前唯一一处刻意偏离 1.3.0 的参数 |
| 分析频段数 | 120 | 对数分带，低频到高频的分辨率一致 |
| 显示柱数 | 150 | 由 120 段重采样而来，只改画面的疏密，不改计算结果 |
| 频率范围 | 20Hz ~ 采样率的 0.45 倍 | 随采样率换算，48kHz 下约为 20Hz ~ 10.8kHz。写死 Hz 值会让整条频段映射错位 |
| 灰度层级 | 14 级 | 柱高分 14 级绘制，级距约 0.077 |
| 峰值线衰减 | 每 tick ×0.90 | 见 §5.6.1 |
| 行波 | 每 6 根柱一周期，约 12 根/秒 | 方向右 → 左，见 §5.7 |
| 一阶跟随 | 上行 0.70 → 0.50、下行 0.58 → 0.80 | 越靠高频，升起越慢、落下越快 |

参数沿用 1.3.0 那一版独立播放器的取值。

### 5.4 高耸条

低频峰的位置逐帧实时计算，其占位随之自动左移到柱体序列最左端，配合倾斜增益，让高峰呈**窄而尖**的形态，而不是胖墩墩的一坨。

### 5.5 鼓点响应

鼓点由**两路**共同反映：一路是低频 onset 驱动的左峰泵动，一路是宽带瞬态强调。

#### 5.5.1 低频 onset 泵动

有一路参考电平持续跟随低频能量，**上升沿触发泵动**；参考电平不对称跟随（高于基准跟得快、低于基准落得也快），密集鼓点因此能各自干净地触发一次，也不会饱和。

泵动是**乘性**的，作用在左峰那一段柱子上：鼓点命中时左峰顶到近满，拍与拍之间掉下来。

> **★ 泵动不能关到 0：它有 0.40 的硬下限。** 归零后乘性闸门恒等于 1，
> 左峰一旦被频段增益顶过钳位点就再也没有东西把它压下来，画面会变成一排死顶在天花板的柱子。
> 0.40 之后**峰值高度一个数没变**，只是拍与拍之间会掉下来。
> 启动时读取已存参数、以及从旧版导入时都会过这道闸门 —— 见 [§3.5](#35-系统设置里的其它几行)。

#### 5.5.2 宽带瞬态强调（敲击的频谱形状）

只看低频 onset 时，推起来的是左峰那一段 —— 底鼓看得见，但**军鼓、踩镲这类宽带或高频敲击**在画面上几乎不动。于是再算一路**谱通量**：逐个频段看它相对上一帧的正向增量，得到
"这一帧谁在涨"，归一化后按**份额**把柱高抬回去 —— 底鼓抬低频、军鼓抬中频、踩镲抬高频。

全局门控只在真的出现敲击时才抬：持续的大音量不会被误判成敲击，整幅频谱不会一直发亮。
**这一层只抬受影响的频段，不是整排一起亮**，所以敲击的频谱形状能看出来。

#### 5.5.3 音色灵敏度（频谱形状）

频谱的"形状"才是音色，而早先整个画面统一按 2.1 次幂压缩，中高频细部被压到原来的三分之一上下，只剩"低频厚、高频薄"一个大轮廓，人声的泛音、镲的空气感、弦乐的共振峰全都糊在一起。两处改动都只动形状、不动低频峰的高度：

1. **频率相关幂次**：低频端仍是 2.1 次幂（保证高耸），向高频端过渡到 1.45，中高频细节因此更显眼
2. **谱锐化**：对对数压缩后的 120 段做一次局部对比增强，凸起更凸、凹陷更凹；每帧都从本帧的新值重算，不跨帧累积

两项都是定值，界面上没有开关。把高频端幂次改回 2.1、锐化归零，就回到原始观感。

#### 5.5.4 节拍预分析（提前点亮 · 2026-10-04）

前面两路鼓点响应（低频 onset、宽带瞬态）都是**因果的**：必须先听到，才可能亮。一个分析窗
512 点约 10.7 毫秒，再叠上 worker 往返与绘制的节拍，画面真正亮起来的时刻比耳朵晚
二三十毫秒 —— 这就是反馈里反复出现的"延迟感严重"。**这个延迟调参救不了**：参数只改灵敏度，
改不了因果性，唯一的根治办法是**提前知道鼓点在哪**。

所以播放前会把整首歌离线过一遍：解成 8kHz 单声道（整首只有 48kHz 的六分之一大），
用 16 段 Goertzel 滤波组算出低频能量包络与谱通量，再自相关测速、搜相位、吸附拍点，
得到一份"乐谱级"先验（节拍网格 + 每拍强度 + 响度曲线）。播放时按播放头查表，得到三件事：

| 收益 | 做法 | 数值 |
| --- | --- | --- |
| **提前点亮** | 在拍点**之前** 28 毫秒就开始升，到拍点时正好满 | 合成点击轨实测：拍点前 2ms 已达这一拍强度的 90% |
| **小节编排** | 每 4 拍换一次柱体形态（尖峰幅度 / 锯齿疏密 / 行波纹理） | 4 种形态循环，幅度都在 ±30% 以内 |
| **副歌预热** | 前瞻 2.5 秒的响度明显高过前 5 秒 → 提前扩动态范围 | 副歌前 1.6 秒开始热，前 0.5 秒到满 |

> **★ 先验只抬上限，从不替换。** 预测值与在线检测值取 `max`：歌没算准、播放头对不上、
> 或者用户直接关掉，这几项全部归零，画面**逐位退回**改动前的观感（回归脚本第 7 组钉的就是它）。
> 预分析本身也不碰音源 —— 只读本来就能读到的副本 / 源路径，不生成任何临时文件，
> 算不出来就是"这一首没有乐谱"，**绝不影响能不能播**。

代价：后台 worker 里跑，一次一首，队列最多 3 首（当前 + 后面两首），一首 4 分钟的歌约 0.5 秒。
结果存在曲目记录里（几 KB），第二次播放直接命中，不用重算。系统设置里可以关掉。

**为什么拍点不会整体偏早**：第 f 帧的窗是 `[f·HOP, f·HOP+WIN)`，但谱通量比的是"新进入窗的那一段"
与"刚离开的那一段"，新段从窗内偏移 `WIN−HOP`（48 毫秒）处开始、Hann 权重在那里最大 ——
所以这一帧检测到的事件时刻是 `f·HOP + (WIN−HOP)`，**不是**窗的起点。漏掉这一项会让整套拍点
比真值早约 48 毫秒，等于把延迟换个方向继续存在（合成点击轨实测：不补 −46ms、补了 +2ms）。

### 5.6 顶端张力、高频抖动与形态

柱高分 14 级绘制，级距约 0.077 —— 比它小的起伏会被四舍五入抹掉，越接近顶端相对影响越大，柱顶因此容易糊成一排方块。下面三层都是为了让顶端重新活起来，各自可以单独关掉。

**① 顶端补抖（低频率、大摆幅）**：在量化与一阶跟随**之后**再叠一层慢抖动，否则跟随器会把这个慢信号抹成常值偏移。幅度随"顶端程度"线性增强（低于 0.35 的矮柱完全不补，底噪区不会出现一排毛刺），
周期约 0.54 秒，读起来是"柱子砸下来又起来"。向上限幅 0.97，让高柱不至于一直顶满（真正要顶满的鼓点交给 §5.5 那一路）；向下最多压 0.45，这一项决定**落差上限**，设小了顶端只会微颤。

**② 顶端高频抖动**：再叠一路快的，周期约 61 毫秒（约 16Hz），幅度刚好跨过 1~2 个灰度级（0.12），看得见又盖不住慢摆幅。它与慢摆幅共用"越靠顶端越强"的权重，但相位是另一路、快约 9 倍。

**③ 顶端形态：锯齿尖峰**：方块来自平顶、曲线来自把相邻柱连成一条线，两者都不要 —— 改成每根柱顶再叠一小段竖条尖峰，各画各的、不连线，顶边呈锯齿。尖峰形状按**柱序确定性生成**
（而不是每帧随机）：同一根柱的形状稳定，只有柱高在动。矮柱不加尖，避免底部尽是碎刺。

### 5.6.1 回落干脆度（2026-10-04）

反馈"频谱回落还是不够干脆"之后单独量了一遍"信号停下之后的衰减曲线"，结论是拖尾不在柱体上：柱体本体一个分析节拍就掉掉六成，干脆；真正拖尾的是那条峰值指示线 ——
改之前半程要 455 毫秒、掉到 10% 要 1.5 秒，一次敲击过去，一条水平亮线还在空中挂近两秒。

两处改动：

1. **峰值线衰减收紧到每 tick ×0.90**：半程 120 毫秒、掉到 10% 约 420 毫秒。峰值线的语义是"最近一次峰值的指示线"，**必须比柱体慢**（否则与柱顶重合、看不出是两条），但不能慢成残影；停播后的收尾也统一到同一个系数
2. **回落插值跨度收到 0.6**：画面在两次分析之间做线性插值，下降只用 0.6 倍跨度（12 毫秒内到位），上升仍走满跨度保持起势顺滑。柱高**数值一个没动**，只改"什么时候把它画出来"

### 5.7 滑动感

早期的「值位移混合」在平滑频谱上完全不可见，随机抖动波的方向也是随机的（平均位移为零，看起来只是抖，不像滑动）。现在改为**相干行波**：每 6 根柱一个完整正弦周期，相位每帧推进，波峰以约 12 根柱/秒的速度**定向**从右向左移动。

### 5.8 性能与时延

- 频谱计算跑在 **Web Worker** 里，主线程零阻塞；Worker 起不来或长时间没有回包时自动退回同步计算，功能不变，只是占用一点主线程时间
- **分析节拍 50Hz（每 20 毫秒一 tick）**，由自己的定时器驱动；rAF 那条循环只管重画 —— rAF 的 16.7 毫秒步长会把 20 毫秒的门量化成 33 毫秒
- **画面按 60fps 重画，画的是两次分析之间的插值**。20 毫秒与 16.7 毫秒不成整数倍，直接画会出现"有时隔一帧才动、有时隔两帧才动"的错拍，看着就是卡；插值后每帧的值都在变，
  节拍到来时正好收敛到当前柱高。柱高**数值**不受影响（详见 [架构说明](架构说明.md)）
- 台阶响应时延：低频到 90% 约 40 毫秒，高频到 90% 约 80 毫秒
- worker 回包**立刻出图**，不再等下一帧
- 播放条那 52 格电平刻度按渲染节拍刷新；暂停后整机降到 15fps（只画收起动画）
- 可视化渲染由**定时器**驱动而不是动画帧回调，窗口被遮挡 / 切后台时不会被节流到 1fps；窗口隐藏 / 最小化则停掉整个循环
- 迷你窗复用主窗已经算好的柱体数据，不重复计算

### 5.9 帧率：频谱的帧率 = 三维场景的帧率

频谱画布和三维档案阵列跑在**同一个渲染队列**里，所以"场景掉到 30fps，频谱就只有 30fps"。觉得频谱有延迟感时先看这里，而不是去调分析参数。

两条措施：

1. **实测帧率显示在设置页**：系统设置 → `RENDER QUALITY` 的摘要行会写当前分辨率、抗锯齿、纹理倍率与实测帧率，偏低时还会写明"把上面的预设调到「性能」能明显改善"
2. **偏低就自动降一档画质**（只降一次，且只在用户没手动改过画质时）：实测中位帧率 `< 50` 且当前是预设档 → 按 `极高 → 高 → 原始 → 性能` 降一档，改完落盘并弹一条提示写明原因与改回的位置；已经是最低档就只提示一次、不再动
3. **播放中不做手动节流**（2026-10-08）：渲染直接跟着 rAF 走满显示器刷新率。原来播放中卡了一道 15ms 的门，60Hz 屏上恰好放行、看不出问题，但高刷屏（如 165Hz，rAF 步长 6ms）上等于"每三帧才画一次"，实测被削掉一半。暂停后仍降到约 15fps（收起动画本身也要画，不能停循环）

另外顺手削掉了每帧的样式重算：详情页的透明度、位移等属性改成**值变了才写**，不再每帧整片标记脏。

### 5.10 GPU 选型与低画质档的精度修正（2026-10-04）

**★ 程序此前一直跑在核显上。** 原代码想用一句开关指定"用直连显示器的核显"，但那个开关名在 Windows 的 Chromium 里根本不存在，等于什么也没指定 —— 程序落在核显上。
现在默认请求独显。退回核显有两种方式：命令行加 `--low-power-gpu`，或把 `settings.json` 里的 `preferDiscreteGpu` 写成 `false`。

这件事直接连到"档案图案模糊"。典型的 Intel 核显 + 独显笔记本（2560×1600@165Hz）上，核显撑不住三维档案 → §5.9 的自动降档把画质降到「性能」档 →
而这一档在 150% 缩放的屏上只渲染到屏所需像素的一半多点，低对比的刻线于是最先糊掉。为此给「性能」档补了三项几乎不花帧率的精度（其余档本来已是目标值）：

| 参数 | 原值 | 新值 | 理由 |
| --- | --- | --- | --- |
| 抗锯齿 | 关 | SMAA | 三维档案走离屏合成渲染，原先全程没有任何抗锯齿，刻线与卡片斜边的锯齿看着就是"糊" |
| 磨砂盖板透光 | 0.5 | 0.75 | 盖板是采屏幕缓冲做折射的，缓冲只有半分辨率时，压在下面的图案必然软 |
| 各向异性过滤 | 4 | 16 | 卡片是斜着看的，各向异性过滤对斜视纹理最有效，而且几乎免费 |

已经存过的画质设置会一次性迁移到新的档位定义：与某个旧档定义**完全一致**的旧设置，按**档位名**映射到当前定义，既保住当初选的档位意图，又真的拿到修正；自定义过的档位不会被误改动。

## 7. 媒体键与耳机线控

### 7.1 双通道

Windows 上媒体键有两条独立路径：

1. **系统媒体会话（SMTC）** — 系统媒体控制面板 / 部分蓝牙耳机走这条
2. **全局热键（Win32 RegisterHotKey）** — 键盘与多数有线耳机线控走这条

两条都注册，命中任意一条都能工作。

### 7.2 幂等注册

注册接口对本进程**已经注册过**的键会返回失败。早先的定时重试因此把健康状态误判成「被占用」，并把快捷键显示成不可用。现在注册是**幂等**的：先查注册状态，已在本进程名下的键直接跳过重注册。

### 7.3 自检

设置面板中的「媒体键」一行显示：

| 显示 | 含义 | 处理 |
| --- | --- | --- |
| `✓ 已注册` | 全部成功 | 无需处理 |
| `⚠ 被占用` | 部分成功 | 关闭冲突程序，或用应用内快捷键 |
| `✕ 全部被占用` | 全部失败 | 同上 |

媒体键在 Windows 上是**独占**资源，同一时刻只能被一个程序注册。

### 7.4 防抖

按键事件做了 300 毫秒防抖，避免部分耳机在单击时连发多次事件导致「播放→暂停」互相抵消（表现为按了没反应）。

```

#### 跟随封面（强调色动态取自封面）

在主界面（`app-rhine` 那套终端）里，强调色**默认从当前封面里取**：选中行左侧竖条、滑槽、进度条把手、卡片描边这些原本用琥珀色的地方，会随封面变色。

取色方式：把封面缩到极小后采样，按饱和度与明度加权挑出既亮又稳的色，再对**色相相近**的像素做一次聚类平均（避免逐帧跳色）；最后按当前是深色还是浅色主题校正明度，保证对比度。

边界处理：

| 情况 | 行为 |
| --- | --- |
| 没有封面 | 去掉内联变量，**回落主题默认色** |
| 封面是灰度图 / 采不出合格颜色 | 同上，回落默认（不会变成脏色） |
| 封面没变 | 指纹判重，不重复采样 |
| 深浅主题切换 | 按新底色**重算**明度修正 |
| 不想要 | 设置面板 → **COVER ACCENT** 关掉（默认开，关一次就记住） |

## 9. B 站缓存提取

用于播放**你本机已缓存**的 B 站音频。入口是**播放条上的电视图标**（`＋` 右边那个）。

### 9.1 流程

1. 点播放条上的电视图标 → 弹出系统的文件夹选择框，**选中 B 站缓存文件夹**
   ```
   手机端：<内部存储>\Android\data\tv.danmaku.bili\download\<av 或 ep 号>\<cid>\
   电脑端：<你设置的下载目录>\<标题>\…        （默认常在 Videos\bilibili\）
   ```选中后从该目录往下遍历（最多 7 层）并识别缓存条目
2. 读取缓存里记录的元数据（标题 / UP 主 / 封面）
3. **按内容而不是文件名判断哪个是音频**：能读到内轨信息就按轨道类型收，名字看不出内容时才退回扩展名兜底。同一集里多个清晰度取最高的一档
4. 把缓存的 `.m4s` 转成标准音频（去掉自定义头），并**固化一份到曲库目录**（`userData\library\audio\`），让播放与源缓存解耦
5. 补齐标题、歌手（UP 主）、封面后加入曲库

> 提示语已经改准：这一步**不会自己去找**缓存目录，而是紧接着请你选文件夹。
> 现在的提示是"请选择 B 站缓存文件夹（含 entry.json 或 audio.m4s）"，
> 选不出来时会提示"这个文件夹里没有识别到 B 站缓存"。

### 9.2 说明

- 只处理**本机已有**的缓存文件，不发起任何网络请求下载音频（只有封面图会按缓存里记录的地址取一次并缓存在本机，那只是图片）；原始缓存文件不被修改或删除
- **与源缓存解耦**：扫描时就直接把可播放副本固化进曲库目录，取音源的优先级是
  **固化副本 → 会话副本（从源缓存现做）→ 源缓存本身**，所以源文件夹被删掉 / 移走之后**照常能播**。三样都没有时，提示里会直接写明原因（例如"原始文件不存在（可能已在 B 站缓存里被删除）：C:\\...\\audio.m4s"），不再静默无声
- 曲库里记录的是**长效地址**（固化副本），另保留原始缓存路径用于溯源与"源还在时重建副本"。早先记的是扫描阶段的会话临时地址，进程一退出就失效却被持久化下来，那是"播放报错一个字节都不变"的元凶
- 列表来源标签如实标注：`B 站缓存 · 已存本地`（已固化）／ `B 站缓存`（仍依赖源）／
  `音源缺失`（源没了、副本也没有，是真的播不了 —— 不再伪装成普通曲目）
- 早期版本导入的曲目可能只有源路径、没有副本 —— 播放时会顺手补一份，也可在设置面板 `LOCAL AUDIO COPIES` 那行点「补齐未固化的」一次性处理
- 播放失败时会自愈一次：强制重建副本 → 再生成临时地址 → 再退回本地保留副本，并提示"正在重建可播放副本…"

### 9.3 数据管控

从 B 站缓存派生出来的可播放音频属于**派生数据**，因此：

- **播放用的临时副本**只写在系统临时目录，退出即擦除；会话目录清掉之后不影响使用：
  **已固化**的曲目直接用固化副本，**没固化**的点开哪首就按需重新生成哪首（幂等），不做启动时全库重建
- **唯一例外，且是刻意为之 —— 导入的 B 站缓存**会在曲库目录固化一份。源缓存在用户自己的 `Videos\bilibili` 下，随时会被客户端或用户手动清掉，不固化就等于把"这首歌还能不能播"押在一个不属于播放器的目录上。
  这份副本同样只存在于本机、不导出、不上传，且**没有任何清理逻辑会碰它**
- 固化副本写完会做**内容头校验**，坏副本（半截文件 / 被覆写成全 0 的那种）一律拒绝交付 —— 宁可判失败并说明原因，也不往曲库塞一个根本播不了的坏引用
- 每次提取都记一条本机审计记录（来源文件 + 产物体积）

> 管控细节见 [数据管控与合规](数据管控与合规.md)。

## 10. 封面 3D 档案

在封面区叠一层可旋转的 3D「档案」，并把**拆解 / 重组**做成可玩交互。

### 10.0 先说清楚：`.blend` 不能直接用，用的是它的导出件

仓库里带 Blender 工程和两个导出好的模型，但 `.blend` 是工程文件、运行中的程序读不了它，实际加载的是导出件：单体档案（装好的那个，默认视图）与拆解件（内部结构，22 个带部件标签的节点）。
本机没装 Blender 时无法重新导出或减面，直接用导出件是唯一可行的做法。

### 10.1 拆解 / 重组

点击封面左下角的「**拆解**」，档案会沿 Z 轴分层散开，露出内部六个部件；再点「**重组**」装回去。「复位」按钮同时把旋转角归零。

| 部件 | 英文 | 分层位置 |
| --- | --- | --- |
| 紧固件 | FASTENERS | 2.75 |
| 透明盖板 | OPTICAL COVER | 1.85 |
| 折射环组 | REFRACTIVE RINGS | 0.75 |
| 光学核心 | OPTICAL CORE | −0.15 |
| 信息基板 | SUBSTRATE | −1.10 |
| 背板与框架 | CARRIER | −2.05 |

拆解是**阻尼跟随**到目标层距，不是硬跳。两个模型**共用同一个中心偏移**（都按单体的包围盒居中）—— 各自按自己的包围盒居中的话，拆解时零件会整体错位。装好时显示单体、拆开时换成拆解件，两者在完全装好时外形一致，所以这个切换看不出来。

### 10.2 与播放状态联动

转速跟着播放状态走：**播放时正常转（0.30 rad/s），暂停时几乎停住（0.05）**，用阻尼过渡避免一按暂停就跳。这样 3D 和"正在放歌"这件事产生联系，而不是自顾自地转。

### 10.3 默认开启策略

**莱茵生命主题下默认开启**（这套主题的封面本来就该是那卷档案）；其它主题默认关闭。只要用户手动关过一次，就**永远尊重用户的选择**、不再自动打开。

### 10.4 为什么必须考虑性能

它要在封面区再开一个 WebGL 上下文，而频谱可视化已经占着 GPU。本机核显上为了帧率折腾过很久（见 [架构说明](架构说明.md)），所以：

| 措施 | 说明 |
| --- | --- |
| 按需加载 | 三维库 + 加载器 + 两个模型共约 7.4 MB，**只有开启时才注入**，不开启一行都不加载 |
| 启动延迟 | 若上次是开启状态，等首屏渲染完 1.5 秒再加载，避免抢启动带宽 |
| 限帧 30fps | 内部按 1/30 秒累积后才渲染；转得慢，看不出差别 |
| 窗口隐藏即停 | 最小化 / 隐藏时直接跳过绘制 |
| 像素比封顶 1.5 | 与可视化那边一致，不在核显上按 2 倍渲染 |
| 取景只做一次 | 按**单体**包围盒定相机（1.72 倍留白吃掉拆解的增量），拆解途中不重新取景，否则镜头自己缩放会晕 |
| 失败自关 | WebGL 不可用 / 模型读不到 / 脚本加载失败 → 提示一次并自动关闭，封面回 2D |

### 10.5 渲染与素材要点

- **透明底叠加**：画布背景透明，不遮住底下的专辑封面，档案像浮在封面之上
- **材质配色沿用原 Theme**：两个模型都没有贴图（合计 39 个材质、约 16.9 万三角形），材质名与原项目的材质表一一对应，未知材质再按名字兜底，保证不会渲染成纯白
- **锁定的三维库版本较老**：受限页面环境下加载不了 ES module，只能用传统 script 版本的构建
- **模型走本机 IPC 读取**：页面限制了对本地文件的直接读取，所以由主进程读字节、页面解析。该通道**只读且只放行白名单文件名**（不接受任意路径），遵守[数据管控](数据管控与合规.md)里那条结构性保证

### 10.6 与主题的关系

3D 档案在**四套主题下都可用**，但模型的材质配色固定用原 UI 那套（材质名就是它的材质体系），不跟随主题换色。

## 11. 音乐档案终端（莱茵生命终端底座）

主界面是一套 1920×1080 的档案终端界面：整套 UI 挂在舞台容器里，按 `min(窗口高/1080, 窗口宽/1840, contain × 1.2)` 整体缩放（纵向按高度铺满、横向最多裁 40 基准像素/侧，实际裁量写进界面的缩放变量）。
音乐库被映射成"档案"，界面上的每一块都改造成了播放器的一部分。

### 11.1 三块界面各自负责什么

| 界面 | 位置 | 对应的播放器功能 |
| --- | --- | --- |
| 档案阵列（五列、每列八份、可循环） | 画面中部三维阵列 | 播放列表：曲目按顺序轮转进五列 |
| 抽出的档案卡片 | 画面左侧三维模型 | **当前曲目的封面印在正面标签板上**（含 `NO.` / 曲名 / 艺术家 / 专辑） |
| 详情区 | 右侧（宽 636 / **底边锚定 112**） | 曲目面板：封面、曲目信息、**实时频谱 ⟷ 歌词列表**（顶部工具栏分段开关切换，见 §4.4） |
| 播放条 | 左下（left 59 / bottom 80 / **900×148**） | 传输控制、进度、播放模式、收藏、导入、B 站缓存导入、播放列表入口；**点曲名区 = 打开当前这首的档案**，**点其它位置 = 回到档案阵列**（控件区不触发，弹窗开着时先收弹窗） |
| 播放列表（抽屉） | 左下（left 59 / bottom **238** / **900×560**，`☰` 开合） | 顶部**排列顺序下拉框**与**搜索框**（曲名 / 艺术家 / 专辑，回车播第一条命中、ESC 清词再按收抽屉、`✕` 清除）＋ 曲目列表：点行播放、**点曲名打开这一首的档案**、`✕` 移除、`↳` 下一首播放、`♡` 收藏、`◐` 昼夜 |

**排列顺序**：导入顺序（默认）/ 曲名 / 艺术家 / 专辑 / 时长（短→长）/ 播放次数（多→少）/ 最近添加。曲目顺序就是档案阵列的顺序，所以排序是**列表与阵列一起变**；中文按拼音排，相同键再按导入次序兜底。

**打开与双击**：回车 / `PLAY TRACK` / 点标题 = **打开档案并播放**（进详情 + 起播这一首，早先"只读不播"的口径已改掉）；**双击档案卡片**与之等效，单击仍然只是选中。
打开与起播走同一条路径，所以右侧详情、播放条、频谱、三维阵列指的永远是同一首。起播时的"自动打开档案"由设置里的 `OPEN ARCHIVE ON PLAY` 控制；开屏结束是终端直接切场景，不走这条路，所以启动不会自己出声。

> **★ 版面遮挡的几条硬约束。** 所有面板都是 1920×1080 舞台里的绝对定位，谁压到谁只能靠矩形算：
>
> 1. **播放条底边距只能是 80，不能再往下压**：底部还有页脚（`bottom: 35`）与 `.powered`（`bottom: 62`）
>    两行。曾经压到 40，播放条就把页脚整行盖住了 —— 也就是反馈里的"全屏后下方存在遮挡"。
>    80 时播放条底边到 1000、页脚顶边 1032，留 32px 空档；抽屉跟着播放条保持 10px 间距。
>    "上下不那么空"靠缩放策略解决，不靠挤压底部间距
> 2. **右下角那一列 `x 1586–1861` 只归 `.powered`**：详情面板右边界是 1790，与它必然在横向重叠，
>    只能靠纵向错开 —— 所以详情区改成**底边锚定**（底边锁在 y 968），内容再长也只向上生长。
>    改之前实测重叠 204×24 像素
> 3. **播放条与抽屉的宽度上限是 910**：右侧面板从 x 970 起，取 900 时右边界 959，留 11px
> 4. **设置弹窗按内容自适应 + 内部滚动**（`max-height: 940px`）：它原来是固定 786px，
>    而设置项加起来有 1656px，超出的部分直接溢出到面框外面盖住播放条与列表
>
> 这几条是用版面探针实测出来的，改布局后应该重跑一遍 ——
> 绝对定位的界面凭肉眼看截图发现不了几十像素的压边（见 [维护指南](维护指南.md)）。

**封面是怎么印上去的**：模型正面本来就有一块印刷标签板，场景在它上面盖一块封面板，画布上画封面（按宽高比居中裁切填满）＋ `NO.` / 曲名 / 艺术家 / 专辑 ＋ 抬头与细线。
封面板在外壳之外，所以解密前后都可见；只有被抽出的那一张卡片带封面，阵列里其余卡片保持素面。换选时收回中的卡片会把封面**快照成独立纹理**，避免共用一张纹理导致旧卡片的封面跟着变。

### 11.2 操作

- **选档**：左右方向键切列、上下方向键翻档案、回车**打开档案并播放**（进详情 + 起播这一首）。已经在详情里时，回车是**播放 / 暂停这一首**；档案栏底下那行提示写的是「`ENTER` 读取」。
  `ESC` 或详情层左上角的返回键回到阵列
- **起播即打开档案**（默认开，设置里可关）：点一行播放或按播放键之后，会自动切到这首歌的详情并收起播放列表抽屉 —— 列表与档案两个入口的结果保持一致
- **播放列表（`☰`）**：点一行＝播放并打开它的档案；`✕` 移除这首歌（**当场从列表与曲库里一起消失**，剩下的行号立刻重排）；`↳` 下一首播放；`♡` 收藏。抽屉点外面会自动收起 —— 它是压在左侧三维阵列上的浮层，不收起来就会吃掉点阵列的那一下
- **播放条**：`⏮ ▶ ⏭`、播放模式 `↻`（列表循环 / 顺序播放 / 单曲循环 / 随机播放）、**播放速度 `1×`**、收藏、导入（右键 ＝ 导入整个文件夹）、**电视图标 ＝ 导入 B 站缓存**（见 §9）、`☰` 播放列表；
  底部一行是 当前时间 / 进度条 / 总时长 / **音量条**（与背景音乐音量各自独立）
- **拖拽导入**：把文件或文件夹直接拖进窗口即可（与 `＋` 同一条管线）
- **播放位置**：只为"下次接着放"而存，不显示、不当作播放记录。落库有两条保护：
  **每 4 秒一次的兜底**（防止崩溃 / 强杀丢位置）＋ 暂停 / 切歌 / 关窗 / 切后台时各落一次；下次从上次的位置续上（离曲尾不足 5 秒或不足 4% 则从头开始，避免一进来就结束）
- **曲库加载**：读库**不挡启动** —— 界面先按空库立起来（占位档案），读回来之后再刷新一遍各处。
  > ★ **超时不等于空库**：一轮读不完会先提示"正在读取曲库…"，再用更长的超时重读一次并补上，
  > 两次都空才认空库。397 首、3.5 GB 的库实测读出就要 2.9 秒，冷盘上很容易超 ——
  > 早先按固定短超时把整轮当空库，表现为"一打开之前导入的歌曲全不见了"，数据其实一条没少
- **详情区**：曲目面板（**没有页签**）—— 封面、曲名与艺术家、元数据四格、顶部工具栏「可视化 ⟷ 歌词」分段开关，往下是**大尺寸实时频谱**（或）**歌词滚动列表**，
  可视化时频谱下方还有一行"当前歌词"字幕；底部 `＋ SAVE TRACK` 收藏、`PLAY ▶` 播放或暂停

### 11.3 实时频谱

详情区右侧整块竖向空间留给可视化与歌词，2.3.0 起这块内容有**两种形态**，用顶部工具栏的分段开关切换（见 [§4.4](#44-右侧可视化--歌词切换230-新增)）：

- **可视化模式**（默认）：大尺寸实时频谱 + 频谱下方一行"当前歌词"字幕
- **歌词模式**：频谱让位给**歌词滚动列表**，当前行高亮居中

分析部分是第 5 章那套自研管线（参数沿用 1.3.0 取值，链路与取值见 §5.2–§5.8）：

- **五种样式**：融合 / 音色 / 条形 / 圆环 / 波形（默认融合），配色取终端令牌
- **播放条**：52 格电平刻度，直接取频谱柱的采样值，跟着渲染节拍走，只在像素高度真的变化时才写 DOM
- **播放条与播放列表不使用背景模糊** —— 背后是持续动画的三维场景，每帧重新模糊一大块区域并不便宜
- **取不到运行中的音频上下文就不接管音频元素** —— 宁可没有频谱，也不能没有声音

**自检与核对**：`?viztest=1` 会用合成信号（粉噪打底 + 基音与谐波 + 扫频 + 每 4 秒一次鼓点包络）驱动频谱，用来在没有真实音频时确认画面链路正常；`?diag=1`（或本机诊断开关）把播放内核与频谱实例
挂到全局对象上，用来核对"点这首有没有接上上次的位置"与渲染帧数。

### 11.7 恢复旧版曲库

新版把界面从随机端口改成固定端口 41739，而 **IndexedDB 是按"源"隔离的**（scheme + host + port）—— 随机端口等于每次启动都换存储域，于是旧版导入过的曲目在新版里读不到。
它们并没有丢，只是分散在几个旧源里（音频以 Blob 形式存在库中）：

| 旧源 | 位置 |
| --- | --- |
| 早期独立播放器 | 当前 profile 的 `file://` 源 |
| 1.4.0 之前的终端界面 | 当前 profile 的 `http://127.0.0.1:<随机端口>` 源 |
| 更早的一份独立安装 | 另一个 profile（`%APPDATA%\music-player-desktop`）的 `file://` 源 |

恢复入口是一条命令：

```
scripts\恢复旧曲库.ps1
```

它分三步：① 恢复当前 profile 里的旧源；② 用 `--user-data-dir` 指向旧 profile 再恢复一次；③ 回到当前 profile 把交接区吃进来。每一步都会弹框报告读了多少条、音频多少个、新增/跳过多少首。

要点：

- 一个页面两种模式：在旧源上把记录（字段 + 音频字节 + 封面）交出来，在新版的源上写进曲库
- 对每个旧端口源，临时起一个只读静态服务把页面送到那个源上 —— **数据只有在该源里才读得到**
- **不往音乐目录写任何文件**：本项目对派生数据有"不导出"的约束（见 [数据管控与合规](数据管控与合规.md)），跨 profile 的交接只走系统临时目录，吃进曲库后立即删除
- 合并按"标题 + 艺术家"去重，可重复运行；**旧数据全程只读**，不改不删

### 11.4 与终端的一致性

- 所有播放器元素都在舞台容器内，跟随 1920×1080 基准一起缩放，不会出现"界面缩了、播放条没缩"
- 配色、字号、字距全部取自终端自身的令牌：纸面 `#e8e5e1`、细线 `#c1b8a7`、实心 `#252820 / #f0eee5`、暖色强调 `#9b7247`、橄榄 `#565c46`
- 昼 / 夜切换（播放列表右上角 `◐`）的夜态同样用终端的深色家族
- 提示条复用终端自己的组件

### 11.4.1 玻璃质感（2026-10-04）

范围与浓淡是刻意克制的：**只做详情区 + 弹层**，播放条与播放列表不做（背后是持续动画的三维场景，每帧重新模糊一大块区域并不便宜）：

| 项 | 详情区 | 弹层（设置 / 检索 / 收藏） |
| --- | --- | --- |
| 底色 | `rgba(243,241,235,0.7)` | `rgba(240,238,231,0.74)` |
| 毛玻璃 | `blur(12px) saturate(1.12)` | `blur(16px) saturate(1.14)` |
| 描边 | `1px rgba(255,255,255,0.55)` | `1px rgba(255,255,255,0.6)` |
| 圆角 | `14px` | `14px` |
| 高光 | `inset 0 1px 0 rgba(255,255,255,0.72)` + 底部深内阴影（厚度感） | 同（更亮一档） |
| 投影 | `0 18px 48px rgba(90,78,58,0.14)` | `0 26px 95px rgba(99,81,58,0.22)` |

深色主题换成"深玻璃"：底色 `rgba(30,34,28,0.62)` / `rgba(26,30,24,0.7)`，高光与投影同步改暗。

两个必须知道的点：

- **毛玻璃是"从背后取样"** —— 元素底色必须**半透明**才看得出效果，写成不透明就等于没加
- **无障碍**：系统开了"减少透明"时，毛玻璃与半透底一起收掉、换回不透明纸面 —— 玻璃不能牺牲可读性

### 11.5 曲目信息与标签编码

界面上**不再出现档案术语**：详情区、检索弹窗、选中提示里的字段一律按播放器语义显示 —— 科室→艺术家、编目范围→时长、相关人物→专辑、权限→来源格式。音乐库为空时也用同一套版式的占位态，不会退回旧的"档案内容"排版。

标题 / 歌手 / 专辑来自音频标签。ID3 文本帧的编码有四种，解码按编码字节分派：

| 编码字节 | 处理 |
| --- | --- |
| 1 | 按 BOM 决定 UTF-16LE / BE（不信任运行时对 UTF-16 的默认字节序） |
| 2 | UTF-16BE |
| 3 | UTF-8 |
| 0 | 先严格试 UTF-8；不成立且高位字节占比 > 50% 时按 GB18030 解；都不是才落回 windows-1252 |

另外：

- ID3v2.2 的三字节帧头（`TT2` / `TP1` / `TAL` / `PIC`）也能读
- 没有 v2 标签时读文件末尾 128 字节的 ID3v1 兜底
- 内嵌封面按图片描述的实际编码跳过描述段（UTF-16 描述以 `00 00` 结尾，逐字节找会截断）
- **旧版本的乱码会被自动修回来**：早先的版本写死 UTF-8，中文标签已按乱码存进曲库；启动时只对"看起来就是乱码"的条目重跑一次识别，修好后写回并从提示条告知修了几首

### 11.6 已知边界

- 档案阵列一屏只有五列 × 八份 ＝ 40 个位置；曲目超过 40 首时，多出来的部分只在播放列表里可见
- 播放列表是覆盖式浮层，在详情视图里会盖住左下的说明行（点面板外面、或在列表里点歌之后会自动收起，见 §11.2）
- 详情展开时，在三维阵列上点**别的**档案会切过去并退回阵列；点正在特写的那一张不算"切换"（那多半是想拖拽看它，保持原样）。⚠ 这一条在无头环境里判不了：无头下三维动画时间轴是停住的，详情取景根本没跑起来
- 终端的界面由本机静态服务提供，**端口固定为 41739**：界面源必须跨启动稳定，否则按源隔离的曲库、收藏、播放进度会读不回来。端口被占用时退回随机端口，此时会写一条日志说明本次的存储域与上次不同
