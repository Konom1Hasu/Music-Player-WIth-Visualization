# 架构说明

本文档说明项目的技术架构、进程划分、关键设计决策与历史踩坑记录。

---

## 1. 技术栈

| 层 | 技术 |
| --- | --- |
| 运行时 | Electron 31.7.7（win32-x64，便携免安装） |
| 主进程 | Node.js（Electron 内置），CommonJS |
| 渲染进程 | 原生 HTML / CSS / JavaScript，**无框架、无构建步骤** |
| 通信 | `contextBridge` + `ipcRenderer.invoke / send` |
| 频谱分析 | Web Worker + 自研 Goertzel 实现 |
| 打包 | PowerShell 脚本（无 Node.js 依赖） |

### 为什么不用框架

整个界面是单文件 `index.html`（约 123 KB），包含样式、图标、状态管理和渲染逻辑。
没有 webpack / vite / React，意味着：

- 改一行 CSS 存盘即生效，不需要构建
- 源码与运行时文件一一对应，构建脚本只做 `Copy-Item`
- 调试时可以直接在 DevTools 里看到未经编译的原始代码

代价是文件较大，因此内部用清晰的注释分节（`/* ===== 段落 ===== */`）组织。

## 3. 主进程设计决策

### 3.1 Chromium 命令行开关

```js
app.commandLine.appendSwitch('disable-features',
  'CalculateNativeWinOcclusion,BatterySaverMode,IntensiveWakeUpThrottling,'
  + 'ThrottleDisplayFrequency,ThrottleFrameRate');
app.commandLine.appendSwitch('disable-backgrounding-occluded-windows');
app.commandLine.appendSwitch('disable-renderer-backgrounding');
app.commandLine.appendSwitch('disable-background-timer-throttling');
app.commandLine.appendSwitch('enable-features', 'HardwareMediaKeyHandling,MediaSessionService');
```

每一条都有明确原因：

| 开关 | 原因 |
| --- | --- |
| `CalculateNativeWinOcclusion` 关闭 | Windows 判定窗口被遮挡 → Chromium 降到 1 fps。**不关掉的话，「打开小窗后主窗 rAF 减半」** |
| `BatterySaverMode` / `IntensiveWakeUpThrottling` | 省电模式会节流后台定时器 |
| `ThrottleDisplayFrequency` / `ThrottleFrameRate` | 防止 Chromium 主动降帧 |
| `disable-backgrounding-occluded-windows` | 同上 |
| `disable-renderer-backgrounding` | 渲染进程在后台时不降优先级 |
| `disable-background-timer-throttling` | 后台标签页的 `setTimeout` 不被压到 1 s |
| `HardwareMediaKeyHandling,MediaSessionService` | **Electron 默认关闭**，导致耳机媒体键根本送不到页面的 Media Session |

**刻意不设**的开关（都试过，弊大于利）：

| 开关 | 不设的原因 |
| --- | --- |
| `enable-gpu-rasterization` | 让 2D canvas 走 CPU 光栅（Skia）再上传合成，主线程不会被 GPU 光栅回压阻塞 |
| `force-discrete-gpu` | 用直连显示器的核显（Intel UHD），避免独显→核显跨显卡回拷 |
| `disable-direct-composition` | blt 呈现会把多窗口合成串行化到主进程 —— **这正是「开小窗后主窗 rAF 减半」的元凶**。保留 flip-model（DComp），它对多窗口是并行呈现 |
| `disable-frame-rate-limit` / `disable-gpu-vsync` | 会把呈现改坏，产生无节流撕裂 |

### 3.2 窗口配置

**主窗口**

```js
width: 1380, height: 920, minWidth: 900, minHeight: 640,
backgroundColor: '#111629',
autoHideMenuBar: true,
webPreferences: {
  contextIsolation: true,
  nodeIntegration: false,
  preload: path.join(__dirname, 'preload.js'),
  backgroundThrottling: false   // 最小化/隐藏时仍满帧 → 小窗可视化不暂停
}
```

刻意**不调用** `webContents.setFrameRate()`：可视化循环已由页面内定时器自驱动，
显式设置帧率会干扰双窗口时合成器的 BeginFrame 调度。

**迷你窗**

```js
width: 330, height: 356,
minWidth: 150, minHeight: 96, maxWidth: 720, maxHeight: 900,
frame: false,
transparent: false,          // 透明窗口在 Windows 上强制昂贵合成路径，拖累主窗
alwaysOnTop: true,
resizable: false,
skipTaskbar: true,
hasShadow: false
```

配套设置：

- `setAlwaysOnTop(true, 'screen-saver')` — 最高置顶层，可盖过无边框全屏游戏
- `setIgnoreMouseEvents(true, { forward: true })` — 默认点击穿透，光标悬停到控件上时
  由页面通过 `mini-set-ignore` 临时恢复可点
- 800 ms 定时 `setAlwaysOnTop + moveTop()` — 无边框全屏游戏运行时会重新抢 Z 序
- `setFocusable(false)` — 点击小窗**不会**让游戏失焦（代价：不能用原生
  `-webkit-app-region: drag`，必须自己实现拖动）

### 3.3 迷你窗拖动与缩放

历史踩坑：缩放曾经"很奇怪"，用渲染层的 `e.screenX` 再除以显示器缩放因子，
但 **Chromium 的 `screenX` 本来就是 DIP（已含缩放）**，再除一次 → 125% 缩放下
窗口增长比光标慢 20%。

最终方案：位移与缩放**全部**改用主进程的 `screen.getCursorScreenPoint()`，
两边处于同一坐标系，彻底不涉及 `scaleFactor`。拖动期间锁定窗口尺寸。

点击穿透原本靠「页面 mousemove → IPC → 主进程」，快速移动后立刻按下时状态还没切过来
→ "有时候拖不动"。现在主进程按 **50 ms** 轮询光标位置（页面只回报可交互矩形），
即使某个 mousemove 丢了也会在 50 ms 内自愈。

### 3.4 媒体键

```js
const tryReg = (key, fn) => (d[key] === true ? true : regHotkey(key, fn));
```

**幂等注册**是关键。早期每次重试都把全部键重注册一遍，而 Electron 对
「已被本程序占用」的键会返回 `false`（`GlobalShortcutListener` 里有 `IsRegistered` 检查）
—— 于是重试反而把正常状态改写成"失败"：界面误报"被占用"，重试永不停止。

现在先查 `hotkeyState.detail`，已成功的键直接跳过。重试定时器 6 s 一次，
在 `media && fallback` 都成功时自动清除；主窗 `focus` 时也补注册一次。

## 4. 渲染进程设计决策

### 4.1 频谱管线

见 [功能说明 § 5](功能说明.md#5-频谱可视化)。要点：

- **Goertzel 而非 FFT**：只需要 120 个特定频点的能量，Goertzel 单 bin 计算内循环
  仅乘加，比完整 FFT 更快，且可以精确指定对数分带的频点
- **放在 Worker**：主线程零阻塞；Worker 构造失败时降级为同步计算
- **定时器驱动而非 rAF**：窗口被遮挡 / 最小化 / 后台时 `requestAnimationFrame` 会被
  Chromium 节流到 1 fps，而可视化必须保持流畅
- **主窗最小化时降频**：主进程通过 `win-state` IPC 通知页面，把 CPU/GPU 让给其它应用

### 4.2 柱体数据的跨窗口复用

小窗**不重新计算**频谱。主窗每帧把柱体数组通过 `mini-bars` IPC 推给小窗，
小窗只负责按自己的画布尺寸绘制。

这解决了两件事：

1. 避免两套音频分析各自跑一遍，CPU 翻倍
2. 保证两个窗口的柱体完全同步，视觉一致

### 4.3 呈现状态机

```js
let mode = 'list'; // list 列表循环 | order 顺序播放 | single 单曲循环 | shuffle 随机
const MODES = [
  { key: 'list',   label: '列表循环', icon: IC.repeat },
  { key: 'order',  label: '顺序播放', icon: IC.order },
  { key: 'single', label: '单曲循环', icon: IC.single },
  { key: 'shuffle',label: '随机播放', icon: IC.shuffle }
];
```

### 4.6 音乐档案终端里的播放器（`app-rhine/`）

> **来源署名：`app-rhine/` 这套界面底座（源码 + Blender 工程文件）来自 B 站 UP 主
> [@路北路陈](https://space.bilibili.com/3546646728820438)**
> （仓库 [LBEILC/RhineLabUI](https://github.com/LBEILC/RhineLabUI)，MIT）。
> 本节描述的是**反向整合**这一层（把播放内核接进既有界面）。

主界面（莱茵生命终端）是 TypeScript + Three.js + Vite 的独立前端，
构建产物同步到 `app/ui/`，由主进程的小型静态服务（随机端口 + 路径穿越防护）提供，
渲染进程加载 `http://127.0.0.1:<port>/index.html`。

**播放器不另起一套坐标系。** 终端的 UI 全部在 `#stage` 里：

```js
const scale = Math.min(innerWidth / 1920, innerHeight / 1080);
$("#stage").style.transform = `translate(-50%, -50%) scale(${scale})`;
```

播放条 / 播放列表必须 `appendChild` 到 `#stage`，并按 1920×1080 的坐标写死位置
（`left:59px; bottom:124px`）。挂在 `document.body` 上就会出现
"界面缩了、播放条没缩"的割裂（默认窗口 1380×920 时缩放系数是 0.719）。

**模块分工**

| 文件 | 职责 |
| --- | --- |
| `app-rhine/src/player.ts` | 音乐库（IndexedDB）、播放内核、导入（文件 / 文件夹 / NCM / B 站）、播放条、播放列表、频谱、曲目面板的 HTML 片段 |
| `app-rhine/src/data.ts` | 把曲目映射成"档案记录"（`records`），供三维阵列与检索使用 |
| `app-rhine/src/main.ts` | 终端本体。详情区渲染时按 `hasSongs()` 分支：有曲目 → `songDetailMarkup()`，空库 → 原来的档案版式 |

**两个方向的桥**

- 终端 → 播放器：`playAt()` / `togglePlay()` / `toggleFav()` 等直接调用
- 播放器 → 终端：`window` 事件。`rhine-track`（正在播放的曲目变了 → 阵列选中态与详情区跟上）
  与 `rhine-lyrics`（歌词异步补全 → 只重绘歌词页签）

**为什么不复用终端的 `AudioContext`**：终端的 `TerminalAudio` 有自己的上下文与音轨。
播放器需要的是**接在 `<audio>` 元素上的** `MediaElementAudioSourceNode`，
因此自己建一个上下文，并在取不到 `running` 状态时放弃可视化而不是接管音频元素。

**★ 本地 UI 服务的端口必须固定（`UI_PORT = 41739`）**

界面跑在 `http://127.0.0.1:<port>`，而 **IndexedDB 是按"源"隔离的**
（scheme + host + port 一起算）。之前用 `listen(0)` 每次启动随机端口，
等于每次开程序都是全新的存储域 —— 曲库、收藏、播放进度全部读不回来，
而"进度记忆""收藏"正是播放器的核心需求。现在固定端口，源稳定，数据跨启动保留；
端口被占用（`EADDRINUSE` / `EACCES`）时才退回随机端口，并写一条日志说明
本次的存储域与上次不同。可用环境变量 `RHINE_UI_PORT` 覆盖。

**★ 读曲库不挡启动（2.0.0）**

`initPlayer()` 先 `buildUI()` + `syncRecords()` 把界面立起来（空库时是"导入音乐"占位档案），
再 `void loadLibrary().then(applyLibrary)` 把数据补进来，由 `notify()` 触发
档案阵列 / 刻度 / 播放列表 / 详情面板各刷一次。

这是为了**先前的固定 1.5 秒超时兜底**：`Promise.race([idb.all(), 1.5 秒后返回空数组])`。
IndexedDB 首次打开要 1.2–8.5 秒（取决于库大小与磁盘），一旦超时，
那一整轮就以空库运行 —— 曲目不显示、每首歌的 `pos` 读不回来，
于是"续播"从根上失效（详见 [更新日志 2.0.0](更新日志.md)）。
现在的兜底是 8 秒，且只在真的没有任何数据回来时才生效。

**渲染节拍与配色**

- 频谱：worker 分析 **30Hz**（与 1.3.0 的分析节拍一致），画布渲染**播放中 60fps / 暂停后 15fps**；
  `Spectrum.render()` **不做二次插值**，只是把同一份 `bars` 按更高的节拍重画 ——
  柱高数值与 1.3.0 逐帧一致（见 [功能说明 § 11.3](功能说明.md)）
- 播放条与播放列表**不用 `backdrop-filter`**：背后是持续动画的三维场景，
  每帧重新模糊 880×134 并不便宜
- 整机深色主题靠 `body.theme-dark` 逐类覆盖终端自己的样式表（终端配色是写死的）；
  播放器新增的类名要同时挂 `theme-dark` 与 `rhine-night`，前者管终端、后者管播放条

## 6. 数据管控层

程序能解出两类**派生数据**（`.ncm` 解出的音频、B 站缓存剥离头后的 m4a 副本），
它们受原平台版权约束，因此主进程里有一层独立的管控实现，见 [数据管控与合规](数据管控与合规.md)。

### 6.1 会话临时目录

```js
const SESSION_ID      = crypto.randomBytes(6).toString('hex');
const SESSION_TMP     = path.join(os.tmpdir(), 'mp-session-' + SESSION_ID);
const SESSION_AUDIO_DIR = path.join(SESSION_TMP, 'audio');
```

所有派生数据只允许落在这里。生命周期：

```
启动  → sweepStaleSessions()   清掉上次崩溃残留的 mp-session-*
        purgeLegacyAudioCache() 擦除 1.0.x 遗留在 userData\bili_audio 的长期副本
运行  → 解密/提取写子目录，读完立即 wipeDir()
退出  → will-quit 拦截 → shutdownSessionTmp() → 真正退出（4 秒兜底）
```

`will-quit` 用 `event.preventDefault()` + `quitCleanupDone` 标志实现"先清理再退出"，
避免 `app.quit()` 递归回到同一个 handler。

### 6.2 擦除

```js
function wipeFile(p) {
  // ★ 硬链接保护：nlink > 1 → 只摘目录项，绝不覆写
  if (st.isFile() && st.nlink > 1) { fs.unlinkSync(p); return; }
  // 否则：0 覆盖 + fsync + unlink，受 WIPE_BUDGET 限制
}
function wipeDir(dir) { /* 递归 wipeFile 后 rmdir */ }
```

单会话覆盖上限 256 MB —— 超出部分只删不擦，防止退出时因为几十个大文件而卡住。

> **为什么必须有 `nlink > 1` 这道闸**：覆写是"写这个 inode"，如果该文件还有别的目录项
> （硬链接），覆写会连别处那份一起毁掉，而随后的 `unlink` 只摘掉自己这一项 ——
> 表现为"文件还在、内容已经没了"。v1.1.0–v1.1.3 曾因此把用户的 B 站缓存原地清成全 0，
> 详见 [数据管控与合规 §2.1.1](数据管控与合规.md)。配套地，`ensureM4a` 也不再使用
> `linkSync`，一律复制出独立副本。
>
> **通用教训**：任何"擦除/覆写"逻辑都要在写之前确认这块内容的独占性。

> **诚实说明**：SSD 的磨损均衡与 TRIM 使软件层无法保证取证级不可恢复。
> 覆盖写零只是提高恢复门槛的**威慑**手段；真正的保底是"根本不长期落盘"。

### 6.3 结构性不可导出

这不是"没做导出按钮"，而是**没有可用的路径能把字节写到磁盘**：

- 28 个 IPC 通道没有任何一个接受"输出路径"参数
- `preload.js` 的 16 个暴露方法里没有写文件方法
- 渲染进程 `contextIsolation: true` + `nodeIntegration: false`，拿不到 `fs`
- 派生数据在渲染进程里只作为 `Blob` / `objectURL` 存在

### 6.4 审计日志

`userData\audit.log`，每行一条 JSON，记录 `t / v / sid / event / src / bytes / ext / result`。
上限 500 条自动裁剪。三类事件：`ncm-decrypt`、`bili-extract`、`bili-scan`。

写入失败（磁盘满、权限问题）静默忽略 —— 审计不能影响播放主流程。

### 6.5 回归验证

`scripts\数据管控验证.js` 提供 16 项断言，`node` 直接跑，不需要 Electron。
其中擦除逻辑的测试是**从 `main.js` 源码里摘出实现再执行**，
所以测的是即将发布的真实代码文本，而不是另写一份复制品。

## 7. 已知限制

| 限制 | 原因 | 状态 |
| --- | --- | --- |
| 独占全屏游戏下悬浮窗不可见 | Windows 让 DWM 交出显示输出，任何普通窗口都无法覆盖 | 无解，建议游戏改「无边框窗口」 |
| 独占全屏游戏下悬浮窗收不到鼠标事件 | 系统层面限制 | 已提供全局快捷键移动/缩放/锁定作为替代 |
| 媒体键被其它程序占用时无响应 | Windows 媒体键是独占资源 | 已提供自检 UI + 备用组合键 + 6 s 自动重试 |
| 60 Hz 显示器下可见帧率上限 60 | 垂直同步 | 目标为「稳定 60 + 无卡顿」，而非追求更高数字 |
| 集成显卡上软件渲染路径较慢 | 走 CPU 光栅 | 设置面板可切换渲染模式 |
