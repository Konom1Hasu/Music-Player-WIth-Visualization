# 架构说明

本文档说明项目的技术架构、进程划分、关键设计决策与历史踩坑结论。

## 1. 技术栈

| 层 | 技术 |
| --- | --- |
| 运行时 | Electron 31.7.7（win32-x64，便携免安装） |
| 主进程 | Node.js（Electron 内置），CommonJS |
| 渲染进程 | 原生 HTML / CSS / JavaScript，无框架、无构建步骤 |
| 通信 | `contextBridge` + `ipcRenderer.invoke / send` |
| 频谱分析 | SelfMusic 移植（96 段对数分带 + 16 项可调显示层，见 §4.1） |
| 打包 | PowerShell 脚本（无 Node.js 依赖） |

项目中提供了一个用来兜底的轻量界面 `app/index.html`（文件体积约 123 KB）。这个页面完全采用单文件结构编写，没有引入 webpack、vite 或者 React 这类前端构建工具与第三方框架。开发时只要修改其中的一行 CSS 样式并保存，改动就会立刻在界面上生效。源文件结构与运行时的实际文件保持一一对应的关系，发布阶段的构建脚本也仅仅是执行 `Copy-Item` 命令将文件复制到目标目录，因此用户在 DevTools 开发者工具中查看到的直接就是未经转译或压缩的原始代码。这种纯原生的做法带来的取舍是单个源码文件偏大，为了方便维护，代码内部通过显式的注释块（例如 `/* ===== 段落 ===== */`）来划分不同的逻辑区域。至于功能更完整的主界面 `app-rhine/`，则使用了 TypeScript + Vite 体系进行模块化构建，具体实现细节见 §4.6。

## 3. 主进程设计决策

### 3.1 Chromium 命令行开关

```js
app.commandLine.appendSwitch('disable-features',
  'CalculateNativeWinOcclusion,BatterySaverMode,IntensiveWakeUpThrottling,'
  + 'ThrottleDisplayFrequency,ThrottleFrameRate');
app.commandLine.appendSwitch('disable-backgrounding-occluded-windows');
app.commandLine.appendSwitch('disable-renderer-backgrounding');
app.commandLine.appendSwitch('disable-background-timer-throttling');
app.commandLine.appendSwitch('enable-features', 'HardwareMediaKeyHandling,MediaSessionService');
```

每一条开关的启用都有明确的技术原因：

| 开关 | 原因 |
| --- | --- |
| `CalculateNativeWinOcclusion` 关闭 | Windows 判定窗口被遮挡 → Chromium 降到 1 fps。**不关掉的话，「打开小窗后主窗 rAF 减半」** |
| `BatterySaverMode` / `IntensiveWakeUpThrottling` | 省电模式会节流后台定时器 |
| `ThrottleDisplayFrequency` / `ThrottleFrameRate` | 防止 Chromium 主动降帧 |
| `disable-backgrounding-occluded-windows` | 同上 |
| `disable-renderer-backgrounding` | 渲染进程在后台时不降优先级 |
| `disable-background-timer-throttling` | 后台标签页的 `setTimeout` 不被压到 1 s |
| `HardwareMediaKeyHandling,MediaSessionService` | **Electron 默认关闭**，导致耳机媒体键根本送不到页面的 Media Session |

还有一部分开关在测试后被刻意**放弃设置**，因为实际接入后弊大于利：

| 开关 | 不设的原因 |
| --- | --- |
| `enable-gpu-rasterization` | 让 2D canvas 走 CPU 光栅（Skia）再上传合成，主线程不会被 GPU 光栅回压阻塞 |
| `force-discrete-gpu` | 用直连显示器的核显（Intel UHD），避免独显→核显跨显卡回拷 |
| `disable-direct-composition` | blt 呈现会把多窗口合成串行化到主进程 —— **这正是「开小窗后主窗 rAF 减半」的元凶**。保留 flip-model（DComp），它对多窗口是并行呈现 |
| `disable-frame-rate-limit` / `disable-gpu-vsync` | 会把呈现改坏，产生无节流撕裂 |

### 3.2 窗口配置

**主窗口**

```js
width: 1380, height: 920, minWidth: 900, minHeight: 640,
backgroundColor: '#111629',
autoHideMenuBar: true,
webPreferences: {
  contextIsolation: true,
  nodeIntegration: false,
  preload: path.join(__dirname, 'preload.js'),
  backgroundThrottling: false   // 最小化/隐藏时仍满帧 → 小窗可视化不暂停
}
```

这里刻意**不调用** `webContents.setFrameRate()`。音频可视化的绘制循环完全由页面内部的定时器自行驱动，一旦主进程显式设定目标帧率，反而会打乱双窗口同时运行阶段 Chromium 图形合成器的 BeginFrame 帧同步调度。

**迷你窗**

```js
width: 330, height: 356,
minWidth: 150, minHeight: 96, maxWidth: 720, maxHeight: 900,
frame: false,
transparent: false,          // 透明窗口在 Windows 上强制昂贵合成路径，拖累主窗
alwaysOnTop: true,
resizable: false,
skipTaskbar: true,
hasShadow: false
```

迷你窗还需要配合以下运行时设置：

**层级与全屏覆盖**
  - `setAlwaysOnTop(true, 'screen-saver')` 与 800 ms 定时 `setAlwaysOnTop + moveTop()` 组合，将其提升至系统最高置顶层级，防止部分无边框全屏游戏抢夺 Z 轴层级，确保稳定覆盖在游戏上方。

**事件穿透与焦点控制**
  - `setIgnoreMouseEvents(true, { forward: true })` 默认让鼠标点击直接穿透窗口；当光标移入特定交互控件时，前端页面会通过 `mini-set-ignore` 通信通知主进程临时恢复点击响应。
  - `setFocusable(false)` 保证用户点击小窗界面时不会夺走游戏的系统焦点；但这导致窗口无法使用原生的 `-webkit-app-region: drag`，拖动逻辑必须完全由代码自行实现。

### 3.3 迷你窗拖动与缩放

#### 坐标系对齐与拖拽计算

窗口在屏幕上的位移量与尺寸缩放计算，**全部**统一改为调用主进程的 `screen.getCursorScreenPoint()` 接口。这是因为 Chromium 内部抛出的事件参数 `e.screenX` 实际已经是基于设备独立像素（DIP，即系统缩放计算后的逻辑像素）的数值，早期的渲染层代码如果再次除以缩放比例因子，就会在 125% 这类高 DPI 缩放下出现换算偏差，使得窗口的物理位移比光标移动慢了整整 20%。通过让计算两端完全处于同一物理坐标系，程序便彻底避开了 `scaleFactor` 的重复换算，同时在鼠标拖拽期间会强制锁定窗口的尺寸。

#### 穿透判定架构演进

鼠标点击穿透功能在旧方案中依赖「页面派发 mousemove → 发送 IPC 消息 → 主进程切换状态」这一异步调用链条。遇到用户高速移动光标并立刻按下鼠标的动作时，主进程的状态切换往往尚未完成，导致点击无法穿透，在交互上表现为"有时候拖不动"。现在的架构改为由主进程按 **50 ms** 的固定间隔轮询系统光标位置，渲染页面只需要被动上报可交互控件的矩形范围，即便是系统事件偶然丢失，整体交互状态也能够在 50 ms 周期内自动纠正恢复。

### 3.4 媒体键

```js
const tryReg = (key, fn) => (d[key] === true ? true : regHotkey(key, fn));
```

保证**幂等注册**是维持媒体按键监听稳定的核心。在底层机制中，如果某个全局按键已经被当前程序自身成功占用，Electron 再次注册该键就会直接返回 `false`（其内部的 `GlobalShortcutListener` 会强制执行 `IsRegistered` 校验）。在早期的重试逻辑中，系统每次遇到注册缺失都会尝试重置并全量重绑所有的按键，这一动作会把原本已经就绪的按键反向改写为"失败"，造成界面频发误报"被占用"，进而引发重试定时器无休止地运行。

目前的实现会在注册前先核对 `hotkeyState.detail` 中的登记记录，凡是已经注册成功的按键一律跳过。针对失败按键的重试定时器按照 6 s 一次的节奏执行，只要检测到 `media && fallback` 对应的两组快捷键均已注册成功，定时器便会自动销毁退出；此外，在主窗口触发 `focus` 获得焦点时，系统也会主动执行一次按键的补注册流程。
## 4. 渲染进程设计决策

### 4.0 音频链路：`createMediaElementSource()` 会接管输出，**必须接回 destination**

要通过 `AudioContext` 绘制频谱，就必须先接入音频元素。PCM 主路径并不依赖 `AnalyserNode`，但用于降级的流式回退路径需要靠它拉取音频样本，具体细节见 §4.1；这一步的统一入口是 `createMediaElementSource(audio)`。开发时需要彻底认清这个 API 的运行机制：一旦针对某个 `<audio>` 标签执行了该方法，**该元素解码出来的音频流就会全权交由 Web Audio 音频图接管并输出**。换句话说，浏览器原有的默认直通发声通道会被直接**取代**，而不是与音频图混合叠加；并且这个接入操作属于不可逆的单向变更，一旦调用就无法解除绑定。由此会产生三条关键的技术推论：

```js
const source = ctx.createMediaElementSource(audio);
source.connect(node);
node.connect(ctx.destination);   // ← 必须写，否则"无声 + 无频谱"
```

1. 如果处理链条没有连接到 destination，整条音频链路的终点就会悬空，扬声器最终完全不会发声；而且当图节点没有连通至 destination 时，底层音频引擎根本不会对这一链路执行渲染计算，中间串联的 `AnalyserNode` 自然采集不到任何有效振幅数据，导致频谱画面彻底静止。
2. 架构上并不存在所谓“只接入 analyser 做只读旁路分析”的折中实现，也绝不可能先尝试纯旁路采集、发现没有声音再重新接回硬件输出。
3. 音质层面的优化原则，就只剩下“确保采样率彼此对齐”这一个切入点：直接使用 `const ctx = new Ctor();` 执行无参构造，让它自动遵循当前物理音频输出设备的首选工作频率。依照 Web Audio 规范，**只有在完全不传入 `sampleRate` 参数时，环境才会自动采用设备的原生推荐采样率**；如果代码中手动指定了数值，该值就必须严格处于 `[3000, 768000]` 这个有效区间之内，只要超出范围，构造函数就会立即抛出 `NotSupportedError` 异常中断执行。

> **⚠ 不要传 `{ sampleRate: 0 }`**。数值 0 **根本不属于支持的合法频率区间**，Chromium 遇到后会直接抛出 `The hardware sample rate provided (0) is outside the range [3000, 768000]` 错误；这会导致上下文初始化失败，错误被 catch 捕获后内部状态会被标记为 `vizDenied`，后果就是**后续播放的所有曲目都会丢失频谱渲染**。类似地，如果曲库资源大多数编码为 44100 Hz，开发者却在代码里硬编码传入 48000，系统在播放时就**必然**会强行追加一道重采样计算，徒增不必要的计算开销与失真。

与之配套的代码设计包括两项具体措施：

- **初始化失败不再触发“永久禁用”逻辑**：内部标记 `vizDenied` 仅代表当前这一次尝试接入没有成功，系统应当允许进行**有限次数的重试机制**（设定重试上限为 `VIZ_MAX_ATTEMPTS = 3`，只要任意一次建立成功就会立即重置计数为零）；只有当 3 次重试机会全部耗尽，界面才会弹出 toast 提示并彻底停止后续尝试。设置面板当中的「ANALYSER ROUTING」一栏会根据这套逻辑，实时并准确地反馈当前的路由接管状态及排查原因。
- **音频变速播放时必须维持音高不变**：代码中需要将 `preservesPitch` 以及兼容前缀属性 `webkitPreservesPitch` 显式赋值为 `true`，同时把当前生效的状态如实展示在设置面板里。这个用于控制播放速度改变时是否保持音调的属性，在不同浏览器中的**默认开关策略**并不统一，还会随着浏览器内核版本的升级而改动，开发时不能依赖环境默认表现；一旦它处于关闭状态，用户调到 0.75× 播放时声音会沉重发闷，切到 1.5× 播放时音色则会发尖失真，而这两个倍速恰恰是用户收听播客内容时最为高频使用的两个挡位。
### 4.1 频谱管线

主界面（`app-rhine/`，§4.6）中的频谱模块直接来自于 **SelfMusic 桌面端的移植**。项目在 v2.7.5 版本完整引入了分析内核以及 16 项可供调节的显示层参数；随后在 v2.7.7 版本中，渲染层被重构为 Python 脚本 `visualizer.py` 的 Canvas 直接转译实现，同时**彻底删除了旧的算法路径**。这套改动移除了原有的 1.3.0 流水线、基于 120 段 Goertzel 算法的 Web Worker、算法档位切换开关，以及旧版的调音参数体系。当前架构下的频谱计算仅保留了这唯一一条处理路径。

具体实现要点如下：

**数据分析与频段计算**
  - 音频文件导入后，系统通过 `OfflineAudioContext` 恒等解码，在不改变采样率的前提下将整曲预先转为单声道 PCM 原始波形数组，避免实时 `AnalyserNode` 常规 FFT 带来的不确定性。
  - 播放期间由平滑时钟以固定的 **16 ms** 间隔截取 `[播放位置, +4096)` 的 4096 采样点窗口送入 SelfMusic 分析链路，直接计算出 96 个对数频段的柱体高度，不再进行早期 96 段到 150 段的二次插值重采样。

**渲染循环与画面绘制**
  - 调度由定时器驱动而非 `requestAnimationFrame`（rAF），规避 Chromium 在后台或窗口遮挡时降频至 1 fps 对固定步长的破坏；同时通过 `visibilitychange` 事件在页面隐藏时完全停运循环、切回时重启，以节约开销。
  - `Spectrum` 组件仅负责画面渲染（包含柱体贴底、独立不透明度、浮动顶盖及左上角四路音色指示条），直接读取分析引擎的原始数值且不作平滑补帧，离线对比桌面端最大绝对误差 max|Δ| ≤ 1.8e-07，确保逐位对齐。

细节见 [功能说明 § 5](功能说明.md#5-频谱可视化)。

> 作为降级方案的兜底界面 `app/index.html` 当中，目前依然保留着 1.3.0 版本的 Goertzel Worker 实现（采用 50 Hz / 20 ms 的调度节拍以及 120 段对数频带划分）。该逻辑只有在主界面加载遭遇异常并发生回退时才会触发执行，后续不会再同步任何新版本特性。
### 4.2 柱体数据的跨窗口复用

迷你小窗口本身**不重新计算**音频的频谱数据，而是完全依赖主窗口的处理结果。通过单向同步机制，系统避免了双窗口重复运行音频分析带来的 CPU 额外开销，同时确保了两端柱体跳动节奏严格一致。

**数据同步机制**
  - 主窗口在渲染每帧画面时，通过 `mini-bars` IPC 通道将计算好的柱体数组推送到小窗。
  - 小窗接收到数组后，仅根据自身画布尺寸执行绘制操作，不参与任何前置计算。

**不同界面的调度策略**
  - **兜底界面（`app/index.html` 配合 `mini.html`）**：采用上述跨窗口复用机制，配合主进程发送的 `win-state` 事件在窗口最小化时降低刷新频率。
  - **新主界面（`app-rhine/`）**：未设计迷你小窗口，改为监听 `visibilitychange` 事件；一旦页面进入不可见状态，便直接自动停止可视化渲染循环。
### 4.3 呈现状态机

播放模式四种：`list` 列表循环 / `order` 顺序播放 / `single` 单曲循环 / `shuffle` 随机，由 `MODES` 数组统一驱动图标与文案（`IC.repeat` / `IC.order` / `IC.single` / `IC.shuffle`）。

### 4.6 音乐档案终端里的播放器（`app-rhine/`）

> **来源署名：`app-rhine/` 这套界面底座（源码 + Blender 工程文件）来自 B 站 UP 主
> [@路北路陈](https://space.bilibili.com/3546646728820438)**（仓库 [LBEILC/RhineLabUI](https://github.com/LBEILC/RhineLabUI)，MIT）。
> 本节描述的是**反向整合**这一层（把播放内核接进既有界面）。

作为主界面的莱茵生命终端是一套基于 TypeScript + Three.js + Vite 构建的独立前端应用。项目打包生成的构建产物会同步输出到 `app/ui/` 目录下，运行时由主进程内嵌的一个小型静态 HTTP 服务负责承载；该服务具备随机端口绑定和路径穿越防护机制，渲染进程启动后直接加载 `http://127.0.0.1:<port>/index.html` 即可呈现整个界面。

**播放器不另起一套坐标系。** 终端所有的 UI 元素都统一挂载在 `#stage` 容器内部，并通过统一的缩放逻辑适配窗口：

```js
const scale = Math.min(innerWidth / 1920, innerHeight / 1080);
$("#stage").style.transform = `translate(-50%, -50%) scale(${scale})`;
```

底部的播放条以及弹出的播放列表，必须使用 `appendChild` 挂载到这个 `#stage` 节点之下，其 CSS 绝对定位参数按照 1920×1080 的基准设计尺寸直接写成 `left:59px; bottom:124px`。假如把它们直接挂载到外层的 `document.body` 上，当桌面端处于默认的 1380×920 窗口尺寸时，计算出来的缩放系数只有 0.719，结果就会导致外层三维界面已经整体等比缩小，而播放条依旧停留在未缩放的原始尺寸，产生严重的排版割裂。

**模块分工**

| 文件 | 职责 |
| --- | --- |
| `app-rhine/src/player.ts` | 音乐库（IndexedDB）、播放内核、导入（文件 / 文件夹 / NCM / B 站）、播放条、播放列表、频谱、曲目面板的 HTML 片段 |
| `app-rhine/src/data.ts` | 把曲目映射成"档案记录"（`records`），供三维阵列与检索使用 |
| `app-rhine/src/main.ts` | 终端本体。详情区渲染时按 `hasSongs()` 分支：有曲目 → `songDetailMarkup()`，空库 → 原来的档案版式 |
| `app-rhine/src/selfmusic-*.ts` + `spectrum.ts` | 频谱三层：分析内核 / 活路径（整曲 PCM + 平滑时钟）/ 绘制层（`visualizer.py` 直译），见 §4.1 |

**两个方向的桥**：从终端调用播放器比较直接，由三维场景或全局快捷操作直接发起 `playAt()`、`togglePlay()` 或 `toggleFav()` 等函数调用；从播放器回传状态到终端则借助 `window` 全局事件进行解耦——抛出 `rhine-track` 事件表示当前播放的曲目发生了切换，提醒阵列选中态与右侧详情区同步更新；抛出 `rhine-lyrics` 事件表示异步歌词解析补全完毕，界面接收后只需要局部重绘歌词页签，无需刷新整个曲目信息。

**为什么不复用终端的 `AudioContext`**：终端自带的 `TerminalAudio` 模块本身管理着独立的音频上下文，并且挂载了多条交互音轨，但播放器所需的频谱分析流程必须使用接在 `<audio>` 媒体元素上的 `MediaElementAudioSourceNode` 节点。为了避免破坏既有音效管线，播放器创建了专属于自己的音频上下文；当这个独立的上下文无法顺利推进到 `running` 状态时，程序会干脆放弃绘制动态可视化频谱，也不会去强行接管或影响底层的音频播放元素。

**★ 本地 UI 服务的端口必须固定（`UI_PORT = 41739`）**

浏览器的 IndexedDB 数据库是严格按照“源”也就是同源策略（由协议 scheme、主机名 host 和端口号 port 共同决定）进行数据隔离的。早期版本直接调用 `listen(0)` 让操作系统在每次启动时随机分配端口，这导致每次打开程序都处于一个完全不同的存储域中，已保存的音乐库索引、收藏记录以及断点播放进度全部无法跨进程读回。现在的做法是锁定固定端口，使本地源保持绝对稳定，确保数据在多次启闭之间长久保留；只有当固定端口被外部占用并抛出 `EADDRINUSE` 或 `EACCES` 错误时，服务才会退回使用随机端口，同时在终端打印一行警告日志，明确提示本次运行的存储域与上次不同，数据将暂时隔离。用户也可以配置环境变量 `RHINE_UI_PORT` 来自定义覆盖默认端口号。

**★ 读曲库不挡启动（2.0.0）**

在 2.0.0 版本中，`initPlayer()` 初始化流程调整为先同步执行 `buildUI()` 注入 DOM，并调用 `syncRecords()` 将界面骨架迅速建立起来（如果检测到曲库为空，就先展示“导入音乐”这一占位档案），之后采用非阻塞的 `void loadLibrary().then(applyLibrary)` 异步读取真实数据库，数据解析完成后再通过 `notify()` 通知下发，促使三维档案阵列、刻度轴、播放列表和右侧详情面板各自完成一次针对性刷新。

这项改动替换掉了过去较为生硬的 1.5 秒超时兜底策略（即原先的 `Promise.race([idb.all(), 1.5 秒后返回空数组])`）。在冷启动或硬盘负载较高时，IndexedDB 数据库首次打开可能需要耗费 1.2 到 8.5 秒不等的时间；一旦越过 1.5 秒的门槛，程序就会彻底把当前运行状态判定为空库，进而导致曲目列表无法正常列出、单曲记录的 `pos` 播放进度读不出来，原有的“断点续播”特性从根本上被切断（具体排查细节见 [更新日志 2.0.0](更新日志.md)）。现行机制将容错超时延长到了 8 秒，并且只在确实没有任何有效数据返回的情况下才会将其视为空库处理。

**渲染节拍与配色**

- 频谱：SelfMusic 引擎按照 **16 ms** 为周期驱动核心音频分析（由配置项 `SM_ANALYSIS_MS` 控制；分析过程完全运行在专有的定时器回调中，浏览器自身的 rAF 即 `requestAnimationFrame` 仅负责画面绘制），Canvas 画布在**播放状态下维持 60fps / 暂停后降频至 15fps** 进行呈现；柱体高度完全取自引擎分析的原始数组输出，中间**不做插值**平滑，保证每一根频段能量与 SelfMusic 的输出逐位对齐（具体算法参考 [功能说明 § 5](功能说明.md#5-频谱可视化)）
- 频谱画布与三维场景共用**同一个 rAF 队列**：三维场景当下的渲染帧率即决定了频谱的实际绘制帧率。为了避免性能恶化，系统会将实测帧率持续输出到设置页面的 `RENDER QUALITY` 一栏，一旦检测到连续 5 秒内的中位帧率低于 50fps，系统就会自动将三维画质预设向下调低一档（该降级策略只执行一次，如果用户已经在界面上手动调整过画质档位，系统就不再自动干预）；此外，详情面板在每一帧需要动态计算的 `opacity / transform / inert / --detail-shade` 这类样式属性，也全面改成了“只有新值与旧值不相等时才写 DOM”的缓存比对机制，减轻渲染重排压力，见 [功能说明 § 5.9](功能说明.md)
- 播放条与播放列表**不用 `backdrop-filter`**：因为这几个浮动面板的底层是持续处于高频动画状态的三维空间场景，如果在尺寸达到 880×134 的面板下方每一帧都强制触发全局像素重新模糊，所带来的 GPU 合成与重绘开销过于高昂
- 整个界面的深色主题是通过在根节点设置 `body.theme-dark` 来逐个覆盖终端原有的固定样式表，因为原作者在终端项目中将配色变量硬编码在了 CSS 中。播放器所有新增的 DOM 容器在应用深色外观时，都必须同时携带 `theme-dark` 与 `rhine-night` 这两个类名，前者用来触发针对终端原生组件的暗色覆盖，后者专门负责控制播放条及列表本身的视觉表现。
## 5. 第三方模块

本节介绍系统集成的外部依赖工具及相关解析逻辑。

**媒体提取与解密工具**
本组模块负责调用底层工具解密专有格式，或检索本地客户端生成的媒体缓存：

**封面解析与回退机制**
**`cover.js`** 负责解析音频封装格式的底层数据结构，提取内置唱片封面：

| 格式 | 定位方式 |
| --- | --- |
| NCM | 元数据 JSON 中的 `albumPic` |
| MP3 | ID3v2 `APIC` 帧 |
| FLAC | `PICTURE` 块 |
| M4A | `moov/udta/meta/ilst/covr` |

## 6. 数据管控层

程序在运行过程中会解出两类**派生数据**，分别是解密 `.ncm` 容器后得到的音频，以及从 B 站客户端缓存中剥离头部特征后生成的 m4a 副本。这两类文件受到原平台的版权约束，因此主进程专门设计了一套独立的数据管控机制来限制其流转，具体的合规设计细节见 [数据管控与合规](数据管控与合规.md)。

### 6.1 会话临时目录

```js
const SESSION_ID      = crypto.randomBytes(6).toString('hex');
const SESSION_TMP     = path.join(os.tmpdir(), 'mp-session-' + SESSION_ID);
const SESSION_AUDIO_DIR = path.join(SESSION_TMP, 'audio');
```

所有的派生数据在生成后，只允许写入这个基于系统临时路径的动态目录，禁止存放到任何持久化存储区域。该目录的完整生命周期管理如下：

```
启动  → sweepStaleSessions()   清掉上次崩溃残留的 mp-session-*
        purgeLegacyAudioCache() 擦除 1.0.x 遗留在 userData\bili_audio 的长期副本
运行  → 解密/提取写子目录，读完立即 wipeDir()
退出  → will-quit 拦截 → shutdownSessionTmp() → 真正退出（4 秒兜底）
```

主进程监听 `will-quit` 事件，并利用 `event.preventDefault()` 阻止默认的直接退出流程，配合 `quitCleanupDone` 布尔状态位来实现"先执行安全清理、再触发最终退出"的执行顺序。这样能够有效避免调用 `app.quit()` 时再次触发同一个退出监听函数，防止程序陷入无限递归调用。

### 6.2 擦除

```js
function wipeFile(p) {
  // ★ 硬链接保护：nlink > 1 → 只摘目录项，绝不覆写
  if (st.isFile() && st.nlink > 1) { fs.unlinkSync(p); return; }
  // 否则：0 覆盖 + fsync + unlink，受 WIPE_BUDGET 限制
}
function wipeDir(dir) { /* 递归 wipeFile 后 rmdir */ }
```

为了兼顾销毁安全性与退出时的响应速度，系统为单次会话设置了 256 MB 的覆盖擦除配额。一旦累积擦除的数据量超出了这个上限，后续的文件将只执行常规删除（`unlinkSync`）而不再进行全零覆写，防止程序在退出阶段因为需要处理数十个大体积文件而出现界面假死。

> **为什么必须有 `nlink > 1` 这道闸**：底层文件系统中的覆写操作是直接修改 inode 指向的物理块。当一个文件的硬链接数（即目录项引用计数）大于 1 时，意味着系统内还有其他路径共享同一批物理块；此时如果执行全零覆写，会导致其他引用路径下的文件数据一并被破坏，而后续调用的 `unlink` 只能解除当前的这一个目录项引用，最终在现象上表现为"用户原路径下的文件依然存在，但内容已经被清空"。在 v1.1.0–v1.1.3 版本中，程序曾因为这一缺陷把用户的 B 站原始缓存文件在原地擦成了全 0，具体事故分析见 [数据管控与合规 §2.1.1](数据管控与合规.md)。为了彻底杜绝该隐患，配套的 `ensureM4a` 逻辑也不再调用 `linkSync` 建立硬链接，而是统一通过数据流拷贝出完全独立的物理副本。这是一条通用的底层开发经验：在对任何文件执行"擦除或覆写"操作之前，必须检查引用计数，确认目标物理块处于当前进程独占的状态。
>
> **诚实说明**：现代固态硬盘（SSD）普遍具备磨损均衡机制与 TRIM 指令支持，这导致任何操作系统层面的文件写入都无法精准控制闪存物理颗粒，因此软件层不可能从底层技术上达成取证级别的数据不可恢复性。代码中写入 0 字节的擦除步骤，本质上是抬高非专业手段还原数据的难度，起到一种技术层面的**威慑**作用；系统真正依赖的合规底线，在于"整个生命周期内派生数据根本不进行长期落盘"。

### 6.3 结构性不可导出

这里的不可导出并不是指"界面上隐藏了导出按钮"，而是在架构层面上**根本没有提供能够将内存或派生字节重新写入持久化磁盘的执行路径**：

**进程与接口边界隔离**
  - 主进程注册的 28 个 IPC 通信通道中，没有任何一个接口允许接收外部传入的"输出路径"参数。
  - `preload.js` 向页面环境暴露的 16 个 API 方法完全排除了所有磁盘写操作，且渲染进程强制启用了 `contextIsolation: true` 并禁用了 `nodeIntegration: false`，阻断在前端环境直接调用 Node.js 的 `fs` 核心模块。

**运行时内存流转管控**
  - 所有派生音频流在渲染进程内部只能以临时的 `Blob` 对象或者内存引用的 `objectURL` 形式进行流式加载。

### 6.4 审计日志

系统会在 `userData\audit.log` 路径下持久化保存审计日志，格式采用逐行独立的 JSON 文本，每条记录依次包含 `t / v / sid / event / src / bytes / ext / result` 等字段。文件设置了 500 条记录的容量上限，超过该阈值时会自动裁剪旧记录以控制文件体积。记录的事件严格限制为三种业务动作：`ncm-decrypt`、`bili-extract` 以及 `bili-scan`。在日志写入过程中，如果因为磁盘空间耗尽或者系统权限受限而引发异常，错误会被静默忽略，避免审计逻辑的故障反过来干扰到正常的音频解码与播放主流程。

### 6.5 回归验证

针对上述数据管控规则，项目在 `scripts\数据管控验证.js` 中编写了 16 项自动化断言。开发者只需在终端直接使用 `node` 命令就能快速执行检测，不需要完整拉起 Electron 运行时与图形界面。测试脚本中的擦除逻辑实现，是**直接读取 `main.js` 源代码文本并动态提取对应函数来执行校验**，确保测试对象与最终打包发布的主进程逻辑完全一致，没有单独维护第二套测试专用的模拟代码。

本程序目前存在以下几个方面的已知运行限制。下表详细列出了每一项具体限制、产生该现象的技术原因以及当前的应对状态。

## 8. 代码规范约定

**注释编写要求**
- 代码中统一使用**中文注释**，重点说明设计决策的**原因和业务背景**，避免机械复述代码已体现的**执行动作**；对于修复过的缺陷或技术陷阱，须在对应位置写清具体现象与产生原因，防止后续维护时误改回问题写法。

**常量与编码规范**
- 业务常量需统一归拢到文件顶部或集中放置在带有说明的常量定义块内，禁止在逻辑中直接散落未经命名的数字或字符串等魔法数字。

**前端构建与开发模式**
- 不引入前端框架、跳过构建打包以及“保存即生效”的开发方式仅针对**兜底界面**。作为主界面的 `app-rhine/` 目录属于例外，其采用 TypeScript 和 Vite 技术栈，修改源码后必须执行构建命令并将产物同步到 `app/ui/` 目录下（具体操作步骤见 §4.6）。
